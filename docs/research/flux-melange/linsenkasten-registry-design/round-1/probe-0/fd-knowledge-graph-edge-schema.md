## Findings

### prune-precondition-narrative-not-machine-checkable
- **Severity:** P0
- **Where:** docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:80-90 (Fork 4), :104-110 (Fork 5 ruling), :120-123 (Fork 5 rationale)
- **What:** CONFIRMED, with one refinement. Fork 4's precondition — "After the harvest is verified in the registry" — names no mechanism: no commit SHA, no harvest-manifest reconciliation, no check that the local machine's git clone of the registry actually contains the merge commit that captured *this* repo's content. Given Fork 5's transport (zklw is canonical, merges, and commits; "the Mac pulls through git," lines 106-107) and per-machine harvest files (`data/harvest/<machine>.jsonl`, Open Questions:147-149), a sweep run on a machine whose local pull is behind zklw's merge commit for that repo has nothing in the document to stop it — "verified" reduces to a human glancing at a possibly-stale local copy. That part of the prior finding is confirmed as written.
  Where the prior finding's framing needs sharpening: Fork 4 itself states "Git history + the registry are the archive" (line 84) — i.e., even a raced deletion is only a normal commit, recoverable from the pruned repo's own git log, not a destructive rewrite. Taken alone, that undercuts "losing the only copy." But Fork 5's own rationale, two paragraphs later, says the opposite: "the store is git-backed, which matters once the repo piles are deleted and **the registry is the only copy**" (lines 122-123). The document is internally inconsistent about whether git history counts as a real recovery path post-prune. Taking Fork 5's self-description at face value (which is the newer, more specific statement, added 2026-09-02, superseding Fork 4's framing), the prior finding's "losing the only copy" is not an overstatement — it's what the design's own rationale asserts happens. Even under the more conservative reading (git history survives), a raced prune still means the content permanently drops out of the *queryable graph* with zero signal distinguishing it from a lens that was correctly harvested and had nothing worth an edge — defeating the registry's stated purpose ("every generated fd-* review lens... becomes a queryable, ranked, reusable graph," line 10-11) even where the raw bytes are archaeologically recoverable.
- **Evidence:** Line 81 ("After the harvest is verified") names no check; lines 106-107 ("zklw... commits the registry data; the Mac pulls through git") establish the exact staleness vector; lines 147-149 confirm harvest is per-machine-file + zklw-side merge, so "verified" for a Mac-local repo depends on a merge commit produced on a different machine; line 84 ("Git history + the registry are the archive") vs. lines 122-123 ("the registry is the only copy") are the internal contradiction.
- **Suggestion:** Gate the per-repo sweep on a local, machine-checkable condition — e.g., the sweep script reads the repo's current HEAD SHA and refuses to run unless that SHA (or a content-hash of its `.claude/agents/fd-*` pile) appears in the locally-pulled registry's harvest manifest for that repo, not merely "a harvest ran at some point."

### dangling-fused-from-edges-from-unverified-prune-race
- **Severity:** P1
- **Where:** docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:80-90 (Fork 4); :147-152 (Open Questions, fused-from sourcing)
- **What:** `fused-from` edges are reconstructed from melange lens records' `parents` field and `-fusion-N` spec files, "not from agent files" (lines 150-152) — i.e., the edge's existence is independent of whether the named parent lens itself ever became a registry node. Combine that with the race confirmed in finding 1: if a parent lens X's repo is pruned before X's own content is verified present in the canonical (zklw) registry, X never becomes a registry entry — yet any melange record whose `parents` names X (because a later fusion genuinely used X) still asserts a `fused-from` edge to it. Nothing in Fork 2, Fork 3, Fork 4, or the Open Questions describes what a `fused-from` edge does when its target id doesn't resolve: silently fail to traverse (a hole with no error), or — worse — silently bind to a same-hash-or-name lens harvested later from a different machine/worktree copy of X, producing a plausible but provenance-mismatched edge target that looks correct under Tier-1/Tier-2 dedupe (per Fork 3) but isn't the lens that was actually fused.
- **Evidence:** Lines 150-152 make the edge source (`parents` field) independent of node existence; Fork 4 (80-90) is the only described path by which a parent's source repo is removed; no dangling-reference or edge-target-validation behavior is specified anywhere in the four forks or Open Questions.
- **Suggestion:** At harvest-merge time (zklw side), validate every `parents`/`fused-from` reference against the registry's own node set and flag (don't silently drop or silently rebind) any edge whose target isn't yet a resolved node — surfaced in the same sweep report Fork 4 already produces, rather than invented as new tooling.

### sweep-report-lacks-harvest-commit-audit-trail
- **Severity:** P2
- **Where:** docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:84-86 (Fork 4, sweep report)
- **What:** "The sweep report lists every file with its registry id" (lines 84-86) — but not the harvest/merge commit SHA it was checked against, nor where the report itself is persisted. If the race in finding 1 occurs, the sweep still "succeeds" (every file gets *a* registry id) with no artifact anyone could later diff against zklw's actual merge history to notice the id was assigned from a stale local view. This is the forensic-trail gap that makes finding 1 undetectable after the fact, not just unprevented at gate time.
- **Evidence:** Lines 84-86 specify the report's content (file → registry id) but nothing about commit provenance or storage location; no other section of the document revisits sweep-report durability.
- **Suggestion:** Add the checked-against harvest/merge commit SHA to each sweep-report row, and commit the report itself (e.g., alongside the sweep commit in the pruned repo) so a later audit can cross-reference sweep timestamps against zklw's merge-commit log without new tooling.

## Verdict
CONFIRMED: Fork 4's verification precondition is narrative, and the two-machine, git-pull transport in Fork 5 gives it a concrete failure path (a stale local pull passing a human "verified" check). The prior finding's "losing the only copy" phrasing is defensible rather than overstated once you weigh Fork 5's own rationale (122-123) against Fork 4's "git history is also an archive" claim (84) — the document contradicts itself on which is true, and either reading leaves the registry's queryable graph silently short a node with no error and no way to tell it apart from a correctly-excluded one.
