# fd-knowledge-graph-edge-schema — round 1

## Findings Index
- [P1] reuse-match-mechanism-unspecified — prior finding is refuted on its literal mechanism but confirmed in a stronger, unstated form: no edge or query path connects a live target to a candidate lens at all (§Why This Approach L24-27,35-36; §Fork 2 L61-62)
- [P2] no-reuse-serving-edge-audit-trail — the schema has no edge recording "lens X was served as a reuse candidate for target Y with score S," so reuse decisions leave no graph-traversable trace distinct from fresh generation (§Fork 2 L56-66; §Open Questions L142-146)
- [P1] embodies-embedding-axis-conflation-risk — the only embedding comparison the schema actually specifies (embodies: lens vs. curated-pattern space) is the wrong axis for reuse-matching (lens vs. arbitrary-target space); absent a specified alternative, implementers are likely to reuse it as a shortcut (§Fork 2 L61-62; §Fork 5 Consequences L124-128)

## Findings

### reuse-match-mechanism-unspecified
- **Severity:** P1
- **Where:** docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:24-27 ("consult the registry reuse-before-regenerate through the existing combine/contrast seam"), :35-36 ("the melange fusion seam already calls interlens tools when available, so reuse-before-regenerate plugs into an existing integration point"), :61-62 (embodies edges "auto-suggested at harvest (embedding match against curated definitions)")
- **What:** The prior finding claims reuse-before-regenerate matches on a *harvest-time* embedding plus stored hit-rate with no query-time re-validation. That literal claim is **refuted**: the design does specify a query-time embedding pipeline (Fork 5, L107-108: "Query-time text embedding tries local Ollama, then zklw's Ollama over Tailscale, then a lexical fallback"), and the codebase's `search_lenses` tool (`apps/api/lens_search_api.py:375-388`, `packages/mcp/index.js:44-51`) already embeds free-text queries fresh at call time against stored lens vectors — that machinery, ported per Fork 5, is available to re-validate against the current target. But the underlying risk is **confirmed, and worse than stated**: the document never actually wires reuse-before-regenerate to that mechanism. The one integration point it *does* name — "the existing combine/contrast seam" — resolves in this codebase to `combine_lenses` (`apps/web/api/mcp-sse.js:391-397`), which takes an array of lens **names**, looks each up by string match, and does no embedding or target comparison whatsoever (`args.lenses.map(name => lenses.find(l => l.name.toLowerCase() === name.toLowerCase()))`). Nothing in Fork 2's typed-edge schema — `embodies` (harvest-time, lens vs. curated pattern) and `variant-of` (harvest-time, lens vs. lens cluster) — provides an edge from "the review target currently being processed" to "a candidate generated lens" either. So as scoped, there is no described match step at *any* time, harvest or query — not a stale match, an absent one. Whatever mechanism ships will be improvised by whoever implements the seam, with no schema or spec constraining it to re-embed the target.
- **Evidence:** `apps/api/lens_search_api.py:376-388` (search_lenses: free-text query, semantic, per-call); `packages/mcp/index.js:44-51` (search_lenses tool signature: `query` string, no lens-list); `apps/web/api/mcp-sse.js:391-397` (combine_lenses: `args.lenses` name array, no query text, no embedding call); brainstorm L24-27, L35-36 (reuse-before-regenerate named only as plugging into "the combine/contrast seam," never disambiguated from search_lenses).
- **Suggestion:** Name, in the plan (not just the brainstorm), which MCP tool call implements the reuse-before-regenerate match step, and require that it pass the current review target's text through the query-time embedding path (not a stored harvest-time vector) before any embodies/variant-of edge is consulted for ranking.

### no-reuse-serving-edge-audit-trail
- **Severity:** P2
- **Where:** docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:56-66 (Fork 2, the three edge types), :142-146 (Open Questions: hit-rate, surfaced-count, use-count "stored beside it as separate signals")
- **What:** Fork 2's schema is exhaustive about lens-to-lens and lens-to-curated-pattern relationships but defines no edge (or edge-adjacent record) for a lens-to-target reuse-serving event — e.g. `served-as-reuse(lens, target-session, score, timestamp)`. Hit-rate is aggregated from ledger `upheld/refuted` findings (L142-144), which only exist *after* a served lens's output was adjudicated; there is no intermediate record of "this lens was offered as a reuse candidate, at this similarity score, for this target" independent of whether a finding was later logged. This is a schema gap distinct from ranking-signal quality (out of scope for this lens per the fd-recsys-reuse-relevance handoff): even a perfect matching algorithm becomes unauditable over time, because the graph cannot answer "how often was this lens served vs. regenerated fresh, and at what similarity, regardless of downstream adjudication."
- **Evidence:** brainstorm L142-146 lists only `hit-rate`, `surfaced-count`, `flux-drive use-count` as stored signals — none is a graph edge, none captures per-serving target-relevance, and use-count/surfaced-count are not defined as target-specific.
- **Suggestion:** Add a lightweight `served-as-reuse` edge or log record (lens id, target/session id, similarity score, timestamp) written at serve time, independent of whether the target later produces a ledger finding — this is the minimum trace needed to later evaluate reuse quality per-target rather than only in aggregate.

### embodies-embedding-axis-conflation-risk
- **Severity:** P1
- **Where:** docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:61-62 (embodies "auto-suggested at harvest (embedding match against curated definitions)"), :124-128 (Fork 5 Consequences: "embeddings are 768-d `nomic-embed-text`... precomputed at harvest and committed")
- **What:** The only embedding comparison this document actually specifies compares a generated lens's own content against the 258-288 *curated pattern* definitions, to decide its embodies edge — a fixed, small target space. Reuse-before-regenerate needs a structurally different comparison: a live, arbitrary review target against the ~thousands of *generated* lenses. Given finding 1 (no reuse-match mechanism is named), the path of least resistance for an implementer is to reuse the embodies-edge embedding that's already sitting on the node — computed once at harvest, in the curated-pattern comparison space — as a proxy for target-relevance, because it's the only embedding property visibly attached to the lens. That produces exactly the failure the prior finding worried about (confident-but-wrong reuse), but via a concrete mechanism the prior finding didn't identify: an axis mismatch baked in by the schema's own economy (one embedding field per lens, one purpose implied), not by staleness of an otherwise-correct comparison.
- **Evidence:** brainstorm L61-62 (embodies embedding is lens-vs-curated-pattern); L126-128 (single committed embedding per lens, no stated second vector or re-embedding-per-query-context); no field in the described record schema (L135-137, "one record file per canonical generated lens plus an index and a committed embedding matrix") distinguishes an "embodies-comparison vector" from a "general-purpose retrieval vector."
- **Suggestion:** If the same 768-d vector is meant to serve both the embodies-edge computation and reuse-before-regenerate retrieval, say so explicitly and confirm nomic-embed-text similarity is meaningful across both comparison spaces; if not, specify that reuse retrieval re-embeds the target and compares against the lens's stored vector as a *retrieval* similarity, separate from the embodies edge's *classification* similarity, so a future schema change to one doesn't silently corrupt the other.

## Verdict
The prior finding's literal mechanism (stale harvest-time match, no query-time re-embedding) is refuted — the design does specify query-time embedding infrastructure. But the underlying worry is confirmed and sharpened: no edge, tool call, or record in this document actually wires a live review target to the graph's embodies/variant-of edges or to search_lenses's free-text path, so the real risk is an unspecified match step, not a stale one — and the schema's single-purpose embedding field makes an axis-mismatched reuse a likely implementation shortcut rather than an edge case.
