## Findings Index
- [P0] materialization-truncates-silently — every one of the six agent files currently in `.claude/agents/` ships with mid-sentence content loss baked into the committed markdown, invisible in frontmatter and in the rendered form, and the harvest as designed has no step that would catch it (§Fork 3 L69-79, §Fork 4 L80-91)

## Findings

### materialization-truncates-silently
- **Severity:** P0
- **Where:** `.claude/agents/fd-living-heritage-transmission.md` (this very lens's own file) at lines 16-17, 36-37, 41-42, 46-47, 51-52, 56-57, 61-62, 77-78, 79-80, 81-82, 84-85, 96-97; identical pattern confirmed in all five sibling files (`fd-distributed-sync-data-integrity.md`, `fd-knowledge-graph-edge-schema.md`, `fd-metrology-traceability.md`, `fd-recsys-reuse-relevance.md`, `fd-stemmatics-witness-loss.md`) — 6/6 agent files currently on disk exhibit it.
- **What:** Whatever step turned `.claude/flux-gen-specs/linsenkasten-registry-design-wide-1.json` (which holds the full, untruncated `persona`, `review_areas`, `severity_examples`, `anti_overlap`, and `success_hints` text — verified by direct read, e.g. spec lines 4-42) into the committed `.md` agent body cut every long paragraph off mid-sentence and spliced in the literal string `[truncated — N chars omitted]` as if it were content, then continued straight into the next markdown heading. This is not a display artifact of any tool in this session — confirmed via `python3` reading the raw file bytes and via `grep`/`wc` directly against the file on disk (10,095 bytes, 115 lines, 12 occurrences of the marker in this file alone). The frontmatter (`generated_by: flux-gen-prompt`, `generated_at`, `flux_gen_version: 6`, `source_spec`) carries no field indicating the body is incomplete — it reads as a normal, finished, professionally-structured lens. This is the design's own P0 language realized literally, not analogically: "the artifact kept its form and lost only its occasion" (this file's own §Severity Calibration, L66) — except here the occasion lost is not a melange round but the file's own generation. Because the harvest (§Fork 3, hash-plus-variant dedupe) has no reference copy to diff against — it hashes whatever bytes are on disk as ground truth — a truncated body hashes cleanly, embodies-edge auto-suggestion embeds the truncated text as if it were the whole persona, and reuse-before-regenerate would serve this gutted prompt (including the bare `[truncated — 502 chars omitted]` string sitting where the actual instruction text should be) to a future reviewing agent as if it were complete. Six for six on the files present right now is not a sampling accident; it says whatever produced this batch does this by default, silently, to every generated lens, meaning a large and unknown fraction of the ~4,750-agent census may already carry this exact defect.
- **Evidence:** `.claude/agents/fd-living-heritage-transmission.md:16` (`"...a corpus can be complete, deduplicated, ind\n[truncated — 502 chars omitted]"` — cuts off mid-word into the next H2); `.claude/flux-gen-specs/linsenkasten-registry-design-wide-1.json:8` (the spec's `persona` field, complete, no truncation, proving the source text existed in full before materialization); `grep -rl "truncated —" .claude/agents/*.md` → 6/6 files matched.
- **Suggestion:** Before harvest ingests any `.claude/agents/*.md` body, add one mechanical completeness check — reject or flag any file containing the literal string `[truncated` (or any body whose length falls far short of its `source_spec`'s corresponding field lengths) rather than hashing and accessioning it as-is. Fix belongs in whatever writes the `.md` from the spec, not in the harvester, but the harvester is the last checkpoint before this becomes permanent registry content.

### anti-overlap-siblings-lose-their-cohort
- **Severity:** P0
- **Where:** `.claude/flux-gen-specs/linsenkasten-registry-design-wide-1.json:43-48` (the `anti_overlap` array: five entries, each naming a specific sibling lens and the territory this lens must NOT cover because that sibling covers it — e.g. "Do not audit any number... all of that belongs to fd-metrology-traceability"); rendered (truncated, see above) into `.claude/agents/fd-living-heritage-transmission.md:77-85` as "## What NOT to Flag"; `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:147-152` (Open Questions: `fused-from` edges are meant to come from melange lens records' `parents` field and `-fusion-N` spec files, not from agent frontmatter).
- **What:** These six agent files are themselves a live instance of the exact artifact class this lens's own review areas name as ephemeral-work-accessioned-as-durable: "sibling lenses whose content only meant anything against the others in their run" (this file's own generation, §Review Approach #2). Each of the six carries a hard-coded `anti_overlap` contract that only makes sense when all six are co-invoked in the same round — `fd-living-heritage-transmission` explicitly declines to audit numbers, edge vocabulary, hit-rate mechanics, or cross-machine consistency *because its five named siblings are assumed present and covering those angles*. Nothing in the typed-edge schema (embodies / fused-from / variant-of) or in the harvest record captures "generated as one of N siblings under a mutual non-overlap contract, valid only when the cohort is invoked together." Once harvested, this file becomes one candidate among thousands, offered by reuse-before-regenerate on embedding similarity to whatever future target it resembles — alone, not with its five siblings. A future reviewer who receives only this lens gets a reviewer that has been deliberately, permanently silent about numeric thresholds, edge semantics, and machine-consistency questions, with no signal that the silence was a negotiated division of labor rather than a judgment that those angles don't matter. This is worse than a generic capability gap: the lens actively asserts scope ("Do not audit any number... belongs to fd-metrology-traceability") pointing at a sibling that reuse-before-regenerate has no mechanism to guarantee is served alongside it.
- **Evidence:** `.claude/flux-gen-specs/linsenkasten-registry-design-wide-1.json:43-48` (anti_overlap array naming all five siblings by exact agent name); `.claude/agents/fd-living-heritage-transmission.md:9` (`source_spec: 'linsenkasten-registry-design-wide-1.json'` — the only place the cohort membership is recorded, and it is a filename, not a structured sibling list or edge); brainstorm.md:56-66 (Fork 2's three edge types, none of which model "generated together with, and mutually dependent on, these N other lenses").
- **Suggestion:** At minimum, harvest an explicit `sibling_cohort` field (the full list of agent names sharing a `source_spec`, taken straight from `flux-gen-specs/*.json`'s own sibling entries) onto each accessioned lens, and have reuse-before-regenerate either serve a lens's full cohort together or strip/flag its `anti_overlap`-derived exclusions when serving it solo. This is a one-field addition to the harvest record, not a new edge type or a scoring change.

### normalization-rule-has-no-author-of-record
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:70` ("Tier 1: content-hash on normalized spec + body collapses byte-identical copies mechanically"); `apps/api/src/lens/graph.py:1-10` (the only existing graph/lens-processing code in the repo — a Pinecone-backed relationship module with no hashing or normalization logic of any kind); confirmed absent via `grep -rn "normaliz\|content_hash" apps/api/src/lens/ packages/mcp/` (zero hits for any lens-body normalization function anywhere in the tree).
- **What:** "Normalized" is doing real work in Fork 3 — it is the entire mechanism by which "byte-identical copies" get collapsed, and per the census (brainstorm.md:157) it is credited with a specific, cited result ("hash dedupe alone removes 41%"). But the transform itself — does it strip frontmatter timestamps? case-fold? collapse whitespace? hash the spec and body separately or concatenated? — is not written down anywhere in this repository: not in the brainstorm, not in graph.py (which predates the harvester entirely and does Pinecone vector search over the 258 curated lenses, nothing hash-related), not in any spec or doc. Per Fork 5's own ruling (brainstorm.md:104-109), zklw alone runs the harvester, so this transform will be invented once, by whoever writes that harvester, and will exist only as source code on the canonical machine. This is exactly the "bearers and successors" question this lens is built to ask: not whether the hash is stable across machines (out of scope per this lens's own anti-overlap instruction), but whether anyone other than the original author — a successor operator six months later, the Mac side of the sync, a fresh session picking this up — could read the repository and reconstruct what "normalized" means well enough to audit a single collapse decision in the sweep report, or to know whether two lenses that *should* have collapsed didn't because the normalization missed a variant form.
- **Evidence:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:70` (the only sentence in the entire design that mentions normalization, stated as a fait accompli with no definition); `apps/api/src/lens/graph.py:1-10` (docstring: "Adds graph-based relationships on top of Pinecone vector search" — confirms no hash/normalize precedent exists to inherit from).
- **Suggestion:** Before the harvester is written, commit the normalization rule as a short, checkable spec (even a single test fixture pairing raw input to normalized output) alongside the harvest transport design (brainstorm.md:147-152), not as an implicit convention inside the harvester's source. One fixture file is enough to make it something other than tacit knowledge held by whoever happens to write `data/harvest/<machine>.jsonl` first.

## Verdict
The registry design's transmission failures are not confined to the future harvest — they are already reproducing at the point of lens *generation*, visible in the exact six files this probe was asked to review: all six carry silent mid-file truncation with no completeness marker, and all six are occasion-bound siblings whose stated scope depends on a cohort the harvest has no field to preserve. A design that accessions these files today, as designed, accessions both defects as permanent, undetectable registry content.
