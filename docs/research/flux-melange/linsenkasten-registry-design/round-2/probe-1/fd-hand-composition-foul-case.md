## Findings

### spec-survives-render-discards
- **Severity:** P1
- **Where:** `.claude/agents/fd-hand-composition-foul-case.md:36,41,46,51,56,61` (six `[truncated — N chars omitted]` markers, this file); `.claude/flux-gen-specs/linsenkasten-registry-design-wide-2.json` (this lens's own `review_areas` array — verified directly, six strings of 748–1081 chars, none truncated); `/Users/sma/projects/interflux/scripts/sanitize_untrusted.py:156` (`text = f"{text[:max_len]}\n[truncated — {omitted} chars omitted]"`); `/Users/sma/projects/interflux/scripts/generate-agents.py:228-235` (`render_agent`: `review_sections` built from `sanitize_list(..., max_item_len=200)` applied fresh to `spec.get("review_areas")` on every render); `docs/plans/2026-09-02-linsenkasten-registry.md:145` (`specs/<id>.json` copied into the registry at harvest), `:568` (`harvest/embed.py` generated text = `thresholds.embedding_text(spec, body)` — reads the spec, not the rendered body, whenever a spec exists), `:655` (`materialize(match, agents_dir, spec)` writes "registry body" verbatim, only overriding frontmatter fields — never re-renders from `specs/<id>.json`)
- **What:** the marker text a compositor would call a bad sort is a *render-time* artifact, not a loss at the source: I pulled this exact lens's own spec file and its `review_areas` entries are fully intact at 748–1081 characters each — `sanitize_list(..., max_item_len=200)` in `render_agent` is what cuts them to ~200 chars and appends the marker, and it does that identically on every render, from the full spec, not from the already-truncated .md. The registry design already knows this: `embedding_text(spec, body)` prefers the spec over the body for exactly this reason, so harvest-time matching quietly reads the clean data. But `materialize()` — the function that actually hands a reused lens to a live repo, the one place where "reused lens worse than fresh" becomes real — copies the *stored* `lenses/<id>.md` body verbatim, and that stored body is the harvest-time render, made by the same 200-char sanitizer, from the same full spec that is sitting one file over in `generated/specs/<id>.json`. The cure is filed next to the disease, permanently (this copy survives Fork 4's prune, which only deletes the *repo's* `.claude/flux-gen-specs/`, not the registry's own `specs/<id>.json`), and nothing in the pipeline ever applies it.
- **Evidence:** `python3` read of `.claude/flux-gen-specs/linsenkasten-registry-design-wide-2.json` → `review_areas` lengths `[1081, 987, 925, 902, 748, 877]`, all above the 200-char `max_item_len` that produced this file's six truncation markers; `sanitize_untrusted.py:156` is the only place that string literal is built.
- **Suggestion:** at merge time (or at `materialize()`), when `specs/<id>.json` exists for a record, re-render the stored body from the spec (same function `render_agent` already uses, or a raised `max_item_len` for the registry copy) instead of trusting the harvested `.md` byte-for-byte. One call, not a new stage — the spec is already loaded for `embedding_text`.
- **Remediation:** wire `materialize()` (and the merge step that writes `data/generated/lenses/<id>.md`) to re-render from `specs/<id>.json` when present, falling back to the harvested body only when no spec survived.

### fork3-hash-formula-drift
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:70` (Fork 3: "Tier 1: content-hash on normalized spec + body collapses byte-identical copies mechanically") vs. `docs/plans/2026-09-02-linsenkasten-registry.md:495-497` (`harvest/thresholds.py:embedding_text(spec, body)` — the only function that reads `spec`) and `:518` (`scan.py`: `body_hash = sha256 of re.sub(r"\s+", " ", body).strip()` — body only)
- **What:** the ratified fork names a two-input hash; the concrete recipe specified one document over hashes the body alone and routes `spec` into a different function entirely (embedding, not identity). This is the trade's "wrong fount": a piece that reads as the same job — both are labeled Fork 3's content-hash dedupe — fits the slot, and is wrong only on paper, where the two documents no longer agree on what "the hash" spans. Nobody has proofed the ruling against the recipe it produced. Whoever implements straight from the brainstorm (the ratified, mk-approved record) builds a different collapse rule than whoever implements from the plan.
- **Evidence:** brainstorm L70 is the only sentence in the target document describing the hash formula; plan L495-497 is the only place `body_hash` is defined, and `spec` never appears in that definition.
- **Suggestion:** pick one formula and say so in both places — a single sentence fix, either "hash on body alone; spec is a separate embedding-time signal" in the brainstorm, or restore spec to the hash in the plan.
- **Remediation:** amend Fork 3's ruling text to match the implemented formula (or vice versa) in the next revision pass over this document.

### domains-default-starves-lexical-fallback
- **Severity:** P2
- **Where:** `.claude/agents/*.md:7` (`domains: ["uncategorized"]` on 5 of 6 files in this exact directory, verified by direct grep); `/Users/sma/projects/interflux/scripts/generate-agents.py:154-192` (`_infer_domains_from_spec`: a fixed ~24-entry filename-segment map, falling back to `["uncategorized"]` when nothing matches); `docs/plans/2026-09-02-linsenkasten-registry.md:244` (`related_concepts: r.domains || []` for every generated record) and `:277` (`lexicalScore`'s `dt` token set folds `related_concepts` into query scoring, +2 per matched token)
- **What:** `domains` is stamped once at generation time from a small filename lookup with no confidence signal, then rides unchanged through harvest and merge into `related_concepts`, which `lexicalScore` reads for both layers — including the tier-3 lexical fallback that fires whenever local and zklw Ollama both miss. Since `uncategorized` describes nothing about an individual lens and is shared by nearly the whole generated layer, the domain half of that scoring signal is dead weight for almost every generated hit the fallback ranks, and no field distinguishes a domain that was actually inferred from one the classifier defaulted on — so a later domain-quality pass can't even tell which records to re-derive.
- **Evidence:** `grep -n "domains:" .claude/agents/*.md` → 5 of 6 files read `["uncategorized"]`; `generate-agents.py:192` (`return sorted(domains) if domains else ["uncategorized"]`) is the only fallback branch.
- **Suggestion:** stamp `domains_source: "inferred" | "default"` alongside `domains` at generate time so harvest/merge and `lexicalScore` can treat the default case as absent signal rather than a real tag.
- **Remediation:** add the source flag to `render_agent`'s frontmatter and thread it through `scan.py`/`merge.py`'s `domains` union.

## Verdict
The truncation bug already on the record (settled, not restated here) has a specific, currently-available, zero-cost fix that the design never takes — the spec that would recast a clean body sits inside the registry itself, forever, unread by the function that serves reuse hits. Alongside that, the ratified hash formula and its downstream implementation have quietly drifted apart, and the domain tag every generated lens carries degrades one real (if minor) scoring path with no way to tell a default from a finding.
