## Findings

### spec-hash-is-shared-not-per-lens
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` line 70 ("Tier 1: content-hash on normalized spec + body collapses byte-identical copies mechanically")
- **What:** The fork's prose treats "spec + body" as two per-lens inputs to the hash, implying the spec differentiates or corroborates the body the way a manuscript's exemplar differentiates a copy. In the actual repo that seeded this very review, that isn't how specs are shaped: `.claude/flux-gen-specs/linsenkasten-registry-design-seed-adjacent.json` is one file holding three unrelated lens definitions (`fd-knowledge-graph-edge-schema`, `fd-distributed-sync-data-integrity`, `fd-recsys-reuse-relevance`), and all three agents' frontmatter cites the identical `source_spec: 'linsenkasten-registry-design-seed-adjacent.json'`. If the normalizer hashes the literal spec file (or even just its filename) as the "spec" component, three agents with completely different bodies and purposes share one spec-hash contribution, so the "+ spec" half of "spec + body" adds zero discriminating power for current-generation output — the design's stated two-part collation is really one part, and no one decided that on purpose. The reverse failure is symmetric and worse: if a future flux-gen version writes one spec per agent (this repo's `flux_gen_version: 6` demonstrably doesn't), the same hash code silently starts behaving differently across generations of harvested material with no version marker anywhere in the normalization the design sketches (there is no sketch at all — Fork 3 names the two tiers but never enumerates what "normalized" strips).
- **Evidence:** `.claude/agents/fd-distributed-sync-data-integrity.md:9`, `.claude/agents/fd-knowledge-graph-edge-schema.md:9`, `.claude/agents/fd-recsys-reuse-relevance.md:9` all read `source_spec: 'linsenkasten-registry-design-seed-adjacent.json'`; `.claude/flux-gen-specs/linsenkasten-registry-design-seed-adjacent.json` contains three `"name"` entries (lines 3, 45, 87). Brainstorm line 70 gives no field list for what the normalizer strips or how the spec component is derived.
- **Suggestion:** Name the exact spec-hash input in the design record before implementation — e.g. "the lens's own entry within the seed file, not the seed file as a whole" — and pin a `flux_gen_version` (or equivalent) into the normalized form so a schema change in spec granularity produces a detectably different hash generation rather than a silent behavior change.

### hit-rate-coverage-forces-codex-optimus
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` line 74 ("picked by ledger hit-rate, else recency") and line 144 (hit-rate is null when nothing was adjudicated), read against the census at lines 158-162 (86 + 32 heat ledgers against ~4,750 agents)
- **What:** This is the codex optimus fallacy the lens is built to catch: an editor picks the "best" witness by a criterion that in practice almost never fires, so the fallback criterion — here, recency — does the real selecting. Heat-ledger coverage (118 ledgers total) against the harvested population (~4,750 agents, 1,685 unique bodies before variant clustering even runs) means the overwhelming majority of variant-of clusters will have zero adjudicated findings for any member, so hit-rate is null for the whole cluster and head selection falls straight to recency. Recency systematically favors whichever repo happened to regenerate the lens most recently — not the copy an editor with ledger evidence would pick — and flux-gen/melange's reuse-before-regenerate seam then serves that recency-selected head every time, which is precisely the "reused lens is worse than a fresh one" failure the task brief names as the top priority.
- **Evidence:** Line 74 states the selection rule; line 144 states null-when-unadjudicated; lines 158-162 give the ledger-to-agent ratio (86+32 = 118 ledgers vs. ~4,750 agents, ~2.5% at the most generous global rate, before accounting for how thinly those 118 spread across however many variant-of clusters Tier 2 produces).
- **Suggestion:** Surface the fallback in the registry record itself — a `head_selected_by: "hit_rate" | "recency"` field per cluster — so reuse-before-regenerate (and a future human auditor) can see when a head was chosen by evidence versus by default, and so gap-detection tooling can report what fraction of the registry is running on the fallback.

### parents-empty-is-ambiguous
- **Severity:** P2
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` lines 147-150 ("Frontmatter carries **no** fusion lineage anywhere in the pile, so `fused-from` edges come from melange lens records (`lenses/*.json`, `parents`) and `-fusion-N` spec files, not from agent files")
- **What:** The design commits to reconstructing `fused-from` lineage exclusively from melange's own `lenses/*.json` records. This repo's own melange record for the metrology lens under review, `docs/research/flux-melange/linsenkasten-registry-design/lenses/fd-metrology-traceability.json`, has `"parents": []` because it's a `"kind": "base"` lens — genuinely unfused. Nothing in the design's harvest description carries the `"kind"` field forward into the registry alongside the empty parents list. A lens whose melange record was never committed, or whose worktree was deleted before the record reached the canonical repo, produces the identical empty-parents shape once harvested — the stemma cannot tell "confirmed independent" from "lineage unknown" from the registry alone, which is exactly the false-independence failure this lens flags at P2.
- **Evidence:** `docs/research/flux-melange/linsenkasten-registry-design/lenses/fd-metrology-traceability.json` line 4, `"parents": []`, alongside `"kind": "base"` at line 3 — the design's harvest description (brainstorm lines 147-150) names only `parents` as the source of `fused-from` edges, never `kind` or any other independence marker.
- **Suggestion:** Carry the melange record's `kind` (or equivalent) through harvest as the edge schema's explicit tri-state — `no-parents-confirmed` / `parents-known: [...]` / `lineage-unknown` — so an empty edge list in the registry means what the design intends it to mean rather than what happened to survive.

### archive-claim-spans-two-repos-and-a-git-pull-lag
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` line 85 ("Git history + the registry are the archive") read against lines 104-107 (zklw commits the registry, "the Mac pulls through git") and lines 167-169 (this very module "is on a sibling session's unpushed `sweep/2026-09-02` branch")
- **What:** Fork 4's archive claim quietly conflates two different git histories: the pruned repo's own history (which still contains the deleted `.claude/agents` files in old commits, on whatever machine holds that clone) and the registry's home repo's history (which is what actually needs to hold the harvested record, per Fork 5). Fork 4's stated precondition is "the harvest is verified in the registry" — but it never says verified against zklw's just-committed canonical state versus a Mac session's locally git-pulled copy, which by Fork 5's own design can lag behind. A sweep commit run on the Mac citing a registry id is citing whatever the Mac's local pull currently contains; if that pull predates zklw's latest merge for this repo's lenses, the id being cited for "this file is safe to delete, it's in the registry" may not yet exist in the copy that will eventually become canonical, or may resolve to a stale record that collapsed a since-superseded variant. The doc's own Facts-checked section demonstrates the underlying condition is live, not hypothetical: this very interlens module currently has unpushed work sitting on a sibling session's branch.
- **Evidence:** Line 85 states the archive claim without naming which repo's history; lines 104-107 establish the zklw-canonical / Mac-git-pull split that creates the lag; lines 167-169 confirm unpushed branches are an active condition in this codebase right now, not a theoretical edge case.
- **Suggestion:** State the prune precondition as "harvest is verified against zklw's canonical registry state (post-merge, post-embedding), not a local git pull" and have the sweep commit message record the registry's commit hash it was checked against, not just a per-file registry id, so a later editor can tell whether the citation was fresh at deletion time.

## Verdict
The design's irreversible step — deleting repo-local `.claude/agents` piles — is gated on two mechanisms (hash-plus-variant dedupe, "harvest verified in the registry") that are underspecified exactly where this repo's own generated artifacts show the underspecification would bite: shared, not per-lens, spec files feeding the hash; near-zero ledger coverage forcing recency to silently pick every canonical head; and an archive claim that spans a canonical/pulled-copy split the document elsewhere admits is live. None of these require abandoning the approach — each has a small, stated remedy — but as written, a later editor has no way to tell a deliberate collapse from an accidental one once the source files are gone.
