## Findings

### embedding-matrix-has-no-realization-record
- **Severity:** P0
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` lines 126-128 ("embeddings are 768-d `nomic-embed-text` via Ollama (serving on both machines, checked 2026-09-02), precomputed at harvest and committed")
- **What:** This is the P0 scenario this lens is calibrated on, verbatim: the design states a model name and dimensionality but records no realization — no Ollama/model build hash, no quantization, no pooling or normalization convention — alongside the committed matrix. "Checked 2026-09-02" is a one-time observation, not a pinned or verified property of the artifact. If either machine's Ollama pulls a newer `nomic-embed-text` build (a routine, unannounced event — Ollama model tags move), harvest-time vectors on zklw and query-time vectors computed locally on the Mac (per the three-tier fallback's first tier) come from different realizations. Cosine similarity between an old-realization stored vector and a new-realization query vector stays numerically plausible — it doesn't error, doesn't return an obviously-degenerate value — it just becomes a comparison between two different quantities dressed as one. Every consumer downstream (variant-of clustering, reuse-before-regenerate's match/no-match decision) inherits the drift silently.
- **Evidence:** Brainstorm lines 126-128 name the model and commit point but no realization identifier; Fork 5's own "Consequences" list (lines 122-128) enumerates what changes under the hybrid ruling and provenance-of-the-matrix isn't among them.
- **Suggestion:** Store a realization tag with the matrix — at minimum the Ollama model digest (`ollama show nomic-embed-text --modelfile` or the manifest digest) — and add a load-time check in the store module that compares the querying machine's currently-served model digest against the tag, warning (or refusing to answer) on mismatch rather than silently blending realizations.

### tailscale-tier-reintroduces-fork-5s-own-failure
- **Severity:** P0
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` lines 108-109 ("local Ollama, then zklw's Ollama over Tailscale, then a lexical fallback") read against the same fork's own rejected-alternative reasoning at lines 112-114 ("fails closed whenever Tailscale drops — the exact failure just found, and it was silent for months")
- **What:** Fork 5 was created because a Tailscale/network-dependent path failed silently for months (the Flask API's 404s). Its own text names "fails closed whenever Tailscale drops" as the specific, disqualifying property of the rejected zklw-hosted-API alternative. The accepted hybrid design still has a Tailscale-dependent hop — tier 2 of the query-time fallback, "zklw's Ollama over Tailscale" — sitting between two tiers that don't depend on the network. The failure class isn't eliminated, it's relocated one tier down and given bookends that make it easier to miss: when Tailscale drops, tier 2 presumably falls through to tier 3 (lexical) rather than surfacing an error, so queries keep returning plausible-looking results at degraded quality with nothing in the design stating that this fallthrough is logged, counted, or alerted on. That is the identical shape of failure Fork 5 exists to prevent, reintroduced inside the fix.
- **Evidence:** Lines 108-109 state the fallback order; lines 112-114 are the same document naming Tailscale-drop-silence as a disqualifying failure mode for a sibling design. No line in Fork 5's Ruling or Consequences (104-128) states that a tier-2-to-tier-3 fallthrough is observable.
- **Suggestion:** Emit a counted, queryable signal (a log line or a stored per-query instrument-tier field, per the P2 finding below) every time the fallback falls through past tier 2, and treat a sustained run of tier-2 failures as the same class of alert Fork 5's postmortem would have wanted for the original 404s — cheap to add now, expensive to reconstruct after the fact.

### variant-of-threshold-uncalibrated
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` lines 72-73 ("Tier 2: high embedding similarity keeps lenses separate but adds `variant-of` edges into a cluster with one canonical head")
- **What:** "High embedding similarity" is the entire specification of the boundary that decides whether a harvested lens becomes its own registry entry or gets folded into a cluster behind someone else's canonical head. No numeric threshold, no stated uncertainty band, and no known-answer set (pairs the design commits should cluster, pairs that must not) appears anywhere in the record. This is a tolerance without a procedure — the exact configuration this lens treats as an opinion, not an acceptance criterion — and it sits directly upstream of Fork 4's prune, whose precondition ("harvest verified in the registry") has no meaning independent of this threshold having been set correctly. A threshold picked once by eyeballing a few examples and never checked against a reference set can't be distinguished, from the outside, from one that's silently merging lenses that would review differently.
- **Evidence:** Lines 72-73 give the qualitative rule with no number; no other line in the document (checked against the full text of Forks 1-5, Open Questions, and Facts checked) supplies a similarity value, a calibration procedure, or example pairs.
- **Suggestion:** Before the dedupe pass runs against real data, assemble a small fixed set of lens-body pairs from the existing census (some genuine near-duplicates from worktree copies, some genuinely distinct fd-* lenses with similar domains) and pick the threshold against that set, recording both the value and the reference set it was checked against in the design record or a committed calibration file.

### canonical-site-has-no-scheduled-comparison
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` lines 104-107 ("zklw, as canonical, runs the harvester and the embedding pass and commits the registry data; the Mac pulls through git")
- **What:** zklw is simultaneously the instrument that produces the registry's numbers and the standard those numbers are measured against — there is no independent site the design checks it against. This lens's own domain framing names the exact historical failure this shape produces: the BIPM prototype kilogram and its national copies drifted by micrograms, and because the prototype defined the unit, no comparison could say which had moved. Nothing in Fork 5's ruling or the Open Questions schedules a comparison between zklw's freshly-computed state and the Mac's pulled copy, nor between zklw's embedding realization today and its own realization at the last harvest. The only stated verification anywhere in the document is the informal "checked 2026-09-02" note on Ollama serving (line 127), which is an observation at one moment, not a recurring check.
- **Evidence:** Lines 104-107 establish the self-referential canonical/copy structure; the Open Questions section (130-152) resolves storage, tool naming, hit-rate formula, and harvest transport, but names no verification cadence or comparison artifact.
- **Suggestion:** Define the smallest version of a periodic check — e.g. the harvester writes a small manifest (model digest, embedding count, a hash of the matrix) on every run, and the Mac's pull step compares the manifest to its own last-known state and warns on an unexplained change — rather than a full monitoring system.

### hit-rate-denominator-may-not-travel-with-the-ratio
- **Severity:** P2
- **Where:** `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` lines 142-146 ("Hit-rate with partial or missing ledgers: per lens, `upheld / (upheld + refuted)` over ledger findings attributed to it, `raw` excluded, **null** (never 0) when nothing was adjudicated; surfaced-count and flux-drive use-count stored beside it as separate signals, not folded in")
- **What:** The null-versus-zero distinction here is exactly right and worth noting as something this design already gets correct. What's still unstated is whether the sample size behind a non-null hit-rate — the `upheld + refuted` count — travels with the ratio wherever it's consumed, specifically Fork 3's canonical-head selection ("picked by ledger hit-rate, else recency", line 74) and any reuse-ranking flux-gen/melange does through the reuse-before-regenerate seam. A cluster with one upheld finding and zero refuted has hit-rate 1.0; a cluster with 39 upheld and 1 refuted has hit-rate 0.975. If the selector compares bare ratios, the single-sample lens outranks the well-attested one — a reported rate with no denominator carries an authority it hasn't earned.
- **Evidence:** Lines 142-146 define the formula and the separately-stored signals (surfaced-count, use-count) but say nothing about a stored `n` (upheld+refuted count) accompanying hit-rate into the consumers named at line 74.
- **Suggestion:** Store `upheld + refuted` as an explicit `n` alongside hit-rate, and have head-selection break ties (or discount low-`n` ratios) using it — a one-field addition to the record already being designed.

## Verdict
The design records what instrument it intends to use (nomic-embed-text, a three-tier fallback, a null-safe hit-rate formula) but not what would make any of those numbers trustworthy over time: no realization pinned to the embedding matrix, no scheduled comparison between the canonical site and its copy, no calibrated threshold behind the collapse decision the prune depends on, and the network dependency Fork 5 was written to eliminate reappears one tier into its own replacement. Every finding here names a small, addable artifact — a digest, a manifest, a threshold-and-reference-set, an `n` — not a redesign.
