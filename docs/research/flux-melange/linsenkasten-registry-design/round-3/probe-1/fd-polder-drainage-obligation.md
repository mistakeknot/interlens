## Findings

### materialize-scan-merge-circular-reinflation
- **Severity:** P1
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md` Task 16 (`materialize` writes `<agents_dir>/<spec name>.md` = registry body verbatim), Task 17 (`--registry=auto` calls `materialize` **before** the `name in existing` check), Task 8 (`scan.py`: `body_hash` = sha256 of normalized body, sighting recorded for every `.claude/agents/fd-*.md` regardless of provenance), Task 9 (`merge.py`: index records are grouped by `body_hash`; `sightings`, `machines`, `repos` are unioned/counted across every sighting that hashes the same; `tier`/`use_count`/`last_used` are "max across sightings" — nothing excludes a sighting from the tally, it only picks the maximum tier label); "Out of scope" line (~802-805: "reuse materializes into it").
- **What:** Because `materialize` copies the registry body verbatim (the same content the canonical index record already hashed), a materialized reuse produces a file whose `body_hash` is identical to the existing index record's hash. The next `harvest scan` on that machine walks `.claude/agents/fd-*.md` with no other filter, finds this file, and records it as an ordinary sighting. `harvest merge` then folds it into the *same* index record: `sightings` increments, the reusing repo's name is added to `repos`, the reusing machine is added to `machines` (if not already present) — the exact three fields the brainstorm names as "the duplication evidence used to justify pruning" (Fork 3, Fork 4). Nothing in the Task 8 sighting schema or the Task 9 merge semantics carries a flag distinguishing "this body was authored independently in this repo" from "this body was written here by `materialize` two minutes ago." Every subsequent `--registry=auto` invocation across ~30 repos adds another such sighting, so the metric that is supposed to measure genuine cross-repo duplication is partly measuring the registry's own circulation, and it compounds continuously rather than as a one-time distortion.
- **Evidence:** Task 8's sighting row is `{kind, machine, repo, path, name, body_hash, frontmatter, spec_path, spec, drive_uses, mtime}` — `frontmatter` is stored (so `tier: registry` set by `materialize` is captured) but no step of Task 8 or Task 9 reads that field to skip or tag the sighting. Task 9's index-record pseudocode is explicit: `"tier":"used"` / `"use_count":4` are computed as "max across sightings" — a selection over the set, not an exclusion from it — while `sightings`, `machines`, `repos` have no such qualifier at all, meaning they are plain unions/counts. Task 23's prune later deletes by `body_hash` membership, so it *will* eventually remove the re-materialized file again — but that only fires on the next prune sweep, and by then the merge/stats/edges passes have already run once (at minimum) against the inflated counts, and there is no step that reverses a `sightings`/`repos`/`machines` value once written.
- **Suggestion:** Have `materialize` write a sentinel the scanner already has a natural place to check — e.g. `tier: registry` in frontmatter (which Task 16 already sets) plus a one-line change to Task 8's scan step: skip sighting-recording (or record under a distinct `kind: "reuse-echo"`) for any file whose frontmatter `tier == "registry"`. This is a single conditional in `scan.py`, not a schema change to the index.

### no-recurring-harvest-prune-trigger
- **Severity:** P1
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md` Task 22 (the only systemd unit in the entire plan: `linsenkasten-explorer.service`, `Restart=on-failure`, `WantedBy=default.target` — a persistent daemon for the read-only HTTP explorer, not a timer for the write pipeline), Task 14 ("First real harvest on this machine, merge, embed, edges; commit the generated layer" — five manual commands, run once), Task 15 (zklw harvest — run once, by hand, with an explicit SSH-handoff caveat), Task 23/24 (Mac/zklw prune sweeps — each a single `--plan` then `--apply` invocation), Task 25 (goal-close checklist).
- **What:** A repo-wide `grep -n "timer|cron|schedule|cadence|daily|weekly|periodic"` across both the plan and the brainstorm returns nothing except the unrelated lens name `lens_161_weekly_eye_of_sauron`. The design's entire operational story for keeping the registry current — scan, merge, stats, embed, edges, and eventually prune again — is a sequence of one-shot commands a human runs by hand on two machines. Stage G's prune (Tasks 23/24) is itself a single sweep, not a recurring job; nothing re-arms it. After go-live, `--registry=auto` continues to produce both reused files (feeding finding materialize-scan-merge-circular-reinflation) and genuinely new `fd-*` bodies from ordinary flux-gen/flux-drive/melange runs, and both kinds accumulate in `.claude/agents/` across the same ~30 repos Stage G just emptied. Task 25's goal-close checklist cites "both machines harvested," "hit-rates attached," "the reuse proof doc," "sweep reports," "the fresh-session MCP check," and "the explorer URL" — none of which is a standing job, and none of which requires one to exist before the goal closes. Fork 4's stated payoff ("ending the per-session agent-list context tax") is therefore a property of the moment the sweep ran, not a property of the system going forward; the pile Stage G drained refills at the rate of ordinary usage, and nothing notices or re-drains it.
- **Evidence:** Same file references as above; the negative-space grep is reproducible (`grep -niE "timer|cron|schedule|cadence|daily|weekly|periodic" docs/plans/2026-09-02-linsenkasten-registry.md docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md` → one hit, the lens name).
- **Suggestion:** Do not propose a new daemon — that would be exactly the recurring chore this lens is warned against inventing for a single operator. Instead, add one line to Task 25's goal-close checklist: name who re-runs Tasks 14/15/23/24 (even "mk, by hand, no fixed interval") and under what trigger (even "next time the agent count in a `git status` on any watched repo looks large" is a trigger; silence is not). The absence of an answer is itself what this lens is asking the plan to write down.

### reuse-log-fallback-swept-by-prune
- **Severity:** P2
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md` Task 16 (`record_reuse(root, entry)`: appends to `<root>/data/generated/reuse-log.jsonl` when writable, **else to `<project>/.claude/flux-gen-specs/reuse-log.jsonl`**), Task 23 ("delete `.claude/flux-gen-specs/` the same way (a spec is deletable when every `name` inside it resolves to an index record)"), Task 25 (goal-close citation list — no reuse-rate line item), Task 18 (`tail -1 data/generated/reuse-log.jsonl` — a one-time verify step, not a standing report).
- **What:** `record_reuse`'s fallback path — the one that fires precisely when `find_registry_root()` fails to find a writable registry (i.e. exactly the "silent because the fallback is graceful" condition this lens's own approach names) — writes into `.claude/flux-gen-specs/`, the same directory Task 23's Stage G sweep deletes from every pruned repo. Task 23's stated deletability predicate ("every `name` inside it resolves to an index record") is written for spec JSON files; the sentence right before it says the sweep will "delete `.claude/flux-gen-specs/` the same way," which reads as a directory-level action. Under a directory-level reading, `reuse-log.jsonl` is deleted unconditionally the next time that repo is swept, with no check at all. Under a per-file reading, the predicate as stated doesn't classify a log file (it isn't a spec with a `name`), so its fate is simply undefined by the text either way. Either reading loses the only artifact that would ever let someone compute a real reuse rate from that fallback path, and no task in the plan ever aggregates or reports from `reuse-log.jsonl` at all — Task 18's `tail -1` is a smoke check for the DONE WHEN item, not an ongoing measure, and Task 25's close checklist cites "the reuse proof doc" (singular, one-time) rather than a log-derived number.
- **Evidence:** the two Task 23 clauses quoted above sit in the same sentence with no distinguishing scope marker; Task 25's full citation list (README, AGENTS.md/CLAUDE.md, roadmap.json, publish, goal-close bullet) contains no reuse-log read.
- **Suggestion:** Smallest fix: name `reuse-log.jsonl` explicitly as never-delete in Task 23's prune semantics (one clause: "never delete `reuse-log.jsonl` even when the rest of the directory qualifies"), independent of resolving the directory-vs-per-file ambiguity for spec JSON. No new recurring job is needed to fix this one — it is a one-line exclusion, not an obligation.

## Verdict
The design's single biggest undisclosed obligation is operational, not architectural: nothing in the plan schedules the harvest→merge→prune cycle to run again, so Fork 4's context-tax fix is a one-time event whose evidence (sightings/repos/machines) is simultaneously polluted by the reuse mechanism's own output feeding back into the same scanner. The reuse-log ambiguity is a smaller, cheaply-fixed instance of the same pattern — evidence of payoff sitting in a spot the design's own cleanup step can reach.
