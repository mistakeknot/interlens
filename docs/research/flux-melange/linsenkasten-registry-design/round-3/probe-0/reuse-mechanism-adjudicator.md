## Findings

### combine-contrast-seam-is-not-a-match-step
- **Severity:** P1
- **Where:** docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:24-27 ("flux-gen and flux-melange consult the registry reuse-before-regenerate through the existing combine/contrast seam"), :35-36 ("the melange fusion seam already calls interlens tools when available, so reuse-before-regenerate plugs into an existing integration point"), :61-62 (embodies "auto-suggested at harvest"), :107-108 (query-time embedding fallback chain)
- **What:** Independently re-verified against the live repo rather than trusting either prior finding's quote. The literal claim that reuse-before-regenerate is "a harvest-time embedding match... with no query-time re-validation" is refuted: Fork 5 does specify a query-time embedding pipeline (local Ollama → zklw Ollama over Tailscale → lexical), and `search_lenses` genuinely embeds free text fresh per call (`apps/api/lens_search_api.py:376-389`, `supabase_store.search_lenses(query, k=20)`), not a cached vector. But the sharper claim survives: the brainstorm names exactly one integration point for reuse-before-regenerate — "the existing combine/contrast seam" — and that phrase resolves in this codebase to `combine_lenses` (`apps/web/api/mcp-sse.js:391-397`), verified directly: it takes `args.lenses` (an array of names the caller already picked), resolves each by exact lowercase string match (`lenses.find(l => l.name.toLowerCase() === name.toLowerCase())`), and produces a blended prose synthesis. There is no `args.query`, no embedding call, and no "current review target" object anywhere in that handler — it cannot perform a reuse match because it was never built to compare a target against candidates, only to blend lenses already selected by name. `search_lenses` could in principle serve as the match tool, but the brainstorm never names it for this purpose, never defines what query text would represent "the current target," and Fork 2's typed edges (`embodies`: harvest-time, lens-vs-curated-pattern; `variant-of`: harvest-time, lens-vs-lens-cluster) supply no target-vs-candidate edge either. As the brainstorm is written, reuse-before-regenerate has zero described match mechanism — an absent step, not a stale one.
- **Evidence:** `apps/api/lens_search_api.py:375-389` (search_lenses: free-text `q` param, semantic, per-call — but no caller wiring in this doc); `apps/web/api/mcp-sse.js:391-397` (combine_lenses: name-array lookup, no query text, no embedding, no target object); brainstorm L24-27, L35-36 (only named seam), L56-66 (edge types, neither target-facing).
- **Suggestion:** Stop describing reuse-before-regenerate as plugging into "the combine/contrast seam" — that phrase names a tool that structurally cannot match a target to candidates. Name the actual match function once one is designed, and specify what text represents "the current target" being embedded.

## Verdict
Position 2 (absent match step) holds over the literal "stale harvest-time match" framing: a query-time embedding pipeline exists at the infrastructure level (Fork 5), but the brainstorm names no function that uses it to compare a live review target against reuse candidates — "the combine/contrast seam" resolves to `combine_lenses`, which does no target matching. This is not a taste call; it is independently confirmed against the live handler code. The one new insight this round adds: the fix a prior round credited as "already mitigated" is unbuilt in every repo checked, so the brainstorm's gap is currently live, not merely theoretical, and nothing in the ratified document points toward the plan that would close it.
