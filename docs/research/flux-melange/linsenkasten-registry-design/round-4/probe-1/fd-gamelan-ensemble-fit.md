# fd-gamelan-ensemble-fit — round 4

## Findings Index
- [P1] severity-examples-skip-every-net — `severity_examples` is the one LLM-authored field the pipeline neither sanitizes, nor matches on, nor overrides at materialize — the least-checked instrument in the whole design (§Stage D reuse seam: Task 8/13/16/17)
- [P2] review-areas-embeds-a-census-snapshot — the one field that *is* embedded for matching bakes in this run's own point-in-time corpus counts, so match score partly measures which review happened to run when (§Task 8 `embedding_text`; source_spec `review_areas`)

## Findings

### severity-examples-skip-every-net

- **Severity:** P1
- **Where:** `interflux/scripts/generate-agents.py:206-260` (`render_agent`, `_render_severity_calibration`); `interflux/scripts/sanitize_untrusted.py:8-19` (chokepoint docstring, channel 2); `docs/plans/2026-09-02-linsenkasten-registry.md:506-511` (`thresholds.embedding_text`), `:655` (`materialize(match, agents_dir, spec)`); `.claude/agents/fd-gamelan-ensemble-fit.md:64-72` (rendered `## Severity Calibration`); `.claude/flux-gen-specs/linsenkasten-registry-design-wide-4.json` (`severity_examples`).
- **What:** Every other LLM-authored, spec-specific field gets at least one pass of cross-context treatment before or at reuse: `persona`, `decision_lens`, `task_context`, `review_areas`, `anti_overlap`, `success_hints` are all routed through `sanitize()`/`sanitize_list()` (bounded, stripped) before rendering, and `persona`/`focus`/`decision_lens`/`review_areas` are additionally the exact text `thresholds.embedding_text` matches a new spec against. `severity_examples` gets none of that. `render_agent` reads `ex.get("scenario","")`/`ex.get("condition","")` straight into the body with no `sanitize()` call anywhere in the function (confirmed: the only three `sanitize(` call sites in the file are `task_context`, `persona`, `decision_lens`, plus `sanitize_list` for `review_areas`/`success_hints`/`anti_overlap`). `sanitize_untrusted.py`'s own docstring enumerates channel 2 as "`persona, decision_lens, review_areas, task_context, anti_overlap`" — `severity_examples` (added in v5, line 57: "v5: severity calibration (severity_examples field + escalation instruction)") was never added to the enumerated sink list when the field was introduced. And `embedding_text`'s recipe (`persona + focus + decision_lens + review_areas`) structurally excludes it, so `resolve()` never sees it either. At `materialize(match, agents_dir, spec)` the function already receives the *new* spec as its third argument — the new review's own worked P0/P1/P2 examples, if the new spec has them, are sitting right there unused — yet Task 16/17 copy the stored body verbatim and touch only `tier`/`registry_id`/`reused_at`/`source_spec`. The net effect: whatever a generating LLM wrote as a P0 scenario for one review's target — real file paths, function names, task numbers, all cited as fact — ships into every future reuse completely unbounded, unmatched, and unregenerated, with no step in the pipeline ever asking whether it still describes the room it's being served into.
- **Evidence:** `sanitize(` call sites in `render_agent`: lines 206, 208, 215 (`task_context`, `persona`, `decision_lens`) plus `sanitize_list(` at 231, 243, 247 (`review_areas`, `success_hints`, `anti_overlap`) — no fourth call for `severity_examples`; `_render_severity_calibration` (lines 111-148) takes `scenario`/`condition` from the raw dict and appends them with an f-string, no wrapper. `sanitize_untrusted.py:8-19` names the five enforced sinks and explicitly warns "A bypass in any one channel amplifies across all of them... finding C-6 (sanitization was advisory-only and bypassable via uncovered sinks)" — `severity_examples` is exactly that shape of uncovered sink, for a field the enumeration predates.
- **Suggestion:** Smallest set-preserving change: at `materialize(match, agents_dir, spec)`, if the incoming `spec` itself carries `severity_examples`, render *that* into `## Severity Calibration` instead of the stored match's — the data is already a parameter, so this is a branch, not a new field or a new pass. If the incoming spec has none, drop the section rather than deliver a fixed exemplar-set built for a different set of neighbours.

### review-areas-embeds-a-census-snapshot

- **Severity:** P2
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md:506-511` (`embedding_text`, `parts += list(spec.get("review_areas") or [])`); `.claude/flux-gen-specs/linsenkasten-registry-design-wide-4.json` `review_areas[1]`/`[2]` (own worked evidence); `docs/brainstorms/2026-09-01-linsenkasten-gate-forks-brainstorm.md:14-16` (Census evidence, 2026-08-26) vs `:156-158` (Facts checked, 2026-09-02) vs this lens's own `generated_at: '2026-09-03T08:10:35+00:00'` frontmatter.
- **What:** `review_areas` is the one body section that is both delivered *and* the field `embedding_text` actually matches a future spec against — the design's implicit answer to "which part of a stored lens is safe to compare for fit." But `review_areas` is written, by construction, as evidence-cited prose naming this run's own measured facts, not durable domain perspective: this lens's own item 2 states "measured on the live Mac pile that is 3,023 agent files, 1,776 distinct names, 1,799 distinct bodies, with 21 names covering 44 distinct bodies," and item 3 repeats "the measured pile already shows 21 names covering 44 distinct bodies." Those are census counts, not persona. The corpus those counts describe is demonstrably a moving target across the design's own documents: 2,500 agents (2026-08-26, brainstorm goal header) → 2,881 agents/1,666 names/1,685 unique bodies (2026-09-02, brainstorm Facts-checked) → 3,023 agents/1,776 names (2026-09-03, this very spec, one day later). A future spec whose `review_areas` cites a later census's numbers will differ from this lens's vector by exactly the words "3,023" vs whatever the next count is, contributing to cosine distance for reasons that have nothing to do with whether the two lenses share a perspective — the one field the pipeline trusts for content-similarity is partly measuring which day the review ran, not what it was about.
- **Evidence:** `.claude/flux-gen-specs/linsenkasten-registry-design-wide-4.json` `review_areas[1]` ("3,023 agent files, 1,776 distinct names, 1,799 distinct bodies... 21 names covering 44 distinct bodies") and `[2]` (repeats "21 names covering 44 distinct bodies"); brainstorm lines 14-16 (~2,500/~4,750), 156-158 (2,881/1,666/1,685) — three different counts of the same corpus across three dated snapshots, none more than eight days apart.
- **Suggestion:** Not a threshold or embedding-recipe question (that's metrology's ground) — a set-preserving authoring convention: keep measured counts and other point-in-time evidence in `severity_examples`/`task_context` (already excluded from the match vector) and reserve `review_areas` for the recipe-level, count-free description of what to look for, so the one field being matched on stays comparable across census snapshots.

## Verdict

Two failure modes the cohort's own review-approach script (this lens's `review_areas`/`severity_examples`, verified against `generate-agents.py`) had not already spelled out: `severity_examples` is not merely excluded from matching like `anti_overlap`/`task_context` (already filed) — it is the only untrusted spec field with zero cross-context treatment of any kind, sanitize included, even though `materialize`'s own signature already holds the fresh spec that could replace it. Separately, the one field the match *does* read, `review_areas`, is demonstrably contaminated with this-run's census arithmetic, so content-similarity is partly an artifact of when a lens was generated rather than what it is about. Both are one-branch, set-preserving fixes, not a redesign.
