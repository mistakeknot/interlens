### harvest-timer-dirty-tree-has-no-recovery
- **Severity:** P1
- **Where:** Task 22, line 765: `scripts/zklw-harvest.sh` (`set -euo pipefail`; `git pull --ff-only origin main`; `python3 -m harvest scan ... && merge && stats && embed --check && edges && audit`; conditional commit+push only `if git status --porcelain data` is non-empty) driving `linsenkasten-harvest.timer` (`OnCalendar=*-*-* 04:30:00`, `Persistent=true`) → `linsenkasten-harvest.service` (`Type=oneshot`).
- **What:** `set -euo pipefail` means the script aborts at the first non-zero-exit command in the chain — but `scan`, `merge`, `stats`, `embed --check`, `edges`, and `audit` are chained with `&&` on one line, so a failure at, say, `embed --check` (Task 5/11's own spec says embed "refuses" on a model-digest mismatch, and Ollama being briefly unreachable is exactly the kind of thing a nightly cron hits) happens *after* `scan` and `merge` have already rewritten `data/harvest/zklw.jsonl` and `data/generated/index.jsonl` in the working tree, and *before* the script reaches its own `git status --porcelain data` / commit / push block. The result: zklw's checkout is left with uncommitted modifications to tracked `data/` files. The *next* night's run starts with `git pull --ff-only origin main`, which git will refuse ("Your local changes to the following files would be overwritten by merge") because of exactly those dirty files — so the script fails again at line 1, every night, and `Type=oneshot` + `Restart=`-less unit (no `Restart=` directive is given at all for `linsenkasten-harvest.service`, unlike the explorer's `Restart=on-failure`) simply reports a failed systemd job with no `OnFailure=` alerting target specified. Nothing in the plan re-checks or resets a dirty `data/` tree, and no health/alert mechanism is specified for this specific unit.
- **Evidence:** Read directly off the script recipe as given at plan line 765 — the `&&`-chain and the trailing `if ... git add ... commit ... push` are exactly as quoted above; I also confirmed via `ssh zklw` that no `linsenkasten-harvest.timer`/`.service` unit exists yet (`systemctl --user list-timers` and `list-unit-files` show nothing matching `linsenkasten|interlens|harvest`), so this is a build-time gap in the unit's own design, not something later tasks patch.
- **Suggestion:** Add a `git status --porcelain data` guard *at the top* of `zklw-harvest.sh` that resets/stashes any pre-existing dirty `data/` before the pipeline runs (e.g. `git checkout -- data` after confirming no unpushed local commits exist, or `git stash --include-untracked -- data` with a report line), and add `OnFailure=linsenkasten-harvest-alert.service` (or at minimum instruct checking `systemctl --user is-failed linsenkasten-harvest.service` from the Mac's own on-demand harvest step) so a wedged nightly run surfaces before Task 23/24's prune preconditions quietly start refusing to run on a stale registry.

### explorer-host-flag-undocumented-file-mode
- **Severity:** P1
- **Where:** Task 22, "Server" paragraph, line 751 (`--host` (default `127.0.0.1`)...) — the complete, only build spec given for `server.js`'s flag parsing — vs. line 759 (`ExecStart=/usr/bin/env node packages/mcp/server.js --host %h/.local/share/linsenkasten/ts-ip --port 7411`) and line 764 (parenthetical: "`--host` accepts a path: the server reads the file to get zklw's Tailscale IP...").
- **What:** The systemd `ExecStart` line passes a *filesystem path* (`%h/.local/share/linsenkasten/ts-ip`, a systemd `%h`-expanded home-directory path to a file written once by `tailscale ip -4 > ...`) as the literal value of `--host`. The only place this file-vs-literal dual behavior is described is a parenthetical eight lines later, in the deployment section — not in the "Server" paragraph that is the actual build spec for `server.js`'s argument parsing, and the two `<verify>` lines for Task 22 (a local curl on `127.0.0.1:7412` and a curl to `$(ssh ... zklw tailscale ip -4):7411`) never exercise the `--host <path>` code path directly — the second one independently re-derives the Tailscale IP via its own `ssh ... tailscale ip -4` and just checks whether *something* answers on that address, so it would not surface an implementation that either crashes on an unresolvable "hostname" (a plain literal-string reading of `--host`) or, if written defensively with a "fall back to all interfaces on parse failure" pattern (a common naive-CLI habit), silently satisfies the plan's own hard rule two sentences earlier — "the unit must never be given `0.0.0.0`" — by accident rather than by a tested guarantee.
- **Evidence:** Direct read of Task 22's text at the cited lines; confirmed via `ssh zklw` that no `linsenkasten-explorer.service` exists yet and nothing is listening on port 7411 today (`ss -ltnp` shows only unrelated local Node dev servers on 4002/3941/4321), so this is genuinely unbuilt/unverified, not a discrepancy already resolved by running code.
- **Suggestion:** Fold the file-path behavior into the "Server" paragraph itself as part of `server.js`'s actual spec ("`--host`: if the value is an existing file, read and trim it for the bind address; otherwise use it literally; default `127.0.0.1`"), and add a unit test plus a `<verify>` line that runs `server.js --host <tmpfile-containing-an-IP>` and asserts it bound to that IP (not `0.0.0.0`, not a crash) — matching the "never `0.0.0.0`" guarantee the plan already states in prose.
