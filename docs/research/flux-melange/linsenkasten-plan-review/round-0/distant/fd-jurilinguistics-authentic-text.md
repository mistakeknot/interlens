## Findings

### resource-handlers-call-retired-fetchfromapi
- **Severity:** P0
- **Where:** `packages/mcp/index.js:451-466` (`case 'lens://episodes'`) and `:475-490` (`case 'lens://graph'`), advertised at `index.js:405` and `:411` via `ListResourcesRequestSchema` (line 390); plan Task 6, the 17-row export table at plan lines 437-459, row `fetchFromAPI(endpoint)` at plan line 442.
- **What:** Task 6's Must-Have artifact is "`packages/mcp/lib/api-local.js` exports the 17 names `index.js` imports today from `api-client.js`... same result shapes" and the table documents `fetchFromAPI` as a row that "throws `Error('linsenkasten: remote API retired; use the local store')`" — framed in the `getCachedData`/`setCachedData` row's own parenthetical as "kept so nothing else breaks," i.e. treated as dead code nobody actually calls anymore. That's false for two call sites the table never accounts for. `index.js:451-466` (the `lens://episodes` resource) and `:475-490` (`lens://graph`) call `api.getCachedData(...)` (which under `api-local.js` always returns `null` per the table), then unconditionally call `api.fetchFromAPI(...)` because the cache is always a miss. Both resources are listed in `ListResourcesRequestSchema` (lines 404-413), so they are visible and readable by any fresh session, not just legacy accidents.
- **Evidence:** `index.js:459-463` — `let episodes = await api.getCachedData('episodes'); if (!episodes) { const lenses = await api.fetchFromAPI('/lenses?limit=500'); ... }`; `index.js:475-479` — `let graph = await api.getCachedData('graph'); if (!graph) { graph = await api.fetchFromAPI('/connections'); ... }`. Both are wrapped by the resource handler's outer `try { switch(uri) {...} } catch (error) { throw new McpError(...) }` (line 423, 498), so a read of either resource always converts into an `McpError` once `api-client.js` is deleted and `api-local.js` is wired in — exactly the plan's own P0 pattern ("an MCP tool throws for every caller from a fresh session on both machines, and the failure appears only after `api-client.js` has been deleted in the same task"), except it's two resources rather than a tool. Task 6's Must-Haves list ("`search_lenses`, `find_lens_journey`, `find_contrasting_lenses`, `detect_thinking_gaps` and `get_central_lenses` answer with no network access") and its `<verify>` block (lines 466-475) never exercise `ReadResourceRequestSchema`, so this break has no test that would catch it.
- **Suggestion:** Add `lens://episodes` and `lens://graph` to Task 6's scope: either route them through `store.getLensesByEpisode`/a new `store` accessor instead of raw `fetchFromAPI`, or drop the two resources from `ListResourcesRequestSchema` in the same commit that deletes `api-client.js`. Add a resource-read to the `<verify>` block (e.g. a `scripts/smoke.mjs` mode that calls `readResource('lens://graph')`) so the gap is machine-checkable.

### digraph-ported-as-undirected
- **Severity:** P1
- **Where:** `apps/api/src/lens/graph.py:22` (`self.graph = nx.DiGraph()`), `:201-217` (`find_contrasts`, which explicitly walks both `self.graph.neighbors(lens_id)` at line 206 *and* `self.graph.predecessors(lens_id)` at line 212) vs. `:219-241` (`get_lens_neighborhood`, BFS using only `self.graph.neighbors(current)` at line 234, no predecessor walk); plan Task 4, line 342 ("**Edge construction (exactly as `graph.py:48-142`):** undirected weighted graph over curated lens ids").
- **What:** The plan's paraphrase of the "second authentic text" states the graph is undirected. The source is a `networkx.DiGraph`, and its own methods disagree with each other about directionality: `find_contrasts` was written to explicitly check *both* outgoing and incoming edges (because the author knew the graph is directed and contrast pairs might only be encoded in one direction), while `get_lens_neighborhood` — the function backing the `find_lens_journey`/`get_lens_neighborhood` MCP tools per plan Task 6's table — only ever calls `.neighbors()`, i.e. out-edges. If `lib/graph.js`'s `buildGraph` produces a genuinely symmetric adjacency map (as "undirected" implies), `neighborhood()`, `findBridges()`, and `findPaths()` will silently return more/different nodes than the Python original ever did for the same curated data, because they will now also traverse edges the original never followed.
- **Evidence:** I read `data/curated/connections.json`'s not-yet-moved source, `apps/api/claude_lens_connections_analysis.json` (280 rows): only 32 of 280 pairs (11.4%) have a reciprocal row in both directions; 248 rows (88.6%) exist in only one direction, e.g. the plan's own graph-test fixture pair `lens_161_weekly_eye_of_sauron` → `lens_161_headline_founder_mode` (`type: contrast`, weight `0.91`) has no reverse row. Under the Python `DiGraph`, `get_lens_neighborhood('lens_161_headline_founder_mode', ...)` would *not* find Eye of Sauron via that edge (wrong direction for `.neighbors()`); under the plan's undirected JS port it would. `centralLenses`'s spec (Task 4, betweenness "written out, not imported") also computes a materially different quantity on a symmetrized graph than `nx.betweenness_centrality` computes on the true `DiGraph` — directed and undirected betweenness are not the same statistic, and `get_central_lenses` is a Must-Have tool.
- **Suggestion:** Either (a) have `buildGraph` build a true directed adjacency (successors map) plus a separate predecessors index, and give each graph.js function the same directional discipline as its Python counterpart (contrasts check both, neighborhood/paths/bridges follow only outgoing edges), or (b) if undirected is a deliberate simplification, say so explicitly in Task 4 and add a test asserting the specific divergence is acceptable (e.g. assert `neighborhood` finds Founder Mode from *both* endpoints, documenting the intentional behavior change) rather than leaving "exactly as graph.py" language over a graph.js that is not, in fact, exact.

### embedding-text-byte-identical-unverified
- **Severity:** P1
- **Where:** Plan Task 13, line 615: "`resolveLens({text?, spec?, k = 3})`: text = `spec ? embeddingText(spec) : text` (JS port of `thresholds.embedding_text`, kept byte-identical)"; Python source of record at plan Task 8, lines 521-530 (`def embedding_text(spec, body)`, using `re.search(r"^Apply the perspective.*?(?=\n\n)", body, re.S | re.M)` and `re.findall(r"^### \d+\. (.+)$", body, re.M)`).
- **What:** Unlike `normalize_body` (Task 8), which gets an explicit golden-hash test (`assert sha256(normalize_body(FIXTURE)) == '<hash literal>'`), the JS `embeddingText` used by `resolveLens` has no code shown anywhere in the plan and no test comparing its output to the Python `embedding_text` on a shared fixture. "Kept byte-identical" is an assertion in prose, not a machine-checkable one. The Python recipe uses `re.S | re.M` (dotall + multiline) on a multi-paragraph agent body; JS `RegExp` needs the equivalent `s` and `m` flags reproduced correctly, and JS's `.` without `s` never matches newlines by default (opposite risk from Python without `re.S`) — a classic place for the two languages' regex semantics to diverge on exactly the kind of body Task 8's own `corrupt`/truncation-marker logic (line 514) shows real agent bodies can have.
- **Evidence:** Grepped the whole plan for `embeddingText` and `embedding_text`: the only occurrences are the Task 13 line above (JS, no implementation shown) and the Task 8 Python definition (line 521) plus its one caller in Task 16/interflux, which explicitly says the *Python* copy is "copied verbatim from `harvest/thresholds.py`" (plan line 672) — i.e. the Python-to-Python copy gets a verbatim-copy discipline, but the Python-to-JS port gets only a prose claim. If the JS port drifts, `resolve_lens` embeds a different string than harvest embedded for the same `fd-*` body; per the plan's own convergence note at Task 5 (line 414), this shows up as cosines quietly landing below `RESOLVE_MIN_COSINE` (0.86) — the registry looks empty rather than broken, and Task 18's proof-of-reuse verify (`reused 1`) is the first place a human would notice, if they notice at all.
- **Suggestion:** Add a `tests/harvest/test_embedding_text_parity.py` (or a Node test with a fixture the Python test also reads) that runs the same 2-3 fixture bodies (including one exercising the corrupt/truncation-marker line and one exercising multi-paragraph `### N.` headers) through both `harvest/thresholds.embedding_text` and the JS `embeddingText`, asserting identical strings — the same discipline Task 8 already gives `normalize_body`.

### grep-c-verify-exit-code-contradiction
- **Severity:** P2
- **Where:** Plan Task 6, `<verify>` block, line 473-474: `run: \`grep -c "api-client" packages/mcp/index.js\`` / `expect: contains "0"`.
- **What:** I ran this exact shell idiom against a zero-match file: `grep -c PATTERN file` on zero matches prints the literal line `0` to stdout **and exits with status 1** (confirmed directly in this worktree, not from memory). If Task 6's execution harness treats "verify" as "run the command, check exit 0 AND that stdout contains the expected string" (the pattern every other `<verify>` line in this plan uses, e.g. Task 1's "expect: exit 0"), this specific line is unsatisfiable as literally written: the moment `api-client.js` really is fully removed from `index.js` (the task's own success condition), the check command itself reports failure via its exit code even though its printed output is exactly what was asked for.
- **Evidence:** Direct execution in this session: `printf 'no matches here\nother line\n' > /tmp/test_grep_c.txt; grep -c "api-client" /tmp/test_grep_c.txt` → prints `0`, `$?` → `1`.
- **Suggestion:** Rewrite as `grep -c "api-client" packages/mcp/index.js || true` (or `! grep -q "api-client" packages/mcp/index.js && echo 0`), or change the expectation wording to make explicit that this one line is stdout-only, unlike the rest of the file's exit-code-checked lines.

### commit-steps-never-write-tmp-msg
- **Severity:** P2
- **Where:** Every "Commit" step across Tasks 1-25, e.g. plan line 110 ("**Step 5: Commit**" / line 115 "(commit message file: `test: node test scaffold for the local engine`)"), line 328, 399, 420, 464, 482, 538 (all "**Step N: Commit** — `<message>`" with no shell command shown at all), contrasted with the three tasks that *do* show the literal command: line 113 (Task 1), line 154 (Task 2), line 651 (Task 15).
- **What:** The plan's own Prior Learnings section (line 26) states the house convention: "`git commit -F <file> -- <paths>`; never prose in a shell-quoted `-m`." Only 3 of the ~20 commit steps across the plan show that literal command; the rest give only a heading and a backtick-quoted message with no `git add`/`git commit` line and, critically, no step anywhere that shows how the message text gets *into* `/tmp/msg` (a `Write` call, a heredoc, `printf ... >`). The plan's stated design goal is "every step names its file, its code, and a machine-checkable expectation. No step says 'use your judgment'" — this specific sub-step (materializing the message file) is the one piece left to inference in the large majority of tasks.
- **Evidence:** `grep -n "cat >\|cat <<\|EOF\|/tmp/msg"` across the whole plan returns only the 3 commit *commands* already cited; there is no `cat > /tmp/msg <<'EOF' ... EOF` or equivalent anywhere in the document.
- **Suggestion:** State the message-writing convention once, near the Prior Learnings note (e.g. "write the commit message with `Write` to `/tmp/msg` before every `git commit -F /tmp/msg` call; the file is regenerated per commit"), or spell out the two-line idiom (`printf '%s\n' "<message>" > /tmp/msg && git commit --no-verify -F /tmp/msg -- <paths>`) in the first task and say "same pattern for every subsequent Commit step" so the instruction is stated once rather than assumed twenty times.

## Verdict
The strongest gap is structural, not stylistic: Task 6's 17-row `api-local.js` table is checked against `index.js`'s *tool* handlers but not its two *resource* handlers, both of which call the now-throwing `fetchFromAPI` directly and are advertised to every fresh session — this is the P0 the first melange's "graph port and the explorer drew one finding each" caveat was warning about. The graph.py→graph.js "undirected" claim is a real, data-verified divergence (88.6% of real connection rows are one-directional) that will change what `neighborhood`/`bridges`/`centrality` return, not just how they're implemented. The two P2s are cheap, mechanical fixes that a sonnet executor would otherwise have to improvise around, contradicting the plan's own "no judgment calls" promise.
