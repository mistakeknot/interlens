## Findings

### graph-py-is-directed-not-undirected
- **Severity:** P0
- **Where:** Task 4, "Edge construction (exactly as `graph.py:48-142`)" (`docs/plans/2026-09-02-linsenkasten-registry.md:342`); source `apps/api/src/lens/graph.py:22` (`self.graph = nx.DiGraph()`), edge-building at lines 48-142 which call `self.graph.add_edge(a, b, ...)` guarded only by `if not self.graph.has_edge(a, b)` — a single-direction guard, never adding the reverse edge.
- **What:** I read `graph.py` in full. Line 22 is `self.graph = nx.DiGraph()`. Every edge-construction block (connections at lines ~61-64, frame edges ~82-89, temporal edges ~110-117, concept edges ~132-139) adds an edge in one direction only (`add_edge(lens1, lens2, ...)`), and checks `has_edge(lens1, lens2)` — not the reverse — before adding. `find_contrasts` (line 201) has to explicitly walk **both** `self.graph.neighbors(lens_id)` (outgoing) and `self.graph.predecessors(lens_id)` (incoming) to catch contrast edges regardless of which way they point — code that only makes sense on a directed graph. `find_path` uses `nx.all_simple_paths` on this same directed graph, so paths only traverse in the direction edges were originally added. `get_central_lenses`'s `nx.betweenness_centrality(self.graph)` (line 306) runs NetworkX's **directed** betweenness algorithm by default on a DiGraph (different reachability sets and a different normalization constant — `1/((n-1)(n-2))` vs the undirected `2/((n-1)(n-2))`) unless the caller explicitly converts to undirected first, which this code never does (the only `to_undirected()` call in the file is in the unrelated `get_lens_clusters` Louvain-community method, line 283). Task 4 states flatly: "undirected weighted graph over curated lens ids" and specifies `adj: Map<id, Map<id, {...}>>` as a single symmetric structure — this is irreconcilable with what the cited source actually is.
- **Evidence:** Direct read of `apps/api/src/lens/graph.py` lines 18-95, 304-320.
- **Which verify line still passes if this happens:** `graph.test.mjs` (Task 4's own test) only checks self-consistency (`assert.deepEqual(a, b)` on two calls to the same JS function) and a synthetic 2,000-node timing bound. No test in the plan compares JS output to real `graph.py` output on the curated corpus, so an undirected port passes every `<verify>` line in Tasks 4 and 6 while producing betweenness/path/neighborhood results that differ from what `apps/api` currently serves for the same inputs.
- **Suggestion:** This is a design decision, not a bug to silently fix — the task needs to explicitly choose (a) preserve directedness (respect `source_id`→`target_id` direction from `connections.json`, and re-derive the exact single-direction guard for frame/temporal/concept edges) or (b) deliberately go undirected as a scoped improvement, and if (b), add one comparison step: run `nx.betweenness_centrality` on the real `graph.py` `LensGraph` for the curated corpus and assert the JS `centralLenses('betweenness')` top-10 is within a stated tolerance, or explicitly document that rankings are expected to change and by how much.

### central-lenses-measure-enum-mismatch
- **Severity:** P0
- **Where:** Task 4 `centralLenses` semantics (`docs/plans/2026-09-02-linsenkasten-registry.md:350`); live schema `packages/mcp/index.js:216-231`
- **What:** I read the live `get_central_lenses` MCP tool definition: `inputSchema.properties.measure.enum = ['betweenness', 'pagerank', 'eigenvector']`, `default: 'betweenness'` — these are the **only** three values a client can currently send. Task 4 specifies `centralLenses(g, measure='betweenness', limit=10, {layer='curated'})` implementing exactly `degree | closeness | betweenness`, and: "Unknown measure → treat as `betweenness`." Two of the three values the live schema accepts today — `pagerank` and `eigenvector` — are "unknown" to the JS port and silently fall through to betweenness. Compounding this, the real Python fallback (`graph.py:325`, the `else` branch of `get_central_lenses`) is `nx.degree_centrality`, not betweenness — so even the *fallback* behavior for an unrecognized measure diverges between the claimed source and the port.
- **Evidence:** `grep -n "enum:" packages/mcp/index.js` at line 223; `sed -n '304,335p' apps/api/src/lens/graph.py` showing the `if/elif/elif/else` chain (betweenness / eigenvector / pagerank / else→degree_centrality).
- **Which verify line still passes if this happens:** Task 4's `<verify>` (`node --test packages/mcp/test/graph.test.mjs`) never calls `centralLenses` with `'pagerank'` or `'eigenvector'`. Task 6's `<verify>` never exercises `get_central_lenses` with a non-default measure through `scripts/smoke.mjs`. A user calling the tool exactly as its own schema advertises (`measure: 'pagerank'`) gets betweenness numbers silently labeled "# Central Lenses (pagerank)" in `index.js:879` — a wrong-but-plausible-looking answer, not a crash, so it would ship unnoticed.
- **Suggestion:** Either (a) implement `pagerank`/`eigenvector` in `graph.js` to match `graph.py`'s `nx.pagerank`/`nx.eigenvector_centrality` calls, and drop `degree`/`closeness` from Task 4's spec since nothing in `index.js` currently requests them, or (b) update the `index.js:223` enum to the new measure set as part of Task 4/6 and treat that schema change as a deliberate, documented behavior change rather than a silent one. Add a smoke-test line exercising every value in the live enum.

### find-bridges-semantics-diverge
- **Severity:** P1
- **Where:** Task 4, `findBridges` semantics (`docs/plans/2026-09-02-linsenkasten-registry.md:347`); source `apps/api/src/lens/graph.py:172-198`
- **What:** Python's `find_bridges(lens_ids)` builds its candidate set from `nx.all_simple_paths(graph, lens1, lens2, cutoff=3)` for **each pair** in the input list, keeping the middle node whenever a length-3 path exists — i.e. a candidate only needs to bridge **one** pair from the group, not all of them (checked via `has_edge` in both directions to score it against the *whole* group afterward, but candidacy itself is per-pair). It returns `sorted_bridges[:5]`. Task 4 specifies: "candidate nodes not in `ids` adjacent to **every** id in `ids`; sort by summed weight to the group descending; return top 10." This is a materially stronger candidacy condition (universal adjacency to the whole group vs. bridging any one pair) and a different result cap (10 vs 5).
- **Evidence:** Direct read of `graph.py:172-198` (`find_bridges` method body).
- **Which verify line still passes if this happens:** `graph.test.mjs`'s bridge assertion is `assert.ok(Array.isArray(findBridges(g, [EYE, FOUNDER])))` — it only checks the return type, not membership or count, so either semantics (or an empty array) passes.
- **Suggestion:** Decide explicitly whether the JS port should match Python's "bridges any one pair" semantics (looser, closer to the cited source) or intentionally strengthen to "bridges every id" (Task 4's current spec) — and if the latter, note it as a deliberate behavior change from `graph.py`, since it will surface materially fewer/different bridge lenses for any group larger than 2.

### find-paths-tie-break-invented
- **Severity:** P1
- **Where:** Task 4, `findPaths` semantics (`docs/plans/2026-09-02-linsenkasten-registry.md:346`); source `apps/api/src/lens/graph.py:143-170`
- **What:** Task 4 specifies: "`findPaths(g, srcId, dstId, maxLen=4, limit=5)`: all simple paths of length ≤ `maxLen` by DFS in ascending neighbor-id order; rank by sum of edge weights descending, tie by shorter length; return `limit`." Python's `find_path` sorts `list(nx.all_simple_paths(self.graph, source, target, cutoff=max_length))` by `path_weight` (descending) with **no secondary tie-break** specified anywhere in the code, and hardcodes `return paths[:3]` — not a caller-supplied `limit`. "Ascending neighbor-id order" and "tie by shorter length" are additions with no basis in the cited source; they may be reasonable design choices, but the task frames them as *the port*, not as new behavior.
- **Evidence:** Direct read of `graph.py:143-170`.
- **Which verify line still passes if this happens:** `graph.test.mjs` only asserts `findPaths(g, EYE, FOUNDER).length >= 1` — any ordering, tie-break, or default limit satisfies this.
- **Suggestion:** Either cite these ordering rules as a deliberate JS-side design decision (not "exactly as graph.py"), or verify NetworkX's actual DFS traversal order for `all_simple_paths` (it's a DFS over `G.adj` dict insertion order, not sorted by id) and match it if true fidelity to `graph.py`'s current output is the goal.

## Verdict
Task 4's framing — "exactly as `graph.py:48-142`" — doesn't hold up against the actual file: the source is a directed multigraph built with NetworkX library calls (`betweenness_centrality`, `eigenvector_centrality`, `pagerank`), and the plan's hand-rolled undirected port invents several behaviors (tie-breaks, bridge universality, a 3-measure/5-measure mismatch with the live tool schema) with no test anywhere in Tasks 4-6 that checks JS output against either the Python source or the schema the MCP tool already advertises to callers.
