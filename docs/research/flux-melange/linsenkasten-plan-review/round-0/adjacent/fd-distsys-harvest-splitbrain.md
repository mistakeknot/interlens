## Findings

### server-host-path-crashes-live-verified
- **Severity:** P0
- **Where:** Task 22, systemd unit `ExecStart` (`docs/plans/2026-09-02-linsenkasten-registry.md:759`) vs. "Server" semantics paragraph (`:751`)
- **What:** Task 22's "Server" semantics say `--host` defaults to `127.0.0.1` with no mention that it can be a file path. The systemd unit two paragraphs later passes `--host %h/.local/share/linsenkasten/ts-ip` and the prose asserts "`--host` accepts a path: the server reads the file to get zklw's Tailscale IP" — but nothing in the "Server" semantics section a sonnet executor would implement `server.js` from actually says to detect and dereference a path argument. I reproduced the failure directly on zklw: `node -e 'require("http").createServer().listen(0, "/home/mk/.local/share/linsenkasten/ts-ip", ()=>{}).on("error", e=>console.log("ERR", e.code, e.message))'` → `ERR ENOTFOUND getaddrinfo ENOTFOUND /home/mk/.local/share/linsenkasten/ts-ip`. `http.Server.listen(port, host)` always treats `host` as a hostname to resolve, never as a filesystem path, unless the implementation explicitly special-cases it before calling `.listen()`.
- **Evidence:** Live command run over `ssh -o BatchMode=yes zklw`, output pasted above verbatim, on the actual Node version installed there (`v22.22.2`).
- **Which verify line still passes if this happens:** none — Task 22's own `<verify>` block curls the live zklw endpoint and would correctly fail. But that's the *only* thing that catches it, after `Restart=on-failure` has already started crash-looping the unit in production.
- **Suggestion:** Add one explicit line to the "Server" semantics: "if `--host` is not a valid IPv4/IPv6 literal, treat it as a file path, read and trim it, and use the contents as the bind address" — and give `server.js` a unit test for that branch (not just an integration curl against the live unit).

### feat-branch-never-merged-before-zklw-pull
- **Severity:** P0
- **Where:** Task 14 step 6 (`docs/plans/2026-09-02-linsenkasten-registry.md:633`, "**Step 6: Commit** ... Push.") and Task 15 (`:644-653`, `cd ~/projects/Sylveste/interverse/interlens && git pull --ff-only origin main`)
- **What:** I checked branch state on both machines directly. On the Mac, the main checkout (`~/projects/Sylveste/interverse/interlens`) is on `sweep/2026-09-02`, and the registered worktree (this one, `~/projects/.worktrees/interlens-linsenkasten`) is on `feat/linsenkasten` — matching the plan's own "Repo path note." On zklw, `git -C ~/projects/Sylveste/interverse/interlens status -sb` shows `## main...origin/main`, and `git branch -a | grep -i sweep` returns **nothing** — zklw has neither `sweep/2026-09-02` nor `feat/linsenkasten`, locally or as a remote-tracking ref. Tasks 1-14 (Stages A-C: the entire local-engine JS code, the `harvest/` Python package, the curated-data move, the first Mac harvest) all commit directly onto `feat/linsenkasten` in the worktree. Task 14 step 6 says only "Push." with no destination ref — git's default behavior for a branch with no upstream override is to push to its own tracked branch name (`origin/feat/linsenkasten`), not `main`. Task 15 then runs `git pull --ff-only origin main` on zklw as its *only* sync step. If Task 14's "Push" doesn't land on `origin/main`, Task 15's pull brings zklw nothing — no `harvest/` package, no `lib/graph.js`, no local-engine code — and `python3 -m harvest scan --machine zklw` fails immediately with `ModuleNotFoundError: No module named 'harvest'`.
- **Evidence:** `git status -sb` on both the Mac checkout and (via `ssh -o BatchMode=yes zklw`) the zklw checkout; `git branch -a` on zklw. Confirmed against the plan text: no task anywhere between Task 1 and Task 15 contains the words "merge" or "into main" or a `git push origin feat/linsenkasten:main`/`git push origin HEAD:main` for Stage B/C's work — Task 15's explicit `git push origin HEAD:main` syntax is only ever written for zklw's *own* run, never for landing the Mac's branch first.
- **Which verify line still passes if this happens:** Task 15's own `<verify>` (`grep` for `['clavain', 'zklw']` in both machines' `index.jsonl` `machines` field) would simply fail loudly at that point — but only after the executor has already tried to run `harvest scan` on zklw and hit an import error with no diagnosis pointing at "your branch never reached main." Task 1's landing-order rule (Step 1) only gates the *sweep* branch merging into `feat/linsenkasten`, not `feat/linsenkasten` merging into `main`.
- **Suggestion:** Add an explicit task (or a step at the top of Task 15) that lands `feat/linsenkasten` on `main` and pushes it — e.g. `git checkout main && git merge --ff-only feat/linsenkasten && git push origin main` (or a PR if `main`'s protection requires one) — run and verified *before* Task 15's `git pull --ff-only origin main` on zklw is attempted. Note: `main`'s branch protection currently has `enforce_admins: true` but no required reviews/status checks configured, so a direct fast-forward push would work today, but the plan should say so rather than leave it implicit.

### ts-ip-file-confirmed-absent
- **Severity:** P1
- **Where:** Task 22 (`docs/plans/2026-09-02-linsenkasten-registry.md:764`, "`~/.local/share/linsenkasten/ts-ip` being written once by `tailscale ip -4 > ...`")
- **What:** The plan phrases the ts-ip file and Linger as already-true facts ("checked 2026-09-02"), not as steps this plan performs. I checked both live on zklw: `loginctl show-user mk -p Linger` → `Linger=yes` (this part is genuinely true, confirmed, not a finding) — but `cat ~/.local/share/linsenkasten/ts-ip` → `No such file or directory`. `tailscale ip -4` on zklw does resolve fine (`100.78.63.67`), so generating the file is trivial, but no task step in Tasks 22-24 actually runs `tailscale ip -4 > ~/.local/share/linsenkasten/ts-ip` or creates the parent directory `~/.local/share/linsenkasten/`.
- **Evidence:** `ssh -o BatchMode=yes zklw 'cat ~/.local/share/linsenkasten/ts-ip'` → exit 1, "No such file or directory"; `ssh -o BatchMode=yes zklw 'loginctl show-user mk -p Linger'` → `Linger=yes` (confirms half the "checked 2026-09-02" claim, refutes the other half).
- **Which verify line still passes if this happens:** none of Task 22's `<verify>` lines would pass — the curl against the live zklw endpoint depends on the unit starting at all, which depends on this file. This is the same root cause as `server-host-path-crashes-live-verified` but independently fatal even if that finding is fixed: even a correct path-aware `server.js` has nothing to read.
- **Suggestion:** Add `mkdir -p ~/.local/share/linsenkasten && tailscale ip -4 > ~/.local/share/linsenkasten/ts-ip` as an explicit Task 22 step (idempotent, safe to make part of `zklw-harvest.sh`'s startup too, since Tailscale IPs can change on re-registration).

### push-race-no-retry-confirmed-both-scripts
- **Severity:** P1
- **Where:** Task 15 (`docs/plans/2026-09-02-linsenkasten-registry.md:651`, `git push origin HEAD:main`) and Task 22's `zklw-harvest.sh` (`:765`, same pattern)
- **What:** Both the Task 15 zklw script and the Task 22 daily-timer script push with `git push origin HEAD:main` inside `set -euo pipefail`, with no pull-rebase-retry loop and no lock. The Mac's counterpart ("harvests on demand," `:765`) is never given a script at all — its exact push invocation is undefined, so it's not even knowable whether it would collide on the same failure mode. If the Mac's on-demand harvest (which per the plan can run "before any prune," at any hour) overlaps with zklw's fixed `04:30` daily timer, the losing push fails, `set -e` aborts immediately, and that machine's harvest data is silently dropped for the day — with no alert, no retry, and no task-level step surfacing the failure to a human.
- **Evidence:** Direct read of both scripts as specified in the plan text (Task 15's inline bash block; Task 22's `zklw-harvest.sh` description). Confirmed the Mac's on-demand harvest has no scripted push step anywhere in the plan to compare against.
- **Which verify line still passes if this happens:** Task 23's prune preconditions (2) — `git fetch origin main` + `HEAD == origin/main` — would correctly refuse a prune run after a dropped push, but nothing surfaces the failure at the moment it happens; a human would only discover it when a routine prune run unexpectedly refuses, with the actual cause (a lost push, hours or days earlier) requiring separate investigation.
- **Suggestion:** Wrap both push sites in a `git pull --rebase --autostash origin main && git push origin HEAD:main` retry (2-3 attempts with backoff), and log a clear one-line failure (e.g. to the harvest report or a marker file `data/reports/push-failed-<date>.txt`) if all retries are exhausted, so the loss is visible immediately rather than discovered later as an unexplained prune refusal.

The more consequential gap this review adds is upstream of the explorer entirely: there is no task anywhere that lands `feat/linsenkasten` on `main` before Task 15 asks zklw to pull it, and zklw's checkout today has no path back to that branch at all.
