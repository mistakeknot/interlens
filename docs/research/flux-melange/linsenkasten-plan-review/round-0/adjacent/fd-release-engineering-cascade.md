## Findings

### task19-verify-blind-to-docs-scope-mismatch
- **Severity:** P1
- **Where:** Task 19 (`docs/plans/2026-09-02-linsenkasten-registry.md:707-714`)
- **What:** The task prose says the sed sweep excludes only `CHANGELOG.md`, `docs/brainstorms/**`, `docs/plans/**`, `docs/research/**` — implying every other doc under `docs/` (including `docs/vision.md` and `docs/interlens-vision.md`) gets renamed. But the `<verify>` line uses a much broader exclusion: `git ls-files | grep -v -E '^(CHANGELOG.md|docs/)' | xargs grep -lI -i interlens | wc -l` — this drops **all** of `docs/`, not the three named subdirectories. I confirmed live: `git ls-files docs | grep -v -E '^docs/(brainstorms|plans|research)/' | xargs grep -lI -i interlens` returns `docs/interlens-vision.md` (8 hits over 47 lines), `docs/roadmap.json`, and `docs/vision.md` — files the prose says should be renamed but the verify line can never see.
- **Evidence:** Confirmed by running both greps against the actual repo. The Must-Haves truth (plan line 38) states "`grep -ri interlens` in the repo hits only the CHANGELOG history and the brainstorm/research/plan docs" — this is a stronger claim than the verify line checks, so a sonnet executor who implements the sed sweep using the *same* simple `docs/`-wide exclusion pattern as the verify line (the only literal, copy-pasteable regex the task actually gives) would leave `docs/vision.md`/`docs/interlens-vision.md`/`docs/roadmap.json` unrenamed, violate the Must-Haves truth, and still see the `<verify>` block print `0` and pass.
- **Which verify line still passes if this happens:** Task 19's own `<verify>` — `git ls-files | grep -v -E '^(CHANGELOG.md|docs/)' | ... | wc -l` — passes regardless, because it shares the same over-broad exclusion.
- **Suggestion:** Change the verify regex to match the prose exactly: `grep -v -E '^(CHANGELOG\.md|docs/(brainstorms|plans|research)/)'`, and give the sed sweep the identical pattern so both use one literal exclusion list instead of two different ones.

### lattice-interweave-connector-hardcoded-path
- **Severity:** P1
- **Where:** Task 20 step 5 (`docs/plans/2026-09-02-linsenkasten-registry.md:722`); breaking code at `~/projects/Sylveste/interverse/lattice/src/lattice/connectors/interlens.py:27` (mirrored byte-identical at `~/projects/Sylveste/core/interweave/src/lattice/connectors/interlens.py`)
- **What:** Task 20 step 5 covers Clavain's 8 named files plus "interlock, lattice, core/interweave mentions: grep, and edit only live config/scripts (not docs/research)." I read the actual `lattice` source: `src/lattice/connectors/interlens.py` defines `class InterlensConnector` with `DEFAULT_LENSES_REL = Path("interverse/interlens/apps/api/all_lenses_for_analysis.json")` — a hardcoded relative path used to ingest lens data into lattice's crosswalk DB, with a dedicated `tests/test_connector_interlens.py` and a `.claude-plugin/integration.json` entry listing `interlens` as a recommended companion. This is real, tested source code, not "config."
- **Evidence:** `find ~/projects/Sylveste/interverse/lattice -iname '*interlens*'` → `src/lattice/connectors/interlens.py`, `tests/test_connector_interlens.py`. File content confirmed via direct read: `DEFAULT_LENSES_REL = Path("interverse/interlens/apps/api/all_lenses_for_analysis.json")`. Two independent breaks compound: (1) Task 2 moves `apps/api/all_lenses_for_analysis.json` → `data/curated/lenses.json`, so the path is wrong even before any rename; (2) Task 20 step 2 renames the directory `interverse/interlens` → `interverse/linsenkasten`, so the path is wrong twice over.
- **Which verify line still passes if this happens:** every `<verify>` block in the plan — none of them run `lattice`'s or `core-interweave`'s test suite, and Task 20's own verify block only checks `gh repo view`, the marketplace grep, and the settings.json grep.
- **Suggestion:** Add an explicit step to Task 20 step 5 naming `lattice/src/lattice/connectors/interlens.py` and its `core-interweave` mirror: update `DEFAULT_LENSES_REL` to `interverse/linsenkasten/data/curated/lenses.json` (after Task 2's move lands), and run `pytest tests/test_connector_interlens.py` in both repos as part of the verify step. Decide explicitly whether `InterlensConnector`/`SUBSYSTEM = "interlens"` itself gets renamed (it's also a stable provenance tag other crosswalk data may key off of) — that's a design call, not something to leave implicit.

### npm-publish-authorization-unverified
- **Severity:** P1
- **Where:** Task 19 (`packages/mcp/package.json` name/version, plan line 707), Task 20 step 6 (plan line 723)
- **What:** I checked the npm registry directly: `linsenkasten-mcp` is at `2.2.1`, `dist-tags.latest = "2.2.1"`, author "Mistake Knot" / maintainer `gensysven`, repository `git+https://github.com/mistakeknot/Linsenkasten.git`. `gh repo view mistakeknot/Linsenkasten` resolves to the *current* repo (`name: "interlens"`, same `createdAt` as `mistakeknot/interlens`) — i.e. this repo was itself named `Linsenkasten` when versions 1.0.0-2.2.1 were published (Nov 2025), then renamed back to `interlens` before this plan was written. So this is **not** an unrelated party squatting the name (contra the obvious first read) — it's this project's own prior identity, dormant since 2025-11-26. But: the currently-published 2.2.1 still carries `express`/`node-fetch`/`cors` and `@modelcontextprotocol/sdk@^0.5.0` — the exact hosted-remnant architecture this plan deletes in Task 21 — and nothing in Task 19/20 acknowledges this history or names which machine/account performs the Task 20 step 6 publish. I ran `npm whoami` on this machine: `401 Unauthorized` — this session has no npm auth at all. Separately, `interlens-mcp` (the name currently in `packages/mcp/package.json`) returns `Not found` on the registry — it was never published under that name.
- **Evidence:** `curl https://registry.npmjs.org/linsenkasten-mcp` (full version history, maintainer, repo URL); `gh repo view mistakeknot/Linsenkasten --json name,createdAt` (redirects to `interlens`, same `createdAt`); `npm whoami` → `401`.
- **Which verify line still passes if this happens:** Task 20's `<verify>` block never runs `interpub:release` itself or checks its exit code — it only checks `gh repo view`, the marketplace grep, and the settings.json grep, all of which are independent of whether the npm publish in step 6 actually succeeded.
- **Suggestion:** Add a pre-publish check to Task 20 step 6: `npm whoami` (or `npm access ls-collaborators linsenkasten-mcp`) confirming the publishing identity owns `linsenkasten-mcp`, run on whichever machine actually executes `interpub:release` (per house convention, that's zklw — the plan should say so explicitly rather than leaving the machine unstated).

## Verdict
The two P0-shaped worries a rename review reaches for by default — "does someone else own the npm name" and "is the GitHub rename reversible" — both check out fine once verified live (same-author npm history, working redirect). The real exposure is elsewhere: the plan's own Task 19 verify line can't see the docs it's supposed to protect, and Task 20 step 5's "grep and edit live config" undersells a real, tested, hardcoded-path dependency in `lattice`/`core-interweave` that this plan will break twice over with no test in either repo ever run.
