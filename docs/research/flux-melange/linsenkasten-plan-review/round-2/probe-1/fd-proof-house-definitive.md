## Findings

### task-18-registry-root-unreachable
- **Severity:** P1
- **Where:** docs/plans/2026-09-02-linsenkasten-registry.md:672 (Task 16, `find_registry_root()` spec) fired against the plan's own Repo path note (line 20) and exercised by Task 18's verify block (lines 690-699).
- **What:** `find_registry_root()`'s entire fallback chain is `$LINSENKASTEN_ROOT` → `~/projects/Sylveste/interverse/linsenkasten` → `~/projects/Sylveste/interverse/interlens` → newest marketplace plugin-cache dir, returning `None` unless the chosen candidate actually contains `data/generated/index.jsonl`. Every task through Stage D runs inside the `feat/linsenkasten` git worktree at `~/projects/.worktrees/interlens-linsenkasten` (plan's own Repo path note, line 20) — a path that is *never* one of the four candidates, under any name. Live-verified this session: the sibling checkout at `~/projects/Sylveste/interverse/interlens` (candidate 3) is checked out on branch `sweep/2026-09-02`, not `feat/linsenkasten`, and has no `data/generated/` directory at all — none of Tasks 2, 9 or 14's commits exist there. So when Task 18 runs `generate-agents.py … --registry=auto` with no `LINSENKASTEN_ROOT` set, `find_registry_root()` returns `None`, `resolve()` is never attempted, and the command prints `reused 0` — not the `reused 1` the verify line demands. This is the plan's single sharpest acceptance check (a "near-certain" hit, explicitly the DONE-WHEN item for Stage D, and the mechanism that is supposed to demonstrate Must-Haves Truth #4) and it cannot pass as written.
- **Evidence:** `git worktree list -v` this session → `/Users/sma/projects/Sylveste/interverse/interlens 7a69704 [sweep/2026-09-02]` vs `/Users/sma/projects/.worktrees/interlens-linsenkasten 53f04c4 [feat/linsenkasten]`; `git show sweep/2026-09-02:` has no `data/` tree; `grep -rn LINSENKASTEN_ROOT` across the plan finds it set only inside Task 16's own fixture test ("`LINSENKASTEN_ROOT` pointed at it" — a `tmp_path` fixture), never in any real invocation. Task 18's exact command (line 695): `python3 ~/projects/Sylveste/interverse/interflux/scripts/generate-agents.py /tmp/lk-reuse-proof --from-specs … --registry=auto --json | … print('reused',len(r['reused']))` with `expect: contains "reused 1"` — no `LINSENKASTEN_ROOT=` prefix anywhere.
- **Suggestion:** smallest fix is at the call site, not the fallback chain: prefix Task 18's (and any other Stage D real-world) invocation with `LINSENKASTEN_ROOT=$(pwd)` (the worktree), or make Task 16 add a fifth, first-checked candidate — the output of `git rev-parse --show-toplevel` when invoked from inside a git checkout — so `find_registry_root()` finds whatever repo the caller is actually standing in before falling back to the two hardcoded interverse paths.

### task-1-ci-pytest-unproved
- **Severity:** P2
- **Where:** docs/plans/2026-09-02-linsenkasten-registry.md:99-108 (Task 1 Step 4, the CI edit) and :117-122 (Task 1's `<verify>` block), against the actual `.github/workflows/ci.yml` on branch `sweep/2026-09-02` that Task 1 modifies once the sweep gate clears.
- **What:** Task 1 appends `node --test packages/mcp/test/` then re-runs `python3 -m pytest tests -q` in CI, with the comment that the second pytest run exists "so a node-side failure cannot hide a python one" — treating the pytest step as a working signal worth protecting. But the plan's own local verify line for that identical command is `PYTHONPATH=$HOME/projects/Sylveste/interverse python3 -m pytest tests -q`, and Step 2's own comment explains why: `tests/structural/conftest.py:7` needs `_shared` from the interverse monorepo, and the worktree's `parents[3]` doesn't reach it. The sweep branch's CI job (the only place `.github/workflows/ci.yml` currently exists, confirmed via `git show sweep/2026-09-02:.github/workflows/ci.yml`) sets no `PYTHONPATH`, vendors no `_shared`, and checks out only this one repo via `actions/checkout@v4` — there is no `~/projects/Sylveste/interverse` on a GitHub Actions runner. So the bare `python3 -m pytest tests -q` line Task 1 is appending a node step alongside will hit the same `ModuleNotFoundError` on `_shared` that the worktree only avoids because the plan's verify lines manually inject a path that has no CI counterpart. Nothing in the plan's 25 tasks ever triggers this CI job for real (no PR is opened, no push-and-poll step exists) and checks that it actually goes green — the "proof" of the CI addition is entirely the local run under a different environment.
- **Evidence:** `git show sweep/2026-09-02:.github/workflows/ci.yml` — full file, 20 lines, `actions/checkout@v4` → `actions/setup-python@v5` → `pip install pytest pyyaml` → `python3 -m pytest tests -q`, no `PYTHONPATH`, no second checkout, no `_shared` vendoring; `tests/structural/conftest.py:6-11` (`sys.path.insert(0, str(_interverse))` where `_interverse = Path(__file__).resolve().parents[3]`); repo has no `_shared` submodule or vendored copy (`find . -iname "_shared*"` → empty, no `.gitmodules`).
- **Suggestion:** either add a step that vendors/checks out `_shared` into the CI workspace (or copies it in before the pytest step) with an explicit `PYTHONPATH`, or add one `<verify>` line to Task 1 (or Task 19, which also touches the same pytest command) that actually pushes to a throwaway branch and polls `gh run list`/`gh run view` for a green run — right now the CI addition is proved only in a condition (manual PYTHONPATH) that CI itself never has.

### task-17-rename-ordering-gap
- **Severity:** P2
- **Where:** docs/plans/2026-09-02-linsenkasten-registry.exec.yaml:79-103 (Stage D tasks 16-18 vs Stage E tasks 19-20); docs/plans/2026-09-02-linsenkasten-registry.md:681 (Task 17: "…update `commands/flux-gen.md:67` and `commands/flux-explore.md`… to say `linsenkasten` MCP tools").
- **What:** Task 17 rewrites live interflux prose (`fusion.md:40`, `phases/seed.md:37`, `phases/retarget.md:31`, `flux-gen.md:67`, `flux-explore.md`) to name the MCP tool surface `linsenkasten`, while the MCP server key itself is renamed from `mcp__interlens__*` to `mcp__linsenkasten__*` only in Task 19/20 (Stage E). In `exec.yaml`, `task-17` depends on `[task-16]` → `[task-14]`; `task-19` depends on `[task-7, task-15]`; there is no edge in either direction between the Stage D chain (16→17→18) and Stage E (19→20). Under `mode: dependency-driven, max_parallel: 3`, a topological executor is free to schedule Task 17 as soon as Task 16 clears — which can happen well before Task 19/20 land, since Stage D's only shared ancestor with Stage E is Task 14. If it does, interflux's live, non-plan documentation tells any reader or agent to call a `linsenkasten` MCP tool that does not exist yet on the still-`interlens`-keyed server for however long the gap lasts.
- **Evidence:** exec.yaml lines 79-93 (`task-16`/`17`/`18` depends chain, rooted at `task-14`) vs lines 94-103 (`task-19` `depends: [task-7, task-15]`, `task-20` `depends: [task-19]`) — no cross-reference either way; plan line 681 names the doc lines Task 17 edits to say `linsenkasten`.
- **Suggestion:** smallest fix is a manifest edge, not new tasks: add `task-20` to `task-17`'s `depends` list (interflux's doc-name edit waits for the real rename), or invert it — have Task 17 write the tool references in name-agnostic language ("the registry MCP tools") and let Task 20 step 5's own sweep patch in the literal `linsenkasten` name once the key actually exists.

## Verdict
The strongest finding (Task 18) is a genuine, live-verified blocker on the plan's own sharpest acceptance check: the worktree the entire plan runs from is structurally invisible to `find_registry_root()`'s fallback chain, so the DONE-WHEN reuse proof cannot print what it promises without an env var the plan never sets. The other two are lower-blast-radius but real instances of the same family — a check proved in a condition (manual local env, unordered task graph) that doesn't match the condition it actually fires in (CI's isolated checkout, a dependency-driven scheduler with no ordering edge). None of the three overlap the already-flagged rename-cascade, graph-port, or harvest/push regions.
