## Findings

### npm-publish-never-invoked-not-auth-absence
- Severity: P1
- Where: docs/plans/2026-09-02-linsenkasten-registry.md:723 (Task 20 step 6: "Publish: `interpub:release` for linsenkasten 3.0.0 and interflux (patch bump).")
- What: Adjudicating the prior contradiction — **Finding 2 holds, with its correction confirmed by direct code reading; Finding 1's part C ("npm auth confirmed absent") is factually wrong, but its underlying alarm was aimed at the wrong mechanism.** `~/.npmrc` on this machine contains a live `_authToken` entry — auth is *present*, not absent — but it is expired/invalid (`npm whoami` returns `401 Unauthorized`). More importantly, and independent of whether that token works: Task 20 step 6 delegates to the `interpub:release` command, which does nothing but `exec ic publish`. The entire `ic publish` implementation (intercore's `internal/publish` Go package) shells out only to `git`, `bash` (for two specific hook scripts and the interchart generator), `ps`, and (in tests only) `go` — there is no `npm` invocation anywhere in the package. `package.json` is treated purely as a version-bump target (`discovery.go:125`: `{"package.json", "json", "version"}`), never as a publish trigger. The one extension point that *could* run `npm publish` per-plugin — `scripts/post-bump.sh` in the plugin root, invoked at `engine.go:353-359` only `if _, err := os.Stat(postBump); err == nil` — does not exist in this repo; `scripts/` under both the canonical checkout and this worktree contains only `bump-version.sh` (itself just `exec ic publish "$@"`) and `validate-gitleaks-waivers.sh`. So no npm auth attempt of any kind happens for the npm package, working token or not.
- Evidence:
  - `~/.npmrc`: `//registry.npmjs.org/:_authToken=npm_[REDACTED-by-push-protection-scrub]` (present).
  - `npm whoami` → `npm error code E401` / `401 Unauthorized - GET https://registry.npmjs.org/-/whoami` (present but non-functional).
  - `/Users/sma/projects/Sylveste/interverse/interpub/.claude-plugin/commands/release.md`: "Delegates to `ic publish`... run `ic publish <args>`" — no npm mention anywhere in the command doc.
  - `grep -rn "npm" /Users/sma/projects/Sylveste/core/intercore/internal/publish/*.go` (excluding `_test.go`): zero matches.
  - `/Users/sma/projects/Sylveste/core/intercore/internal/publish/discovery.go:125-126`: `package.json`/`server/package.json` registered only as `{"json", "version"}` bump targets.
  - `/Users/sma/projects/Sylveste/core/intercore/internal/publish/engine.go:353-359`: `postBump := filepath.Join(pluginRoot, "scripts", "post-bump.sh")` guarded by `os.Stat`; this is the sole shell-out capable of an arbitrary per-plugin command.
  - `ls /Users/sma/projects/Sylveste/interverse/interlens/scripts/` and the worktree's `scripts/`: only `bump-version.sh` (341 bytes, `exec ic publish "$@"` fallback to `interbump.sh`) and `validate-gitleaks-waivers.sh` — no `post-bump.sh`.
  - `ic version` → `ic 0.3.5` (installed and on PATH at `~/.local/bin/ic`, so the `bump-version.sh` fallback branch is moot — `ic publish` is what actually runs).
- Suggestion: Rewrite Task 20 step 6 to either (a) add a real npm-publish leg — a `scripts/post-bump.sh` in the repo root (or an explicit standalone step) that runs `npm publish --access public` from `packages/mcp` after asserting `npm whoami` succeeds (refresh `~/.npmrc`'s token first — it currently 401s) and add a `<verify>` line hitting the registry (e.g. `npm view linsenkasten-mcp version` equals the new version) — or (b) explicitly state npm distribution is out of scope for this plan and the 2.2.1 package on npm will diverge from the renamed repo. Either way, don't leave it implied-but-undone.

### npm-registry-drift-uncaught-by-verify
- Severity: P1
- Where: docs/plans/2026-09-02-linsenkasten-registry.md:723-733 (Task 20 step 6 and its `<verify>` block)
- What: New insight the contradiction exposes beyond the auth question — since `interpub:release`/`ic publish` never touches npm, and Task 20's `<verify>` block checks only `gh repo view`, a `marketplace.json` grep count, and a `settings.json` grep count, the plugin ecosystem (repo, marketplace row, settings key) will correctly read "linsenkasten" 3.0.0 everywhere the plan checks, while the actual `npm install`-able `linsenkasten-mcp` package stays frozen at 2.2.1 — the pre-existing same-author 2025 publish — with no task, verify line, or Must-Have in this plan ever detecting the gap. This is exactly the kind of split the review brief's Fork 1 flags as in-scope ("npm linsenkasten-mcp already published at 2.2.1" is listed alongside the GitHub redirect, MCP server key, marketplace row, and settings keys as parts of the rename cascade), but the plan's own verify coverage stops one layer short of it.
- Evidence: Task 20 `<verify>` block (lines 727-733) runs exactly three checks — `gh repo view mistakeknot/linsenkasten --json name -q .name`, `grep -c '"linsenkasten"' .../marketplace.json`, `grep -c 'linsenkasten@interagency-marketplace": true' ~/.claude/settings.json` — none queries `registry.npmjs.org` or runs `npm view`/`npm info`. Combined with the prior finding (no `npm publish` call exists in the pipeline at all), nothing in Task 20 can ever fail loudly on this.
- Suggestion: Add a fourth verify line to Task 20 (e.g. `npm view linsenkasten-mcp version` expected to equal `3.0.0` after whatever npm-publish step is added per the sibling finding), so a stale npm package is a visible plan failure rather than a silent drift discovered later by an external consumer running `npm install -g linsenkasten-mcp`.

## Verdict
Finding 2 is CONFIRMED over Finding 1: this is not a taste call. `~/.npmrc` demonstrably holds a present-but-invalid token (refuting "confirmed absent"), and reading intercore's `internal/publish` Go package end-to-end shows `ic publish` — the entirety of what `interpub:release` does — never shells out to `npm` and has no `post-bump.sh` hook in this repo to fill the gap, so no npm auth attempt of any kind occurs regardless of token validity. The disputed language should be corrected in place rather than re-litigated, and the plan should gain an explicit npm-publish step plus a registry-checking verify line.
