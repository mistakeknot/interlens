## Findings

### merge-rebuilds-from-emptied-ground

- **Severity:** P0
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md:547` (Task 9 header "union of machines into `index.jsonl`"), `:549-561` (the semantics and example record), `:562` (`first_seen`/`last_seen` sourcing), `:535` (Task 8: `scan.py` rewrites `data/harvest/<machine>.jsonl` fresh each run), `:765` (Task 22: `zklw-harvest.sh` chains `scan && merge && stats && embed --check && edges && audit` unattended, nightly), `:791` (Task 24: zklw prune sweep deletes live `fd-*.md` files), `:600` (Task 12: `harvest audit` checks index-records ⇔ body-files, too late to prevent the local overwrite)
- **What:** `merge.py`'s only inputs are today's `data/harvest/*.jsonl` files — themselves rewritten from scratch by `scan.py` walking the live filesystem each run. Every field of an index record, including `first_seen`/`last_seen`, is recomputed "from frontmatter, falling back to file mtime" (line 562) of a *currently-sighted* file, not carried forward from the previous `index.jsonl`. Nowhere in Task 9, the Key Links section, or the Must-Haves does anything union this run's sightings with the outgoing index; a direct grep of the whole 852-line plan for "tombstone", "never remov", "carry forward", "persist" returns zero hits. Stage G's entire premise is that pruning a repo's `.claude/agents/fd-*.md` files is safe *because* the registry already holds a durable copy (goal header: "delete repo piles post-harvest with a sweep report"). But once Task 24 deletes those files from zklw's disk (their most common home — sessions run and leave `fd-*.md` on whichever machine ran them), the very next 04:30 `zklw-harvest.sh` run re-scans the now-empty spot, finds no sighting for that `body_hash` anywhere (Clavain's `clavain.jsonl` won't have it either unless the same lens happened to be independently sighted there too), and `merge` writes a new `index.jsonl` that simply omits the record. The body (`data/generated/lenses/<id>.md`) and spec (`data/generated/specs/<id>.json`) stay on disk, but nothing in the index points at them any more — `search_lenses`, `resolve_lens`, `get_central_lenses`, the hit-rate/cluster/embodies metadata Tasks 10 and 12 computed for it — all gone, in a commit that looks like an ordinary nightly harvest. `harvest audit` (line 600) would in principle catch the id⇔body-file mismatch on the same run, but `merge` has already overwritten `index.jsonl` on disk by the time `audit` runs in the chain, and (per the already-established dirty-tree-abort behavior of this same script) the process exits before the commit/push block — so the loss is silent, local, and indistinguishable from an ordinary failed run until a human specifically investigates.
- **Evidence:** Task 9, line 547: "`harvest/merge.py` — union of machines into `index.jsonl`"; line 549: "read every `data/harvest/*.jsonl`; group sightings by `body_hash`; one index record per hash"; line 562: "`generated_at` for `first_seen`/`last_seen` from frontmatter, falling back to file mtime". Task 8, line 535: scan's output section describes `data/harvest/<machine>.jsonl` as written fresh each run with no append/merge-with-prior language. No counter-evidence found anywhere in the plan (`grep -n -i "tombstone\|never remov\|carry.forward\|persist.*index\|retained\|preserve"` → 0 matches).
- **Suggestion:** Give `merge.py` a third input — the outgoing `data/generated/index.jsonl` itself (or a separate append-only "ever indexed" ledger) — and change the semantics from *rebuild from current sightings* to *union current sightings into the existing index, never drop a row for lack of a fresh sighting*. Actual removal of a record should be an explicit, reviewed act (reuse prune's own precondition machinery) rather than a side effect of a file simply going unseen on the next scan.

### sylveste-archive-stranded-on-pr-branch

- **Severity:** P1
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md:780` (Task 23, the Sylveste-root special case: "main is protected → commit on a branch `chore/prune-fd-agents` and open a PR; list it in the report as 'PR opened'"), same line for the general-case discipline ("Commit per repo on its current branch, checked in the same command"); Task 25 dependencies in `docs/plans/2026-09-02-linsenkasten-registry.exec.yaml` (`task-25` depends on `task-18, task-22, task-24` — sweep having *run*, not the PR having *merged*)
- **What:** For every ordinary target repo, Task 23 is careful about branch identity — it checks the current branch *in the same command* as the commit, matching this workspace's own known "shared checkout switches branch under you" hazard. The Sylveste-root case is the one place that discipline is abandoned: because `main` is protected, the recipe is to create a *new* branch, commit the 396 deletions there, push, and open a PR — with no step in Task 23, 24, or 25 that returns the working tree to whatever branch it was on before, and no step that waits for or verifies the PR merged. Live-checked against the actual repo (read-only, Mac side): `~/projects/Sylveste` is presently checked out on `estate-checks-falsifiable`, not `main`, and has exactly 396 `fd-*.md` files under `.claude/agents` — matching the plan's own count exactly. So `git checkout -b chore/prune-fd-agents` would fork from whatever `estate-checks-falsifiable` happens to be at run time, not from `main`, and the shared checkout is left on that new branch — meaning the 396 `fd-*.md` files vanish from the *live working tree* the moment the branch is checked out, for every tool that reads `.claude/agents/*.md` directly from disk (which includes Claude Code's own subagent loader, not only linsenkasten's registry), regardless of whether the PR is ever merged. Task 25 only depends on the sweep having run (`task-24`), not on the PR merging, so the whole plan can finish and the goal can close while Sylveste's checkout sits permanently parked on a side branch.
- **Evidence:** `git -C ~/projects/Sylveste rev-parse --abbrev-ref HEAD` → `estate-checks-falsifiable`; `find ~/projects/Sylveste/.claude/agents -maxdepth 1 -name 'fd-*.md' | wc -l` → `396`, both checked this session.
- **Suggestion:** After opening the PR, explicitly `git checkout` back to the branch captured by the same `symbolic-ref --short HEAD` call the plan already uses for the general case, so the shared checkout is undisturbed regardless of PR status. Record the PR URL and its merge state as an open item on Task 25's close checklist rather than treating "PR opened" as a completed action.

### graph-py-deleted-without-golden-fixture

- **Severity:** P2
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md:335-395` (Task 4: reference is "read, do not modify", tests in `graph.test.mjs` assert properties from the plan's own prose spec), `:738` (Task 21: "Delete the Flask app and deploy configs" — deletes `apps/api/` entirely, `lens_search_api.py` included)
- **What:** Task 4 names `apps/api/src/lens/graph.py:18-335` and `lens_search_api.py` (several line ranges) as reference material, and its test suite checks properties the plan author wrote by hand from reading that source (graph size, an edge's `type`, determinism, coverage counts) — none of it is produced by actually *running* `graph.py` against the real curated corpus and pinning the output as a committed fixture. Task 21 then deletes `apps/api/` entirely; the file survives in git history, but nothing in the plan captures a snapshot of `graph.py`'s real runtime behavior first, and nothing in `data/README.md`, `CLAUDE.md`, or the plan itself points a future reader at "check out the pre-Task-21 commit if graph.js and graph.py ever disagree." The prose-derived spec this task's tests are built from has already been shown (elsewhere in this review) to diverge from the source in more than one place — meaning there is already a live discrepancy the plan has no way to adjudicate against ground truth once Task 21 lands, short of git archaeology nobody is pointed toward.
- **Evidence:** Task 4 line 340: "Reference (read, do not modify): `apps/api/src/lens/graph.py:18-335`, `apps/api/lens_search_api.py:134-200` …"; Task 21 line 740: "Delete: `apps/api/` entirely (data already moved; `scripts/generate_contrasts*.py` stay in git history) …" — note the plan explicitly reasons about what "stays in git history" for one file class (`generate_contrasts*.py`) but never makes the same argument, nor adds a fixture, for `graph.py`/`lens_search_api.py`'s actual behavior.
- **Suggestion:** Before Task 21 runs, add one throwaway step that executes `graph.py` against the real curated corpus for the functions `graph.js` ports and commits the raw output as a fixture (e.g. `tests/fixtures/graph-py-golden.json`) that `graph.test.mjs` can diff against — cheap insurance that outlives the deletion.

## Verdict

The registry's core failure mode is structural, not incidental: `merge.py` treats "currently sighted" as synonymous with "known," so the very Stage-G prune this plan exists to justify erases its own justification the first time the nightly harvest runs afterward — a P0 that inverts the project's stated goal. The Sylveste-root PR exception silently drops the workspace's own branch-safety discipline it applies everywhere else, live-verified to be sitting on a non-main branch right now. The `graph.py` deletion is lower stakes but leaves an already-known discrepancy permanently unadjudicable except by git archaeology nobody is pointed toward.
