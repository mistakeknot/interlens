## Findings

### npm-publish-step-never-exists
- **Severity:** P1
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md:707` (Task 19), `:723` (Task 20 step 6, `Publish: interpub:release for linsenkasten 3.0.0 and interflux (patch bump).`)
- **What:** CONFIRMING (with a correction) the prior finding. Part A is confirmed and stronger than stated — see the next finding. Part B ("no task verifies publish authorization before Task 20 step 6") is confirmed by direct grep: `npm publish`, `npm whoami`, `npm auth`, `_authToken`, and `interpub` never co-occur with any auth check anywhere in the plan. Part C ("this session's npm auth is confirmed absent") is **refuted as stated, but the underlying risk is worse, not milder**: an `_authToken` is present in `~/.npmrc`, so auth is not literally absent — but it does not authenticate (`npm whoami` → `401 Unauthorized`; a direct `curl` to `/-/whoami` with that exact token returns `{}`, not an identity). More importantly, the entire premise that Task 20 step 6 attempts an authenticated `npm publish` at all is unsupported: `interpub:release` delegates to `ic publish`, and `ic publish`'s own docs (`~/projects/Sylveste/interverse/interpub/.claude-plugin/commands/release.md`, `docs/interpub-vision.md`) describe it as bumping `plugin.json`/`marketplace.json`/`package.json` version fields for the Claude Code plugin marketplace — there is zero mention of `registry.npmjs.org` or `npm publish` in interpub's own documentation, and `ic publish --help`'s command list (`publish <ver>`, `--patch`, `doctor`, `clean`, `status`, `init`) names no npm-registry action. So the risk isn't "an unauthorized publish might fail loudly" — it's that **no task in the plan ever runs `npm publish` for `packages/mcp` at all**, authenticated or not.
- **Evidence:** `grep -n -i "npm publish\|npm whoami\|npm auth\|interpub\|_authToken" docs/plans/2026-09-02-linsenkasten-registry.md` → only the one `interpub:release` line (723), no auth check. `npm whoami` in this session → `E401 Unauthorized`. `~/.npmrc` contains `//registry.npmjs.org/:_authToken=npm_kxdd…` (present, non-functional). `~/projects/Sylveste/interverse/interpub/.claude-plugin/commands/release.md` and `docs/interpub-vision.md` contain zero occurrences of "npm publish" or "registry.npmjs.org".
- **Suggestion:** Rewrite the prior finding's framing from "no auth check before publish" to "no publish step exists at all for the npm package"; add an explicit `npm publish` (or documented decision to skip it) with an `npm whoami` precondition to Task 20 step 6, and a post-publish `<verify>` line comparing `npm view linsenkasten-mcp version` to the local `package.json` version.

### repo-is-linsenkasten-not-just-same-author
- **Severity:** P2
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md:723` (Task 20 step 1, `gh repo rename linsenkasten -R mistakeknot/interlens --yes`)
- **What:** Live verification makes Part A of the prior finding stronger than "same author's separate 2025 publish": `npm view linsenkasten-mcp` shows the 2.2.1 tarball's `repository.url` is already `git+https://github.com/mistakeknot/Linsenkasten.git`, and — independent of npm — `gh repo view mistakeknot/linsenkasten --json name -q .name` run *today, before any plan task has executed*, already resolves (via GitHub's own historical rename-redirect) to the live `mistakeknot/interlens` repo. This is direct proof the repo now called `interlens` was itself named `Linsenkasten` at some earlier point, not a coincidentally-named sibling project. That de-risks Task 20 step 1's `gh repo rename linsenkasten -R mistakeknot/interlens`: GitHub already permits `linsenkasten` to resolve to this exact repo via the pre-existing redirect, so reclaiming that name is very likely to succeed cleanly (renaming back to a name the repo itself once held is a well-known-safe GitHub operation), which is good news the plan doesn't call out and the prior finding didn't have visibility into.
- **Evidence:** `npm view linsenkasten-mcp --json` → `"repository":{"url":"git+https://github.com/mistakeknot/Linsenkasten.git"}`, `"author":"Mistake Knot"`, `"maintainers":["gensysven <mistakeknot@vibeguider.org>"]`. `gh repo view mistakeknot/linsenkasten --json name,owner,url` → `{"name":"interlens","owner":{"login":"mistakeknot"},"url":"https://github.com/mistakeknot/interlens"}` (run before any rename task executed). Local `packages/mcp/package.json` `"author": "Mistake Knot"` matches.
- **Suggestion:** Fold this evidence into Task 20 step 1 as a stated precondition/reassurance (`linsenkasten` already redirects here per GitHub's own history — the rename target is not contested), and note it in the plan so a reviewer doesn't have to re-derive it under time pressure.

### readme-install-path-serves-stale-2025-snapshot
- **Severity:** P1
- **Where:** `docs/plans/2026-09-02-linsenkasten-registry.md:707` (Task 19's sed sweep rewrites `README/CLAUDE/AGENTS/PHILOSOPHY`)
- **What:** `packages/mcp/README.md` documents `npm install -g interlens-mcp` twice as a real install path (line 46, under "Command line interface"; line 340, under "### Option 2: global install" for wiring a standalone/Claude-Desktop MCP config) — this is not throwaway text, it is the documented non-Claude-Code-plugin distribution channel (Claude Desktop config, ChatGPT/Codex via the package's own `openapi`/`gpt-actions`/`chatgpt` keywords). Task 19's mapping-table sed sweep turns this into `npm install -g linsenkasten-mcp`, which — combined with the prior finding's confirmed absence of any actual `npm publish` step — means a fresh non-Claude-Code-plugin user who follows this exact renamed instruction after the rename lands receives npm's already-published Nov-2025 `2.2.1` snapshot: pre-registry, pre-local-graph, and (per Task 21) referencing an `apps/api` Flask backend the plan is about to delete from the repo entirely. Nothing breaks loudly; the install just silently serves materially different, stale software forever, and no task or `<verify>` line ever diffs the local `package.json` version against the live npm `dist-tags.latest`.
- **Evidence:** `packages/mcp/README.md:46` and `:340` both show `npm install -g interlens-mcp`. `npm view linsenkasten-mcp version` → `2.2.1`, unchanged since 2025-11-26 per the registry's `time` map. No `<verify>` block in Task 19 (lines 707-714) or Task 20 (lines 715-729) references `npm view` or a version comparison.
- **Suggestion:** Either (a) add the missing `npm publish` step from the prior finding so the README's claim becomes true again, or (b) if npm publish is deliberately out of scope for this pass, have Task 19 rewrite that README section to say "install via the Claude Code plugin marketplace; npm global install is currently stale" rather than silently renaming a broken instruction to a differently-broken instruction.

## Verdict
The prior finding's core claim (A: same-project prior publish; B: no auth check before Task 20 step 6) is CONFIRMED and, on live evidence, A is stronger than stated — `linsenkasten` is this exact repo's own former GitHub name, not merely the same author's separate package. Part C ("npm auth confirmed absent") is REFUTED on its literal wording — a non-functional auth token is configured, not no token — but the substantive risk is worse than "unauthorized publish would fail": `interpub:release`/`ic publish` never calls `npm publish` at all, so the plan has no step that would even attempt authentication, leaving the already-documented `npm install -g` path (renamed in place by Task 19) pointed permanently at a stale, pre-registry 2.2.1 snapshot with no verify line able to catch it.
