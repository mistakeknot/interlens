## Findings Index
- [P1] hit-rate-tie-blind-cluster-head — CONFIRMED: name-level attribution + identical-name clustering guarantees a hit_rate tie that the spec doesn't say how to break, and the given fixture never exercises it (§Task 10, §Task 12)
- [P2] attributions-jsonl-duplicate-rows — per-index-record iteration over a name-shared attribution set risks writing the same (run, finding_id, lens) row once per duplicate-name record, with no dedupe or test to catch it (§Task 10)

## Findings

### hit-rate-tie-blind-cluster-head
- **Severity:** P1
- **Where:** Task 10 `harvest/stats.py` semantics (plan line 596, test line 598) vs. Task 12 `harvest/edges.py` variant-of clustering + head rule (plan line 620, test line 625)
- **What:** Task 10 attributes ledger rows to an index record by `lens == name` — explicitly "name-level: a lens's findings attribute to its name" (line 596) — so `findings`, `upheld`, `refuted`, `raw`, `adjudicated`, `hit_rate`, and `smoothed_hit_rate` are computed from the identical row set, and therefore come out byte-identical, for every index record that shares that `name`. Task 12's `variant-of` clustering unions generated records whose pairwise cosine is `≥ VARIANT_MIN_COSINE` **or** whose `name` is identical (line 620) — the second clause exists specifically to catch repeat generations of the same-named `fd-*` agent whose bodies drifted enough that cosine alone might miss them. Because `adjudicated` is computed the same name-scoped way, every member of an identical-name subgroup clears (or fails) the head rule's `adjudicated >= 2` gate simultaneously, and if it clears, every member ties at the exact same `smoothed_hit_rate`. The head rule's primary tier ("the non-corrupt member with the highest `stats.smoothed_hit_rate`... `head_selected_by: 'hit_rate'`") cannot discriminate inside that subgroup at all — it is a guaranteed tie for exactly the case name-identity clustering exists to discriminate (two different generations of the same agent name, which is the natural real-world source of `variant-of` pairs, since re-running `/flux-gen` on an edited spec keeps the name and changes the body/body_hash).
- **The escape hatch is itself ambiguous.** The rule reads: "...`(head_selected_by: "hit_rate")`; else highest `use_count + drive_uses` (`"usage"`); else latest `last_seen` (`"recency"`); ties by id." Two different sonnet-grade readings are both defensible: (a) "ties by id" is the terminal tie-break for *whatever* tier ends up applying — so a tie inside the hit_rate tier is broken by id **without ever falling to usage/recency**, and the head is still labeled `"hit_rate"` even though the actual discriminator was arbitrary id order; or (b) a tie inside a tier means that tier "didn't determine a winner" and the selection falls through to the next tier (usage, then recency), in which case the label should really be `"usage"` or `"recency"`, not `"hit_rate"`. The spec gives no test that would force either reading, and the two readings produce different persisted `head_selected_by` values for the same input.
- **The fallback tier is also inconsistently scoped**, which weakens reading (b) as a reliable rescue: `drive_uses` is computed by scan.py/stats.py as "max over sightings" (line 596) where the sightings are the ones the flux-drive usage-count was already collected against per body_hash (line 556's per-sighting `_count_usage_from_synthesis` count) — i.e., record-scoped (own body_hash), not name-scoped. Every other field in the same paragraph is explicitly name-scoped (`lens == name`). Nothing in Task 10 says whether `drive_uses`'s "sightings" means the record's own current sightings or the union across every same-name record; if a sonnet executor makes it name-scoped for consistency with the rest of the block, the usage tier ties too, and the chain falls all the way to `recency`/id with no field left that can legitimately discriminate between two generations of the same name.
- **Consequence:** this isn't cosmetic — `head_selected_by` counts are the literal content of the "calibration table a human reads before Task 23" (line 622, "counts of clusters by `head_selected_by`"), the report that gates whether `VARIANT_MIN_COSINE` gets adjusted before the Mac-side prune sweep. If ties are silently mislabeled `"hit_rate"`, the human calibrating the threshold overestimates how often head selection is evidence-driven versus arbitrary, for precisely the identical-name clusters where getting head selection right matters most (an unreviewed generated write-up becoming the surfaced `get_lens` answer for that name).
- **Evidence it's untested:** Task 10's own test (line 598) uses one index record per name (`fd-a`, `fd-b`) and never exercises two records sharing a name. Task 12's test (line 625, "4 generated + 3 curated... head choice by hit-rate") is described as testing head choice *by differing* hit-rate, not a tie; no fixture in either task includes a same-name duplicate pair, so the ambiguity above would ship unnoticed either way it's implemented.
- **Suggestion:** state explicitly which of the two tie-break readings is intended (recommend: a tie inside a tier falls through to the next tier, and the persisted `head_selected_by` reflects whichever tier actually produced a strict winner, falling to a new `"id"` label if every tier ties); pin `drive_uses`'s "sightings" scope to the record's own current sightings (matching scan.py's per-sighting collection, not the name-scoped block around it); add a Task 12 fixture with two same-name generated records with identical `adjudicated`/`smoothed_hit_rate` to force the tie path and assert the resulting `head_selected_by` value.
- **Verdict on the prior claim:** CONFIRMED as stated — the tie is guaranteed for identical-name clusters, and it does fall through to an arbitrary id tie-break under the more natural reading of the rule's prose, while `head_selected_by` still literally says `"hit_rate"` under that reading. The one caveat: the plan's wording is genuinely ambiguous rather than unambiguously wrong, so the sharper framing is "the spec does not say how to break this guaranteed tie, and every reading that resolves the ambiguity either mislabels the provenance or silently degrades the discriminator to id" — worth reporting as an executability gap even under the more charitable reading.

### attributions-jsonl-duplicate-rows
- **Severity:** P2
- **Where:** Task 10 `harvest/stats.py` semantics, output-write sentence (plan line 596: "Writes back into `index.jsonl`... and `data/generated/attributions.jsonl` (the raw rows, sorted by `(run, finding_id, lens)`)"); cf. line 153's file-layout description, "`attributions.jsonl` — ledger finding ↔ lens rows."
- **What:** the per-record computation is framed as a loop — "for each index record, over attribution rows whose `lens == name`: ... Writes back into `index.jsonl`... and `attributions.jsonl` (the raw rows...)." Because multiple index records can legitimately share a `name` (the same scenario finding #1 relies on), the SAME underlying ledger rows are the matched set for each of those records. If a sonnet-grade executor implements this literally as "for each record, gather its matching raw rows and append them to the attributions accumulator," the identical physical row gets appended once per index record sharing that name, and the file ends up with N duplicate copies of the same `(run, finding_id, lens)` triple where N is the size of the identical-name subgroup — even though line 153 describes the file as one row per "ledger finding ↔ lens" pairing (implying uniqueness) and the sort key `(run, finding_id, lens)` reads like an intended natural primary key.
- **Why it's plausible, not just theoretical:** the spec never says "deduplicate" or "write attributions.jsonl once, independent of the per-record loop," and Task 10's own test (line 598) again only covers single-record-per-name fixtures, so a duplicate-row regression from a same-name pair would not be caught by the stated test. Task 12's `audit` command (line 623) checks index records against body files and embedding rows, edge endpoints, cluster head cardinality, and `hash_recipe` — it does not mention `attributions.jsonl` at all, so nothing downstream would flag the duplication either.
- **Suggestion:** either (a) build `attributions.jsonl` as one global pass over the ledger keyed by `(run, finding_id, lens)` before/independent of the per-index-record stats loop, or (b) dedupe on write; add a test with two index records sharing a `name` asserting `attributions.jsonl` contains each `(run, finding_id, lens)` triple exactly once.

## Verdict
The prior finding is confirmed: Task 10's name-level attribution and Task 12's identical-name clustering clause combine to guarantee a hit_rate tie exactly where variant-of clustering is meant to be most useful, and neither task's test fixture exercises that path — the sharpest fix is to pin down what "ties by id" scopes over and to stop labeling a tie-broken selection `head_selected_by: "hit_rate"`. A second, related gap surfaced in the same code: the per-record write of `attributions.jsonl` has no stated dedupe guard against the same name-sharing scenario, so it can silently accumulate duplicate ledger rows with nothing in Task 10 or Task 12's audit positioned to catch it.
