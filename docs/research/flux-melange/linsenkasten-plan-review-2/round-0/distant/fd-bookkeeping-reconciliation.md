## Findings

### prune-sweep-ignores-branch-ownership
- **Severity:** P0
- **Where:** Task 23 candidate-repo rule (plan line ~822: "(c) has a clean `git status --porcelain` for paths outside `.claude/`") and the per-repo commit step (plan line ~823: "Commit per repo on its current branch, checked in the same command"); compare the plan's own Task 1 (line 20-21): "the main checkout currently sits on a sibling session's unpushed `sweep/2026-09-02` branch."
- **What:** Task 23's three candidacy conditions are (a) is a git repo, (b) not under a worktree/session/spike-named directory, (c) clean `git status --porcelain` outside `.claude/`. None of the three asks *what branch the repo is currently on* or whether that branch belongs to someone else's in-flight work. The plan special-cases exactly one repo for this — `~/projects/Sylveste` itself, routed through a disposable worktree + PR because "main is protected and the shared checkout is on someone else's branch… never switch it" — but that carve-out is written for one path, not generalized to the other ~50 repos the sweep walks. I checked the real corpus (read-only, no repo touched): `git -C ~/projects/Sylveste/interverse/interkasten symbolic-ref --short HEAD` and the same for `~/projects/Sylveste/interverse/tldr-swinton` both return `sweep/2026-09-02` — the *identical* branch name Task 1 names as a sibling session's unpushed work — with clean working trees (`git status --porcelain` empty). Both are separate git roots (confirmed via `git rev-parse --show-toplevel`, distinct from the Sylveste superproject root) nested inside the Sylveste tree, and both were already in the raw `fd-*.md` file scan (they carry generated agent piles). Under Task 23's rule as written, both qualify as ordinary prune targets: clean, not a worktree/session/spike directory, is a git repo. `--apply` would `git rm` their `fd-*.md` files and `git commit --no-verify … && git push` *directly onto `sweep/2026-09-02`* — a branch this same plan elsewhere treats as belonging to another agent's unfinished, unpushed work. A concurrent commit from that sibling session (rebasing, amending, or simply continuing the sweep on that branch) now has to reconcile with a "chore: prune" commit it never made, on a branch its owner may not expect anyone else to be pushing to at all.
- **Evidence:**
  ```
  $ git -C ~/projects/Sylveste/interverse/interkasten rev-parse --show-toplevel
  /Users/sma/projects/Sylveste/interverse/interkasten
  $ git -C ~/projects/Sylveste/interverse/interkasten symbolic-ref --short HEAD
  sweep/2026-09-02
  $ git -C ~/projects/Sylveste/interverse/interkasten status --porcelain | wc -l
  0
  $ git -C ~/projects/Sylveste/interverse/tldr-swinton symbolic-ref --short HEAD
  sweep/2026-09-02
  ```
  (both checked live 2026-09-03, alongside a same-tree standalone `~/projects/tldr-swinton` checkout that *is* on `main` — confirming these two are genuinely on the sibling-session branch, not just misreported.) Plan line 20: "The main checkout currently sits on a sibling session's unpushed `sweep/2026-09-02` branch" (about the linsenkasten repo itself, but the branch name is evidently in use across the Sylveste tree, not scoped to one repo).
- **Suggestion:** Add a fourth Task 23 candidacy condition: the repo's current branch must be its configured default/remote-HEAD branch (`git symbolic-ref refs/remotes/origin/HEAD` or equivalent), or the repo is routed through the same worktree+PR path already built for Sylveste. That single rule generalizes the existing special case instead of leaving it as a one-off, and would have correctly excluded (or worktree-routed) `interkasten` and `tldr-swinton` today without a human needing to notice the branch name by hand.

### harvest-push-trap-wipes-unrelated-data
- **Severity:** P0
- **Where:** `scripts/harvest-and-push.sh` (Task 22, plan lines 789-808), specifically the `trap` registration and the very next line: `STEP=pull;  git pull -q --ff-only origin main`.
- **What:** The trap's *blast radius* is correctly scoped — `git checkout -q -- data && git clean -fdq data` touches only the `data/` pathspec, not the whole repo. But the trap's *trigger* is not scoped to anything the run itself did: `set -euo pipefail` plus `STEP=pull; git pull -q --ff-only origin main` as the very first command means the trap fires — discarding everything uncommitted or untracked under `data/` — the instant a plain fast-forward pull fails for *any* reason, including one that has nothing to do with `data/` at all. A fast-forward pull fails when the local branch has diverged: local carries an unpushed commit *and* the remote has moved since. In this repo that is not a rare condition — this very plan has 25 tasks touching dozens of files across a shared checkout that both machines and (per Task 1's own note) sibling sessions commit to, and zklw's nightly timer pushes to `main` every night regardless of what state the Mac's checkout is in. Concretely: a human runs `python3 -m harvest scan && python3 -m harvest merge` by hand on the Mac to review a `prune-targets.txt` candidate before running `--apply` (an explicitly human-gated step per Task 23), leaves it uncommitted while reviewing, and separately has an unrelated unpushed local commit sitting on the branch (e.g. mid-edit on a Stage E/F task file) from earlier in the same session. Anyone — including the same human — invoking `bash scripts/harvest-and-push.sh clavain` in that window (Task 15's precondition literally routes through this script; the Mac is also told to run it "on demand… always before any prune") hits a diverged pull on the very first line, the trap fires, and `git clean -fdq data` deletes the uncommitted review work under `data/` before a single harvest subcommand has run. The failure log records `rc` and `step=pull`, not what was in the working tree at that moment, so there is no record of what was lost.
- **Evidence:**
  ```bash
  trap 'rc=$?; if [ $rc -ne 0 ]; then git checkout -q -- data && git clean -fdq data; echo "$(date -u +%FT%TZ) rc=$rc step=${STEP:-?}" >> "$STATE/harvest-failed.log"; fi' EXIT
  STEP=pull;  git pull -q --ff-only origin main
  ```
  (plan lines 797-798, quoted verbatim). Task 1 line 121: "**Task 15 must not start until Task 14's data commit is visible in `git log -1 origin/main` from zklw**" and Task 23's own precondition (2) ("no machine can be pruning against an index the other has never seen") both assume this repo's branch state is routinely ahead/behind between the two machines — the exact condition that makes a diverged pull plausible, not exotic.
- **Suggestion:** Scope the failure-recovery step to only discard what *this run* produced, not whatever predates it: `git stash -u -- data` (or record `git status --porcelain data` to a temp file) *before* the pull, and only `git clean` paths that weren't already dirty/untracked at invocation time. Simpler alternative: check `git status --porcelain data` is empty as a precondition *before* attempting the pull, and abort with a distinct, non-destructive message (not the generic trap) if it isn't — the same "human review gate" discipline Task 23 already applies to `prune-targets.txt` should apply to this script not deleting someone's in-progress review.

### name-collision-smears-attribution-stats
- **Severity:** P1
- **Where:** Task 10 `harvest/stats.py` (plan line 596: "for each index record, over attribution rows whose `lens == name`"); Task 12 `harvest/edges.py` variant-of clustering (plan line 620: "union-find over generated pairs with cosine ≥ `VARIANT_MIN_COSINE` **or** identical `name`" and the head-selection rule immediately after).
- **What:** Two `gen:*` records with different `body_hash` values (genuinely different bodies — the whole reason they're separate index records) but the *same* `name` field are both scored by Task 10 against attribution rows filtered only by `lens == name`. Since the ledger's attribution rows record the lens as a bare name string (there is no per-body/per-hash key in a heat ledger — flux-melange records findings against whatever name the agent file declared), both records match the *identical* set of attribution rows and end up with identical `findings`/`upheld`/`refuted`/`adjudicated`/`hit_rate`/`smoothed_hit_rate`. This isn't a rare edge case the plan is unaware of — Task 12's own clustering rule explicitly anticipates name collisions across the corpus by making identical `name` alone (no cosine check required) sufficient to merge two records into one `variant-of` cluster. But by the time Task 12 runs, Task 10 has already made the two candidate heads statistically indistinguishable on the one signal (`smoothed_hit_rate`) the head-selection rule is supposed to use to prefer the record that actually earned its adjudications. Since both members now report the same `smoothed_hit_rate`, the "highest `smoothed_hit_rate` among members having `adjudicated >= 2`" rule can no longer discriminate by quality at all for exactly the population it exists to discriminate within (name-sharing variants) — it falls straight to `use_count + drive_uses`, then recency, then id, none of which reflect which body actually produced good findings. A frequently-*reused* but low-quality copy (high `use_count` from `record_reuse` calls, not from ledger performance) can beat a rarely-reused but genuinely effective one, and either way `data/generated/attributions.jsonl` (Task 10's raw-row output) and any `registry_stats` total built from per-record `stats.findings` double-counts the same ledger rows across both records.
- **Evidence:** Task 10 (plan line 596): `` for each index record, over attribution rows whose `lens == name` … `hit_rate = upheld / adjudicated` … `` — the filter key is literally the name string, with no `body_hash`/id disambiguation anywhere in the described join. Task 12 (plan line 620): `` `variant-of`: union-find over generated pairs with cosine `≥ VARIANT_MIN_COSINE` **or** identical `name` `` and `` head = the non-corrupt member with the highest `stats.smoothed_hit_rate` among members having `adjudicated >= 2` ``. This worktree already demonstrates the name-collision precondition is real: two distinct `.claude/agents/fd-bookkeeping-reconciliation.md`-style generated files with the same slug legitimately exist across different repos in this corpus today (per the live scan run for the sibling finding above), so the plan's own name-based dedup path is not a hypothetical.
- **Suggestion:** Change Task 10's attribution join key from bare `name` to `(name, body_hash)` when the ledger can supply it (a heat ledger row could carry the agent file's hash at record time, since flux-melange already reads the generated `.md` file to run the lens), falling back to name-only only when no hash is available (and flagging that fallback in the report, similar to how `weak` embodies edges are already flagged in Task 12's calibration table) — so a genuine multi-hash name collision doesn't silently inherit another body's track record.

### zero-sighting-field-preservation-gap
- **Severity:** P1
- **Where:** Task 9 `harvest/merge.py` semantics (plan lines 572-585), specifically the record shape and the sentence "`tier`/`use_count`/`last_used` = max across **non-reuse** sightings… `cohort` from the first sighting with a spec; `domains` = sorted union minus `uncategorized`"; the test at plan line 587 only asserts `on_disk`, `sightings`, and `accessioned_at` for the zero-current-sightings case.
- **What:** Task 9 explicitly names a preservation rule for four fields when a record has zero current sightings: `accessioned_at` never changes, `sightings`/`sightings_seen`/`on_disk` are computed to reflect the absence correctly, and the body file is left untouched. It says nothing about what happens to the other eight fields the merge writes on every run — `machines`, `repos`, `tier`, `use_count`, `last_used`, `domains`, `cohort`, `lineage` — when the sightings that would normally supply them have all vanished. Read literally, `tier`/`use_count`/`last_used` = "max across non-reuse sightings" and `domains` = "sorted union minus uncategorized" are both computed *from the current run's sighting rows*; with zero current sightings for that hash, the natural reading of "max of an empty set" / "union of nothing" is `None`/`[]`, which would silently blank fields that were previously populated and meaningful (a record that once had `domains: ["migration"]` and `tier: "used"` reverting to empty the moment its last file is pruned from every repo on every machine). This directly undermines the accretive-index promise Task 9 exists to deliver (melange f-028's top finding was exactly "a merge that rebuilds from the current filesystem erases every record") for every field except the four it names — the fix landed narrowly.
- **Evidence:** Task 9 test (plan line 587): "a prior index containing a record whose hash has no current sighting is retained with `on_disk == False`, `sightings == 0`, its `accessioned_at` unchanged, and its body file untouched" — no assertion touches `machines`, `repos`, `domains`, `tier`, `use_count`, `last_used`, `cohort`, or `lineage` for that same fixture record. The record JSON example at plan line 574-583 shows all of these fields populated but gives no branch for what merge does to them on a re-run where the hash's sightings list is empty.
- **Suggestion:** Extend Task 9's semantics with one explicit sentence: on a record with zero current sightings, every field not itself computed fresh from *this run's* sightings is carried forward unchanged from the prior `index.jsonl` entry (the same rule already applied to `accessioned_at`), and extend the merge test fixture to assert `machines`, `domains`, and `tier` survive a sighting going to zero and then reappearing, matching the existing `on_disk` flip-back assertion.

### corpus-scale-undercounted
- **Severity:** P3
- **Where:** This review's own task context and `.claude/flux-gen-specs/…` / `docs/research/flux-melange/linsenkasten-plan-review-2/lenses/fd-prunesweep-hostverification.json:12` ("At 48 repos and roughly 2,900 files…"); compare Task 14's embed-time estimate (plan line 653: "~1,700 generated + 258 curated texts; expect < 10 min").
- **What:** The "~2,900 files, 48 repos" figure that this pass's own north star and a sibling generated-lens spec use to reason about corner-case probability at corpus scale does not appear anywhere in the plan document itself, and doesn't match a live count. A read-only walk of `~/projects` for `.claude/agents/fd-*.md`, excluding `.worktrees`/`worktrees`/`node_modules` paths exactly as Task 8's `EXCLUDE_DIR_NAMES` does, finds **43 distinct git-repo directories carrying `fd-*.md` piles** just among top-level scan hits (before applying Task 23's `-sessions`/`-f2`/`-spike-*` name exclusions or the "clean working tree" filter), and roughly **4,800+** individual `fd-*.md` files across them — not 48 repos / 2,900 files. This doesn't invalidate Task 14's ~1,700-*unique-body* estimate on its own (raw file count and post-dedup unique-body count are different numbers, and heavy duplication is the entire premise of the harvest), but it does mean any reasoning calibrated against "48 repos, 2,900 files" — including the exact corner-case-probability argument `fd-prunesweep-hostverification`'s own seed makes — is working from a smaller corpus than actually exists, in the direction that makes low-probability-per-repo failure modes more likely to actually occur, not less.
- **Evidence:**
  ```
  $ find ~/projects -maxdepth 8 -path '*/.claude/agents/fd-*.md' \
      -not -path '*/.worktrees/*' -not -path '*/worktrees/*' -not -path '*/node_modules/*' \
    | sed 's#/.claude/agents/.*##' | sort -u | wc -l
  43
  $ find ~/projects -maxdepth 8 -path '*/.claude/agents/fd-*.md' \
      -not -path '*/.worktrees/*' -not -path '*/node_modules/*' | wc -l
  4843
  ```
  (both checked live 2026-09-03 on Clavain; zklw's corpus was out of scope for this read-only pass but is not expected to be smaller.)
- **Suggestion:** Before Task 14's first real harvest, run `python3 -m harvest scan --dry-run` and record the actual `scanned=`/`unique_bodies=` counts in the task's own report rather than carrying the ~2,900/48 figures forward uncorrected into capacity or probability arguments elsewhere (Task 14's `< 10 min` embed estimate is the one line in the plan that would most directly need revisiting if the real unique-body count turns out meaningfully above 1,700).

## Verdict
The two P0s share one shape: a rule the plan states carefully for one repo (Sylveste's branch protection) or one path (this run's own uncommitted state) turns out, checked against the corpus as it actually exists today, to also apply to repos and states the plan never named — a sibling session's branch reused verbatim by two other real repos, and a whole-repo pull precondition guarding a data/-scoped but still destructive cleanup. Both are fixable with one additional, generalized condition rather than a redesign. The name-collision and zero-sighting gaps are narrower but hit the same nerve as the plan's own "accretive index" fix: the preservation and attribution rules that were written explicitly cover the fields called out by name, and are silent — not wrong, just unstated — everywhere else a field is computed from sightings that can vanish or collide.
