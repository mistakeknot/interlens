### gate-a-loads-stale-marketplace-cache
- **Severity:** P0
- **Where:** Task 1 line 121 landing rule; Stage B Gate A (plan line 512: `"interlens@interagency-marketplace": true`); Task 20 step 6 (publish timing); `.claude-plugin/plugin.json` (this worktree); `~/projects/interagency-marketplace/.claude-plugin/marketplace.json:445-452` (this Mac); zklw `~/.claude/settings.json:260` and `~/.claude/plugins/cache/interagency-marketplace/interlens/2.2.5/` (read-only ssh, checked live 2026-09-03).
- **What:** Gate A's verify step is "re-enable the plugin on this machine … and confirm from a fresh session that `mcp__interlens__search_lenses` answers with no network access." But the marketplace row for `interlens` is `{"source":{"source":"url","url":"https://github.com/mistakeknot/interlens.git"},"strict":true,"version":"2.2.5"}` — checked on the Mac just now — and nothing in Tasks 1–19 touches `~/projects/interagency-marketplace/.claude-plugin/marketplace.json`; that file is only edited in Task 20 step 3, which happens after the rename, long after Gate A and Gate B. So flipping the settings key to `true` at Gate A time can only ever populate `~/.claude/plugins/cache/interagency-marketplace/interlens/2.2.5/` — the pre-plan snapshot, confirmed present on both the Mac and zklw and still importing `api-client.js` against the dead Railway API. A fresh session's `search_lenses` call at Gate A is not touching `lib/store.js` at all; it is touching 2.2.5's `fetchFromAPI`, which either times out against a dead host or returns whatever the old Railway/Supabase backend still serves. Either the check quietly "passes" against stale hosted data (false confidence that the local engine works) or fails for a completely unrelated reason (the API being retired, not the local engine being broken) and the executor chases the wrong bug. Gate B (line 682) has the identical problem — it never says a fresh session goes through the marketplace cache either, and Task 15's precondition text only checks git state, not what a session actually loads.
- **Evidence:** `~/projects/interagency-marketplace/.claude-plugin/marketplace.json:445-452` on Clavain: `"name": "interlens", "source": {"source": "url", "url": "https://github.com/mistakeknot/interlens.git"}, "strict": true, "version": "2.2.5"`. `~/.claude/settings.json:279` on Clavain and `:260` on zklw (`ssh -o BatchMode=yes zklw`, read-only): `"interlens@interagency-marketplace": false`. `~/.claude/plugins/cache/interagency-marketplace/interlens/` contains only a `2.2.5/` directory on both machines (zklw's copy carries a `.in_use` marker, dated June); neither cache has a `data/` directory, consistent with 2.2.5 predating this design entirely.
- **Suggestion:** Gate A and Gate B need to say explicitly how a "fresh session" reaches the new code before Task 20 ever runs — either a documented local-plugin-path override for `interlens@interagency-marketplace` during Stages B–D (if Claude Code's plugin loader supports one), or replace the marketplace-toggle instruction with `node packages/mcp/scripts/smoke.mjs …` (which the plan already uses elsewhere) as the actual Gate A/B acceptance mechanism, reserving the settings-key toggle for after Task 20's publish. If no local-path override exists, say so and drop the "re-enable the plugin" sentence from both gates.

### find-lens-journey-path-shape-mismatch
- **Severity:** P0
- **Where:** Task 6 table row for `findLensJourney` (plan line 465: `paths: [{lenses: [lensObj...], total_weight}]`); `packages/mcp/index.js:762-800` (unmodified by any task — Task 6 only touches the import line and the `get_central_lenses` enum).

Task 6's own table promises each entry is `{lenses: [...], total_weight}`, an object, not an array. On the promised shape `path.length` is `undefined` and `path.forEach` is not a function — `find_lens_journey` throws inside the handler on every call that finds a path, which is the plan's own Gate A tool. Task 6's verify line (`node packages/mcp/scripts/smoke.mjs find_lens_journey … → contains "Conceptual Journey"`) only checks a string printed *before* the loop runs, so this never gets caught by the plan's own acceptance check.
- **Evidence:** Read both sides directly — `index.js:770-772`:
  ```
  results.paths.forEach((path, idx) => {
    response += `## Path ${idx + 1} (${path.length} steps)\n\n`;
    path.forEach((lens, i) => {
  ```
  vs. Task 6's table (plan line 465): `findLensJourney(src, dst)` → `{success, source_lens, target_lens, paths: [{lenses: [lensObj...], total_weight}], error?}`.
- **Suggestion:** One-line fix at the seam, either side: either have `api-local.js`'s `findLensJourney` flatten each result to a bare lens array (drop the `{lenses, total_weight}` wrapper) to match what the handler already expects, or fix the handler to `path.lenses.forEach(...)` / `${path.lenses.length} steps`. ### gap-analysis-coverage-shape-mismatch
- **Severity:** P1
- **Where:** Task 4 `frameCoverage` (plan line 365: returns `explored`/`underexplored`/`unexplored` as lists of frame names, `total_frames`, no counts, no percentage); Task 6 table rows for `getRandomProvocation` and `detectThinkingGaps` (plan lines 471-472); `index.js:1027-1052` (`detect_thinking_gaps`) and `index.js:960-967` (`random_lens_provocation`).
- **What:** `detect_thinking_gaps` reads `cov.explored_frames` as an object and does `Object.keys(cov.explored_frames).length` and `Object.entries(cov.explored_frames).forEach(([frame, count]) => …)`, plus `cov.coverage_percentage` as a ready number. `random_lens_provocation` reads `gap.coverage.explored` and `gap.coverage.total` as numbers, plus `gap.was_gap_biased` and `gap.suggested_from_frame`. None of these fields — `explored_frames` as a counted map, `coverage_percentage`, a nested `coverage.explored`/`.total`, `was_gap_biased`, `suggested_from_frame` — appear anywhere in Task 4's `frameCoverage` semantics or in the `getRandomProvocation`/`detectThinkingGaps` rows of Task 6's table. Both tools are named in the plan's first Must-Have Truth as things a fresh session must answer. As written, `detect_thinking_gaps` prints `NaN%` / `undefined/28 frames` rather than throwing (property access on a defined-but-wrong-shaped object doesn't crash), and `random_lens_provocation`'s `gap.coverage.explored / gap.coverage.total` divides `undefined` by `undefined` — also `NaN`, not a throw — so this degrades silently rather than failing Gate A's smoke test, which is worse for a "sonnet-grade executor cannot perform exactly as written" concern: nothing here forces a fix.
- **Evidence:** `index.js:1031`: `` `- **Explored**: ${cov.coverage_percentage}% (${Object.keys(cov.explored_frames).length}/${cov.total_frames} frames)\n` ``; `index.js:963`: `` `Coverage: ${gap.coverage.explored}/${gap.coverage.total} frames explored (${Math.round((gap.coverage.explored / gap.coverage.total) * 100)}%)\n` ``. Task 4 (plan line 365): `frameCoverage(store, exploredNames): explored = frame names …; underexplored = …; unexplored = the rest; total_frames = 28.`
- **Suggestion:** One finding, one cause: `api-local.js`'s `detectThinkingGaps`/`getRandomProvocation` wrappers (Task 13) need to build the `explored_frames` counted-map, `coverage_percentage`, and the nested `coverage.{explored,total}`/`was_gap_biased`/`suggested_from_frame` fields themselves from `frameCoverage`'s lists — Task 4's function contract should say so explicitly rather than leaving api-local.js to reverse-engineer the handler's exact dereferences from reading index.js. Add both fields to Task 13's fixture test in `generated.test.mjs` and assert on the printed response text (not just the raw JSON), since the print path is where the mismatch is invisible.

### embed-digest-refuse-vs-nightly-check
- **Severity:** P1
- **Where:** Task 11 (plan line 607: "**Refuse** to append rows when the live digest differs from `meta.model_digest` unless `--reembed-all`"); Task 22 `harvest-and-push.sh` (plan line 799: `"embed --check"`, no `--reembed-all` anywhere in the loop).
- **What:** `embed.py` is specified to hard-refuse whenever the locally-running Ollama's live digest for `nomic-embed-text` differs from what's recorded in `data/embeddings/meta.json`, unless `--reembed-all` is passed. `harvest-and-push.sh` — the *only* script Task 15 and the zklw nightly timer run — passes `embed --check` and nothing else; there is no branch that adds `--reembed-all`, and no operator is in the loop for the unattended nightly run. Checked read-only just now: both machines report the identical digest for `nomic-embed-text:latest` today (`0a109f422b47…`, via local `curl 127.0.0.1:11434/api/tags` on Clavain and `ssh -o BatchMode=yes zklw curl 127.0.0.1:11434/api/tags`), so the refuse path does not fire today. But the moment either machine's Ollama independently repulls or upgrades the model (an ordinary `ollama pull nomic-embed-text`, unrelated to this plan), the next `embed --check` step on whichever machine drifted first exits non-zero, `set -euo pipefail` propagates it, and the trap (`git checkout -q -- data && git clean -fdq data`) discards that night's entire harvest — silently, with only a one-line entry in `harvest-failed.log`. This is exactly the decay mode melange f-039 was raised against ("without it the context-tax fix decays while the deletion stays permanent"), but the fix that landed (the nightly timer) has no path through a digest drift at all.
- **Evidence:** Local: `curl 127.0.0.1:11434/api/tags` → `nomic-embed-text:latest 0a109f422b47e3a30ba2b10eca18548e944e8a23073ee3f3e947efcf3c45e59f`. zklw (read-only ssh, `-o BatchMode=yes`): identical digest. Task 22 line 799: `for STEP in "scan --machine $MACHINE --roots $ROOTS" merge stats "embed --check" edges audit; do python3 -m harvest $STEP; done` — no `--reembed-all` anywhere in this file.
- **Suggestion:** Either (a) have the nightly script distinguish "digest drifted, needs `--reembed-all`" from other embed failures and re-run once with that flag automatically when the *only* difference is `model_match: false` (safe because both machines are meant to converge on one canonical model), logging the re-embed distinctly from a generic failure, or (b) alert instead of silently discarding — write the digest-mismatch case to a separate, more visible log/state file than the generic `harvest-failed.log`, since this failure mode is expected to recur (models get repulled) rather than being a genuine one-off error worth discarding a night's harvest over.

### triad-progression-insight-fields-unspecified
- **Severity:** P2
- **Where:** Task 4 `triads()` and `progression()` (plan lines 366-367); Task 6 table rows for `getDialecticTriads`/`getLensProgressions` (plan lines 473-474); `index.js:1176-1177` (`triad.synthesis_insight`) and `index.js:1216-1218` (`results.overall_insight`).
- **What:** `index.js`'s `get_dialectic_triads` handler reads `triad.contrast_insight` (guarded, fine — `triads()` emits it) but also `triad.synthesis_insight` (guarded with `if (triad.synthesis_insight)`), and `get_lens_progressions` reads `results.overall_insight` (guarded with `if (results.overall_insight)`). Neither field is produced anywhere: Task 4 states `triads(g, store, id, limit=3)` emits exactly `{thesis, antithesis, synthesis, contrast_insight}` — no `synthesis_insight` — and `progression(...)` emits `{step, lens, insight}` per step with no summary-level `overall_insight`. Because both handler reads are `if (field)`-guarded, this doesn't throw; it silently omits a whole documented section of the tool's own markdown output ("How it integrates" for triads, "Journey Insight" for progressions) forever, which is the kind of quiet degradation a smoke test asserting on a fixed substring (Task 13's tests check `.length >= 1`, not field completeness) won't catch. Both fields are plausible to derive from the same graph data other insight fields already use — e.g. `synthesis_insight` from the `insight` on whatever typed edge (`synthesis`/`emergence`/`application` per `connections.json`'s type vocabulary in `data/README.md`) joins `synthesis` to `antithesis`, and `overall_insight` from a description of the path's dominant edge type or its total weight — but the plan names no such rule for either.
- **Evidence:** `index.js:1174-1177`: `` `### 🔄 Synthesis: ${triad.synthesis.name}\n> ${triad.synthesis.definition}\n\n`; if (triad.synthesis_insight) { response += `**How it integrates**: ${triad.synthesis_insight}\n\n`; } ``. Task 4 (plan line 366): `` triads(g, store, id, limit=3): thesis = lens; for each contrast neighbor (antithesis) find a synthesis node adjacent to both with the highest summed weight; emit {thesis, antithesis, synthesis, contrast_insight}; limit triads. `` — no `synthesis_insight`. Same pattern at `index.js:1216-1218` vs. Task 4 line 367's `progression()` contract, which defines only per-step `insight`.
- **Suggestion:** Add one sentence each to Task 4's `triads()` and `progression()` semantics naming the source of `synthesis_insight` and `overall_insight` (even "static string, not derived from edge data" is an acceptable answer, as `insight` wrapper strings elsewhere in the table appear to be) so `api-local.js` has something to implement against instead of inventing it ad hoc.

## Verdict
The plan's biggest untested seam is not inside any one file but between the files and the mechanism a real session loads them through: Gate A's own acceptance check, as currently worded, verifiably exercises the pre-plan 2.2.5 marketplace snapshot rather than anything Tasks 1–7 build, which would let every other shape bug in this list — the `find_lens_journey` crash chief among them — slip past every gate up through Task 20. The shape mismatches themselves are narrow, mechanical, one-line-each fixes once someone reads both sides of the seam, which is exactly what the plan asks a sonnet-grade executor to do but the smoke tests as specified don't force.
