## Findings

### detect-thinking-gaps-coverage-shape-mismatch
- **Severity:** P1
- **Where:** Task 4 (`frameCoverage(store, exploredNames)`) vs. Task 6's `detectThinkingGaps` row vs. `packages/mcp/index.js:1013-1082` (`detect_thinking_gaps` case, read in full)
- **What:** Task 4 defines `frameCoverage`'s return as `{explored, underexplored, unexplored, total_frames}`, where `explored`/`underexplored`/`unexplored` are **arrays of frame names**. The live `index.js` handler for `detect_thinking_gaps` — unconditional once `results.success` is true, which it always is once `context` is non-empty (the handler already rejects empty context earlier in the same case) — does `Object.keys(cov.explored_frames).length`, then `Object.entries(cov.explored_frames).forEach(([frame, count]) => ...)` (treating `explored_frames` as an **object** keyed by frame name → lens count), and separately does `cov.unexplored_frames.slice(0,10).forEach(frame => ...)` and `cov.underexplored_frames.length` (treating those two as **arrays**), plus reads `cov.coverage_percentage` directly. None of `explored_frames`/`unexplored_frames`/`underexplored_frames`/`coverage_percentage` exist on `frameCoverage()`'s output — the key names don't even match (`explored` vs `explored_frames`), and `coverage_percentage` isn't computed anywhere in Task 4's semantics at all. If `api-local.js`'s `detectThinkingGaps` wraps `frameCoverage()`'s output directly (the only wiring Task 6 describes), `Object.keys(cov.explored_frames)` throws (`cov.explored_frames` is `undefined`) on **every single successful call** — this is the same tool the Must-Haves "Truths" line names by name as one of five tools that "answer with no network access" from a fresh session.
- **Evidence:** `index.js:1024-1030` — `const cov = results.coverage; ... Object.keys(cov.explored_frames).length ...`; Task 4's `frameCoverage` definition in the plan text — `explored`/`underexplored`/`unexplored`/`total_frames`, no `_frames` suffix, no `coverage_percentage`; Task 6's own table entry for `detectThinkingGaps` copies the handler's field names (`explored_frames`, `unexplored_frames`, `underexplored_frames`, `total_frames`, `coverage_percentage`) without reconciling them against what Task 4 actually produces.
- **Suggestion:** Add an explicit adapter step to Task 6 (or fold into Task 4): `api-local.js`'s `detectThinkingGaps` must build `coverage_percentage` (`explored.length/total_frames*100`, rounded) itself, and re-key `frameCoverage()`'s `explored` array into an `explored_frames` object mapping each frame name to its explored-lens count (which `frameCoverage()` as specified doesn't compute either — it only knows a frame *is* explored, not by how many lenses). State this transform once, explicitly, rather than leaving Task 6's table to imply `frameCoverage()`'s output is already the right shape.

### random-provocation-gap-analysis-shape-mismatch
- **Severity:** P1
- **Where:** Task 4 (`frameCoverage`) vs. Task 6's `getRandomProvocation` row vs. `packages/mcp/index.js:951-1006`
- **What:** The live handler reads `gap.coverage.explored`, `gap.coverage.total`, `gap.was_gap_biased`, `gap.suggested_from_frame` off `results.gap_analysis`. `frameCoverage()`'s output has no nested `coverage` key at all (its fields are top-level), no `was_gap_biased` flag, and no `suggested_from_frame` string — none of these three are mentioned anywhere in Task 4's or Task 6's semantics for `getRandomProvocation`, which only says `gap_analysis?: coverage`. Wiring `frameCoverage()`'s output straight into `gap_analysis` makes `gap.coverage.explored` throw (`gap.coverage` is `undefined`) the moment `gap_analysis` is populated — i.e., every `random_lens_provocation` call that passes a `context` argument, since that's the one case Task 6 says `gap_analysis` gets set.
- **Evidence:** `index.js:960-966` — `if (results.gap_analysis) { const gap = results.gap_analysis; ... gap.coverage.explored ... gap.coverage.total ... if (gap.was_gap_biased) { ... gap.suggested_from_frame ... } }`; Task 4's `frameCoverage` semantics (no `coverage` nesting, no bias flag, no suggested-frame field).
- **Suggestion:** Task 6's `getRandomProvocation` row needs to spell out the actual `gap_analysis` shape (`{coverage: {explored: <count>, total: <count>}, was_gap_biased: bool, suggested_from_frame: string}`) as a distinct, hand-built object — not a pass-through of `frameCoverage()` — and state which unexplored frame was picked from and why it counts as "biased."

### missing-insight-narrative-fields
- **Severity:** P2
- **Where:** Task 4 (`triads`, `progression`) vs. Task 6's `getDialecticTriads`/`getLensProgressions` rows vs. `index.js:1155-1230`
- **What:** Task 6 promises `triads: [{antithesis, synthesis, contrast_insight, synthesis_insight}]` for `getDialecticTriads` and `overall_insight` for `getLensProgressions`; `index.js` reads both (`triad.synthesis_insight`, `results.overall_insight`), guarded by `if`. But Task 4's actual semantics for `triads(g, store, id, limit)` only emits `{thesis, antithesis, synthesis, contrast_insight}` — no `synthesis_insight` — and `progression(g, store, startId, targetId, maxSteps)` only emits per-step `{step, lens, insight}` with no aggregate `overall_insight` field anywhere. No task assigns whose job it is to synthesize either narrative string. Because both reads are `if`-guarded, this doesn't crash — the sections silently never render, forever.
- **Evidence:** Task 4 text: `"emit {thesis, antithesis, synthesis, contrast_insight}"` (triads) and `"each step {step, lens, insight} where insight is the edge insight from the previous step or ''"` (progression) — neither mentions the two fields Task 6's table promises callers.
- **Suggestion:** Either drop `synthesis_insight`/`overall_insight` from Task 6's promised shapes (and update the Must-Haves accordingly), or add one line to Task 4 stating how each is derived (e.g., `overall_insight` = the last non-empty step `insight`, or a fixed template sentence) so a sonnet executor doesn't have to invent copy.

### export-count-self-consistency
- **Severity:** P2
- **Where:** Must-Haves "Artifacts" line vs. Task 6 header vs. Task 6's table vs. live `packages/mcp/api-client.js`
- **What:** Verified directly against the repo: `grep -c "^export "  packages/mcp/api-client.js` gives **18** current exports (`getCachedData`, `setCachedData`, `fetchFromAPI`, `searchLenses`, `getLens`, `getLensesByEpisode`, `getRelatedLenses`, `findLensJourney`, `findBridgeLenses`, `findContrastingLenses`, `getCentralLenses`, `getLensNeighborhood`, `getRandomProvocation`, `detectThinkingGaps`, `getDialecticTriads`, `getLensProgressions`, `getAllLenses`, `getFrames`). The Must-Haves line says `api-local.js` exports "the **17** names `index.js` imports today" — off by one against the real file. Task 6's header says "these **18** names" — but the rendered table has 18 *rows*, one of which (`getCachedData(key) / setCachedData(key, data)`) bundles two identifiers, so the table actually names **19** individual functions, and one of those 19 (`getGraph`) is explicitly a **brand-new** export this task adds (per the `lens://graph` resource rewrite), not one of "today's" names at all. Three numbers appear in the same document (17, 18, 19-effective) and none of them is "18 names that exist today plus 1 new one," which is the actual truth.
- **Evidence:** live `grep -n "^export " packages/mcp/api-client.js` → 18 matches; Task 6 table row count = 18; individual identifiers in that table = 19 (including `getGraph`, introduced in the same task's prose: `"both must be rewritten in this task to api.getAllLenses() grouped by episode and api.getGraph()"`).
- **Suggestion:** Fix the Must-Haves line to "18 names `index.js` imports today, plus the new `getGraph`," and have Task 6's header say "19 exports (18 carried over, 1 new)." A sonnet executor grepping for "exported exactly N names" has no single number to check against otherwise.

### degree-enum-not-discoverable
- **Severity:** P2
- **Where:** Task 6 Step 4 vs. live `packages/mcp/index.js:220-225`
- **What:** Task 6 Step 4 says only "add `'degree'` to the `measure` enum of `get_central_lenses` in `index.js`." Verified live: the tool's `description` field currently reads `'Centrality measure (betweenness=bridges, pagerank=importance, eigenvector=influence)'` — an explicit enumeration of exactly the three old measures, with no template or trailing note that would make adding a fourth enum value self-documenting. Task 6 never says to touch this description string, so after the change the JSON-schema `enum` accepts `degree` but the human/agent-readable description a fresh session actually reads still only advertises three measures. Separately, Task 6's own `<verify>` block only smoke-tests `get_central_lenses '{"measure":"pagerank","limit":3}'` — `degree` is exercised only at the lower `graph.test.mjs` unit-test layer (Task 4's test explicitly loops `['pagerank','eigenvector','degree']`), never through the actual MCP tool call path this task rewires.
- **Evidence:** `index.js:223-225` (live): `enum: ['betweenness', 'pagerank', 'eigenvector'], description: 'Centrality measure (betweenness=bridges, pagerank=importance, eigenvector=influence)', default: 'betweenness'`; Task 6 Step 4 text names only the enum edit; Task 6's `<verify>` block's `get_central_lenses` line uses `pagerank`, not `degree`.
- **Suggestion:** Add "and its description string" to Task 6 Step 4's instruction (e.g., `"...degree=connectivity)"`), and add a fifth `<verify>` line calling `get_central_lenses '{"measure":"degree","limit":3}'` through `smoke.mjs` so the new measure is proven reachable end-to-end, not just unit-tested at the graph layer.

## Verdict
The two coverage-shape mismatches (`detectThinkingGaps`, `getRandomProvocation`) are the load-bearing findings here: both trace a full round-trip from a fresh MCP call through `index.js`'s literal field reads back to Task 4's actual `frameCoverage()` semantics, and both show a real crash path on ordinary, expected input — one of them on a tool the plan's own Must-Haves names explicitly. The other three findings are genuine but lower-stakes completeness/consistency gaps a sonnet executor can work around, not crash on.
