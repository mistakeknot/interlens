## Findings

### name-keyed-attribution-degenerates-head-selection
- **Severity:** P0
- **Where:** Task 10 ("`harvest/stats.py` — hit-rates and usage") and Task 12 ("`variant-of`" clustering, cluster-head rule)
- **What:** Task 10's own text is explicit about the join key: *"for each index record, over attribution rows whose `lens == name` (name-level: a lens's findings attribute to its name, which is what the ledger records)... `hit_rate`... `smoothed_hit_rate`..."* — matched by the plain string `name`, not by `id`/`body_hash`. Task 12's `variant-of` clustering unions generated records on **"cosine ≥ VARIANT_MIN_COSINE **or** identical `name`"** — same-name is one of only two clustering triggers, and it is the common one: clustering exists precisely to group repeated rewrites of the same-named `fd-x.md` across repos/machines/time. Task 12's head-selection rule is *"the non-corrupt member with the highest `stats.smoothed_hit_rate` among members having `adjudicated >= 2` (`head_selected_by: "hit_rate"`)."* Since every member of a same-name cluster shares one `name`, and attribution is joined by `name`, every member of that cluster inherits **byte-identical** `findings`/`upheld`/`refuted`/`adjudicated`/`hit_rate`/`smoothed_hit_rate` regardless of which specific rewrite (`body_hash`) actually produced the adjudicated findings. The "highest `smoothed_hit_rate`" comparison is therefore a guaranteed tie across the whole cluster in exactly the case clustering is built for, and the rule silently falls through to `"ties by id"` (arbitrary/lexicographic) — while the record it lands on still gets reported as `head_selected_by: "hit_rate"`, implying real evidence discriminated when none did. Concretely: `fd-authplatform-migration` gets rewritten three times across two machines (three `body_hash` records, one `name`); one melange run adjudicates 40 findings against the name "fd-authplatform-migration"; all three records inherit `hit_rate=0.9`/`adjudicated=40` identically; the cluster head is whichever record id sorts last, with zero relationship to which BODY actually produced the good results. The entire empirical purpose of variant clustering — reward the better-performing rewrite — silently fails for its own core use case, and Task 16's re-render-from-spec reuse path then serves whichever body won the id tie-break as if it were evidence-backed.
- **Evidence:** Task 10 text: `"attribution rows whose lens == name"`; Task 12 text: `"union-find over generated pairs with cosine ≥ VARIANT_MIN_COSINE or identical name"` and `"head = the non-corrupt member with the highest stats.smoothed_hit_rate among members having adjudicated>=2 (head_selected_by: "hit_rate"); ... ties by id"`. Checked the fold table (both melange rounds, 44+14+10 findings) for any prior treatment of the join-key granularity — none of the folded findings (including the closely-related `c-hit-rate-lacks-sample-size` cluster, f-010/f-014/f-021, which only fixed the *lack of Laplace smoothing/sample size*, not the join key) address this.
- **Suggestion:** Change Task 10's attribution join to `body_hash` (or `id`) instead of `name` — a melange run adjudicating findings against a lens by name should attribute those findings to *whichever `body_hash` was actually active in the roster at the time of that run* (Task 8 already records `body_hash` per sighting; the ledger's own run metadata should be enough to disambiguate, or, failing that, attribute generically to the cluster and drop the false-precision `head_selected_by: "hit_rate"` label for ties, reporting `"tie:id"` instead so the report doesn't overclaim.

### incremental-cache-key-garbled
- **Severity:** P1
- **Where:** Task 11 ("`harvest/embed.py`") incremental clause, cross-referenced against the `meta.json` shape defined earlier in the same task
- **What:** Task 11 defines `meta.json`'s `index_sha256` as a **single, whole-index** field (one hash for the entire committed `index.jsonl`, alongside `model`, `dim`, `curated: n`, `generated: n`, etc.). The very next paragraph's incremental clause reads: *"Incremental: keep rows whose id is unchanged (`meta.index_sha256` per id map stored in `<layer>.hashes.json`) so re-runs only embed new records."* Taken literally, this names the **same single whole-index hash field** as something stored **"per id"** in a map — but a whole-index hash cannot function as a per-record staleness key: it changes identically for *every* record the instant *any* record anywhere in the index changes, which would make every record look stale on every run (breaking incrementality entirely) or, if implemented as "store the current whole-index hash once and compare wholesale," would make the skip decision all-or-nothing across the entire layer rather than per-record. Neither reading matches "keep rows whose id is unchanged" or "embeds exactly one text" in Task 11's own test description ("a second run with one new record embeds exactly one text"), which requires genuinely *per-record* granularity. The far more sensible reading — that the hash map is keyed by `body_hash` — is never actually written down; a sonnet executor has to guess the field name to use. And even granting that charitable reading, `thresholds.embedding_text(spec, body)` (Task 8) branches on whether a spec is attached: a record first harvested with no matching `spec_path` (body-fallback embedding text) that later gains a spec file on a subsequent harvest has its actual embedding **input text** change while its `body_hash` (a hash of the body alone, per `normalize_body`) stays fixed — such a record would be skipped by a `body_hash`-keyed incremental map, keeping a stale vector indefinitely and feeding Task 12's cosine clustering and Task 13's `resolveLens` with an embedding that no longer represents the record's current embedding input.
- **Evidence:** Task 11 text, `meta.json` shape: `"index_sha256"` listed once as a whole-file field; incremental clause: `"keep rows whose id is unchanged (meta.index_sha256 per id map stored in <layer>.hashes.json)"`; Task 8's `embedding_text(spec, body)`: `"if spec: ... else: [body-derived heads]"` — spec-presence is a hard branch on the input text, decoupled from `body_hash`.
- **Suggestion:** State explicitly: `<layer>.hashes.json` is `{id: body_hash}` (or, better, `{id: sha256(embedding_text)}` so a spec attaching later is correctly detected as a change) written after each embed run; drop the confusing `meta.index_sha256` reference from the incremental clause entirely (keep `index_sha256` as the whole-index freshness stamp it's defined to be, used only for the `--check` command, not for per-record skip logic).

### malformed-jsonl-handling-unspecified
- **Severity:** P1
- **Where:** Task 9 (`merge.py` semantics) vs. Task 8's own `<verify>` block, Task 14 Step 1, and Task 22's `harvest-and-push.sh`
- **What:** Task 9's accretive-merge text never states how a truncated or malformed trailing line in `data/harvest/<machine>.jsonl` is handled — loud parse failure vs. a `filter(Boolean)`-style silent skip. `data/harvest/<machine>.jsonl` is fully rewritten (not appended) by every `scan` run per Task 8 ("Output: `data/harvest/<machine>.jsonl` — rows... sorted by `(kind, repo, name, path)`"), so an interrupted `scan` (Ctrl-C, OOM, closed terminal) can leave this file truncated mid-write with no documented atomic-write-then-rename guarantee. The one safety net the plan does specify — `harvest-and-push.sh`'s `trap '... git checkout -q -- data && git clean -fdq data ...' EXIT` (Task 22) — only fires for invocations that go **through that wrapper**, and only on exits the trap can catch (not `SIGKILL`/hard crash). But the plan's own text runs `harvest scan` **bare**, unwrapped, in two places: Task 8's `<verify>` block (`python3 -m harvest scan --machine clavain --roots ~/projects --dry-run | tail -1`) and Task 14 Step 1 (`python3 -m harvest scan --machine clavain --roots ~/projects`) — neither routed through `harvest-and-push.sh`. If either of these bare invocations is interrupted mid-write and the resulting truncated `data/harvest/clavain.jsonl` is not noticed before the next `merge` (whether run immediately after, or by a later session), `merge.py`'s undocumented parse behavior decides whether this fails loudly (safe) or silently drops the tail of that machine's sightings — which is precisely the loss the accretive design (`accessioned_at` never changes, "nothing removed except by explicit prune") exists to prevent.
- **Evidence:** Task 9 text has no parse-failure clause; Task 8 `<verify>` line 2 (`python3 -m harvest scan --machine clavain ...`, bare); Task 14 Step 1 (`python3 -m harvest scan --machine clavain --roots ~/projects`, bare, no wrapper); Task 22's trap (`trap '...git checkout -q -- data...' EXIT`) is defined only inside `harvest-and-push.sh`.
- **Suggestion:** Have `merge.py` fail loudly (raise, non-zero exit) on any line that doesn't parse as JSON rather than silently filtering it — matching the plan's existing "unreadable paths reported separately from empty ones" discipline (Prior Learnings). Separately, either route Task 8's `<verify>` and Task 14 Step 1 through `harvest-and-push.sh` (dropping `--dry-run`'s value if incompatible) or have `scan.py` itself write via a temp-file-then-rename so a bare invocation can never leave a torn file at the real path.

### audit-checklist-misses-duplication
- **Severity:** P1
- **Where:** Task 12, `python3 -m harvest audit` checklist
- **What:** The stated checklist is: *"every index record has a body file and an embedding row; any body file or embedding row without an index record is an error (an orphan means a record was lost); `on_disk: false` records are expected, never errors; every edge endpoint exists; every cluster has exactly one head; `meta.hash_recipe == HASH_RECIPE`; exit 1 on any mismatch."* Walking this against the two failure modes the review goal names by name — "can a record be lost or duplicated across the two machines' harvest files": the **lost** case is reasonably well covered, because `scan.py` writes body files at `data/generated/lenses/<id>.md` independently of `merge.py` (per Task 8), so a `merge.py` bug that fails to carry a hash forward into `index.jsonl` would surface as an orphan body file under the existing "any body file... without an index record is an error" rule. The **duplicated** case has no corresponding check at all: nothing in the checklist asserts that a given `body_hash` appears in exactly one `index.jsonl` row. A merge bug that produced two separate index records for one `body_hash` (e.g. an accidental extra field folded into the grouping key) would pass every listed check — both records would still each have a body file and an embedding row, `on_disk` would be legitimately true for both, edges would resolve fine, and "one head per cluster" doesn't apply to two records that were never even seen as duplicates of each other in the first place.
- **Evidence:** Task 12's full audit checklist (quoted above, verbatim from the plan) contains five checks; none of them is a uniqueness assertion over `body_hash` (or `id`) across `index.jsonl`.
- **Suggestion:** Add one line to the audit checklist: "no two `index.jsonl` rows share a `body_hash`" (equivalently, since `id = f"gen:{name}@{body_hash[:8]}"`, this reduces to an `id`-uniqueness check, which is nearly free to add alongside the existing "every cluster has exactly one head" pass).

## Verdict
The name-keyed attribution finding is the one that matters most: it is fully verified against the plan's current Task 10/Task 12 text (not the seed hypothesis alone), it silently defeats variant clustering's entire empirical purpose for the exact case clustering targets, and none of the two folded review rounds' 44+14+10 findings touch the join-key granularity — only the separate (and now-fixed) lack of sample-size weighting. The other three findings are concrete, traceable gaps in the merge/embed/audit trio that a sonnet executor cannot resolve from the text as written.
