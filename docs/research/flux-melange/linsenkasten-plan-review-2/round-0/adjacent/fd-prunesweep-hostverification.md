## Findings

### precondition-4-whole-sweep-refusal
- **Severity:** P0
- **Where:** Task 23, precondition (4), contrasted with precondition (5) in the same list
- **What:** Precondition (4) reads: *"the newest `fd-*.md` mtime in **every target** is older than `data/harvest/<machine>.jsonl`'s timestamp ('re-harvest first')."* The preconditions block is introduced as *"Preconditions, all machine-checked, **any failure refuses the whole run** with the reason printed."* Precondition (5), immediately below it, gets an explicit carve-out the others don't: *"a repo failing (5) is skipped and listed, not pruned."* No equivalent carve-out exists for (4) — by the "every target" phrasing and the absence of a stated per-repo fallback, a single `fd-*.md` anywhere across the 48-repo corpus with a newer mtime than that machine's harvest timestamp appears to refuse the **entire** sweep, not just skip that one repo. Verified live, read-only, over `ssh -o BatchMode=yes zklw`: the `interlens` repo itself (`~/projects/Sylveste/interverse/interlens`) carries a `.git-autosync` marker on zklw — i.e., it is one of this workspace's repos subject to routine, automated `git-autosync-repair.sh` (daily) and `git-autosync-promote.timer` (hourly) sync per this session's own operating context, both of which perform git operations (pull/merge/fast-forward) that reset the mtime of any file whose content changes at that moment to wall-clock time, independent of the file's actual edit history. A live scan of the Mac side alone (`find ~/projects -path "*/.claude/agents/fd-*.md" -not -path "*worktrees*"`) returned **3,055 files across 43 distinct repos** right now — already exceeding the plan's own "~2,900 files, 48 repos" estimate before zklw's files are even added. At that scale, with routine background sync active across dozens of repos, the odds that precondition (4) is satisfied simultaneously across every one of 48 repos at the moment a human wants to run `--apply` are low, and the plan gives no override flag, no "skip this repo and continue" path, and no guidance for what an operator or a sonnet executor should do when the sweep refuses for this reason on a normal day.
- **Evidence:** Live ssh: `test -f .git-autosync` on `~/projects/Sylveste/interverse/interlens` on zklw → `HAS .git-autosync marker` (checked read-only, no modification). Live Mac-side count: `find ~/projects -maxdepth 6 -path "*/.claude/agents/fd-*.md" -not -path "*/.claude/worktrees/*" | wc -l` → `3055`; distinct repo roots → `43`. Plan text for precondition (4) vs. (5)'s explicit skip-and-continue language, quoted above verbatim.
- **Suggestion:** Either (a) state explicitly that precondition (4) is checked and enforced **per target repo** with the same skip-and-list behavior as (5) (i.e., a stale-mtime repo is excluded from `--apply` for this run and listed under `kept: stale harvest`, not a whole-sweep refusal), or (b) if a whole-sweep refusal really is intended, add an explicit `--force-repo <path>` escape hatch and a documented "re-run `harvest scan` immediately before `--apply`" step so the window between harvest and prune is minimized, and note in the report exactly which repo's mtime tripped the gate so a human doesn't have to bisect 48 repos to find it.

### task1-landing-gate-stale-live
- **Severity:** P1
- **Where:** Task 1, Step 1 ("Confirm branch and landing order")
- **What:** Task 1 Step 1 instructs the executor to run `git log --oneline main..sweep/2026-09-02 | wc -l` and states: *"Expected: branch `feat/linsenkasten`; the sweep count is `4` until the sibling session lands it."* Re-running this exact command live, in this session, from the worktree: **the count is 5, not 4.** This is a direct demonstration of the failure mode this lens exists to catch — a "checked live on \<date\>" value that has already drifted by the time a fresh session re-verifies it, because the sibling session's `sweep/2026-09-02` branch gained a commit between plan-authoring time and now. The plan gives a hard, specific number ("4") formatted exactly like every other "Expected: ..." assertion in the document (which the plan's own header claims are all "machine-checkable"), but the actual gating logic later in the same step only cares about the count reaching `0` ("**When it prints 0**, run `git rebase main`..."). Nothing in the text tells a sonnet-grade executor whether landing on "5" instead of "4" is a harmless drift to ignore, or a signal that something is wrong and the run should pause. This is the very first live-state check in the entire plan, gating everything in Stage D/E behind it.
- **Evidence:** Live command run in this session: `git -C /Users/sma/projects/.worktrees/interlens-linsenkasten log --oneline main..sweep/2026-09-02 | wc -l` → `5`. Plan text: `"the sweep count is 4 until the sibling session lands it"`.
- **Suggestion:** Drop the specific "4" from the Expected line entirely (it's a snapshot, not an invariant) and state only the actual gate: "print the count; the only value that matters is `0`, meaning the sibling session's `sweep/2026-09-02` branch has landed — any nonzero count means keep waiting, regardless of the exact number."

### preconditions-not-rechecked-mid-sweep
- **Severity:** P1
- **Where:** Task 23, preconditions (1)-(3) vs. the per-repo loop body
- **What:** Preconditions (1) "the registry checkout is clean," (2) "the registry state the prune cites is pushed" (`HEAD == origin/main`), and (3) "`python3 -m harvest audit` exits 0" are evaluated as a single up-front gate before the sweep starts — nothing in Task 23's text re-checks any of them partway through. But the per-repo body of the same task does real, sequential, potentially slow work across up to 48 repos: for each one, compute hashes, `git rm`/`rm`, commit, and — explicitly — *"Push each prune commit **before moving to the next repo** (a deletion that exists only locally is the split-brain the review warned about)."* That's up to 48 sequential network pushes. Precondition (2)'s guarantee — "so no machine can be pruning against an index the other has never seen" — is a snapshot taken once, at the start. If zklw's `linsenkasten-harvest.timer` (Task 22, `OnCalendar=*-*-* 04:30:00`) fires and lands new commits on `origin/main` partway through a long-running Mac sweep, or if `git-autosync-promote.timer` (hourly, per this workspace's own infrastructure) fast-forwards `main` mid-run, precondition (2)'s "pushed and seen" guarantee is silently invalidated for every repo processed *after* that point in the same run — with no detection, since nothing re-checks `git rev-parse HEAD` against `origin/main` again after repo #1.
- **Evidence:** Task 23 preconditions block (checked once, "any failure refuses the whole run"); per-repo loop text ("for each target: ... Push each prune commit before moving to the next repo"); Task 22's `linsenkasten-harvest.timer` schedule (`OnCalendar=*-*-* 04:30:00`, `Persistent=true`).
- **Suggestion:** Re-run preconditions (2) and (3) — the two that can change from outside the prune process itself — once per repo (or once per N repos) inside the loop, aborting the *remainder* of the sweep (not undoing what already landed) the moment either one no longer holds, and note the last-verified commit SHA per repo in the report rather than only once in the header.

### untracked-deletion-report-gap
- **Severity:** P2
- **Where:** Task 23, candidate filter + deletion branch + report shape
- **What:** Corrected finding: the candidate filter requires *"a clean `git status --porcelain` for paths **outside** `.claude/`"* — meaning an untracked `.claude/agents/fd-x.md` in an otherwise-clean repo does pass the candidate filter, and the deletion step does branch `rm` for untracked files, `git rm -q` for tracked ones. However, checked carefully against the actual deletion rule — *"for every `.claude/agents/fd-*.md`, compute `body_hash`; **if the hash is not in the index → keep** and list under `kept: not in registry`; **else delete**"** — a file is only ever a delete candidate once its `body_hash` is *already present in the index*, which by construction means its content has already been captured by a harvest (this machine's or the other's) and persisted at `data/generated/lenses/<id>.md` **before** deletion is even considered. So the intuitive "an untracked file created after the last harvest gets silently, unrecoverably lost" scenario does **not** actually reproduce: such a file's hash wouldn't be in the index yet, so it would be kept and reported, not deleted. The real, narrower gap is auditability, not data loss: for a file deleted via the bare-`rm` branch (untracked), there is no `git rm`/commit in that repo at all, so the sweep report's `path | registry id | action | commit` table has no defined value for the `commit` column on that row — Task 23 never says what goes there (blank? "untracked"? the *central* linsenkasten repo's own harvest commit SHA, which would be misleading since it names a different repo?). A human auditing the report to decide "which of these deletions can I `git revert` in the source repo" can't distinguish a tracked, revertable row from an untracked, no-git-record one without re-deriving it from the raw filenames.
- **Evidence:** Task 23 deletion rule, quoted above verbatim (`if the hash is not in the index → keep`); report shape `data | registry id | action | commit` with no stated untracked-row convention.
- **Suggestion:** Have the report's `commit` column print `(untracked, no repo history)` explicitly for `rm`-branch rows, so a reader never has to guess whether a given deletion is git-revertable in its source repo.

## Verdict
The precondition-(4) whole-sweep-refusal finding is grounded in live, read-only verification of this exact repo's autosync status on zklw plus a real file/repo count on the Mac, and it names a concrete, near-certain operational failure at the stated real-corpus scale with no documented recovery path. The Task 1 staleness catch is a direct, reproducible demonstration (not a hypothetical) of the class of risk this lens exists to find. The untracked-file finding required correcting the seed hypothesis's own premise against the actual deletion rule — the real gap is narrower (an audit-trail hole, not data loss) than first suspected.
