## Task Context

The ontology must serve dual purpose: (1) development planning — tracking ~555 DF features mapped to ER equivalents, with implementation status, dependencies, and sprint assignment; (2) in-game simulation — 40+ ECS components, entity types (Elf, Building, Composition, Revel, etc.), and procedural relationships. Existing infrastructure includes hecs ECS in Rust, RON data files, beads issue tracker (Dolt/SQLite), and markdown brainstorms. The ontology must be version-controlled and queryable by both humans and code.

### 5. Evaluate whether the ontology schema supports provenance ...

## Severity Calibration

- **P0**: The planning ontology and runtime ontology share a class 'Elf' with contradictory identity semantics — planning uses it as a role archetype, runtime uses it as an instantiated entity with a hecs EntityId
  - When: No separation between type-level ontology (what kinds of things exist) and instance-level ontology (specific game entities), causing queries across both layers to produce nonsense intersections
- **P1**: DF 'creature:elf' maps to multiple ER entity types (Elf, Curator, PerformingElf) but the ontology represents this as subclassing, causing feature coverage audits to double-count features that apply to all subtypes
  - When: IS-A used where HAS-ROLE or ASPECT-OF is semantically correct, collapsing a many-to-many mapping into a strict hierarchy
- **P2**: Refactoring a DF feature slug (e.g., 'mood:happy' renamed 'mood:joyful') breaks all audit records and historical queries because IRIs were constructed from mutable labels
  - When: No stable numeric or UUID-based identifier layer beneath human-readable labels

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Prioritize findings where (a) entity types collapse distinct concepts (e.g., a DF 'creature' maps to multiple ER entity types that should be separate classes), (b) relationship cardinalities are underspecified and will become ambiguous when populated, or (c) the planning-layer ontology (feature matrix, audit tracking) and the runtime-layer ontology (ECS components, simulation queries) are trying to share classes but have incompatible identity semantics. A class with dual-purpose semantics (used both as a feature-backlog item and as a runtime entity type) is P1. An ontology with no version scheme is P2.
