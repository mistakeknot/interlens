## Task Context

Elf Revel native full-screen Rust colony sim evaluating 6 rendering stack options. Option A is porting shadow-work's proven Bevy 0.18 rendering-only crate (sw-renderer) including SimStateProvider trait bridge and bevy_metalfx. Elf Revel uses hecs ECS for simulation, needs ASCII-aesthetic multi-layer glyph grid rendering at 100K+ glyphs/60fps. WASM is a secondary target.

## Review Approach

### 1. SimStateProvider trait portability audit: shadow

- SimStateProvider trait portability audit: shadow-work's trait exposes pressure_values(), country_count(), pressure_type_count() — none of these map to Elf Revel's colony grid (tile data, glyph layers, entity positions, flora state); evaluate whether the trait must be redesigned or can be extended with a second trait (ColonyStateProvider) without breaking shadow-work

### 2. Cargo workspace version lock risk: if Elf Revel

- Cargo workspace version lock risk: if Elf Revel and shadow-work share sw-renderer as a path dependency or git dependency, any Bevy 0.18 patch update must be coordinated across both projects; assess whether Bevy 0.18 API surface in sw-renderer is large enough to create a maintenance burden when Bevy releases a patch

### 3. Bevy_metalfx portability: the MetalFX upscaling crate tar...

- bevy_metalfx portability: the MetalFX upscaling crate targets macOS 13+ via objc2-metal-fx FFI; verify this constraint is explicitly documented and that the WASM build path disables it cleanly via Cargo features rather than cfg blocks scattered through rendering code

### 4. Plugin system coupling: sw

- Plugin system coupling: sw-renderer likely registers Bevy plugins that assume a 3D globe scene (GlobePlugin, OrbitCameraPlugin, HeatmapPlugin); does porting to Elf Revel require either stripping these or maintaining a hollow stub, and what is the binary size cost of unused Bevy plugin infrastructure?

### 5. Benchmark harness reusability: shadow

- Benchmark harness reusability: shadow-work has a proven benchmark harness for renderer performance; verify it can be pointed at a 2D glyph-grid workload (100K glyphs, instanced sprite rendering) without architectural changes, or document what must change

### 6. ECS isolation guarantee: the key promise of the trait bri...

- ECS isolation guarantee: the key promise of the trait bridge pattern is that Bevy's ECS never sees hecs entities and vice versa; verify no accidental coupling exists where hecs entity IDs are passed as Bevy component data or where Bevy schedules fire hecs queries

## Severity Calibration

- **P0**: Porting sw-renderer as a workspace dependency causes a Bevy version conflict because Elf Revel's direct dependencies (bevy_ecs, bevy_render pulled transitively) resolve to a different Bevy 0.18.x patch than sw-renderer expects, producing duplicate type registrations and a linker error
  - When: Cargo.toml does not pin Bevy to an exact version across the workspace; patch versions differ between sw-renderer and Elf Revel dependencies
- **P1**: The SimStateProvider trait cannot express the data Elf Revel's renderer needs (per-tile glyph character, foreground color, background color, entity layer, flora lifecycle stage) without adding 8 new trait methods, invalidating the 'proven' claim and requiring as much design work as a fresh build
  - When: SimStateProvider was designed for scalar pressure heatmap data, not structured per-cell grid data; the impedance mismatch forces a new trait that shares only the name with shadow-work's version
- **P2**: The MetalFX WASM exclusion is handled by a #[cfg(not(target_arch = "wasm32"))] block inside the renderer plugin's build() method, causing the WASM build to silently skip upscaling without a compile-time error when MetalFX-dependent code paths are accidentally reached
  - When: No Cargo feature flag for metalfx; platform exclusion is runtime cfg rather than compile-time feature gating

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
