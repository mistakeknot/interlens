## Severity Calibration

- **P1**: Agent reasoning is surfaced at full technical resolution by default for all participants
  - When: If Ryan sees raw agent output — token counts, model IDs, governance snapshot refs, CRDT operation logs — the system has failed the translation requirement. The front-of-house principle is that the kitchen's complexity is the kitchen's problem; the guest experiences the result. Ryan should see 'Editorial agent revised the introduction to reduce passive voice' not a diff with CRDT metadata.
- **P2**: Rejecting a proposal requires a rationale or triggers a follow-up flow
  - When: If declining a proposal requires selecting a rejection reason, confirming the decline, or results in an agent re-engaging with questions, Ryan experiences rejection as work rather than decision. In fine dining, a guest can decline a dish without explaining why — the system should accept a simple 'no' without interrogation.
- **P2**: Governance vocabulary uses technical terms without translation for non-technical participants
  - When: Terms like 'direction', 'merge', 'proposal', 'governance event', 'ceremony', 'cooling period' are the platform's vocabulary, not Ryan's. If these terms appear untranslated in the annotation interface, Ryan is being asked to learn the kitchen's terminology to order his meal — a service failure. The interface should present these concepts in the vocabulary of editorial review, not system architecture.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Every disclosure decision is evaluated by asking: does this information serve the guest's enjoyment at this moment, or is it being provided for the kitchen's convenience? Expert knowledge should arrive precisely when it is useful, not when it is available. The guest should never feel managed. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
