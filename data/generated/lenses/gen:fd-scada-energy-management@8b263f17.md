## Task Context

Brainstorm for interop — a Go-based unified integration daemon replacing interkasten, bridging Notion, GitHub, beads, and local FS through goroutine-isolated adapters with an event bus hub, webhook-first sync, and three-way merge conflict resolution

## Review Approach

### 1. Per-subsystem isolation and the cascading failure boundary: EMS systems

- Per-subsystem isolation and the cascading failure boundary: EMS systems partition metering, state estimation, and contingency analysis into isolated subsystems that can fail independently without cascading — assess whether interop goroutine pool isolation actually prevents a panicking Notion adapter from affecting GitHub adapter throughput, specifically whether shared resources (the event bus channel, the HTTP server, shared caches) create hidden coupling that makes isolation weaker than the architecture diagram suggests

### 2. Alarm management and the silent failure problem: SCADA operators cannot watch

- Alarm management and the silent failure problem: SCADA operators cannot watch every subsystem constantly — alarm management systems filter, prioritize, and escalate abnormal states — check whether interop exposes adapter health as structured operational alarms (adapter down, event lag, error rate spike) that can be consumed by a monitoring system (Prometheus, structured logs), or whether failures are only visible in raw Go logs that require manual inspection

### 3. Degraded-mode operation contracts: when a transmission line trips

- Degraded-mode operation contracts: when a transmission line trips, the EMS switches to degraded-mode state estimation using the remaining metering — check whether interop defines degraded-mode contracts for each adapter: if the Notion adapter is down, does beads to GitHub sync continue normally? If GitHub webhooks are unavailable, does the local FS adapter still process file changes? The contracts should be explicit in the design, not emergent from goroutine scheduling

### 4. Circuit breaker calibration and the nuisance trip problem: SCADA protection

- Circuit breaker calibration and the nuisance trip problem: SCADA protection engineers calibrate protective relays carefully to avoid nuisance trips (false positives that isolate healthy equipment) — check whether interop circuit breaker thresholds are configurable per adapter (a slow Notion API during rate limiting should not trip the breaker the same way a crashed adapter would), and whether the breaker reset strategy (automatic after backoff, or manual operator reset) is appropriate for an unattended daemon

### 5. Startup sequencing and the cold-start problem: EMS systems have strict startup

- Startup sequencing and the cold-start problem: EMS systems have strict startup sequences — metering must be healthy before state estimation runs, state estimation must converge before AGC activates — assess whether interop daemon has an explicit startup sequence that gates adapter activation on dependency readiness (webhook receiver healthy before accepting inbound events, beads adapter connected before routing bead-related events), or whether adapters race to start independently and the hub processes events against partially initialized state

### 6. Historian and the event log as operational record: SCADA historians record

- Historian and the event log as operational record: SCADA historians record every telemetry point with timestamps for post-incident analysis — assess whether interop maintains a durable, queryable event log (separate from adapter logs) that records every event received, routed, and applied with sufficient metadata to reconstruct what happened during a sync conflict or missed update, and whether this log is the authoritative source for reflect and audit queries

## Severity Calibration

- **P0**: The Notion adapter goroutine panics mid-write during a bulk sync; the panic recovery restarts the goroutine but does not flush the adapter in-flight event queue; events that were dequeued from the bus before the panic are lost (the bus considers them delivered), and the Notion adapter restarts with a stale cursor, replaying already-applied events and creating duplicate beads updates
  - When: When panic recovery restarts the adapter goroutine without atomic in-flight event accounting — events dequeued from the bus before the panic are lost if the adapter crashes before writing the acknowledgment
- **P1**: All four adapters share a single HTTP client for outbound API calls; when GitHub rate-limits the daemon (HTTP 429), the HTTP client connection pool is exhausted waiting for retry backoff; Notion API calls queue behind the exhausted pool; local FS events cannot be written back to Notion even though the Notion API is healthy, because the shared client is saturated by GitHub retries
  - When: When adapters share transport-layer resources (HTTP clients, connection pools, TLS sessions) that are not partitioned per adapter, allowing one adapter traffic to starve another outbound capacity
- **P2**: The daemon is deployed without readiness and liveness probes; Docker Compose restarts the container on crash but has no visibility into adapter health; the GitHub adapter is in a crash-loop due to a bad webhook secret, the container stays running (the main goroutine is alive), Docker marks the service healthy, and GitHub webhooks are silently discarded for hours until a developer notices missing bead updates
  - When: When the daemon health endpoint reflects only process liveness and not adapter operational health, making the container appear healthy to orchestration tools while individual adapters are failing

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
