## Task Context

Brainstorm for interop — a Go-based unified integration daemon replacing interkasten, bridging Notion, GitHub, beads, and local FS through goroutine-isolated adapters with an event bus hub, webhook-first sync, and three-way merge conflict resolution

## Review Approach

### 1. Master data authority hierarchy and the conflict resolution order: supply chain

- Master data authority hierarchy and the conflict resolution order: supply chain control towers designate a system of record for each data domain (the ERP owns SKU master data, the WMS owns location master data, the TMS owns shipment status) — assess whether interop conflict resolution strategy defines per-entity-type authority hierarchies (beads is authoritative for work item status, GitHub is authoritative for PR merge state, Notion is authoritative for page content) and whether the three-way merge falls back to this hierarchy when automated merge fails, or whether all adapters are treated as co-equal authorities producing non-deterministic resolution

### 2. Golden record maintenance and the duplicate entity problem: control towers

- Golden record maintenance and the duplicate entity problem: control towers maintain a golden record for each master data entity that reconciles versions across all connected systems — check whether interop maintains an equivalent golden record for cross-system entities (a beads bead linked to a GitHub issue linked to a Notion page) and whether the golden record is updated atomically when any system modifies the entity, or whether the three systems can hold divergent versions of the same logical entity between sync cycles

### 3. EDI transaction semantics and the acknowledgment chain: supply chain EDI (X12

- EDI transaction semantics and the acknowledgment chain: supply chain EDI (X12, EDIFACT) uses functional acknowledgments to confirm receipt and semantic acceptance of each transaction — assess whether interop event delivery model includes an acknowledgment chain that distinguishes between event received by adapter and event applied to external system successfully, and whether failed applications trigger an explicit compensating event or are silently retried until the external system accepts them

### 4. Inventory snapshot reconciliation and the full sync fallback: control towers

- Inventory snapshot reconciliation and the full sync fallback: control towers run periodic full-inventory reconciliation snapshots to detect drift between real-time event streams — check whether interop has a full-sync reconciliation mode that can detect entities that have drifted out of sync (a bead modified directly in the beads DB without going through the adapter event path) and bring them back into alignment, and whether this reconciliation is scheduled or only triggered manually

### 5. Cross-party version conflict and the business rule layer: in supply chains

- Cross-party version conflict and the business rule layer: in supply chains, a warehouse may reject an inventory update from the ERP because it violates a physical constraint (quantity would go negative) — check whether interop adapters can apply business-rule validation before writing an event to an external system and reject the write with a structured error that the hub can route to a dead-letter queue or operator review, rather than propagating an invalid state

### 6. Visibility latency and the in-transit state: supply chain visibility platforms

- Visibility latency and the in-transit state: supply chain visibility platforms model entities in an explicit in-transit state (the shipment has left the origin but not arrived at the destination) — assess whether interop event model includes an explicit in-flight state for cross-adapter operations: a beads update triggered by a GitHub webhook is in-flight from the moment the webhook arrives until the beads write is confirmed, and during that window the entity state is ambiguous — whether this ambiguity is surfaced to the MCP layer or hidden

## Severity Calibration

- **P0**: A beads bead is closed manually via the bd CLI at the same moment a GitHub issue is closed via the GitHub API; both events arrive at the interop hub within the same sync window; the three-way merge resolves both as closed with no conflict (both edits agree on the final state), but the merge writes back the GitHub closure reason to beads and the beads closure notes to GitHub, overwriting content that was intentionally different in each system
  - When: When the three-way merge algorithm treats same-state convergence as conflict-free and does not check whether the associated content fields are also identical, allowing field-level overwrite even when the top-level state merge succeeds
- **P1**: A Notion database is the authoritative source for a set of project pages; an operator manually updates 15 pages in Notion during a maintenance window; interop Notion adapter is offline during the window; when the adapter reconnects, it replays its last cursor position rather than running a full reconciliation, missing the 15 manual updates; the local FS copies of those pages remain stale indefinitely with no operator alert
  - When: When adapter reconnection restores event streaming from the last cursor without checking whether manual changes were made to external systems during the offline window, and when there is no scheduled reconciliation to catch drift
- **P2**: The GitHub adapter applies a webhook event that creates a new GitHub issue for a newly created beads bead; GitHub API is slow and responds after 3 seconds; the Notion adapter, operating concurrently, also creates a Notion page for the same beads bead (as per the configured mapping); both writes succeed, but neither adapter records the other external ID, so the bead has a GitHub issue ID in beads but no Notion page ID, and future cross-system events for this entity cannot be correlated
  - When: When parallel adapter writes for the same entity are not coordinated to collect and store all created external IDs before the entity golden record is finalized

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
