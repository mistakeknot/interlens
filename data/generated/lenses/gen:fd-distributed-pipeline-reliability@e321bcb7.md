- Rate limit heterogeneity: Paid OpenAI and OpenRouter free-tier have radically different rate limits (tokens/min, requests/min, concurrent requests). Does the pipeline implement per-provider rate limiting, or does it apply a single global throttle? A single throttle calibrated for the free tier wastes paid API capacity; calibrated for paid API it burns through free tier quota.

- Reasoning model content=None handling: Models that return content=None with the answer in reasoning_details require special extraction logic. What happens when a non-reasoning model returns content=None due to a content filter or error -- does the pipeline correctly classify this as an error rather than a reasoning model response, or does it silently drop the dilemma?

### 5. Streaming JSONL consistency: If the pipeline is aborted mid-write to the JSONL

- Streaming JSONL consistency: If the pipeline is aborted mid-write to the JSONL file (power loss, OOM kill, SIGKILL), partial JSON records can corrupt the file. Does the resume logic validate JSONL integrity before treating existing records as complete, or does it rely on line-count heuristics that pass with a truncated last record?

- Cross-provider output schema normalization: 12 models from 3+ provider APIs will return lens selections in provider-specific response structures. ## Decision Lens

A pipeline is only as reliable as its failure envelope is explicit. Evaluates every design decision against: what happens when this component fails mid-run, does the resume path replay correctly, and is the output corpus internally consistent after a partial failure and resume? Pays special attention to the difference between idempotent failures (safe to retry) and non-idempotent failures (produce duplicate or corrupt output on retry). If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
