## Task Context

interop is a long-running daemon on zklw where each adapter (GitHub, Notion, Beads, local FS) runs in its own goroutine pool. The architecture bet is that goroutine isolation prevents a crashing adapter from affecting others. This bet only holds if panic recovery, context propagation, channel backpressure, and circuit breaker scoping are all implemented correctly. A single missing recover() or a shared backpressure resource defeats the entire isolation model.

- Check that the central event bus uses buffered channels with explicit capacity limits and that producers implement non-blocking sends with drop-or-backpressure semantics -- an unbounded or full channel that blocks the GitHub webhook handler because the Notion adapter is slow is a cross-adapter coupling bug

- Confirm that adapter Start() and Stop() methods respect a passed context.Context and that Stop() drains in-flight events before returning -- a daemon that loses events on SIGTERM because goroutines are killed mid-dispatch violates the webhook-first reliability guarantee

- Validate that circuit breakers are per-adapter and not shared -- a shared circuit breaker that opens on Beads failures and then rejects GitHub webhook events is a cascade failure, not isolation

- Check that goroutine counts are bounded and measurable -- an adapter that spawns one goroutine per incoming event without a worker pool cap will exhaust file descriptors under a webhook burst, causing daemon-wide failures unrelated to the triggering adapter

- Ensure that the event bus distinguishes between slow-consumer backpressure (adapter overwhelmed but healthy) and dead-consumer (adapter goroutine has exited) -- treating them the same causes events to pile up against a dead consumer indefinitely

## Severity Calibration

- **P0**: A nil pointer dereference in the Notion adapter's block-to-markdown converter panics an adapter goroutine with no recover() wrapper, propagating to the Go runtime and killing the entire interop daemon, taking GitHub and Beads sync offline
  - When: When adapter goroutine pool workers do not wrap their execution loop in a deferred recover(), which is the default Go behavior -- panics are not caught unless explicitly recovered
- **P1**: The event bus channel fills because the local FS adapter is slow to process a directory rename, blocking the GitHub webhook handler goroutine from emitting its event -- webhooks pile up at Caddy, timeouts fire, and GitHub marks the webhook endpoint as unhealthy and disables delivery
  - When: When the event bus uses a synchronous send (ch <- event) rather than a select with a default drop or a per-adapter output channel with independent backpressure
- **P2**: The Beads adapter circuit breaker opens during a Dolt server restart, and because the circuit breaker state is shared, the GitHub adapter also starts rejecting events until the circuit resets -- Beads downtime causes GitHub sync to silently stop
  - When: When circuit breaker state is stored in a global or shared variable rather than in a per-adapter struct

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Correctness under partial failure is non-negotiable -- a panicking Notion adapter that takes down the GitHub adapter is a P0 even if Notion is down 0.1% of the time. Evaluates every concurrency design against: does a single adapter failure stay contained, and does the hub make forward progress when one pool is saturated? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

- P0: Issues that block other work, cause data loss or corruption — drop everything

- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
