## Task Context

Hassease runs headless on a server as a long-lived Go daemon receiving code instructions over Signal. It imports Skaffen's internal packages (agent loop, tool registry, session persistence). The operator interacts exclusively through Signal messages — there is no local terminal for manual intervention. This makes daemon robustness a safety property: a stuck or zombie daemon silently blocks all code execution without any visible error to the operator.

## Severity Calibration

- **P0**: SIGTERM during an active approval flow causes the daemon to exit immediately, leaving the builder's Signal thread in a waiting state with no recovery — the next restart has no record of the abandoned task.
  - When: No graceful drain on shutdown, no JSONL checkpoint before exit, no restart recovery path.
- **P1**: Goroutines spawned per agent loop turn accumulate when LLM provider calls hang at their default 30s timeout — after 100 sessions, the process holds thousands of zombie goroutines and begins OOM-killing itself.
  - When: No per-turn context deadline, no goroutine lifecycle bounded to turn scope, no errgroup parent that cancels children on turn completion.
- **P2**: Double-instantiation: operator restarts the daemon while a previous instance is still draining. Both instances hold the Signal connection, causing approval messages to be consumed by whichever instance wins the race.
  - When: No PID lockfile, no instance election, no Signal session locking.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

A daemon is only as reliable as its shutdown path. Every goroutine must have a clear owner; every blocking call must respect context cancellation; every restart must leave no orphaned child processes. Evaluates Hassease as if it will run unattended for 30 days on a server the operator cannot SSH into — because that is what a Signal-native headless daemon implies. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
