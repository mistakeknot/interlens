## Review Approach

### 1. Orthogonal classification axes: Burgundy classifies the s...

- Orthogonal classification axes: Burgundy classifies the same vineyard parcel by geography (hierarchical), by quality (tiered), by grape regulation (categorical), and by production rules (quantitative constraints). These axes are independent — you cannot derive quality from geography alone. The Elf Revel ontology similarly needs to classify the same entity along multiple independent axes: a flora species has a biological classification (growth form, soil preference), an aesthetic classification (beauty value, seasonal appearance), a gameplay classification (harvestable, garden-eligible, revel-decoration), and a development classification (implemented in sprint 1, depends on geology system). Does the format support multiple orthogonal classification axes per entity, or does it force a single hierarchical organization? Directory structures impose single hierarchy. RON structs can have multiple tagged fields. SQLite supports multi-column indexing. Which format respects the Burgundian insight that classification axes are independent?

### 2. Granularity calibration

- Granularity calibration — the Premier Cru problem: Burgundy has 635 Premier Cru vineyards because the Cistercian monks determined that terroir variations at the parcel level were meaningful. But Bordeaux classifies at the chateau level because parcel-level distinctions were less meaningful there. The ontology must calibrate its granularity to where meaningful distinctions actually exist. Is a per-component ontology entry warranted (635 Premier Crus), or would a per-system entry suffice (Bordeaux chateaux)? 555 features suggests near-parcel-level granularity. But are all 555 features truly distinct ontological entities, or are some better described as properties of a coarser entity? Over-classification creates maintenance burden without information gain. Under-classification loses meaningful distinctions.

### 3. Formal schema vs

- Formal schema vs. informal overlay: the AOC classification is legally fixed — you cannot declare your wine Grand Cru without the formal designation. But the market's informal reputation system (critic scores, auction prices) overlays it and often disagrees. The ontology will similarly have a formal schema (the typed objects and relationships it explicitly declares) and informal overlays (developer notes, audit comments, 'this feature is actually more complex than its classification suggests'). Does the format support both? Markdown+frontmatter naturally accommodates informal prose alongside formal metadata. RON and SQLite are all-formal. The Rust type system is maximally formal. Where does informal knowledge live?

### 4. Stability over centuries

- Stability over centuries — the long-term maintenance question: the Burgundy classification has been stable since medieval monks surveyed the vineyards. Minor boundary adjustments happen, but the core schema (geographic hierarchy + quality tier + grape regulation) has not changed in 800 years. The Elf Revel ontology will be maintained by a solo developer over years. Does the format favor long-term stability? Formats that depend on external tooling (SQLite browsers, RDF engines) are fragile — the tools may change. Plain-text formats (RON, TOML, markdown) are readable with any editor in any decade. Rust types are stable as long as the compiler exists. Which format has the longest expected shelf life for a solo project?

### 5. The terroir principle

- The terroir principle — classification should describe inherent properties, not imposed categories: terroir means the classification reflects something real about the land — soil, microclimate, drainage, sun exposure. The best ontology classifications similarly describe inherent structural properties of entities rather than imposing arbitrary categories. Does the ontology's type system capture something real about each entity (this is a flora species because it has growth stages and soil preferences, which are inherent) or impose arbitrary groupings (this is a 'Phase 2 feature' because we decided to ship it second, which is contingent)? The format should make inherent classifications easy and contingent classifications clearly marked as overlays.

## Severity Calibration

- **P1**: The ontology forces a single hierarchical organization (geographic OR quality OR development phase) when entities need to be independently classified along multiple axes — like forcing Burgundy to choose between geographic and quality classification instead of maintaining both
  - When: A directory-structure-as-hierarchy approach is chosen, and entities can only live in one directory, forcing a choice between organizing by system (ECS components, flora, social) or by development status (sprint 1, sprint 2, backlog)
- **P2**: All 555 features are classified at the same granularity when some entities are genuinely distinct (individual flora species with unique properties) and others are mere variants of a coarser entity (individual mood modifiers that differ only in magnitude)
  - When: The ontology schema has a single entity type with uniform fields for all 555 features, regardless of whether the feature is a full system (revel engine), a component (mood modifier), or a property (a single aesthetic axis value)
- **P3**: Informal developer knowledge (this feature is harder than it looks, this dependency is fragile, this component needs redesign) has no place in the ontology and lives only in the developer's head, because the format is entirely formal with no room for annotation
  - When: RON or Rust types are chosen as the sole format, with no mechanism for attaching informal notes, audit commentary, or contextual warnings to formal entity definitions

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
