## Task Context

The brainstorm proposes periodic tree-SHA comparison every 5 minutes as the reconciliation mechanism that catches force-pushes, missed webhooks, and network blips. The GitHub adapter uses this as a FullSync analog mirroring the Notion adapter pattern. The path-based correlation rule governs what files are in sync scope.

## Review Approach

### 1. The design specifies what tree-SHA is being compared: the commit SHA

- Verify the design specifies what tree-SHA is being compared: the commit SHA, the tree SHA of the root directory, or the tree SHA of each configured sync path — if the comparison is on the root tree SHA, any change anywhere in the repo (including files outside sync scope) will trigger a full reconciliation, which could be expensive for large repos with frequent CI activity in unsynced paths

### 2. Whether the reconciliation correctly handles the case where a file is added to

- Check whether the reconciliation correctly handles the case where a file is added to GitHub that does not exist locally: the path-based correlation rule says files only in one system are not synced unless explicitly created via event — the poll must distinguish between a file that has never been synced versus a file that was deleted locally since last sync, and apply different behaviors for each

### 3. Assess the reconciliation behavior for repos with large file trees: the GitHub

- Assess the reconciliation behavior for repos with large file trees: the GitHub Trees API returns up to 100,000 entries in a recursive tree response, but repos exceeding that require pagination — if pagination is not handled, reconciliation silently misses files in large repos

### 4. The poll interval rationale: 5 minutes is stated as the reconciliation frequency

- Confirm the poll interval rationale: 5 minutes is stated as the reconciliation frequency, but if the GitHub API is unavailable for 5 minutes (maintenance window, rate limit exhaustion), the next poll runs immediately after recovery — the design must specify whether reconciliation back-fills missed changes by walking commit history or only compares against the current state

### 5. The reconciliation handling of file renames: a file renamed on GitHub appears

- Validate the reconciliation handling of file renames: a file renamed on GitHub appears as a delete of the old path and an add of the new path in the tree diff — without rename detection, the reconciliation will delete the local file at the old path and create a new local file at the new path, which is correct but may surprise users who expected rename tracking

### 6. The reconciliation does not create sync loops: if interop writes a file to

- Check that the reconciliation does not create sync loops: if interop writes a file to GitHub (advancing the tree SHA), the next poll detects that change and could re-trigger a sync event for the file interop just wrote — the design must specify how reconciliation identifies and skips changes that originated from interop itself

## Severity Calibration

- **P0**: A repo has a CI pipeline that generates build artifacts in an out/ directory (not in sync scope) — every CI run changes the root tree SHA, triggering a full reconciliation every 5 minutes even though no synced files changed — over time, the reconciliation API calls exhaust the GitHub personal access token's rate limit (5,000 requests per hour), causing all Contents API writes to fail with 403 until the hour resets
  - When: When the tree-SHA comparison is performed on the repository root tree rather than on the specific subtrees of the configured sync paths, causing unrelated repo activity to trigger expensive reconciliations
- **P1**: The GitHub API is unavailable for 20 minutes due to an incident — during this time, a collaborator pushes 5 commits modifying synced files, and all webhooks are undelivered — when the API recovers, the next reconciliation poll compares the current tree SHA against the last-seen SHA and detects a diff, but only syncs the final state of each file rather than replaying intermediate versions, potentially missing intermediate content
  - When: When reconciliation uses point-in-time tree comparison rather than walking the commit history between the last-known commit SHA and the current HEAD to identify all files that changed in the gap
- **P2**: Interop writes a markdown file to GitHub, advancing the tree SHA — 30 seconds later, the periodic poll runs, sees the tree SHA has changed, finds that docs/README.md has a different SHA than the locally-held ancestor, and re-queues a sync event for a file that interop itself just wrote, triggering a no-op write back to GitHub that still consumes a rate limit slot and creates a spurious commit
  - When: When the reconciliation does not record the tree SHA or commit SHA of writes that interop itself initiates, causing interop-originated changes to appear as external changes during the next reconciliation cycle

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

A tree-SHA comparison tells you that something changed somewhere in the tree, but it does not tell you what changed or whether that change is within the configured sync scope — a reconciliation strategy that fetches and compares individual file SHAs only when the tree SHA changes is efficient but risks missing changes if the tree SHA comparison itself has edge cases. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
