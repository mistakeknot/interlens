## Task Context

Garden Salon is a multi-garden platform where each garden has independently defined governance. Participants may belong to multiple gardens. The platform provides shared primitives. 'Bring your own compute' means API keys must be correctly scoped to garden sessions.

## Review Approach

### 1. Isolation of attribution records

- Isolation of attribution records — each garden's token attribution must be isolated from other gardens. If a participant belongs to multiple gardens, their API key usage must be correctly partitioned so that Garden A's agent runs are not attributed to Garden B's direction.

### 2. Platform invariant vs garden policy boundary

- Platform invariant vs garden policy boundary — the design says governance is garden-defined but the platform provides universal primitives. The line between what gardens can redefine and what the platform enforces immutably is not drawn. A garden should not be able to declare a policy that voids attribution or removes platform-level audit trails.

### 3. Shared primitive namespace pollution

- Shared primitive namespace pollution — directions, roles, and attribution are platform primitives. If gardens can rename or redefine these concepts, onboarding and cross-garden tooling becomes inconsistent. Is there a canonical schema that gardens extend but cannot override?

### 4. Agent identity across gardens

- Agent identity across gardens — a participant's agent (running under their key) may operate in multiple gardens concurrently. The platform must ensure that an agent working in Garden A cannot read or write Garden B's state, even if the participant is a member of both.

### 5. Governance template integrity

- Governance template integrity — when a garden adopts a Cooperative template, does the platform enforce the template's invariants, or does the garden's constitution supersede them? Partial template compliance can create gardens that appear governed but are not.

### 6. Scaling governance model heterogeneity

- Scaling governance model heterogeneity — with fully custom constitutions, platform-layer features (e.g., direction status displays, contribution dashboards) must work across arbitrary governance models. Heterogeneous governance creates a product surface explosion.

## Severity Calibration

- **P0**: API key attribution cross-contamination
  - When: A participant runs an agent on Direction X in Garden A, but a timing or session boundary error attributes those tokens to Direction Y in Garden B. Since attribution is the foundational accounting primitive, cross-garden contamination corrupts the ledger for both gardens.

- **P1**: Garden constitution overrides platform audit trail
  - When: A garden declares a constitution that disables attribution recording for certain directions ('private research' exemption). If the platform honors this, the universal attribution primitive is no longer universal, breaking the design's core invariant.

- **P2**: Governance heterogeneity breaks direction UI
  - When: The salon view shows direction status and contributions. If each garden has a different governance model with different lifecycle states, the UI must either render a lowest-common-denominator view (losing information) or become garden-specific (violating the platform-primitive model).

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
