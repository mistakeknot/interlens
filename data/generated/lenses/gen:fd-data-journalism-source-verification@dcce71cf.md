## Task Context

MVP covers Amazon + App Store + Steam + Kindle. Pipeline is consent-gated (Gmail OAuth gmail.readonly), idempotent, and private-by-default.

## Review Approach

### 1. Cross-parser semantic equivalence: each retailer gets an independent parser

- Cross-parser semantic equivalence: each retailer gets an independent parser module — assess whether the output schema is enforced consistently across parsers so that 'price' from the App Store parser and 'price' from the Amazon parser are semantically equivalent (same currency handling, same precision, same treatment of free items, same treatment of in-app purchases vs. app purchases), or whether each parser makes independent decisions that produce incompatible outputs that look compatible in the unified wardrobe

### 2. Parser version drift in long-running pipelines: Amazon

- Parser version drift in long-running pipelines: Amazon, Apple, and Steam change their email templates periodically — assess whether each parser module is versioned and whether the pipeline detects when a parser is failing against a template variant it has not seen before, or whether template changes cause silent output degradation (fields extracted as None, prices as 0.0) without any alerting

### 3. External cross-reference design for enrichment: the brainstorm defers ASIN

- External cross-reference design for enrichment: the brainstorm defers ASIN enrichment to v2 but relies on ASIN as the unique product identifier in MVP — assess whether the MVP pipeline is designed to make enrichment a clean bolt-on (ASIN present and logged) or whether ASIN handling in MVP would require rework when enrichment is added, and whether the external cross-reference architecture (Amazon PA-API or Exa) is at least stubbed in the design

### 4. Multi-retailer aggregation validity: the brainstorm aggregates across Amazon

- Multi-retailer aggregation validity: the brainstorm aggregates across Amazon, App Store, Steam, and Kindle into unified constructs like 'category distribution' and 'spending rhythm' — assess whether the category taxonomy is consistent across all four parsers or whether 'Entertainment' from Steam (games) and 'Entertainment' from App Store (apps) are being collapsed into a single category without an explicit decision that this is the intended behavior

### 5. Source authenticity: order confirmation emails can be forged or manipulated by

- Source authenticity: order confirmation emails can be forged or manipulated by a malicious actor with Gmail access — assess whether the pipeline applies any sender verification (DKIM check, SPF validation) before trusting parsed content, or whether it treats any email from the sender address list as a valid order confirmation regardless of authentication status

### 6. Incremental update consistency: the pipeline processes all available emails on

- Incremental update consistency: the pipeline processes all available emails on each run and relies on upsert_sku for idempotency — assess whether a new email that arrives between two runs is processed correctly on the second run, and whether the timestamp ordering of processing (oldest first vs. newest first) affects the output of any stateful extraction (e.g., 'first purchase date' or 'brand loyalty' based on order history)

## Severity Calibration

- **P1**: Apple changes the App Store receipt email template in an iOS update — the App Store parser extracts price as None for all new receipts because the price field moved in the HTML — the pipeline imports the purchases successfully (name and date extracted) with price=None and status=OWN, and the spending pattern model treats these as $0 purchases, silently corrupting the user's price sensitivity signals for all App Store purchases after the template change
  - When: When the parser treats partial extraction (name found, price not found) as a successful parse rather than a structured failure, and when there is no parser health monitoring that would detect a sudden increase in None-valued fields
- **P1**: The Amazon parser and App Store parser both produce a 'category' field but Amazon uses Amazon's own taxonomy (Electronics, Books, Clothing) while App Store uses Apple's App Store categories (Games, Productivity, Entertainment) — aggregated category distribution reports 'Entertainment: 45%' but this is a collision of Amazon Entertainment and App Store Entertainment with no shared definition, making the construct meaningless for cross-category recommendation
  - When: When the output schema defines a 'category' field but does not specify a canonical taxonomy, allowing each parser to populate it from the source's native taxonomy without normalization to a shared vocabulary
- **P2**: Steam changes its receipt email from HTML to plaintext format in a platform update — the Steam parser, written for HTML, produces zero successful parses but no errors because it handles the format gracefully by returning None for all fields — the pipeline reports '0 Steam purchases found' which the user cannot distinguish from 'you have no Steam purchases' without inspecting the raw parse output
  - When: When format-level parser failure (wrong format entirely) is indistinguishable in the pipeline output from genuine zero-results, because both produce the same empty result set with no failure indicator

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Evaluates whether the pipeline can defend every imported record — where did this come from, how was it parsed, what was normalized and how, what external source confirmed it — the same way a data journalist must be able to defend every data point in a published story, because silent pipeline inconsistencies produce findings that look correct in aggregate but fail on individual record inspection. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
