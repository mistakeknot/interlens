## Task Context

Three JSON files (lens_library_v2.json: 291 lenses, lens_edges.json: 1,779 edges, lens_communities.json: 7 communities + 15 bridge lens IDs) are embedded via //go:embed into pkg/lens/data/. A package-level Load() function parses them once via sync.Once and returns the LensLibrary struct used by all other functions. Reset() is needed for testing. The open question of whether to support runtime reload from filesystem vs always embedding is unresolved.

## Severity Calibration

- **P0**: sync.Once caches an initialization error permanently because the embed path was wrong during a refactor — all subsequent calls return the cached nil graph with no error, causing silent empty lens selection for the lifetime of the process
  - When: sync.Once does not retry on error; the error path returns without setting the done flag only if using a manual flag pattern, but the standard Once.Do pattern always marks done even if the function panics or the data is corrupt
- **P1**: Reset() in tests nils out the package-level var but does not replace the sync.Once, so the second Load() call after Reset() is a no-op and tests run against stale data
  - When: Test suite passes on first run, produces confusing failures on parallel or repeated test execution
- **P2**: lens_edges.json references a lens ID that was deleted from lens_library_v2.json in a data update — graph construction silently creates a dangling node with no lens metadata, and bridge lens lookup returns a node with empty name and description
  - When: Broken lens presented to users without error; only caught if lens selection attempts to format the result

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
