- WebGPU browser support reality check as of April 2026: Chrome 113+ ships WebGPU; Firefox 124+ ships it behind a flag (may be stable by 2026); Safari 18+ ships it on iOS/macOS but with known gaps in compute shaders and WGSL feature parity; evaluate what fraction of Elf Revel's target audience can use WebGPU natively vs requiring the wgpu WebGL2 fallback backend

### 2. Wgpu WebGL2 fallback completeness: wgpu's webgl2 Cargo fe...

- wgpu WebGL2 fallback completeness: wgpu's webgl2 Cargo feature enables a WebGL2 backend that covers most 2D rendering needs; evaluate whether Elf Revel's required features (instanced rendering, custom vertex attributes, atlas texture sampling, potentially compute shaders for tile preprocessing) are fully supported on WebGL2 or whether the fallback silently degrades

### 3. WASM memory budget for colony sim: a 200x200 colony grid ...

- WASM memory budget for colony sim: a 200x200 colony grid with per-tile glyph state (char: u8, fg_color: u32, bg_color: u32, layer: u8) = 14 bytes × 40K tiles = 560KB; a 512x512 RGBA glyph atlas = 1MB; hecs simulation state at colony scale = estimate 2-10MB; wgpu texture/buffer allocations = estimate 5-20MB; verify total WASM linear memory footprint stays under 256MB default, with a clear path to the 4GB maximum if needed

### 4. Bevy WASM build complexity: Bevy 0

- Bevy WASM build complexity: Bevy 0.18 WASM support requires specific feature flags (bevy/webgpu or bevy/webgl2), wasm-bindgen, wasm-pack or trunk build tooling, and async initialization because WebGPU adapter acquisition is async in browsers; evaluate whether the WASM build of a Bevy-based renderer requires a significantly different code path from the native build, or if a single Cargo.toml feature controls the difference cleanly

### 5. Macroquad WASM maturity: macroquad has first

- macroquad WASM maturity: macroquad has first-class WASM support via its own web platform abstraction; however, known issues include texture memory leaks on long sessions and performance degradation on mobile browsers; evaluate whether macroquad's simpler WASM story justifies its limitations for Elf Revel's secondary WASM target use case

### 6. Binary size

- Binary size and load time: Bevy WASM binaries are large (commonly 15-40MB uncompressed); raw wgpu with a minimal 2D renderer can be 3-8MB; macroquad is typically 5-12MB; evaluate whether Elf Revel's target audience (likely desktop-primary) tolerates a 30+ second load on a slow connection, and whether WASM binary size is a constraint worth optimizing for

## Severity Calibration

- **P0**: The chosen rendering stack (Bevy 0.18 with WebGPU) requires async GPU adapter initialization but the WASM entry point uses a synchronous wasm_bindgen main function — the game initializes without a GPU context, rendering nothing, with no error displayed to the user
  - When: WASM async initialization not handled; no wasm-bindgen(start) async entry point or equivalent; GPU adapter acquisition failure not surfaced to the user
- **P1**: The WebGL2 fallback path silently disables instanced rendering for browsers that don't support WebGPU, causing the WASM build to fall back to one draw call per glyph — 100K draw calls per frame produces <1fps in every non-Chrome browser
  - When: Instanced rendering not verified on WebGL2 backend; ANGLE instanced arrays extension assumed present but not checked; no fallback rendering strategy for non-instancing browsers
- **P2**: The WASM build of the colony sim allocates 150MB of WASM linear memory for a large colony, exceeding the default 256MB limit when combined with the Bevy/wgpu texture allocations and hecs simulation state — the game crashes with an out-of-memory error on large saves in Firefox which has a tighter WASM memory limit than Chrome
  - When: WASM memory limit not calculated or enforced; colony size allowed to grow without checking remaining WASM heap; no memory pressure telemetry

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
