## Task Context

Garden Salon encryption brainstorm presenting 5 named options ranging from at-rest encryption to full E2E with client-side AI. The platform uses Yjs CRDTs for real-time collaboration, Postgres for governance state, git repos for persistence, and an AI proxy that must see plaintext. Per-garden encryption policy (Sealed Rooms) is the leading hybrid option.

## Review Approach

### 1. Trust boundary consistency

- Trust boundary consistency — Option 3 ('Blind Relay') claims the server never sees plaintext, but the server still routes Yjs binary updates. Are Yjs update metadata (document IDs, update sizes, timing) sufficient to leak information about content structure even when payloads are encrypted?

### 2. Encryption layer placement relative to Yjs

- Encryption layer placement relative to Yjs — encrypting before Yjs encoding means the CRDT operates on ciphertext, which breaks merge semantics. Encrypting after Yjs encoding preserves CRDT properties but means the Yjs library operates on plaintext in the client. The design acknowledges this tension but does not resolve it — the choice is architecturally load-bearing.

### 3. Sealed Rooms hybrid model coherence

- Sealed Rooms hybrid model coherence — Option 5 creates two classes of garden with different security properties. The boundary between 'open' and 'sealed' must be enforced at every layer (relay, database, AI proxy, governance). A single layer that fails to check the encryption policy creates a full bypass.

### 4. Content hash integrity under encryption

- Content hash integrity under encryption — the design uses SHA-256 of plaintext for merge records and attribution. In E2E-encrypted gardens, plaintext is not available server-side. Client-computed hashes are unverifiable by the server unless the server is given a zero-knowledge proof or the hash itself is considered non-sensitive. This is an unresolved contradiction.

### 5. Key lifecycle across the full stack

- Key lifecycle across the full stack — the design discusses who holds keys but not key rotation, key revocation on participant removal, or forward secrecy. A participant removed from a garden retains the ability to decrypt all historical content unless re-encryption is performed.

### 6. Downgrade attack surface

- Downgrade attack surface — if per-garden encryption policy is a configuration flag, a compromised server could silently downgrade a 'sealed' garden to 'open' and begin reading content. The client must independently verify the encryption policy is active, not trust the server's claim.

## Severity Calibration

- **P0**: Yjs CRDT merge breaks on encrypted payloads
  - When: If encryption is applied before Yjs encoding, the CRDT cannot merge updates because ciphertext is not a valid Yjs data type. This is not a design flaw that can be patched — it requires a fundamental architectural decision about where in the stack encryption occurs. The brainstorm identifies the constraint but every named option depends on this being resolved.
- **P1**: Server-side downgrade of encryption policy
  - When: In the Sealed Rooms model, the server tells the client whether a garden is sealed or open. If the server is compromised (the threat model Option 5 partially addresses), the attacker can flip the flag and the client begins sending plaintext. Without client-side policy pinning or out-of-band verification, the E2E guarantee is only as strong as the server's honesty.
- **P1**: Removed participant retains decryption capability
  - When: Client-managed keys (Dimension 2B) mean participants hold the garden key. When a participant is removed, they retain the key and can decrypt all content encrypted under it. The design does not address key rotation on membership change, which is the single hardest problem in group E2E encryption.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Every encryption architecture decision is evaluated against: does the trust boundary actually exclude the actors it claims to exclude, are there plaintext leakage paths the design does not acknowledge, and does the system degrade to a known-safe state when a component is compromised? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
