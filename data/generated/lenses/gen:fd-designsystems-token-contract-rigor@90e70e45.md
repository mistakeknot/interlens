## Severity Calibration

- **P0**: Comfort-scale color is both continuous terrain-data and a closed discrete accent set
  - When: A token author implementing the comfort scale must choose: a continuous HSL/OKLCH interpolation driven by live UTCI (satisfies Mêtis §1's 'reads a token, not a literal... varies with sun') or four fixed named tokens shade-teal/warm-amber/hot/extreme-brick (satisfies ACRONYM §6's 'closed set of signal accents'). The canon cites both as binding without reconciling them, so the very first token (color, the exposure scale) that gets built will violate one of the two principles it's supposed to trace back to, and no later reviewer can say which violation is the real one.
- **P1**: No token or enum exists for 'temperature' despite it governing every surface
  - When: A component author building StatStrip needs to know whether it is hot or cool per §2, but the token layer roadmap only names color/type/space/motion — without a temperature token/prop, two component authors will make incompatible calls (one treats StatStrip as hot per its description in §2, another treats a similar comfort card as cool by analogy to the map) and nothing in the system catches the inconsistency until a design review, which is the exact failure mode a design-system canon is meant to prevent.
- **P2**: Aesthetic-disposition rules with no operational test ship unchanged into the component library
  - When: 'The reticle whispers, it does not shout' and 'ornament that reads as instrumentation is allowed' both survive into `@shadewright/*` component specs verbatim, and a code reviewer has no way to reject a PR that adds a heavier reticle stroke or a merely-pretty icon except by invoking personal taste — exactly the flattening-into-brand-veneer the canon claims to avoid in its own 'toolkit not brand veneer' framing (§6).

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
