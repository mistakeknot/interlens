## Review Approach

### 1. Atomic dual-entry vs sequential update: Pacioli's system requires both ledger

- Atomic dual-entry vs sequential update: Pacioli's system requires both ledger entries to be written from a single journal entry before the transaction is considered recorded — assess whether the event bus guarantees that a file change event is processed by both the filesystem adapter and the GitHub adapter atomically, or whether one side can acknowledge and persist while the other fails, creating a half-posted transaction that the trial balance cannot detect because only one ledger was updated

### 2. Trial balance as aggregate vs entry-level verification: the trial balance

- Trial balance as aggregate vs entry-level verification: the trial balance proves debits equal credits in aggregate but cannot detect compensating errors (a debit posted to the wrong account offset by a credit posted to the wrong account) — assess whether the tree-SHA polling reconciliation detects only aggregate divergence (different tree hashes) or entry-level divergence (specific file path mismatches), and whether a scenario exists where two compensating errors produce matching tree SHAs despite individual file content differences

- The giornale as append-only ancestor: the journal is chronological and append-only — entries are never modified, only corrected by posting reversing entries — assess whether AncestorStore maintains the ancestor state as immutable reference or whether ancestor records can be overwritten by subsequent syncs, potentially destroying the three-way merge base and making future conflict resolution impossible for files that were silently re-based

### 4. Closing the books as sync epoch: Venetian merchants closed their books annually

- Closing the books as sync epoch: Venetian merchants closed their books annually, carrying forward balances to new ledgers and verifying all entries against the journal — assess whether the sync system has an equivalent epoch mechanism that periodically verifies all synced files against their ancestor state, or whether ancestor records accumulate indefinitely without pruning or verification, creating unbounded storage growth and stale ancestor references

### 5. Correspondent accounts and intercompany reconciliation: when two merchants

- Correspondent accounts and intercompany reconciliation: when two merchants traded, each maintained independent books that needed periodic bilateral reconciliation — assess whether the sync handles the case where both GitHub and local filesystem make independent changes to the same file between poll intervals, and whether the reconciliation protocol correctly identifies which changes are 'posted' (committed) vs 'pending' (staged but uncommitted) on each side

## Severity Calibration

- **P0**: AncestorStore records are overwritten on each successful sync rather than preserved as immutable history — when a subsequent sync encounters a conflict, the ancestor state reflects the last sync rather than the true common ancestor, causing three-way merge to silently accept changes that should have been flagged as conflicts because the merge base was incorrect
  - When: When AncestorStore updates the ancestor record to the post-merge state after each sync cycle without retaining the pre-merge ancestor, and a rapid sequence of changes on both sides creates a scenario where the ancestor is newer than both divergent states
- **P1**: The event bus delivers a file change event to the GitHub adapter, which successfully pushes the update, but the acknowledgment back to the filesystem adapter fails — the GitHub side reflects the new state while the local side still holds the old state and will re-emit the change on the next poll, creating a duplicate push that either fails on SHA mismatch or succeeds by overwriting with identical content (wasting API quota)
  - When: When event delivery to the two adapters is not transactional and one side can complete while the other fails to acknowledge, and the poll-based reconciliation does not distinguish between 'I changed this' and 'the remote changed this' for changes the local side originated
- **P2**: Tree-SHA polling detects aggregate divergence but does not identify which specific files diverged — the reconciliation must then diff the entire tree to find the changed files, which for large repos with many synced paths creates a burst of Contents API calls that hits the rate limit, causing the reconciliation to abort and retry on the next poll interval, never completing for repos above a certain size
  - When: When tree-SHA comparison detects divergence and the fallback is exhaustive per-file comparison rather than a recursive tree diff that narrows to changed subtrees

## Decision Lens

Every bidirectional sync mechanism evaluated through the bookkeeper's lens: are both representations updated atomically from a single journal entry, or can one side advance without the other? The trial balance is not a correctness guarantee — it only proves that debits equal credits, not that individual entries are correct. A sync system that checks aggregate consistency without entry-level verification will miss compensating errors (two wrong entries that happen to balance).
