## Severity Calibration

- **P0**: Task 5 Step 2 declares interface HomeRoomRow { uncId: string; roomId: string; since: string; challenger: string | null; challengerDays: number } and then, in the same paragraph, requires that challengerDays increment only when dateKey differs from the last counted day, storing that day in a since-style field lastDay. There is no lastDay on the interface, in the artifact list, or anywhere in the store. An executor implementing exactly what is declared has no way to gate the increment, and the gate is load-bearing: Task 8 Step 2 mounts the resolution in a useEffect on [presences, rhymeStepsByRoom, rooms, dateKey], and presences is rebuilt with a fresh array identity every sixty seconds because app/page.tsx:735 depends on view, which depends on nowMs, which useSceneClock re-reads once a minute. So the effect runs about 1,440 times a day. Ungated, challengerDays crosses CHALLENGE_DAYS = 3 in three minutes, every present Unc's home room migrates to whichever room currently has the best rhyme, changed is true on nearly every pass, and saveHomeRooms writes to IndexedDB once a minute forever. The feature whose entire purpose is that a regular has somewhere they belong instead becomes the fastest-churning value in the game, and the player watching the house sees everyone rearrange while they are looking at it. This is a timekeeping error, not a state-machine error: the code counts occasions on which it was asked, and the design meant days. It must be fixed in the plan before Task 5 is executed, because the field is part of a persisted schema and the store lands in the same task.
  - When: A day-count with no field to count it in, in an effect that fires every minute.
- **P0**: lib/residency.ts:131 builds the key as `${d.getFullYear()}-${d.getMonth() + 1}-${d.getDate()}` with no zero padding, giving 2026-9-2 and 2026-10-2. Task 5 Step 1 creates house_snapshots with keyPath id and an index on dateKey; Task 13 Step 3 sets id to `${dateKey}:${daypart}` and specifies getSnapshots(limit = 30) newest first. IndexedDB orders strings by code unit, and under that ordering 2026-10-1 sorts before 2026-9-1, and 2026-9-15 before 2026-9-2. The record drawer — which after Task 14 is the only remaining record of this world, the journal having been deleted — therefore shows October above September, the fifteenth above the second, and the thirty-row window keeps a nearly arbitrary subset rather than the recent past. The existing shipped uses of dateKeyFor all compare for equality, which is why this has never surfaced; this plan is the first to sort by it. The fix is either a padded key or an explicit numeric sort key on the row, and it must be decided before the store is created in Task 5 rather than discovered in Task 13, because changing the shape of a persisted id after rows exist costs a migration this plan has not budgeted.
  - When: A date key that cannot be ordered, in a store whose only contract is newest first.
- **P1**: Task 13 Step 1 gives pickSnapshotMoments(dateKey, dayparts, presencesByDaypart) selecting one to three of the day's dayparts that had anyone present, preferring dayparts whose presence set differs from the previous one, and Step 4 has House capture once per (dateKey, daypart) when the moment list names the current daypart. The selection is a statement about the whole day, and the capture is an act inside one daypart of it. At 07:00 nobody knows which dayparts will have presence, so either the function is called with a partial map and returns a different answer at every daypart — in which case a moment chosen at dawn may be unchosen by dusk, and a moment chosen at dusk has already passed uncapturable — or it must be called with a full day's presence, which presentRegulars can supply for all six dayparts of a dateKey because it is deterministic in (dateKey, daypart), but the plan never says so and the caption's came by and had gone lines then describe presence the player never actually saw. The two readings produce different products and the plan does not choose between them. State which one is intended, or the executor will pick the one that typechecks.
  - When: A table consulted before its inputs exist.
- **P1**: Task 7 Step 1 gives House the rAF loop as accumulate elapsed, call stepWalk once per TICK_MS, then every registered draw, with TICK_MS = 100 and no clamp specified in the task, the artifact list, or the acceptance criteria. Browsers suspend rAF for a backgrounded tab, and useSceneClock's visibilitychange handler explicitly anticipates a player who leaves and returns. A phone left on the house overnight returns with roughly eight hours of accumulated elapsed, which is 288,000 stepWalk calls the loop will attempt inside a single frame while every walker paths, opens doors, and rolls bubbles. The right answer here is almost certainly discard and re-init, since the model is rebuilt from a fresh clock read on foreground regain anyway, but that is a ruling the plan must make in Task 7 rather than leave to whoever writes the loop.
