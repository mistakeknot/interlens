## Task Context

Hassease is Signal-native by design — the brainstorm explicitly says it owns its own Signal connection rather than routing through Auraken's Telegram bot. The Signal transport is the primary human oversight channel: every destructive tool action (Edit, Write, Bash) requires builder approval via Signal. This makes the transport layer a safety-critical component — failures in message delivery directly affect whether the builder's intent is honored. The brainstorm lists signal-cli as the existing integration path but flags it as an open question.

## Review Approach

### 1. Signal-cli vs Signal API choice: The brainstorm flags this as an open question.

- signal-cli vs Signal API choice: The brainstorm flags this as an open question. signal-cli requires a linked device (shares a Signal account) and has process management complexity in a Go daemon. What are the operational trade-offs between signal-cli subprocess management vs. a Signal API service (if one exists with sufficient features)?

### 2. Approval message delivery guarantees: Signal does not guarantee delivery

- Approval message delivery guarantees: Signal does not guarantee delivery acknowledgment at the application layer. If the builder's approval message ('y') is dropped or delayed, does the daemon time out and skip the action, wait indefinitely, or have a configurable policy? What is the behavior on timeout?

### 3. Approval ambiguity handling: The brainstorm defines 'y'

- Approval ambiguity handling: The brainstorm defines 'y', 'approve', 'go', thumbs up for approval and 'n', 'deny', 'skip' for denial. What happens with partial matches ('yeah', 'yep', 'yes please'), emoji reactions, or messages in a different thread? Is there a confirmation echo before execution?

### 4. Thread management and multiplexing: A builder may have multiple concurrent

- Thread management and multiplexing: A builder may have multiple concurrent Hassease sessions (different projects, different terminals). How does the Signal transport multiplex approval flows across sessions? Does each session have its own thread, or is there a shared inbox that can interleave approvals?

### 5. Signal account lifecycle: signal-cli linked devices expire if not used

- Signal account lifecycle: signal-cli linked devices expire if not used, and Signal accounts can be deregistered. What happens when the Signal session expires mid-long-running-task? Does the daemon detect session expiry and alert before it becomes a silent delivery failure?

### 6. Rate limiting and message flooding: A busy agent loop can generate many

- Rate limiting and message flooding: A busy agent loop can generate many approval requests in quick succession (e.g., editing 10 files). Does the transport have rate limiting to prevent flooding the builder's Signal inbox? Is there a batching mechanism for approving multiple related edits?

## Severity Calibration

- **P0**: Approval message is delayed by Signal's infrastructure (network partition, push notification failure). The daemon interprets silence as implicit approval after a timeout and executes a write to a production config file without explicit builder authorization.
  - When: Timeout defaults to implicit approval rather than implicit denial; no retry with explicit re-confirmation after timeout.
- **P1**: Builder sends 'y' approval in the wrong thread (e.g., the previous task's thread). The transport routes the approval to the current pending action, executing an unintended edit on a different file than the builder was reviewing.
  - When: No thread-scoped approval matching; all 'y' messages in the Signal conversation are treated as approvals for the current pending action.
- **P2**: signal-cli process crashes mid-session; the Go daemon has no detection mechanism and continues the agent loop, sending approval requests into the void. Builder receives no notifications for the next 10 edits.
  - When: No health check on signal-cli subprocess; no delivery receipt tracking; no alerting on send failure.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Consumer messaging protocols are not designed for machine-to-machine control planes. Every message can be dropped, reordered, or delayed. An approval flow built on Signal must treat every approval as potentially lost and every denial as potentially delayed — the daemon must never assume a message was received, and never act on an ambiguous approval state. Evaluates the transport layer as if Murphy's Law applies to every message. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
