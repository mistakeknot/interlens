The brainstorm's stated advantage is that 'all state lives on the filesystem in the existing conventions' — this is a strength for interoperability but a risk for concurrent access. The project model is the shared substrate for the Swift app, FastAPI, and Claude Code skills. Corruption here affects all three surfaces simultaneously.

## Severity Calibration

- **P0**: The Swift app and a Claude Code skill both save shotlist.json at the same time; the last-write wins, silently discarding the other's changes because no file coordination is used
  - When: If writes to structured project files do not use NSFileCoordinator or a FastAPI-mediated write mutex
- **P1**: A ComfyUI render writes shots sequentially; the app loads the episode timeline, displays 3 of 12 shots as 'complete', and the user triggers a publish workflow on an incomplete episode
  - When: If there is no render manifest or completion sentinel to distinguish a full render from an in-progress one
- **P2**: After 50 episodes, research/ contains 2,000 markdown files; every app launch triggers a full directory scan to build the search index, adding 8 seconds to startup time
  - When: If the corpus index strategy does not use incremental updates driven by FSEvents rather than full rescans

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Every filesystem interaction is evaluated against: can two writers corrupt this file? Will the Swift UI see stale data if Python writes without notification? Is a partial write observable as a valid state? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
