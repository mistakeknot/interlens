- **P0**: Adapters bootstrap in parallel without dependency ordering — the GitHub adapter starts receiving webhooks and emitting events before the identity mapping is loaded, causing events with unresolvable identity references to be routed to other adapters, which either crash on the unresolvable reference or silently drop the identity information, creating entities with missing attribution that cannot be retroactively fixed

- **P1**: The interkasten migration port focuses on feature parity (same sync capabilities) but does not migrate interkasten's accumulated sync state (WAL position, conflict resolution history, entity mapping cache) — after cutover, interop re-syncs from scratch, creating duplicate entities in Notion/beads for everything that interkasten had already synced, requiring manual deduplication
  - When: When the migration plan defines feature completeness as the cutover criterion but does not include state migration or a deduplication pass, and there is no mechanism to detect that an entity was previously synced by interkasten and should not be re-created
- **P2**: Each adapter encodes entity references in its own format (GitHub uses org/repo#number, Notion uses UUID, beads uses bead-ID) and the event bus carries these references opaquely — when the hub needs to correlate events about the same entity from different adapters, it relies on a mapping table that must be explicitly populated, and any entity synced before the mapping table entry was created has events that cannot be retroactively correlated
  - When: When the event bus does not enforce a canonical entity reference format and adapters use their native reference schemes, requiring explicit pre-population of cross-reference mappings for event correlation to work

## Decision Lens

Every coordinated multi-component construction with planned teardown evaluated as a mandala problem: do the components enforce geometric alignment at their shared boundaries, or do they each develop independently and hope to fit together? Is there a dependency ordering that prevents later components from building on unverified foundations? And critically — is there a plan for the deliberate, clean dissolution of the predecessor system (interkasten) that captures the wisdom of the practice while releasing attachment to the artifact? The mandala builder knows that the most common failure is not a single monk's error but a misalignment between monks that each followed their own protocol correctly — the interface specification was ambiguous, and each monk resolved the ambiguity differently. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.
