## Task Context

The 12-model ensemble spans providers with fundamentally different API designs, output conventions, and model behaviors. The value of a multi-model ensemble depends on each model contributing genuine signal -- if three models are silently producing null or malformed outputs due to extraction bugs, the 'ensemble' is actually 9 models with overstated consensus. The mixing of free-tier and paid-tier providers introduces rate limits, model substitution risks, and reliability differences that must be explicitly handled rather than assumed away.

## Review Approach

### 1. Prompt consistency across provider types: The same prompt sent to OpenAI API

- Prompt consistency across provider types: The same prompt sent to OpenAI API, OpenRouter, and a CLI tool will be processed through different tokenizers, system prompt handling conventions, and instruction-following tuning. Is there a single prompt template, or are there provider-specific prompt adaptations? If a single template, is it validated to produce structurally equivalent output across all 12 models?

### 2. Selection cardinality calibration: Models are instructed to select 0-3 lenses.

- Selection cardinality calibration: Models are instructed to select 0-3 lenses. Instruction-following capability varies: some models will reliably select exactly N when asked, others will select a list of arbitrary length. Does the pipeline enforce cardinality constraints on output, or does it trust model compliance? If it trusts compliance, does it characterize per-model cardinality distributions?

### 3. Reasoning model output extraction: Reasoning models (o1

- Reasoning model output extraction: Reasoning models (o1, o3, Claude extended thinking) embed the useful answer in reasoning_details or thinking blocks, not the content field. The extraction logic must correctly identify which reasoning format each model uses -- OpenAI and Anthropic reasoning output structures differ. Is there a per-model extraction configuration, or a fragile heuristic?

### 4. Lens vocabulary normalization: Different models may refer to the same lens

- Lens vocabulary normalization: Different models may refer to the same lens using paraphrases, abbreviations, or alternative names. If the pipeline does string matching against the 291-lens library, models with different paraphrasing styles will show systematically lower lens selection rates -- not because they don't select a lens, but because their output doesn't match the canonical name.

### 5. Safety tuning differential: Highly safety-tuned models (Claude

- Safety tuning differential: Highly safety-tuned models (Claude, Gemini) may refuse or hedge on morally-charged dilemmas that less-tuned models engage with directly. This creates a systematic missingness pattern -- safety-tuned models will show lower selection rates for certain dilemma categories, which analyze_cookoff.py may interpret as lower relevance rather than refusal.

### 6. Free-tier OpenRouter rate limiting and model substitution: OpenRouter's free

- Free-tier OpenRouter rate limiting and model substitution: OpenRouter's free tier can silently substitute a requested model for a cheaper variant when the requested model is at capacity. Is the pipeline verifying that the model actually used matches the model requested, or does it trust OpenRouter's model_id in the response to be the requested model?

## Severity Calibration

- **P1**: A reasoning model's lens selections are extracted from the content field (which returns None) rather than reasoning_details, causing all dilemma responses from that model to be recorded as empty lens selections -- the model appears to have no calibration signal when it actually produced 1,360 detailed reasoning traces.
  - When: content=None classified as zero-lens response without checking for reasoning_details; no per-model extraction strategy.
- **P1**: OpenRouter silently substitutes a cheaper model for one listed model during the run, and the pipeline records output under the requested model_id -- the corpus contains output from 13 distinct models labeled as 12, with one model double-counted under two different names, biasing all agreement and frequency statistics.
  - When: No model_id verification against OpenRouter response metadata; provider-reported model_id trusted without validation.
- **P2**: Lens name matching uses exact string comparison against the 291-lens library, and models that paraphrase lens names (e.g., 'consequentialist thinking' vs. 'Consequentialism') have 20-40% of their selections silently discarded -- their effective selection cardinality is suppressed, making them look like low-information models in analyze_cookoff.py.
  - When: No fuzzy matching, no synonym normalization, no per-model selection-discard rate monitoring.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

LLM outputs are not exchangeable units -- each model brings its own implicit priors about what counts as a good answer to a structured task. Evaluates whether the pipeline treats model outputs as if they were equivalent (introducing systematic measurement error) or whether it explicitly models inter-model behavioral differences as a data property to be characterized and corrected. Especially attentive to the difference between capability differences (model can't do the task) and instruction-following differences (model interprets the task differently). If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
