## Task Context

The Adapter interface is the architectural spine of interop. All four day-1 adapters and every future adapter must implement it correctly. An interface that is ambiguous about behavioral contracts will accumulate subtle incompatibilities as adapters are developed independently -- one adapter blocks on HandleEvent, another closes its Emit channel on Stop, a third panics on malformed events. The hub cannot compensate for all of these at runtime without knowing the contract. Identity mapping is a cross-cutting concern that must be designed correctly from day one because retrofitting it after adapters are deployed requires schema migrations across all synced systems.

## Review Approach

### 1. The Adapter interface documents behavioral contracts for each method beyond the

- Verify that the Adapter interface documents behavioral contracts for each method beyond the type signature -- Start() returning without error must mean ready to handle events, not initialization started; HandleEvent() must specify whether it is allowed to block and for how long; Emit() must specify whether the channel is closed on Stop()

### 2. The interface is designed for extension without breaking existing adapters --

- Check that the interface is designed for extension without breaking existing adapters -- adding a new required method to the Adapter interface in a future version requires all four adapters to be updated simultaneously; evaluate whether optional capabilities (e.g., HealthCheck(), SyncState()) should be separate interfaces checked via type assertion rather than mandatory methods

### 3. That the identity mapping configuration (GitHub user <-> Notion user <-> beads

- Confirm that the identity mapping configuration (GitHub user <-> Notion user <-> beads assignee) is specified as a first-class data structure and not as ad-hoc string comparison -- a config that maps by display name will break when a user changes their GitHub username, silently creating a new unknown identity in the sync system

### 4. That adapters have a documented error taxonomy for HandleEvent() return values

- Validate that adapters have a documented error taxonomy for HandleEvent() return values -- the difference between event malformed (discard) and event valid but external API down (retry) and event valid but creates a conflict (escalate) requires explicit error types, not a single error return that the hub interprets by string content

### 5. The Beads adapter's constraint of access via bd CLI only is enforced at the

- Check that the Beads adapter's constraint of access via bd CLI only is enforced at the interface level, not by convention -- if the adapter struct exposes a direct Dolt connection field, a future contributor will use it, bypassing the CLI contract and creating a coupling that breaks when the bd CLI interface changes

### 6. The Adapter interface's Event type is versioned or extensible -- an Event

- Ensure that the Adapter interface's Event type is versioned or extensible -- an Event struct with a fixed set of fields will need to be extended as new adapter types are added (e.g., Google Drive), and a non-extensible Event type forces all adapters to be updated when new event metadata is required

## Severity Calibration

- **P1**: The GitHub adapter's HandleEvent() blocks for up to 30 seconds during a GitHub API call because the interface contract does not specify a timeout requirement. When GitHub API is slow, the hub's event dispatch goroutine blocks, causing all other adapters to stop receiving events for the duration of the GitHub API call.
  - When: When the Adapter interface specifies HandleEvent(Event) error with no documented timeout contract, and the hub calls HandleEvent synchronously in a dispatch loop rather than in a per-adapter goroutine
- **P1**: Identity mapping uses GitHub display name (not username) as the matching key. A team member changes their GitHub display name. All subsequent GitHub issue assignments to that person are mapped to unknown in beads, and their beads assignments are no longer reflected in GitHub -- silent identity split with no error or warning.
  - When: When the identity mapping config uses human-readable display names as keys rather than stable identifiers (GitHub numeric user ID, Notion user UUID)
- **P2**: A new Google Drive adapter is added in v2. Its events include a folder_id field not present in the original Event struct. The adapter adds folder_id as a tag on the event metadata map, but the hub's routing logic ignores unknown metadata keys. Drive events route correctly but lose folder context, causing all Drive-to-local-FS syncs to place files in the root directory instead of the correct folder.
  - When: When the Event struct uses a fixed field set rather than a typed metadata extension mechanism, and adapter-specific context is conveyed via untyped string maps

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

An adapter interface is a contract between the hub and the external system. A good contract specifies not just method signatures but behavioral invariants: what Start() must guarantee before returning, what HandleEvent() must do if the event is malformed, and what Emit() must do when there are no events. Evaluates every interface design decision against: can a correct implementation of this interface still violate the hub's assumptions? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
