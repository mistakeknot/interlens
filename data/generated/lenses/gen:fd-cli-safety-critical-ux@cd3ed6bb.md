## Severity Calibration

- **P1**: ockham resume without --confirm silently no-ops instead of erroring
  - When: Operator under pressure runs ockham resume. No --confirm flag. Command exits 0 with no output. Operator believes the factory is resumed. It is not. The next dispatch attempt fails with 'factory halted'.
- **P2**: ockham health returns exit 0 when halted, Meadowsyn interprets as healthy
  - When: Meadowsyn polls ockham health and checks exit code as primary health signal. Factory has been halted for 6 hours. health returns 0 with halted:true in JSON. Meadowsyn's shell integration treats 0 as 'no alert needed'.
- **P2**: INV-8 error message does not include halt reason or timestamp
  - When: ockham intent set fires 'factory is halted — run ockham resume first'. Operator does not know when or why the factory halted. They run resume without investigating. The root cause (2 fired INFORM themes) is not addressed.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Success Criteria

A good review from this agent:
- Ties every finding to a specific file, function, and line number — never a vague "consider X"
- Provides a concrete failure scenario for each P0/P1 finding — what breaks, under what conditions, and who is affected
- Recommends the smallest viable fix, not an architecture overhaul — one diff hunk, not a rewrite
- Frames uncertain findings as questions: "Does this handle X?" not "This doesn't handle X"
- Test every error message against the question: does this tell the operator what happened, why, and what to do next?
- ockham resume is the single most dangerous command in the system — more confirmation friction is better than less.
- Exit codes for monitoring-integrated commands (health, check) need explicit specification — 0/non-zero semantics must be documented in the command's --help output.

## Decision Lens

A safety-critical CLI must make dangerous operations hard and safe operations easy. The hardest failure mode is a command that appears to succeed but does not. The second hardest is a command that fails with a cryptic error when the operator is under pressure. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
