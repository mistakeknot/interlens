## Task Context

Brainstorm for Gmail purchase import pipeline: Auraken parses order confirmation emails, calls interjawn MCP to upsert SKUs and wardrobe entries in jawncloud, and builds purchase-pattern context in Auraken's preference models. MVP covers Amazon + App Store + Steam + Kindle. Pipeline is consent-gated (Gmail OAuth gmail.readonly), idempotent, and private-by-default.

## Review Approach

### 1. Chain of custody for parsed records: each upserted SKU should carry a reference

- Chain of custody for parsed records: each upserted SKU should carry a reference to its source email (message ID, sender, date) so a user can trace any imported item back to the specific email that produced it — assess whether the pipeline logs source provenance or discards it after parsing, making post-import auditing impossible

### 2. Completeness testing and silent drops: forensic accountants count expected

- Completeness testing and silent drops: forensic accountants count expected records before normalizing them — assess whether the pipeline detects and surfaces parse failures rather than silently skipping emails that don't match the expected HTML structure, and whether a partial-parse (order date extracted but ASIN not found) is treated as a gap or as a successful import with missing fields

### 3. Normalization audit trail for brand fuzzy-matching: step 4 of the data flow

- Normalization audit trail for brand fuzzy-matching: step 4 of the data flow normalizes brand names against jawncloud via fuzzy match — assess whether each normalization decision (raw brand 'AMZN' → canonical 'Amazon') is logged with its confidence score, or whether the match is silent and irreversible, making it impossible to audit or correct systematic normalization errors later

### 4. Idempotency proof vs. idempotency claim: the brainstorm states the pipeline is

- Idempotency proof vs. idempotency claim: the brainstorm states the pipeline is idempotent via upsert_sku — assess whether idempotency is verified by a test that re-runs the full pipeline against the same inbox and checks for duplicate records, or whether it is a design assumption that rests entirely on upsert_sku behaving correctly for all edge cases (same ASIN, different price; same ASIN, different date)

### 5. Gap detection for expected-but-missing emails: if a user has Amazon order

- Gap detection for expected-but-missing emails: if a user has Amazon order history but Gmail returns zero results for `auto-confirm@amazon.com`, the pipeline should detect the anomaly (filter too narrow? wrong sender address?) rather than reporting '0 purchases found' as success — assess whether the pipeline distinguishes 'no qualifying emails' from 'search returned zero results due to a possible pipeline error'

### 6. Re-order and return handling as a reconciliation problem: the brainstorm defers

- Re-order and return handling as a reconciliation problem: the brainstorm defers dedup to v2 — assess whether deferring creates a completeness problem where return/refund emails are imported as additional 'owned' items rather than being ignored, silently inflating the wardrobe count with items the user no longer owns

## Severity Calibration

- **P1**: Parse failures are silently skipped — 10% of Amazon order confirmations use a slightly different HTML layout (A/B test variant, localized template) and are dropped without any record, so the user's purchase history is systematically incomplete with no indication of the gap
  - When: When the parser catches exceptions and continues rather than logging a structured failure record for each email that could not be fully parsed
- **P2**: Brand normalization applies a fuzzy match with 0.7 similarity threshold — 'Kindle' from digital receipts matches 'Kindl' in jawncloud (typo in existing brand), silently mapping all Kindle purchases to a malformed brand entry — the error is invisible until a user notices their Kindle purchases aren't grouping correctly
  - When: When brand normalization matches are applied without logging the raw input, matched canonical, and confidence score in a way that can be audited or corrected
- **P2**: Return confirmation emails from Amazon (`return-confirmation@amazon.com`) are treated as order confirmations and parsed as new purchases — items the user returned are added to the wardrobe with status OWN, producing false positives that contaminate the preference model
  - When: When the sender allowlist for Amazon includes return-confirmation senders, or when the parser does not distinguish order confirmation content from return confirmation content before creating wardrobe entries

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
