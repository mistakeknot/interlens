## Severity Calibration

- **P0**: The 'atomic' manifest rewrite is a naive in-place overwrite (or a temp write without correct fsync/rename ordering), so a crash or app-kill mid-write truncates the manifest into a file that still parses as valid but is missing artifact entries or lifecycle state — a bulla rolled shut mid-count that reads as sealed — and a subsequent reclaim or reconciliation, trusting the torn manifest, ORPHANS or DESTROYS unconfirmed quarantined raw that the truncated manifest no longer references, violating §3's never-force-delete and losing the only redactable source.
  - When: when the manifest rewrite is not crash-atomic (temp + fsync + rename + dir-fsync) with the prior manifest recoverable, allowing a torn write to be read as a valid complete session
- **P1**: Reconciliation after a crash mid-capture or mid-device→node-transfer has no way to distinguish a torn transaction from a complete one — an on-disk artifact with no manifest entry, a manifest entry whose bytes are partial, or a raw file that was half-transferred to the node — so the session either passes as valid (orphaned/partial artifacts silently trusted) or the interrupted transfer strands/duplicates raw, breaching §8.1's 'never strand or duplicate raw' and §3's defined dead-letter path.
  - When: when the reconciliation/startup pass cannot detect and route every interruption shape (orphaned artifact, missing/partial manifest entry, half-transferred raw, hash mismatch) to a defined state
- **P2**: Content-addressed sha256: hashes are computed once and recorded in the manifest but never re-verified against the actual bytes — not at manifest-write and not at reclaim — so silent bit-rot, a truncated write, or a mislabeled artifact leaves the manifest's outer count drifted from the sealed tokens, and verify-then-delete reclaim (Decision 7) destroys raw while trusting a hash that no longer matches its derived replacement, discarding the irreplaceable token behind a seal that was never actually checked.
  - When: when artifact hashes are recorded-and-trusted rather than verified against bytes at write time and re-verified against bytes at reclaim before raw destruction

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
