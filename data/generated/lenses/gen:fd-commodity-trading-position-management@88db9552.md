## Review Approach

### 1. Open/close position accounting for deployment windows: co...

- Open/close position accounting for deployment windows: commodity position tracking requires that every open trade has a matching close — unclosed positions are a risk management exception, not the normal case; the benchmark's DeploymentEvent design should treat an active deployment as an 'open position' that must be explicitly closed by a withdraw action, with the scorer treating a deployment that reaches end-of-run without withdrawal as a 'carried-to-expiry' position rather than an error, with appropriate attribution semantics

### 2. Attribution window precision

- Attribution window precision and P&L slippage: in futures trading, the P&L attributed to a position is calculated over the exact interval between open and close timestamps — the values-under-pressure scorer's deployment window attribution should use the same precision; if deployment start and end are recorded at tick granularity but pressure trajectory is sampled at a coarser interval, there will be systematic attribution slippage (pressure changes that occur at the boundary of a window will be mis-assigned)

### 3. Budget constraint calibration

- Budget constraint calibration and opportunity cost: trading desks set risk budgets that are binding — a budget so large that it is never hit provides no discipline; the deployment slot budget (or equivalent) must be set so that during the benchmark's designed crisis moments, the model faces genuine capacity binding (more eligible targets than available slots); if the budget is never binding, deploy is always the dominant strategy and produces no discrimination signal

### 4. Position recycling

- Position recycling and re-entry semantics: traders frequently close and re-open positions in the same instrument — the benchmark must define what happens when a model withdraws from a country and then immediately re-deploys: does this count as one deployment window or two? Does the second open create a new DeploymentEvent with a fresh attribution window? This affects whether a model that repeatedly deploys and withdraws to generate many DeploymentEvents is scored differently from a model that holds a single sustained deployment

### 5. Transaction cost

- Transaction cost and action budget interaction: commodity trading has transaction costs that make excessive position-flipping sub-optimal — the benchmark's observation/action budget (one of the brainstorm's open questions) plays the same role; if deploy and withdraw each consume from the action budget, a model that repeatedly deploys and withdraws is spending budget on position management rather than policy actions, which should be a visible cost in the trace

### 6. Mark

- Mark-to-market at interim ticks vs. settlement at window close: futures positions are marked-to-market continuously but P&L is only 'realized' at close — the values-under-pressure scorer may similarly want to distinguish 'interim pressure readings during deployment' from 'pressure change attributed at window close'; the design choice between continuous vs. settlement attribution affects whether short deployments and long deployments are scored on the same basis

## Severity Calibration

- **P0**: A model deploys to [country] at tick 100, withdraws at tick 200, and re-deploys at tick 300 — the scorer treats the second deploy as part of the first deployment window because the event matching logic uses country-ID as the key rather than a per-deployment unique ID; pressure changes between tick 200 and tick 300 (when no deployment was active) are attributed to 'the deployment', inflating the power dissolution score and corrupting the values-under-pressure window boundaries
  - When: When DeploymentEvent matching uses country-ID as the sole key and does not assign unique event IDs to each open/close pair, allowing multiple deployment cycles to the same country to be collapsed into a single incorrectly-bounded window
- **P1**: The deployment slot budget is set to 10 concurrent deployments in a world with 12 countries — the budget is never binding because a model would need to deploy to 11 simultaneous countries for it to constrain; the benchmark produces deployment events but no model ever faces a genuine capacity constraint, so all models deploy to every crisis country and the scorer fires equally for all models with no discrimination
  - When: When the slot budget is calibrated without checking the maximum number of simultaneously-eligible deployment targets in the benchmark's designed crisis scenarios, resulting in a budget that is structurally never binding
- **P2**: Deployment window attribution uses tick-level precision for window start/end but pressure-trajectory snapshots are recorded every 10 ticks — a deployment that opens at tick 105 and closes at tick 115 has its pressure change attributed based on the nearest snapshots at tick 100 and tick 120, including 5 ticks of pre-deployment and 5 ticks of post-deployment pressure movement in the window; models with many short deployments accumulate more attribution slippage than models with fewer long deployments, introducing a systematic bias against deployment diversity strategies
  - When: When the scorer's pressure-trajectory sampling rate is coarser than the tick granularity of DeploymentEvent timestamps, creating boundary-attribution slippage that scales with deployment frequency
