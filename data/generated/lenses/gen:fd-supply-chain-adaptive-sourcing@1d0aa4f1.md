- Assess whether the MODEL_REGISTRY cost metadata (tokens per dollar) is kept current — models on flat-rate CLI have a different marginal cost structure than API models, and mixing them on a cost-per-token Pareto curve produces a misleading frontier

### 2. Examine whether the Pareto benchmark reuses cached reconstruction outputs

- Examine whether the Pareto benchmark reuses cached reconstruction outputs across runs — if a model's API version has changed since the cache was written, the cached output reflects the old model's quality on the new model's cost

### 3. Whether the overnight runner's directive budget system accounts for the

- Check whether the overnight runner's directive budget system accounts for the asymmetric cost of directive failure — running 50 experiments that all fail wastes the same budget as running 50 that succeed, but the information value is different

### 4. Evaluate whether the training scout's weakness-targeted content discovery

- Evaluate whether the training scout's weakness-targeted content discovery creates a feedback loop where the training set becomes dominated by the most-recently-discovered weakness, at the cost of underrepresenting weaknesses that were addressed in earlier cycles

### 5. Review whether the model benchmarking accounts for latency cost

- Review whether the model benchmarking accounts for latency cost — a model that is 2x cheaper per token but has 5x higher P95 latency may dominate on cost-per-quality but bottleneck the real-time editorial pipeline

### 6. Whether the model selection from Pareto benchmarks is version-pinned

- Check whether the model selection from Pareto benchmarks is version-pinned — if a model is selected as optimal and then the API provider silently rolls the model forward, the Pareto analysis is no longer valid

## Severity Calibration

- **P1**: claude-haiku-cli is included on the same Pareto cost axis as claude-haiku-4.5 (anthropic-api) using a token-based cost estimate for the CLI model, when the CLI model is actually flat-rate — the Pareto analysis incorrectly places the CLI model at a cost point that makes it appear non-optimal when it is actually near-zero marginal cost
  - When: The benchmark selects an API model over the flat-rate CLI model, increasing per-run costs by 10-100x
- **P1**: The overnight runner has a fixed per-directive experiment budget but no cross-directive budget governor — a slow directive that runs 100 experiments (each timeout after 60s) can consume the full overnight window without advancing to higher-priority directives
  - When: High-priority directives are never executed because the lowest-priority directive with a large hypothesis template library exhausts the budget
- **P2**: The training scout identifies 'specificity' as the weakest pillar across three consecutive overnight cycles and targets content acquisition toward specificity examples — after 6 months, the training corpus has 4x more specificity examples than any other pillar, creating a training imbalance that degrades performance on de-aiisms and cadence
  - When: Pillar performance improves on the targeted weakness but regresses on previously-adequate pillars, reducing overall editorial quality

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Flags benchmark designs where the Pareto frontier is computed on stale data, where the cost model omits relevant cost drivers (latency, retry overhead, flat-rate vs per-token differences), or where the training scout's weakness discovery targets create systematic oversampling of one editorial weakness at the expense of others. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
