## Task Context

Choosing a rendering stack for a native Rust colony sim. Options span: reusing a proven sibling project renderer vs. building fresh vs. lighter frameworks vs. hybrid prototype→production. Core tension: proven reuse vs. 2D-first design without 3D baggage.

## Review Approach

### 1. Technical rider vs

- Technical rider vs. actual venue spec: touring shows carry a technical rider describing the minimum venue capability — does the sibling renderer have an equivalent minimum platform spec, and does the native Rust target meet it without compromise?

### 2. Production elements that cannot tour: some set pieces

- Production elements that cannot tour: some set pieces, automation rigs, and lighting fixtures are house-specific and are cut from the tour — which parts of the sibling renderer are fundamentally tied to its original host (WASM, 3D pipeline, browser event model) and cannot transfer?

### 3. Rep plot vs

- Rep plot vs. bespoke design: repertory theatre reuses standard light positions across productions; touring shows adapt to each venue's grid — is the rendering stack designed as a rep plot (configurable) or a bespoke installation (fixed)?

### 4. Advance work

- Advance work and prep time: touring productions send an advance team weeks before opening to adapt the show — what is the equivalent 'advance work' budget for adapting the sibling renderer to the native target, and has it been honestly estimated?

### 5. Understudy systems: touring shows always have understudy ...

- Understudy systems: touring shows always have understudy plans for when the primary system fails in an unfamiliar venue — does the rendering stack decision include a fallback if the touring adaptation fails partway through?

### 6. Audience experience continuity: touring is justified only...

- Audience experience continuity: touring is justified only if the audience experience is preserved — what specific rendering qualities must be preserved from the sibling project to justify reuse, and are those the qualities that actually transfer?

## Severity Calibration

- **P1**: Renderer design assumes browser event loop as the outer tick driver — porting to native requires restructuring from inside out, not a surface adaptation
  - When: No technical rider analysis performed; 'venue spec' of native Rust target assumed compatible without verification
- **P2**: Key visual qualities (shader effects, compositing pipeline) require GPU features available in the original platform but not guaranteed in the native target's deployment environments
  - When: Platform capability matrix not produced before adoption decision
- **P0**: Touring adaptation consumes the full development sprint without producing a working rendering baseline — prototype→production path collapses into open-ended porting work
  - When: No explicit cut decision: which sibling renderer elements will NOT tour, accepted before adaptation begins

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
