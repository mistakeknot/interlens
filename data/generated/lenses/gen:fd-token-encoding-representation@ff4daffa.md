## Task Context

Tuivision is a TUI testing/automation MCP server that gives AI agents visual access to terminal applications. Current modes: get_screen text (~200-400 tokens, no style), get_screenshot png (~1600 vision tokens), get_screenshot svg (~2000-8000 tokens, contains text+style but verbose). The goal is a new representation that captures text + task-relevant visual semantics at significantly fewer tokens than PNG/SVG while preserving the semantic information that plain text loses. Ideas already proposed include local OCR on PNGs and optimized SVG stripping.

## Severity Calibration

- **P0**: The encoding format uses characters that the BPE tokenizer splits into 3-4 byte tokens each (e.g., Unicode box-drawing characters as region delimiters), causing a 2x token inflation versus the naive text grid despite appearing shorter in character count.
  - When: Occurs when encoding design optimizes for character count or human readability rather than actual tokenizer behavior.
- **P1**: A diff-based encoding sends 'line 5 changed: [new content]' but the LLM loses track of which version of the screen is current after 3 sequential diffs, causing it to reference stale state and send incorrect keystrokes.
  - When: Triggered in multi-turn TUI sessions where cumulative diffs exceed the LLM's working memory for stateful reconstruction.
- **P2**: The encoding uses a custom DSL syntax that the LLM has never seen in training data, reducing its ability to parse the representation compared to well-known formats like markdown or HTML that appear extensively in training corpora.
  - When: Occurs when novel encoding formats prioritize theoretical compactness over the LLM's prior familiarity with the syntax.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

The encoding is optimal when the ratio of task-relevant information bits to consumed tokens is maximized. A format that is 20% smaller in characters but fragments into 40% more BPE tokens is worse, not better. Every design choice is validated against actual tokenizer behavior (cl100k_base, o200k_base) not character count.
