## Task Context

You are reviewing the Mahrai active-work reconciler (src/mahrai/reconciler.py), the tmux runtime reader (src/mahrai/tmux_reader.py), and the active-work state contract (docs/contracts/active-work-state.md) through the lens of an ICU charge nurse responsible for safe shift handoff. Mahrai compares intended session state (control-plane config) against actual runtime state (live tmux) and emits drift records. Your job is to assess whether the system produces handoff artifacts that are complete, self-contained, actionable, and safe for an incoming operator who has no prior context. - Handoff completeness: does each DriftRecord carry enough context (explanation, suggested_action, detected_at) that a new operator can act without re-running reconciliation from scratch?

### 2. 'Who is the responsible provider?'

- 'Who is the responsible provider?' — does every session have an unambiguous owner or escalation target, or do sessions go without accountability when agent_kind is missing or ambiguous?

### 3. Deterioration trajectory vs. snapshot bias: the reconciler emits point-in-time

- Deterioration trajectory vs. snapshot bias: the reconciler emits point-in-time drift; is there any trending or recurrence detection, or does every run see the same chronic drift fresh with no memory of prior reports?

### 4. Triage severity calibration: 'warning' and 'info' are used

- Triage severity calibration: 'warning' and 'info' are used, but the ICU model requires a third dimension — acuity velocity (how fast is the patient deteriorating?). Is a long-standing 'info' drift that never resolves more dangerous than a new 'warning'?

- Unmanaged-session filtering as 'not my patient': sessions excluded by _UNMANAGED_SESSION_NAMES are silently dropped; a charge nurse would still log the exclusion reason so it can be audited if something goes wrong with a 'main' session later.

### 6. Observation vs. intervention asymmetry: the reconciler detects drift but emits

- Observation vs. intervention asymmetry: the reconciler detects drift but emits only suggested_action strings — there is no escalation pathway that fires automatically, which in a clinical setting would be equivalent to charting a critical lab value and leaving it in the chart without paging anyone.

## Severity Calibration

- **P0**: A session with intent_status='in_progress' has emitted a missing_runtime drift for more than two consecutive reconciliation cycles with no resolution and no acknowledgment field on the DriftRecord.
  - When: Equivalent to a nurse handing off a critical patient with no documented plan-of-care and no attending notified. The system cannot tell whether this is a known, accepted gap or a silent failure.
- **P1**: The reconciler's runtime_key derivation means two differently-named tmux sessions for the same logical project could each be treated as unknown_session independently, never triggering a host_mismatch or agent_mismatch because neither maps to intended sessions.
  - When: Ghost patients: the charge nurse sees two beds occupied by people who are not in the census. The care plan for the real patient exists but is not linked to the actual bed.
- **P2**: agent_kind inference from tmux session name uses only the last token after '@'; a session named 'project-a|task@claude' and one named 'project-a|maintenance' would have very different agent contexts but only the first is inferred — the second gets agent_kind=None silently.
  - When: Underdocumented patient: a care plan says 'nurse-managed' but the actual attending is unknown because the name badge fell off. Not immediately dangerous, but a liability in any review.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
