## Severity Calibration

- **P0**: The partial-order DAG topological sort is not deterministic across engine versions, producing different Uncs for the same seed
  - When: If the engine resolves ties in the topological sort using JavaScript's `Array.sort()` (which is not guaranteed stable across V8 versions prior to V8 7.0) or using object-key enumeration order (which is insertion-order-dependent in V8 but not guaranteed by the spec), the roll sequence may differ between Node 18 and Node 20, or between development and production builds. A seed that produces `vocation → class_current → politics_posture` in development may produce `class_current → vocation → politics_posture` in production, resulting in different Uncs for the same seed.
- **P0**: A `when:` clause in a bias rule references an axis that has not yet been rolled, causing the engine to apply zero bias instead of the intended bias
  - When: If the YAML contains `when: {politics_posture: 'traditionally-loyal'}` in a bias rule for `class_current` roll, and `politics_posture` follows `class_current` in the DAG (so `axesSoFar` does not contain it when `class_current` is rolled), the engine silently finds no match for the `when:` clause and applies no bias. The YAML is syntactically valid, Zod validates it, the engine runs without error, and the output distribution is wrong for every `traditionally-loyal` Unc. This is the most dangerous category of matrix authoring error: syntactically valid, schema-valid, semantically wrong.
- **P1**: Stub-to-matrix migration breaks stable Unc IDs for previously generated Uncs
  - When: If `uncStub.ts` generates a stable Unc ID as `hash(walkId + lure.id)` and `solwend-1zp` generates it as `hash(walkId + lure.id + matrixVersion)`, any Unc generated before the migration that was saved to the porch ledger will have a different ID when regenerated by the new engine. The porch ledger's `Unc` references will be orphaned. This is a data-integrity failure if the migration does not include a stable-ID compatibility layer.
