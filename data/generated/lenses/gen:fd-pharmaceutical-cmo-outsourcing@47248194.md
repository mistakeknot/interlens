## Review Approach

### 1. Provider qualification matrix and task-type boundary governance: pharmaceutical

- Provider qualification matrix and task-type boundary governance: pharmaceutical CMOs are qualified per process, not per molecule — a CMO qualified for oral solid dosage forms cannot manufacture sterile injectables without separate qualification — assess whether Hassease's provider routing rules define explicit qualification boundaries per task type (not just per complexity tier), and whether there is a governance mechanism to add new task types to GLM/Qwen's qualification scope without implicitly expanding their scope to adjacent unqualified task types

### 2. Quality agreement equivalency and per-provider oversight calibration: pharma

- Quality agreement equivalency and per-provider oversight calibration: pharma quality agreements specify minimum requirements that scale with CMO risk tier — a Tier 1 CMO with a strong quality track record requires less oversight than a Tier 3 CMO — check whether Hassease's trust evaluator and auto-approve configuration are calibrated per provider (GLM/Qwen receiving higher approval scrutiny and narrower auto-approve scope than Claude), or whether the same approval thresholds apply to all providers regardless of their quality track record

### 3. Tech transfer completeness and provider context sufficiency: pharmaceutical

- Tech transfer completeness and provider context sufficiency: pharmaceutical tech transfer ensures the CMO has complete process knowledge before manufacturing — the CMO cannot fill gaps with assumptions — assess whether GLM/Qwen receive sufficient task context (code context, project conventions, adjacent file content) to execute tasks without making assumptions that a more contextually-aware Claude session would not have made, and whether insufficient context sent to GLM/Qwen is a latent quality risk that manifests as plausible-looking but subtly wrong outputs

### 4. Change control and provider-sourced modifications: in CMO governance

- Change control and provider-sourced modifications: in CMO governance, any manufacturing process change must go through a formal change control process even if the change originates with the CMO — check whether Hassease's evidence logging correctly identifies which provider model generated each change, and whether changes generated by GLM/Qwen go through an equivalent review step before committing to git, or whether the same-session auto-approve rules that apply to Claude also apply to GLM/Qwen outputs without differentiation

### 5. Supply chain risk distribution and provider concentration: pharma companies

- Supply chain risk distribution and provider concentration: pharma companies distribute manufacturing across multiple CMOs to avoid single-source dependency — check whether Hassease's routing is resilient to individual provider API failures (GLM API down, Qwen rate-limited), and whether the costrouter has a fallback routing path that escalates to Claude when the primary cheap-tier provider is unavailable, rather than blocking the task queue until the cheap-tier provider recovers

### 6. Regulatory accountability and non-delegable principal obligations:

- Regulatory accountability and non-delegable principal obligations: pharmaceutical law holds the sponsor company accountable for all CMO-manufactured product — the sponsor cannot cite CMO fault to the FDA — assess whether Hassease's architecture makes it structurally clear that the human builder is accountable for all executed changes regardless of which model generated them, and whether the per-tool approval flow is the mechanism that preserves this accountability rather than an optional convenience feature that could be disabled in a 'trust all providers' configuration mode

## Severity Calibration

- **P1**: A 'simple single-file edit' is routed to GLM 5.1. GLM lacks the project context to know that the file uses a custom error handling convention that differs from Go stdlib conventions. GLM produces a syntactically correct edit that uses fmt.Errorf wrapping instead of the project's sentinel error pattern. The edit passes the auto-approve rule (single src file, small change). The JSONL receipt records 'provider: glm-5.1, task: edit, outcome: success' — but the change violates the project's error handling contract. No human ever reviewed the output because the auto-approve rule fired before the approval gate.
  - When: When auto-approve rules apply equally to GLM/Qwen and Claude outputs despite the providers having materially different levels of project-context awareness, causing GLM-generated changes to bypass human review at the same rate as Claude-generated changes even though GLM's unfamiliarity with project conventions creates a higher rate of plausible-wrong outputs

During the outage, 12 tasks that should have gone to GLM are routed to Claude. After the outage resolves, the costrouter resumes GLM routing — but the session's per-session routing ratio counter shows 60% Claude usage for the session so far, triggering the ratio enforcement logic to route the next 12 tasks aggressively to GLM to rebalance. These 12 tasks include 3 that would normally have been escalated to Claude based on complexity signals, but the ratio rebalancing overrides the complexity-based routing decision.
  - When: When the ratio rebalancing logic overrides individual task complexity signals to correct for outage-induced ratio drift, causing post-outage tasks to be under-routed to the cheap tier in compensation for the over-routing that occurred during the outage
- **P2**: Hassease's JSONL execution log records provider, task type, outcome, and token count for each task. A post-session cost analysis shows GLM tasks average 2.3x more tokens than equivalent Claude tasks for the same task type — GLM's longer outputs require more back-and-forth correction cycles. The costrouter's savings estimate was based on per-token pricing only, not on total-tokens-per-task completion. The actual cost savings from GLM routing are 40% lower than projected because the token-per-task multiple was not measured before routing targets were set.
  - When: When the cost routing target is calibrated against per-token price differentials without measuring the task-completion token multiple for each provider, causing the projected savings to be systematically overestimated for providers that require more tokens to complete equivalent tasks
