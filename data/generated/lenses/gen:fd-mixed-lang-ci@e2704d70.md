- **P1**: The Swift and Python conformance suites each hardcode their own expected pass/fail outcome per fixture (e.g., an in-code table mapping fixture filename to expected valid/invalid) rather than both suites reading a single expected-outcome manifest alongside `fixtures/`, so a fixture's intended classification can be changed in one language's test code without the other language's suite ever being touched — both CI jobs stay green while silently asserting different things about the same fixture file.
  - When: Check whether expected pass/fail outcomes for each fixture vector are declared once (e.g., in a fixture-adjacent metadata file) and consumed by both language test suites, versus duplicated as separate in-code expectations per language.
- **P2**: No Xcode version pin is configured for the macOS CI runner (no `.xcode-version` file, no explicit `xcode-version` input to `setup-xcode`-equivalent step), so `swift test` results depend on whichever Xcode GitHub's macOS runner image ships by default at the time the workflow runs, and a routine GitHub Actions macOS image update could silently change Swift compiler/language-mode behavior between two otherwise-identical PRs.
  - When: Check the CI workflow YAML (once written) for an explicit Xcode version pin rather than relying on the macOS runner's default toolchain.
- **P2**: Branch protection is configured with required-status-check names that reference the current job names in the CI workflow YAML, but there's no note/convention in CLAUDE.md warning that renaming a workflow job (a routine refactor) silently detaches it from being a required check on GitHub, letting a broken suite merge un-blocked with the branch-protection UI still showing a check listed as 'required' from a stale name.
  - When: Check whether the plan documents the required-check-name-to-job-name coupling and includes a convention/reminder to avoid silent detachment on workflow renames.
