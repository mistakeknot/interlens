Tuivision's annotated format uses [r]...[/] inline markers to deliver style-annotated terminal text. ## Review Approach

### 1. Span merging correctness and edge cases

- Span merging correctness and edge cases — caption formats have spent decades debugging span-merge implementations: adjacent spans with same style merge cleanly, but spans that differ in one attribute don't merge, zero-length spans at style boundaries cause parser ambiguity, and spans that split across line breaks require special handling. Assess whether the SVG span-merging proposal (.5) and the annotated text marker design (.1) have explicit rules for these cases, or whether they handle only the common case.

### 2. Marker nesting and overlap semantics

- Marker nesting and overlap semantics — SRT doesn't support overlapping inline tags; TTML and WebVTT do, with defined resolution rules. Assess whether the [r]...[/] marker design handles the case where a cell has multiple active style attributes (bold + red + inverse) and whether the nesting is defined (does [r fg=red][r bold]...[/][/] work?) or whether the format assumes at most one active marker per cell.

### 3. Empty and degenerate spans

- Empty and degenerate spans — caption engines must handle zero-length spans (style markers with no content between open and close), which arise when a styled region starts and immediately ends (cursor at boundary, empty selection). Assess whether the annotated format defines behavior for [r fg=red][/] and whether this generates valid output or crashes the renderer.

### 4. Lossless semantic preservation of inverse

- Lossless semantic preservation of inverse — TTML has explicit tts:showBackground and tts:textOutline attributes that preserve semantic intent rather than pre-resolving visual effects. Assess whether the inverse boolean preservation decision (.4) is implemented as a semantic flag that survives round-trips (encode -> parse -> re-encode produces the same flag) or as a visual approximation that could drift.

### 5. Format extensibility without parser breakage

- Format extensibility without parser breakage — WebVTT and TTML both have extension mechanisms (cue settings, custom namespaces) that parsers are required to ignore gracefully rather than fail on. Assess whether the [r role=error] extension mechanism (.1 optional roles) is designed so that a parser written before roles were added ignores the role= attribute gracefully, or whether unknown attributes will cause parse errors in older consumers.

## Severity Calibration

- **P1**: A terminal cell with bold + red + inverse requires three simultaneous style attributes in the annotated format — if the marker design only supports one style attribute per [r] span, these cells are unrepresentable and silently drop attributes
  - When: When the [r fg=red] marker syntax is defined for single attributes and the multi-attribute case is not specified in the brainstorm, leaving the implementation to make an ad-hoc choice that may not be consistent
- **P1**: SVG span-merging (.5) merges adjacent cells by style equality, but the equality check uses the pre-inverse-preservation attributes — after fixing .4, cells that were equal before may differ in the inverse flag, changing the merge output and potentially breaking existing SVG consumers who expected the old per-cell structure
  - When: When .4 (inverse preservation) and .5 (SVG span-merging) are implemented as independent children without an explicit integration test that verifies their interaction
- **P2**: The [r]...[/] marker design uses [/] as the universal close tag — if the format ever supports nested markers, [/] is ambiguous about which open tag it closes, requiring a lookahead parser rather than a simple stack or state machine
  - When: When the marker grammar is specified for the MVP flat case without documenting that [/] ambiguity is a known constraint that rules out future nesting

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
