## Task Context

interop's webhook-first sync model depends entirely on reliable, idempotent webhook ingestion. GitHub delivers webhooks with at-least-once semantics and retries for 72 hours. Notion webhook reliability is less documented. Any ingestion bug -- missing signature check, synchronous processing, or missing deduplication -- creates a permanent operational risk that is hard to detect because duplicate events look like normal activity in logs.

## Review Approach

### 1. GitHub webhook payloads are validated against the X-Hub-Signature-256 HMAC

- Verify that GitHub webhook payloads are validated against the X-Hub-Signature-256 HMAC header before any processing -- accepting unauthenticated payloads allows an attacker with knowledge of the webhook URL to inject arbitrary issue create/close/comment events into beads and Notion

### 2. That every webhook handler returns a 2xx response quickly (before processing

- Confirm that every webhook handler returns a 2xx response quickly (before processing completes) and processes the event asynchronously -- GitHub marks a webhook endpoint as failed if it does not respond within 10 seconds, and a slow Notion API call in the synchronous handler path will eventually cause GitHub to disable the webhook

### 3. The event processor uses a delivery ID (GitHub's X-GitHub-Delivery header

- Check that the event processor uses a delivery ID (GitHub's X-GitHub-Delivery header, Notion's equivalent) as an idempotency key before processing -- GitHub retries failed deliveries with the same delivery ID, so processing the same event twice must be safe (idempotent create, idempotent close)

### 4. That the deduplication store (whether in-memory or persisted) has a bounded

- Validate that the deduplication store (whether in-memory or persisted) has a bounded retention window and does not grow unboundedly -- storing every delivery ID forever will exhaust memory on a long-running daemon receiving hundreds of webhooks per day

### 5. Notion webhook event types are explicitly allowlisted and that unknown event

- Ensure that Notion webhook event types are explicitly allowlisted and that unknown event types are logged and discarded rather than passed to the adapter -- Notion adds event types in minor API updates, and a handler that panics on an unknown event type will be killed by a new Notion event type release

### 6. The Caddy reverse proxy configuration preserves the original

- Check that the Caddy reverse proxy configuration preserves the original X-Hub-Signature-256 and X-GitHub-Delivery headers when forwarding to interop -- header stripping by the proxy silently breaks signature verification for all incoming GitHub webhooks

## Severity Calibration

- **P0**: GitHub webhook signature verification is absent or skipped during development and never re-enabled -- an attacker sends a POST to the webhook URL with a crafted payload that closes a beads issue corresponding to a real bead, causing work to be marked done when it is not
  - When: When the HMAC verification middleware is commented out, behind a feature flag that defaults off, or only checked when a secret is configured (and the secret config is missing in production)
- **P1**: The webhook handler calls the Notion API synchronously before returning a response -- a Notion API timeout (common during Notion outages) causes the handler to hold the connection for 30 seconds, GitHub fires a delivery timeout, retries the event, and the handler processes it again, creating a duplicate beads issue
  - When: When event processing is synchronous inside the HTTP handler function rather than dispatched to the adapter's event channel before returning 200
- **P1**: No delivery ID deduplication -- GitHub retries a webhook delivery that timed out (because interop was briefly overloaded), and the retry creates a second beads issue for the same GitHub issue, resulting in split tracking state across two beads
  - When: When the event bus does not check the delivery ID against a recent-deliveries store before dispatching to adapters

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

A webhook endpoint that returns 200 without processing the event is lying to the sender. A webhook endpoint that processes an event twice is corrupting state. Evaluates every ingestion design decision against: what does the sender infer from the response code, and is event processing idempotent on replay? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
