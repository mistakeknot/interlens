## Severity Calibration

- **P1**: The builder sends two Signal messages in rapid succession: 'create a new file src/handler.go with this implementation' and 'add unit tests for the handler'. Signal delivers them out of order — the test creation message arrives first. Hassease begins creating test files that reference src/handler.go, which does not yet exist. The Glob tool returns no match for handler.go, the test generation proceeds with assumptions about the handler's interface, and when the handler creation message arrives second and executes, its interface differs from the test assumptions. Both tasks complete with a 'success' receipt — but the codebase is in a broken state.
  - When: When Hassease processes Signal messages in arrival order without sequence numbering, and dependent tasks execute in the wrong order because Signal's delivery ordering is not guaranteed, especially under rapid successive message conditions
- **P1**: The daemon is restarted mid-task (OOM kill, systemd restart). When it comes back online, it has no mechanism to detect the interrupted task. The builder sends a new instruction. The daemon begins the new task while the previous task's partial edits remain uncommitted to git. The new task's Glob discovers the partial edits and includes them in its working set, causing the new task to treat the incomplete edits as valid context and build on top of them. The JSONL log shows the interrupted task as having no completion record, but the daemon's startup logic does not check for incomplete tasks before accepting new work.
  - When: When daemon restart does not include a startup-phase recovery check that scans for JSONL tasks with a start record but no completion record, and does not surface these interrupted tasks to the builder before accepting new instructions
- **P2**: Hassease sends a Signal approval request containing a 200-line diff preview. Signal splits the message across two delivery units due to size. The builder receives the first half, sees the beginning of the diff, and replies 'y'. The second half of the diff arrives after the 'y' — but the approval parser has already matched the 'y' to the approval ID and committed to execution. The builder approved a diff they only partially read.
  - When: When large Signal messages are chunked by the Signal transport layer and the approval parser commits to the approval decision based on a 'y' received before all chunks of the proposal have been delivered to the builder's device

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
