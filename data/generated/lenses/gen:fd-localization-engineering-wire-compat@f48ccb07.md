## Review Approach

### 1. JSON struct tag completeness audit: every field in ModeProfile and Fingerprint

- JSON struct tag completeness audit: every field in ModeProfile and Fingerprint that participates in the JSON wire format must have an explicit json:"field_name" struct tag matching the Python dict key exactly — fields without struct tags serialize with Go's default PascalCase naming (AvgWords instead of avg_words), silently breaking the Python reader; verify against style.py:206-225 _empty_mode_profile keys and the Fingerprint serialization format

### 2. Omitempty semantics for zero-value numeric fields: ModeProfile fields like

- omitempty semantics for zero-value numeric fields: ModeProfile fields like emoji_density and pct_contraction will be 0.0 for modes where the user never uses emoji or contractions — if these fields are tagged with omitempty, Go will omit them on serialization; the Python reader will then reconstruct them as absent from the JSON (KeyError or None rather than 0.0), causing the Python update logic to initialize them to a non-zero seed value rather than treating them as confirmed-zero observations

### 3. Float64 round-trip precision: Go encodes float64 to JSON using the shortest

- Float64 round-trip precision: Go encodes float64 to JSON using the shortest representation that round-trips (strconv.FormatFloat with 'g' format) — for EMA values like 0.3 * prev + 0.7 * new, the encoded string may be '0.30000000000000004' in Go and '0.3' in Python due to floating-point representation differences; when Python reads the Go-written value, it gets a slightly different float64, and subsequent EMA updates compound the difference; verify that the float encoding is stable across at least 100 EMA updates by running the cross-runtime golden fixture

### 4. Vocabulary token list serialization: vocabulary counters are stored as slices

- Vocabulary token list serialization: vocabulary counters are stored as slices of strings (word lists per category) — Go serializes nil slices as null in JSON while Python serializes empty lists as []; a mode profile that Go writes with a nil vocabulary slice will be read by Python as None rather than [], causing Python's list-append update logic to fail with a TypeError on the first vocabulary token update for that mode

### 5. Fingerprint top-level serialization envelope: verify that the Fingerprint

- Fingerprint top-level serialization envelope: verify that the Fingerprint struct's JSON representation matches exactly what Python's auraken writes to the core_profiles.style_fingerprint JSONB column — including any top-level wrapper keys (e.g., {'global': {...}, 'per_mode': {...}}) and any metadata fields (version, last_updated_at) that the Python system writes and the Go system must preserve on read even if it does not use them

### 6. Unknown field handling on deserialization: if the Python system writes fields

- Unknown field handling on deserialization: if the Python system writes fields that the Go struct does not declare (e.g., aspirational fields from the docstring's cadence gap tracking), Go's encoding/json silently discards them on deserialization and the next Go write will omit them permanently — verify that the Go Fingerprint struct either declares all Python-written fields (even as ignored interface{}) or that the Python system's writer is audited to never write fields the Go system does not declare

## Decision Lens

JSON wire compatibility during a concurrent operation window is correct only when: (1) every field name in the Go struct tags matches the Python dict key exactly, including case, underscores, and abbreviations — a single field name divergence causes that field to be silently zero-valued on deserialization by the other runtime; (2) float64 JSON encoding in Go produces values that Python's json.loads can reconstruct with identical precision — Go's encoding/json uses strconv.AppendFloat with 'g' format, which may produce different decimal representations than Python's json.dumps for the same float64 value; (3) absent/zero fields are handled consistently — Go's omitempty omits zero-value fields while Python's json.dumps includes them by default; a field that Python writes as 0.0 and Go reads as absent (due to omitempty on the other side) will silently initialize to Go's zero value on the next write. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
