## Severity Calibration

- **P0**: The name-keyed attribution scheme (Task 10) means Task 12's hit-rate-based cluster-head selection can silently degenerate to arbitrary id-ordering for every cluster whose members share a name — the common case, since clustering exists precisely to group near-duplicate rewrites of the same fd-* lens. Concrete scenario: `fd-authplatform-migration` is rewritten three times across two machines (three distinct `body_hash` records, one name); a melange run adjudicates 40 findings generically against "fd-authplatform-migration"; all three records inherit `hit_rate=0.9, adjudicated=40` identically; Task 12 reports `head_selected_by: "hit_rate"` for whichever record happens to sort last by id, even though the evidence says nothing about which BODY produced the good results — the entire empirical purpose of variant clustering (reward the better-performing rewrite) silently fails.
  - When: A cluster has ≥2 members sharing one `name`, and at least one ledger run adjudicated findings against that name (the common, intended case for clustering to matter).
- **P0**: If `merge.py`'s per-machine-file read races a concurrent write — e.g. the Mac's on-demand `harvest scan` runs while `harvest-and-push.sh` is mid-merge from a timer, or a scan is interrupted leaving a truncated final JSONL line — the read path's handling of that partial line determines whether the run fails loudly (safe) or a line-filtering reader (`filter(Boolean)`-style) silently drops the last-scanned sighting for that record, which is exactly the loss the accretive design's core promise (nothing removed except by explicit prune) exists to prevent.
  - When: A `data/harvest/<machine>.jsonl` write is interrupted or races a concurrent reader, and `merge.py`'s JSONL parsing does not distinguish a truncated line from a legitimately absent one.
- **P2**: `harvest/embed.py`'s incremental skip-list, keyed by `body_hash` via `<layer>.hashes.json`, does not account for `embedding_text` changing independent of `body_hash` (a spec file attaching to a previously spec-less record on a later harvest) — a record could keep a stale embedding vector indefinitely once its hash is marked 'seen,' feeding Task 12's cosine-based clustering and Task 13's `resolveLens` with a vector that no longer represents the record's actual embedding input.
  - When: A record is first harvested with no matching spec (body-fallback embedding text), then a matching spec file appears in a later harvest without the body itself changing.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
