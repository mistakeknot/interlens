## Severity Calibration

- **P0**: OpenRouter rate limit (429) causes all parallel agents to fail simultaneously, producing zero findings
  - When: When parallel dispatch exceeds per-key concurrent request limit without backoff
- **P1**: Timeout mismatch: OpenRouter agent takes 90s but flux-watch.sh times out at 60s, marking it failed when it would have succeeded
  - When: When timeout config doesn't account for OpenRouter's higher latency variance
- **P2**: Cost data from OpenRouter not recorded in interstat, making budget estimates progressively wrong
  - When: When token-count.py only parses Claude JSONL format, not OpenRouter response JSON

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

When OpenRouter returns a 500 or times out at 45s into a 60s agent run, does the system degrade gracefully or corrupt the review? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
