## Task Context

Palantir-style ontology format and architecture for a Rust ECS game (Elf Revel). The ontology maps typed objects with relationships across both a development meta-layer (555 game features, dependency graphs, audits) and an in-game simulation layer (ECS components, flora species, elf relationships, composition properties). Key tension: formal enough to query, lightweight enough for a solo Rust game project. Format candidates: RON, TOML, SQLite, markdown+frontmatter, Rust type system, RDF-lite, JSON-LD. The project is solo-developer, Rust-centric, targets WASM, and has a philosophy of embracing system complexity for emergent richness.

## Review Approach

### 1. Typed objects with fixed properties

- Typed objects with fixed properties and flexible roles: every wayang puppet has an immutable type (Arjuna is always refined, always an archer, always the third Pandawa) but participates in unlimited narrative combinations — Arjuna in the court scene, Arjuna in battle, Arjuna in love, Arjuna in disguise. The ontology similarly needs entities with fixed type properties (a flora species always has soil_preference, growth_stages, beauty_value) that participate in flexible relational contexts (this species in this biome, affected by this blight, part of this garden composition). Does the format separate type-level properties (the puppet's carving) from instance-level relationships (the puppet's current narrative position)? RON and Rust types naturally encode type-level properties. SQLite separates schema from rows. Markdown conflates type description with instance documentation.

### 2. The banana

- The banana-log registry — spatial encoding of relationships: in wayang kulit, the gedebog (banana log) is the physical ontology. Puppets stabbed on the right are protagonists; on the left, antagonists. Proximity encodes relationship intensity. The dalang reads the entire state of the narrative by glancing at the gedebog. The Elf Revel ontology needs a similarly scannable overview — a developer glancing at the ontology should immediately understand which features are blocked, which components relate to which systems, which species are in which biomes. Does the format support spatial or structural scanning? Directory structure (one file per entity, organized into folders) provides spatial scanning. SQLite requires a query. A single large RON file provides textual scanning. Which format lets the solo developer 'read the gedebog' at a glance?

### 3. The kayon as universal delimiter: the kayon (tree

- The kayon as universal delimiter: the kayon (tree-of-life puppet) appears between every scene in wayang kulit — it marks transitions, separates narrative contexts, and resets the audience's attention. The ontology needs equivalent delimiters between its layers — clear boundaries between the development meta-layer and the simulation layer, between feature definitions and dependency declarations, between entity types and relationship types. Does the format have natural kayon boundaries? TOML has [section] headers. RON has struct boundaries. SQLite has table boundaries. Markdown has heading levels. JSON-LD has @context switches. Which format's natural boundaries best serve as kayons between ontology layers?

### 4. The dalang's mental model

- The dalang's mental model — solo-operator ergonomics: the dalang holds the entire wayang world in their head — 200+ characters, their genealogies, their rivalries, their dramatic functions — without external reference during a 9-hour performance. This is the solo developer's situation: one person must hold the entire ontology in their head while coding. The format must support this cognitive load, not add to it. A format that requires specialized tooling (SQLite browser, RDF query engine) forces context switches. A format that is plain-text-readable (RON, TOML, markdown) stays in the dalang's flow. But the dalang also benefits from the gedebog's physical organization — puppets are pre-sorted, pre-positioned. Does the format pre-organize information so the solo developer can find things by spatial habit rather than search?

### 5. Dual

- Dual-sided screen — simultaneous views for different audiences: in wayang kulit, the dalang's side of the screen shows colored, textured puppets with visible rods and mechanisms. The audience side shows only shadows — simplified, abstracted, beautiful. The same performance is two different experiences. The ontology similarly serves two audiences: the developer (who needs full type information, dependency details, audit state) and the game runtime (which needs only the simulation-relevant subset). Does the format support publishing different views of the same ontology? Rust types naturally compile into only what the runtime needs. SQLite supports views. Markdown has no view mechanism. RON is all-or-nothing. Can the format serve both the dalang's side and the audience's side from a single source?

## Severity Calibration

- **P1**: The ontology conflates type-level properties (a flora species always has these growth stages) with instance-level state (this particular ancient oak is in growth stage 3), making it impossible to update the type definition without touching every instance record
  - When: The format stores type definitions and instance data in the same structure without a clear type/instance separation, and there are more than 50 typed entities with multiple instances each
- **P2**: The ontology requires specialized tooling to browse and query, breaking the solo developer's cognitive flow — every lookup requires switching from editor to database browser or running a query script, like a dalang who must consult a reference book during the performance
  - When: SQLite is chosen as the primary format without an accompanying plain-text view or editor integration, and the developer must context-switch to inspect the ontology more than once per coding session
- **P2**: The ontology has no natural boundary markers between the development meta-layer and the simulation layer, causing developers to accidentally modify simulation definitions when updating feature tracking metadata
  - When: A single-format approach is used with no section delimiters, context markers, or file-level separation between meta-layer and simulation-layer content

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
