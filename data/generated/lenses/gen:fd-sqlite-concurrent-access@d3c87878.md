## Review Approach

### 1. Resume's ratchet_state atomic reset: D3 specifies a single transaction for

- Resume's ratchet_state atomic reset: D3 specifies a single transaction for UPDATE SET tier='supervised' WHERE tier='autonomous'. Verify this is the correct SQL — a WHERE clause filtering on 'autonomous' only resets autonomous domains, but supervised domains should not be touched. Also verify the transaction is explicitly started (db.conn.Begin()) not implicit.

### 2. SetSignalState upsert under concurrent ockham check runs: the existing INSERT

- SetSignalState upsert under concurrent ockham check runs: the existing INSERT ... ON CONFLICT upsert is not atomic with the surrounding read-modify-write in evaluator.go (loadPriorSignal → evaluate → persistSignal). Two concurrent check invocations could both read the same prior state and produce conflicting writes. Assess whether this is a real concurrency risk given typical invocation patterns.

### 3. Signals.db recovery path deletes WAL and SHM files before reopening: verify

- signals.db recovery path deletes WAL and SHM files before reopening: verify this is correct for WAL mode. Deleting -wal while another process has the DB open can corrupt the database for that other process. Flag if ockham check and ockham health could run concurrently.

### 4. Health command (new in F7) reads signal_state

- Health command (new in F7) reads signal_state, authority_snapshot, and ratchet_state in a single logical read. Without an explicit transaction, these reads are not snapshot-consistent — a concurrent check write could produce a health snapshot where signal states are from before the write but ratchet_state is from after.

### 5. Busy_timeout(5000) in the connection string: 5 seconds is long for a CLI.

- busy_timeout(5000) in the connection string: 5 seconds is long for a CLI. Verify this is intentional and that it does not cause ockham health to appear hung when signals.db is locked by a long check run.

## Severity Calibration

- **P1**: Health command reads signal_state and ratchet_state without a transaction
  - When: A concurrent ockham check is mid-evaluation. Health returns signals showing 2 themes fired (BYPASS state) but ratchet_state shows all domains at 'supervised' (post-resume state from a different concurrent run). Meadowsyn displays contradictory data.
- **P1**: Resume transaction targets wrong tier filter
  - When: SQL is UPDATE ratchet_state SET tier='supervised' with no WHERE clause — resets shadow and supervised domains to supervised as well. Shadow domains that were never autonomous get promoted prematurely.
- **P2**: WAL file deletion in recover() races with concurrent ockham health read
  - When: ockham health has the DB open in WAL mode. recover() deletes the -wal file mid-read. SQLite returns SQLITE_IOERR or produces corrupt read results for the health command.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

SQLite WAL mode allows concurrent readers and one writer, but Go's database/sql pool can open multiple connections that compete. A CLI tool that opens and closes the DB on every invocation is not the same risk profile as a long-running server. Understand which operations are atomic at the SQL level vs. which require explicit transactions. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.
