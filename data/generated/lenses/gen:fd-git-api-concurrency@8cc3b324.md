## Task Context

The brainstorm proposes using GitHub's REST Contents API for file CRUD in a bidirectional sync system. Local filesystem changes trigger writes to GitHub; GitHub push webhooks trigger local writes. The design uses path-based correlation, a hybrid push-webhook-plus-poll detection strategy, and three-way merge via AncestorStore for conflict resolution.

## Review Approach

### 1. The brainstorm accounts for SHA staleness: when interop reads the current file

- Verify the brainstorm accounts for SHA staleness: when interop reads the current file SHA to include in a PUT, a concurrent push from another writer can land between the GET and PUT, causing the PUT to return a 409 Conflict — the design must specify a retry strategy (re-fetch SHA, re-attempt) with a bounded retry count and backoff

### 2. Whether the one-commit-per-file-write assumption is acceptable given interop's

- Check whether the one-commit-per-file-write assumption is acceptable given interop's expected sync volume: if 10 markdown files change in a 5-second burst (e.g., a bulk edit), the Contents API will create 10 separate commits on the default branch, polluting the commit history — the design should state whether this is intentional and whether batching via the Git Data API (trees/blobs) is a future escape hatch

### 3. The design specifies what happens when a Contents API PUT fails with a 422

- Confirm the design specifies what happens when a Contents API PUT fails with a 422 (file too large, content encoding error) or 403 (branch protection rule): these are non-retryable errors that require the sync to dead-letter the event, not retry indefinitely

### 4. That the brainstorm addresses the GitHub secondary rate limit (previously

- Validate that the brainstorm addresses the GitHub secondary rate limit (previously 'abuse detection'): creating many commits in a short window triggers a 403 with a Retry-After header — the sync adapter must honor this header and queue pending writes rather than hammering the API

### 5. Whether delete operations are covered: if a local file is deleted

- Check whether delete operations are covered: if a local file is deleted, the Contents API requires both the SHA and a commit message to delete — the design must specify how the adapter retrieves the SHA for a file that no longer exists locally before issuing the DELETE

### 6. Assess whether the design handles non-default encoding: GitHub's Contents API

- Assess whether the design handles non-default encoding: GitHub's Contents API returns file content as base64, and the adapter must decode correctly for UTF-8 text — multi-byte sequences corrupted during base64 decode produce silent data loss

## Severity Calibration

- **P0**: Two concurrent local saves to the same file (common in editors that write-rename atomically) cause interop to issue two nearly simultaneous PUT requests; the first succeeds and advances the SHA, the second carries the stale SHA and returns 409 — if the adapter treats 409 as a terminal error rather than a retryable conflict, the file diverges silently between local and GitHub
  - When: When the SHA-based optimistic concurrency retry loop is absent or treats 409 as a dead-letter condition rather than a re-fetch-and-retry
- **P1**: A GitHub branch protection rule (required status checks, required reviewers) blocks direct pushes to the default branch — every interop write returns 403, the sync adapter dead-letters the event, and the user never learns why their local changes are not appearing on GitHub
  - When: When the design assumes unrestricted push access to the default branch and does not check for branch protection rules during configuration or emit a distinct error category for authorization failures
- **P2**: A user saves 20 files in a docs/ bulk rename — interop emits 20 fs:file:* events that each result in a separate GitHub commit within seconds, triggering GitHub's secondary rate limit and causing a 403 with Retry-After: 60; subsequent writes queue but the adapter's in-memory queue is lost on restart
  - When: When the rate limit handling strategy does not persist the pending write queue to durable storage (e.g., the SyncJournal) before honoring the Retry-After delay

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Every file write through the Contents API is an optimistic transaction; any design that does not model the SHA staleness window — the gap between a GET for the current SHA and the subsequent PUT — is silently broken under concurrent access. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
