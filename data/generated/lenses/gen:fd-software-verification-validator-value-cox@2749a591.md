## Severity Calibration

- **P0**: Executor and validator both pass an implementation that violates the actual goal because the frozen plan omitted the load-bearing requirement, making three pilots falsely validate the architecture.
  - When: The design treats agreement against incomplete criteria as end-to-end correctness.
- **P1**: The pilots cannot tell whether Opus found any defect the executor's verify block would not have found, so Q-A remains unanswerable after spending the validation budget.
  - When: No unique-catch taxonomy, counterfactual, or evidence log is defined before execution.
- **P2**: A nondeterministic verify block causes repeated validator FAIL results and frontier escalation even though the implementation is correct.
  - When: The verdict protocol cannot distinguish product failure from test flake or environmental failure.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Repeating the same check is not independent evidence; a validator earns its cost only by reducing a specified false-acceptance or false-rejection risk through a distinct observation, interpretation, or fault model. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.
