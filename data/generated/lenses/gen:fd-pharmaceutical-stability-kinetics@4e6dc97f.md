## Review Approach

### 1. EMA cold-start initialization: the Python implementation must specify what

- EMA cold-start initialization: the Python implementation must specify what value is used before any observation is recorded — if it initializes to 0.0, the first 'engaged' event produces 0.1 (not the full weight), creating a systematic cold-start suppression bias that the Go port must replicate exactly or consciously diverge from with documented justification

### 2. Alpha and floor immutability across Store implementations: Tracker.RecordEvent

- Alpha and floor immutability across Store implementations: Tracker.RecordEvent must receive alpha and floor as constructor parameters fixed at Tracker initialization, not as per-call arguments — if a caller can vary alpha between calls on the same lensID, the EMA series is mathematically invalid as a measurement of lens effectiveness

### 3. Exploration bonus interaction with EMA sequence: the +0.15 exploration bonus

- Exploration bonus interaction with EMA sequence: the +0.15 exploration bonus for usage_count < 3 must be applied after the EMA update or before — the order changes the numeric result; document which the Python source does and verify the Go port matches to the same decimal precision

### 4. Floating-point accumulation across long series: after 10,000 RecordEvent calls

- Floating-point accumulation across long series: after 10,000 RecordEvent calls on a single lensID, the EMA value must remain within the [floor, 1.0] range; verify that the floor clamp is applied after every update (not just on read) and that repeated engaged events cannot overflow the EMA above 1.0 due to float64 accumulation

### 5. Store interface numeric contract: the in-memory Store returns float64 EMA

- Store interface numeric contract: the in-memory Store returns float64 EMA values; if a caller-provided persistence implementation serializes to JSON or SQL with truncated precision (e.g., REAL column instead of DOUBLE PRECISION), the reconstituted EMA will drift on the first RecordEvent after restoration — the Store interface must specify the required numeric precision

### 6. Concurrent RecordEvent safety on the same lensID: two goroutines calling

- Concurrent RecordEvent safety on the same lensID: two goroutines calling RecordEvent with the same lensID simultaneously must produce a deterministic serialized result — if the in-memory Store uses a map without a per-key mutex, the EMA update (read-modify-write) has a race condition that produces a non-reproducible effectiveness score

## Decision Lens

An EMA implementation is correct only if: (1) initial state is explicitly specified and matches the design intent (cold-start bias versus steady-state initialization); (2) the decay constant alpha and the floor value are immutable for the lifetime of a tracking series — changes invalidate all prior observations for comparison purposes; (3) the EMA value after N observations is bit-reproducible given the same input sequence, regardless of execution order or goroutine scheduling. Any deviation from these three conditions means the effectiveness score is not a measurement of the lens — it is a measurement of the implementation's numeric history.
