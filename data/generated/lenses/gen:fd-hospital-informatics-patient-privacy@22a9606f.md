## Task Context

Review the Garden Salon encryption design brainstorm through the lens of health informatics — does the proposed architecture protect participant content from the operator with the same rigor hospitals protect patient data from IT staff?

## Review Approach

### 1. Is there a 'minimum necessary' principle

- Is there a 'minimum necessary' principle — does each component (relay, AI proxy, governance engine) access only the content fields it strictly needs, or does it decrypt the entire garden?

### 2. Is there a 'break

- Is there a 'break-the-glass' protocol — a documented, auditable, consent-gated emergency path for when the operator MUST access encrypted content (e.g., abuse reports, legal subpoena)?

### 3. Does the key management model support care

- Does the key management model support care-team rotation — when a participant leaves or a new one joins, can keys be re-shared without re-encrypting the entire history?

### 4. Is there an audit trail that proves the operator never ac...

- Is there an audit trail that proves the operator never accessed plaintext — not just a promise of E2E, but a verifiable log that the server only handled ciphertext?

### 5. Does the 'Sealed Rooms' (Option 5) model account for the ...

- Does the 'Sealed Rooms' (Option 5) model account for the informed consent problem — do users understand exactly which features they lose when choosing encryption, like a patient choosing which data to share?

### 6. How does the design handle the 'consulting physician' pat...

- How does the design handle the 'consulting physician' pattern — a temporary participant who needs access to a subset of garden content without getting the master key?

## Severity Calibration

- **P0**: No break-the-glass protocol exists — in a legal subpoena or abuse case, the operator has no way to access content, OR the operator can access content routinely with no audit trail
  - When: Missing emergency access protocol or missing access audit
- **P1**: When a participant is removed from a garden, the encryption key is not rotated — the removed participant can still decrypt new content using the old key
  - When: No key rotation on membership change
- **P2**: The AI proxy decrypts the entire garden state to extract one field — violates minimum necessary access
  - When: Over-broad decryption scope

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Patient data must be accessible to the care team but invisible to the hospital's IT department. The system operator runs the infrastructure but must not be able to read the charts. Every access is logged, every exception justified, and the patient can audit who saw what. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
