## Task Context

interflux uses a 2-stage dispatch pipeline. Stage 1 runs top agents, Stage 2 expands based on findings. Currently all use models from a single pre-dispatch resolution call.

## Review Approach

### 1. Model resolution timing

- Model resolution timing — does re-resolving at Step 2.2b create race conditions with concurrent Stage 1 completions?

### 2. State consistency

- State consistency — can a Stage 2 agent receive a stale model assignment if expansion scoring and routing overlap?

### 3. Idempotency

- Idempotency — does calling routing_adjust_expansion_tier multiple times produce the same result?

### 4. Edge case: all Stage 2 agents are exempt

- Edge case: all Stage 2 agents are exempt — does the adjustment loop degrade gracefully?

### 5. Integration with incremental expansion (Step 2.2a.6)

- Integration with incremental expansion (Step 2.2a.6) — speculative launches happen during Stage 1, before expansion scoring completes

## Severity Calibration

- **P0**: Safety-critical agent dispatched below min_model floor
  - When: Safety floor applied before downgrade instead of after
- **P1**: Stage 2 agent receives model from Step 2.0.5 cache instead of adjusted model
  - When: Dispatch reads stale model map after adjustment
- **P2**: Speculative launches use unadjusted model while later Stage 2 agents get adjusted models
  - When: Inconsistent tier within same expansion pool

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
