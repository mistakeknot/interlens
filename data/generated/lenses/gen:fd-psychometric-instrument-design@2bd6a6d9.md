## Task Context

The lens calibration pipeline feeds a 291-lens selection system for Auraken's cognitive augmentation agent. The anchor suite and near-miss scenarios become the implicit test battery for evaluating lens selection quality in production. - Consensus as criterion validity: High inter-model agreement is used as the anchor criterion, but model consensus is not the same as human expert consensus and is not the same as actual utility. What is the theoretical justification for treating model agreement as a proxy for lens applicability? Has any held-out validation been run against human expert selections?

### 3. Lens library construct coverage: The 291-lens library with scale/tier metadata

- Lens library construct coverage: The 291-lens library with scale/tier metadata implies a latent taxonomic structure. Has the library been subjected to any factorial analysis to check for redundancy, coverage gaps, or correlated clusters that could inflate apparent diversity in the cookoff results?

### 4. Position bias as measurement artifact: The finding that models over-select

- Position bias as measurement artifact: The finding that models over-select early-indexed lenses is a classic response set problem in psychometrics. The bias-correction approach must go beyond reweighting -- it should verify the corrected scores do not introduce systematic deflation of genuinely early-positioned strong lenses.

### 5. Near-miss scenario validity: build_anchor_suite.py extracts high-disagreement

- Near-miss scenario validity: build_anchor_suite.py extracts high-disagreement scenarios as near-misses. In psychometric terms this is like using hard items (high discrimination) as your test battery. Are high-disagreement scenarios actually ambiguous-domain scenarios, or are they noise from model idiosyncrasies? These are not equivalent.

### 6. Reliability estimation: What is the test-retest reliability of the lens

- Reliability estimation: What is the test-retest reliability of the lens selection signal? If lens_cookoff.py were re-run with different random seeds (for models that have temperature), would the anchor/near-miss classification be stable? An unstable classification is a reliability problem, not a calibration problem.

## Severity Calibration

- **P1**: The anchor suite is built on a stimulus corpus with systematic topic gaps -- if 8 of 17 topic groups are over-represented in the dilemma dataset, anchor scenarios cluster in those domains, leaving the lens library uncalibrated for under-represented domains that Auraken will encounter in production.
  - When: No topic-stratified sampling check, no coverage report by topic group before anchor extraction.
- **P1**: Position bias correction over-deflates scores for lenses 0-30 in the library, systematically excluding lenses that are both genuinely strong and early-indexed -- anchors reflect corrected-for-artifact bias rather than corrected-for-response-set signal.
  - When: Bias correction subtracts a flat position weight without checking whether the correction coefficient is heteroscedastic across lens tiers.
- **P2**: High-disagreement near-miss scenarios are driven by model idiosyncrasies (one model never selects lenses in certain topic groups due to training data gaps) rather than genuine domain ambiguity, causing the near-miss suite to encode model quirks instead of calibration-relevant edge cases.
  - When: No per-model outlier detection before using disagreement as the near-miss criterion; no check for model-specific topic blindspots.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Measurement validity has three pillars: construct validity (are you measuring what you think you're measuring), reliability (would you get the same answer twice), and criterion validity (does the measurement predict real-world outcomes). Evaluates the pipeline against all three: the lens library is an implicit theoretical model of moral reasoning frameworks, the dilemma battery is the test stimuli, and model agreement is the scoring key. Each layer can introduce construct-irrelevant variance that masquerades as signal. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
