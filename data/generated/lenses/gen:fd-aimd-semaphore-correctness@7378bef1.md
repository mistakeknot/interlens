## Severity Calibration

- **P1**: A connection error causes sem.acquire() to succeed but sem.release() is never called (exception path), permanently consuming one permit per failure until the semaphore deadlocks at 0 available permits
  - When: The exception handler in llm_call's retry loop does not call sem.release() on non-rate-limit errors
- **P1**: After rate-limit recovery, the semaphore stays at minimum=1 forever because ramp-up threshold is ceil(current)=1 consecutive successes needed, but each success immediately triggers a ramp attempt, causing the semaphore to oscillate between 1 and 2 indefinitely

- **P2**: Two concurrent processes both read a stale cooldown_until of 0, both immediately proceed, both hit 429, and both write competing cooldown_until values — the second write may overwrite the first with a shorter cooldown
  - When: State file write is not atomic (no temp-file-then-rename pattern)

## Decision Lens

Prioritizes permit accounting bugs that permanently reduce concurrency (leaked permits never restored) and cross-process races that cause all processes to wait on a stale cooldown. A semaphore that gets stuck at concurrency=1 kills throughput silently. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.
