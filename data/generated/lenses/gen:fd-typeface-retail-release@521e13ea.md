## Severity Calibration

- **P1**: install.sh fetches a resource from github.com at runtime (e.g., the auraken-lens binary via go install pointing to HEAD) rather than from the pinned release asset — the tarball is not self-contained and breaks when the live repo changes
  - When: Practitioner installs v0.1.0 six months later and gets v0.2 behavior from the binary, contradicting the pinned MANIFEST
- **P1**: MANIFEST.yaml lists gpt-5.4 and gpt-5.5 in the model matrix without noting that 'register drift is observed' — a practitioner installs expecting full compatibility and gets degraded behavior with no warning
  - When: The brainstorm mentions 'observed register drift documented' but MANIFEST does not surface this as a caveat
- **P2**: Release tag scheme 'auraken-distribution/v0.1.0' uses a forward slash, which some git tooling renders as a nested tag path — tarball URL may behave differently than expected across GitHub release UIs and curl invocations
  - When: One-liner install breaks on certain curl/tar combinations because of tag path resolution

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Success Criteria

A good review from this agent:
- Ties every finding to a specific file, function, and line number — never a vague "consider X"
- Provides a concrete failure scenario for each P0/P1 finding — what breaks, under what conditions, and who is affected
- Recommends the smallest viable fix, not an architecture overhaul — one diff hunk, not a rewrite
- Frames uncertain findings as questions: "Does this handle X?" not "This doesn't handle X"
- Every compatibility claim in MANIFEST.yaml should carry a 'tested' or 'expected' qualifier — practitioners can work with honest uncertainty, not with false precision
- The one-liner install curl URL should be stable even if the repo is renamed — use a direct asset URL, not a redirect through the repo root
- excluded_from_v01 is most useful when each entry names the version where the feature lands — 'thinker-profile-mcp → v0.3 (sylveste-i0px)' is actionable; 'thinker-profile-mcp: deferred' is not

## Decision Lens

A font release that ships with an overstated compatibility matrix destroys trust immediately — the designer who claims 'works in all apps' and then fails in Figma gets a refund request and a one-star review. State exactly what was tested; mark everything else 'expected to work, untested.' If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
