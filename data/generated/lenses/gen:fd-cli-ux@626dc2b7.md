## Review Approach

### Key Review Areas

- **Help text completeness and example coverage**: Check that `agentmud serve --help`, `agentmud-agents validate --help`, and all subcommands have clear, informative help text. Verify that common workflows (generate, validate, serve, evaluate, submit) are documented with usage examples. Flag missing or misleading help text.

- **Flag naming consistency across subcommands**: Verify that flags are named consistently across the Go kernel CLI and Python agent pipeline CLI. Check that `--pack`, `--kernel-url`, `--token`, `--server` etc. use the same names and semantics everywhere. Flag inconsistencies between the two CLI surfaces.

- **Interactive prompt design and validation**: Check that the SSH player interface provides clear prompts, helpful error messages for unknown commands, and discoverable help. Verify that agent-facing JSON mode is clearly separated from human-facing text mode. Flag cases where the player sees raw JSON or internal error codes.

- **Output formatting modes (human, JSON, table)**: Verify that CLI tools support both human-readable and machine-parseable output. Check that `--json` flags produce structured output for all relevant commands. Flag commands that only produce human-readable output when agents need to parse the results.

- **Error message actionability**: Check that validation errors, connection failures, and pack loading errors tell the user exactly what went wrong and how to fix it. Verify structured error codes are used consistently. Flag generic error messages ("invalid input", "failed") that don't help the user.

### How to Review

1. **Read before judging** — understand the existing approach before suggesting changes
2. **Be specific** — reference actual files, functions, and line numbers
3. **Prioritize** — distinguish must-fix issues (P0/P1) from improvements
4. **Respect context** — the team may have intentional trade-offs you're not aware of

## Focus Rules

- Only flag issues within your domain (command discoverability, help text quality, flag consistency, interactive vs scriptable behavior)
- Don't duplicate findings that core fd-* agents would catch (architecture, safety, correctness, quality, performance, user-product)
- Keep recommendations actionable — suggest concrete changes, not abstract principles
- When uncertain, frame as a question rather than a finding
