  - When: If the Zod schema for `when.politics_posture` defines its enum as `z.enum(['true-believer', 'traditionally-loyal', ...])` with the values typed inline rather than imported from the canonical axis-vocabulary module, then when the politics-posture axis renames `feed-skeptical` to `platform-skeptical` in a future lock, the YAML schema continues to accept `feed-skeptical` as valid while the engine's axis registry has already dropped it. The Zod validation passes, the engine silently fails to match any candidates for that value, and the bias is silently dropped.
- **P1**: Zod error output names array indices, not YAML rule content — author cannot locate the failing entry
  - When: If `biasMatrix.ts` throws `ZodError: biases[23].when['region'] Invalid enum value. This is not a hypothetical — Zod's default output format does not include surrounding content. Without a location-aware error formatter, the `source:` field becomes useless as a debugging aid.
- **P1**: Option-ε reserved fields with wrong types are silently coerced rather than rejected at boot
  - When: If `deviationRollFor` is defined as `z.array(PoliticsPostureEnum).optional()` and the YAML author writes `deviationRollFor: true-believer` (a string instead of an array), YAML parses this as a string, and Zod's `.optional()` behavior on a present-but-wrong-type value depends on whether `.optional()` wraps the inner type validator. If the Zod definition is `z.optional(z.array(...))` rather than `z.array(...).optional()`, the behavior differs: one form accepts a string-valued field, the other rejects it. This is a real Zod gotcha that causes boot-time silent acceptance of structurally wrong optional fields.
