## Task Context

Elf Revel native full-screen Rust colony sim evaluating 6 rendering options including raw wgpu, macroquad, and Bevy 0.18. Needs 100K+ glyphs at 60fps in a top-down ASCII-aesthetic grid. Target hardware: Apple Silicon native (primary), WASM browser (secondary). Team size: solo/small. The raw wgpu and macroquad options compete against Bevy on performance vs ergonomics.

## Review Approach

### 1. Bevy rendering overhead at 100K glyph scale: Bevy 0

- Bevy rendering overhead at 100K glyph scale: Bevy 0.18's render pipeline runs entity extraction (copying Transform+Sprite data from the main world to the render world), prepare (binding groups), and queue (sorting by key) every frame; at 100K entities these phases take measurable time; estimate whether a hand-written instanced quad renderer (single InstanceBuffer update, single draw call) could save 3-5ms per frame that Bevy cannot recover

### 2. Raw wgpu instanced quad renderer design: the minimal viab...

- Raw wgpu instanced quad renderer design: the minimal viable glyph renderer is one wgpu::Buffer with per-instance data (world_xy: vec2, atlas_uv: vec4, fg_color: u32, bg_color: u32) uploaded via queue.write_buffer() each frame, one wgpu::RenderPipeline with a vertex shader that reads instance data, one bind group for the atlas texture — evaluate whether this design correctly handles the 100K glyph case and what the GPU memory footprint is

### 3. Macroquad evaluation: macroquad provides Rust 2D renderin...

- macroquad evaluation: macroquad provides Rust 2D rendering with a simple draw_texture_ex API and handles wgpu/OpenGL abstraction; its WASM support is mature but has known issues with texture atlas memory on mobile; evaluate whether macroquad's glyph drawing API is expressive enough for per-glyph foreground/background color, depth layering, and custom fragment shader effects, or whether it requires dropping to macroquad's low-level API anyway

### 4. Frame

- Frame-to-frame buffer update strategy: for a colony sim, most tiles do not change each frame; evaluate a dirty-tile tracking strategy where the InstanceBuffer is only partially updated (via write_buffer with byte offset) for changed tiles, versus a full re-upload of all 100K instances — at what change rate does full re-upload become cheaper than partial update bookkeeping?

### 5. WGSL shader complexity for multi

- WGSL shader complexity for multi-layer glyph compositing: the fragment shader must composite terrain glyph + entity overlay + weather effect with correct alpha blending; in Bevy this is handled by the render graph; in raw wgpu it requires a manual multi-pass render setup or a single-pass shader with layer selection logic — evaluate the shader complexity and whether it remains maintainable

### 6. Long

- Long-term maintenance cost assessment: a custom wgpu renderer is a significant codebase investment; estimate LOC to implement (vertex buffers, index buffers, texture management, render pass, depth/stencil if needed, resize handling, HiDPI support) and compare against Bevy's amortized maintenance cost; identify which rendering features Elf Revel actually needs that Bevy cannot provide

## Severity Calibration

- **P0**: The raw wgpu renderer is chosen to save 3ms vs Bevy, but the 6-month implementation timeline delays the game's first playable milestone — the performance optimization was premature given that Bevy's overhead was never profiled on the actual target hardware
  - When: Architecture decision made without a Bevy 2D benchmark at colony scale; raw wgpu chosen based on theoretical overhead rather than measured frame time
- **P1**: The custom InstanceBuffer approach re-uploads all 100K glyph instances every frame via queue.write_buffer(), consuming 800KB of CPU→GPU bandwidth per frame (8 bytes × 100K instances at 60fps = ~48MB/s) and causing PCIe contention on integrated Apple Silicon that degrades performance below Bevy
  - When: No dirty-tile tracking; full InstanceBuffer re-upload per frame regardless of how many tiles changed; bandwidth cost not profiled on target hardware
- **P2**: macroquad is chosen for prototyping speed but its draw_texture_ex API does not support per-quad custom fragment shader parameters — foreground and background color tinting requires calling draw_texture_ex twice per glyph (once for bg, once for fg with alpha), doubling draw calls and breaking the original performance rationale
  - When: macroquad selected without verifying per-glyph dual-color rendering capability; API limitations discovered after prototype is built

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
