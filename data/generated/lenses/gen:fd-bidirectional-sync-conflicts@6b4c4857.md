## Task Context

Bidirectional sync across four systems (GitHub, Notion, Beads, local FS) is the core value proposition of interop. The brainstorm notes three-way merge for content and LWW for metadata as the conflict resolution strategy, ported from interkasten. The correctness of this strategy depends on assumptions (trusted clocks, persisted ancestors, explicit policies per adapter pair) that are easy to get wrong in implementation. A sync daemon that silently loses writes is worse than no sync daemon at all.

## Review Approach

### 1. Three-way merge uses a stored common ancestor (the last successfully synced

- Verify that three-way merge uses a stored common ancestor (the last successfully synced version) rather than the current state of one side as the base -- using current Notion state as the base when a GitHub-side edit exists produces a merge that silently discards the GitHub edit if the Notion version is newer by timestamp

### 2. Last-write-wins for metadata uses a trusted monotonic clock source

- Check that last-write-wins for metadata uses a trusted monotonic clock source, not wall-clock timestamps from external systems -- Notion API timestamps, GitHub event timestamps, and local filesystem mtime can all be skewed, and LWW decisions based on skewed clocks silently discard valid writes from the losing system

### 3. That the conflict resolution policy is per-adapter-pair and configurable

- Confirm that the conflict resolution policy is per-adapter-pair and configurable, not a global setting -- the right policy for Beads<->GitHub (issues are authoritative on beads) is different from Notion<->local FS (local edits are authoritative for drafts) and different again from Notion<->GitHub repo files (repo is source of truth for code docs)

### 4. That unresolvable conflicts (both sides changed the same field with no common

- Validate that unresolvable conflicts (both sides changed the same field with no common ancestor) surface as a structured conflict record rather than being silently resolved by a tiebreaker -- silent tiebreaking means the user never knows data was overwritten

### 5. The common ancestor store is persisted across daemon restarts -- if interop

- Check that the common ancestor store is persisted across daemon restarts -- if interop restarts and loses the last-sync state, the next sync cycle treats the current state of both systems as diverged from an empty base, potentially producing a merge that combines all content rather than detecting no change

### 6. The migration of interkasten's WAL and conflict history into interop's ancestor

- Ensure that the migration of interkasten's WAL and conflict history into interop's ancestor store is planned -- without migrating the ancestor store, the first sync after migration treats all existing Notion<->beads sync history as starting from scratch, triggering false conflicts on every previously-synced item

## Severity Calibration

- **P0**: A bead is updated in both beads and GitHub Issues while interop is briefly offline. When interop restarts, it has lost the common ancestor because the ancestor store is in-memory only. It resolves the conflict by taking the Notion-side version (per its tiebreaker rule), silently discarding the beads-side update. The beads update is permanently lost with no error or conflict record.
  - When: When the common ancestor store is in-memory (not persisted to disk or a database) and daemon restart resets all sync state to unknown
- **P1**: Beads<->GitHub sync uses GitHub event timestamps as the LWW clock. A developer's machine clock is 3 minutes ahead. She closes a GitHub issue from her machine at 10:00:00 (real time 09:57:00). The beads close event fires at 09:57:30 (real time). LWW picks the GitHub close (timestamp 10:00:00 > 09:57:30) even though the beads close happened first -- the underlying skew means any bead update in the next 3 minutes will be silently overwritten by any GitHub event
  - When: When LWW uses event-originating-system timestamps rather than interop's own receive-time monotonic clock for ordering decisions
- **P2**: After the interkasten-to-interop migration, interop's ancestor store has no history for any Notion database that interkasten previously synced. The first sync run produces a false conflict for every page that has been edited since the last interkasten sync, prompting the user to manually resolve hundreds of spurious conflicts
  - When: When the migration plan does not include converting interkasten's WAL/sync-state records into interop's ancestor store format before the first sync run

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Sync correctness means: no data is lost silently, no false conflict is raised for a true concurrent modification, and no resolved state is worse than leaving the conflict unresolved. Evaluates every merge decision against: what is the common ancestor, are clocks trustworthy, and can the user recover if the merge is wrong? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
