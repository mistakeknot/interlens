## Review Approach

### 1. Phase type exhaustiveness: if Phase is defined as a string or untyped int

- Phase type exhaustiveness: if Phase is defined as a string or untyped int constant, the Go compiler cannot reject an invalid NextPhase return; it must be a typed enum with a default case that returns an explicit error — not a silent no-op — to mirror interlocking 'unknown route' handling

### 2. Transition guard atomicity: NextPhase reads StackOrchestrator state and writes

- Transition guard atomicity: NextPhase reads StackOrchestrator state and writes the next phase as two separate operations; without a mutex covering both, a concurrent caller can observe the state between read and write, producing a split-brain phase where two goroutines believe they own the current phase

### 3. Deadlock-free serialization proof: if StackOrchestrator is wrapped in a mutex

- Deadlock-free serialization proof: if StackOrchestrator is wrapped in a mutex and NextPhase calls any callback that itself acquires a lock (e.g., the Tracker.RecordEvent persistence callback), the call graph must be proven lock-order-consistent to eliminate circular wait — interlocking lore calls this the 'conflicting route' failure mode

### 4. Session persistence round-trip invariants: StackOrchestrator serializes to JSON

- Session persistence round-trip invariants: StackOrchestrator serializes to JSON for session persistence; after deserialization, the reconstituted state machine must be in exactly the phase the serialized form claimed — verify that all unexported fields that affect transition behavior are either exported and serialized or re-derived deterministically from exported state

### 5. Phase terminal detection: interlocking systems have explicit 'route cancelled'

- Phase terminal detection: interlocking systems have explicit 'route cancelled' states that prevent spurious re-activation; the stack orchestrator needs an explicit terminal state (stack exhausted, user disengaged) that NextPhase cannot transition out of, preventing infinite re-entry loops if a caller mishandles the end-of-stack condition

### 6. Transition template embedding: the three transition templates (deep_gold

- Transition template embedding: the three transition templates (deep_gold, shallow_gold, wax) embedded as constants must survive Go's string interning — if templates contain format verbs and are fed to fmt.Sprintf, a template corruption (e.g., missing verb argument) must produce a caught error, not a silent partial substitution that creates a malformed prompt sent to the LLM

## Severity Calibration

- **critical**: NextPhase is not mutex-guarded and StackOrchestrator is shared across goroutines in Skaffen's agentloop
  - When: Two concurrent agentloop iterations (e.g., a timeout retry and a normal completion) both call NextPhase simultaneously — one reads Phase N, the other reads Phase N, both compute Phase N+1, and both write it; the orchestrator skips a phase silently, causing the wrong transition template to fire for the remainder of the session without any error signal
- **high**: Phase is defined as a string type with no exhaustiveness check on NextPhase's switch statement
  - When: A future contributor adds a new Phase constant for a fourth template variant but fails to add a case to the NextPhase switch; Go compiles without warning, the new phase silently falls through to the default no-op, and users whose sessions enter the new phase receive no lens stack progression — the failure is invisible in logs until session analytics reveal a cohort of stalled sessions
- **medium**: JSON serialization omits the internal phase history slice used for loop detection
  - When: After a session is persisted and restored, the deserialized StackOrchestrator has an empty phase history; if the underlying user conversation loops (user repeatedly rephrases the same question), the loop detection that would have triggered a transition to the wax template never fires post-restoration, causing the orchestrator to cycle the same phase indefinitely

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

A state machine is safe only when: (1) every reachable state is enumerated in the type system, not just the happy-path states; (2) every transition has an explicit guard condition that is evaluated atomically with the state write; (3) concurrent entry to a transition handler produces a deterministic serialization outcome, not undefined behavior. Any stack orchestrator that relies on caller discipline rather than type-enforced state transitions is a latent derailment. StackOrchestrator.NextPhase must be provably non-reentrant or explicitly mutex-guarded, and all Phase constants must be typed enums that the compiler rejects unknown extensions of. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.
