## Task Context

Auraken applies lens stacks for multi-phase problems — sequential application of different conceptual frameworks. The Etak lens asks whether these stacks are architected as reference frame management (each lens redefines the coordinate system) or as additive analysis (each lens adds a layer to a fixed problem). Carolinian navigators solved an identical challenge: how to apply multiple contradictory spatial reference frames sequentially without losing orientation, across a voyage where the 'landscape' (open ocean) provides no external landmarks.

## Review Approach

### 1. Does Auraken's lens stack architecture treat sequential lenses as reference

- Does Auraken's lens stack architecture treat sequential lenses as reference frame shifts (each lens redefines what is held fixed and what is examined) or merely as additive filters (each lens adds a new perspective to the same fixed frame)?

### 2. How does the system manage the cognitive load of holding multiple reference

- How does the system manage the cognitive load of holding multiple reference frames — does it help users maintain orientation during transitions, or does rapid frame-switching cause 'navigation loss' where the user loses track of their original problem?

### 3. Is there a concept of 'Etak segments'

- Is there a concept of 'Etak segments' — recognized phases of a problem-solving voyage where different reference frames are appropriate, with explicit transition markers between segments?

### 4. Do contraindications detect when a reference frame shift would cause

- Do contraindications detect when a reference frame shift would cause disorientation (the user is not ready to abandon their current frame) vs. when the current frame is exhausted and a shift is necessary?

### 5. How does the system handle the 'moving island' inversion

- How does the system handle the 'moving island' inversion — situations where the user's assumed fixed point (their framing of the problem) is actually the thing that needs to move, and the lens stack must engineer this inversion without the user losing orientation?

### 6. Is there a 'dead reckoning' fallback

- Is there a 'dead reckoning' fallback — when all reference frames are uncertain, does the system have a method for maintaining approximate orientation using accumulated micro-observations rather than any single framework?

## Severity Calibration

- **P0**: Lens stacks cause navigation loss
  - When: Rapid sequential lens application causes the user to lose track of their original problem — they have been through three reframings and can no longer connect the analysis back to their actual situation. The lens stack disorients rather than reorients.
- **P1**: No reference frame transition management
  - When: Lens stacks treat each lens as an independent analysis pass rather than as a reference frame shift — the system never helps the user understand that lens B redefines what lens A held fixed, so the insights don't compose into a navigational path
- **P2**: Contraindications ignore readiness for frame shift
  - When: The system checks whether a lens fits the problem but not whether the user is ready to abandon their current reference frame — like telling a navigator to switch star courses before they have confirmed their current position

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Etak reference frame management — complex navigation requires holding multiple reference frames simultaneously and knowing which one to foreground at each phase. A lens stack is not a sequence of filters applied to a fixed problem — it is a sequence of reference frame shifts where each lens redefines what counts as 'stationary' (the fixed assumption) and what counts as 'moving' (the variable under investigation). Contraindications signal when a reference frame shift would cause disorientation rather than reorientation. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
