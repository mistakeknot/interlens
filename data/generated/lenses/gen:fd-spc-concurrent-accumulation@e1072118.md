## Decision Lens

A concurrent EWMA accumulator is correct only when: (1) every update is atomic — the read of the prior EWMA and the write of the new EWMA are a single critical section with no observable intermediate state; (2) the lock granularity matches the sharing unit — a single mutex on a struct that holds multiple independent EWMA series (one per mode) can be replaced by per-mode locks for better concurrency, but the brainstorm's decision to use a single mutex on Fingerprint is valid only if callers never need per-mode concurrent updates; (3) BuildMirroring reads a consistent snapshot — it must either acquire the lock for the duration of the read or copy the relevant fields under the lock and release before generating text. An EWMA that reads half its fields before a concurrent Update and half after is not reading a fingerprint — it is reading statistical noise. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.
