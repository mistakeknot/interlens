## Task Context

interop is a Go-based integration daemon connecting Notion, GitHub, beads, and local file system through adapter-based event-driven architecture. Data flows through multiple transformation layers: external webhook/event to internal event format to adapter-specific processing to cross-adapter routing. The urushi layering lens examines whether these transformation layers validate semantic integrity at each boundary, whether shared infrastructure can propagate corruption past adapter isolation, and whether the migration from interkasten properly verifies converted state.

## Severity Calibration

- **P0**: An adapter panics mid-event-processing after writing partial state to its local store but before acknowledging the event on the bus — the event is re-delivered on restart but the adapter's partial state causes a duplicate or conflicting write, silently corrupting the sync state for that entity across systems
  - When: When event processing and local state writes are not wrapped in a transaction or idempotency mechanism, and the event bus can re-deliver events to an adapter that has already partially processed them
- **P1**: The Notion-to-markdown transformation strips inline database references (Notion relation properties rendered as @-mentions) that interkasten preserved, and downstream consumers (beads sync, local file sync) silently receive markdown that is missing cross-references that were present in the original Notion content — the surface format looks correct but semantic content is lost
  - When: When the Notion adapter's content transformation does not have a coverage test for every Notion block type and property type, and novel or uncommon block types are silently dropped rather than flagged as unconvertable
- **P2**: The identity mapping table is a shared component accessed by all adapters, and a corrupt entry (GitHub user mapped to wrong Notion user) silently propagates wrong attribution across every adapter that resolves identity, with no per-adapter ability to detect or override the mapping
  - When: When the identity mapping is a single shared lookup with no per-adapter validation or override mechanism, and a mapping error is indistinguishable from correct operation until a human notices wrong attribution

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Every multi-layer data transformation pipeline evaluated as a lacquer layering problem: does each transformation layer cure (validate) completely before the next layer is applied? Are incompatible materials (data schemas from different systems) bonded through explicit interfacing treatments (type converters, schema mappers), or are they pressed together and hoped to adhere? Can a surface-level test (API response looks correct) mask a substrate defect (data semantically corrupted during transformation)? The urushi master knows that adding more layers never fixes a bad foundation — it only delays and obscures the failure. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
