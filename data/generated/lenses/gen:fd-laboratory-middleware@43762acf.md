## Task Context

Brainstorm for interop — a Go-based unified integration daemon replacing interkasten, bridging Notion, GitHub, beads, and local FS through goroutine-isolated adapters with an event bus hub, webhook-first sync, and three-way merge conflict resolution

## Review Approach

### 1. Adapter translation fidelity and round-trip testing: lab middleware must

- Adapter translation fidelity and round-trip testing: lab middleware must translate instrument-native result formats (ASTM, LIS01, proprietary serial protocols) to HL7 v2 messages without losing precision, units, or status codes — check whether each interop adapter (GitHub, Notion, beads) has a formal translation contract that specifies how every field in the external system payload maps to the canonical Event type, and whether round-trip tests exist that verify a Notion page webhook to canonical event to Notion API write produces bit-identical content

### 2. Bidirectional message correlation and the result-order problem: laboratory

- Bidirectional message correlation and the result-order problem: laboratory systems must correlate an outbound order (EMR to instrument) with an inbound result (instrument to EMR) using a specimen ID that must survive the round trip — assess whether interop bidirectional flows (beads to GitHub issue, GitHub comment to beads event) use a durable correlation ID that survives external system round-trips, and whether the correlation store handles out-of-order result delivery (a GitHub webhook arrives before the beads write completes)

### 3. Instrument interface versioning and the adapter lifecycle: lab middleware must

- Instrument interface versioning and the adapter lifecycle: lab middleware must manage instrument firmware upgrades that change result formats without a coordinated migration — check whether interop adapter interface specifies a versioning protocol for when external APIs change (Notion API version upgrades, GitHub webhook payload schema changes), and whether adapters can be updated independently without restarting the hub or disrupting other adapters

### 4. Critical value routing and priority escalation: lab middleware applies business

- Critical value routing and priority escalation: lab middleware applies business rules to route critical result values (e.g., glucose < 40) to urgent notification channels before normal result processing — assess whether interop event bus supports priority routing based on event content (a GitHub issue labeled P0 routes differently than a routine issue), or whether all events are treated uniformly regardless of semantic priority

### 5. Quality control and the calibration run: laboratory instruments run QC samples

- Quality control and the calibration run: laboratory instruments run QC samples periodically to verify calibration — if QC fails, the instrument results are quarantined until recalibration — check whether interop has an equivalent for adapter health: if a Notion adapter begins producing events that fail schema validation or consistency checks, does the hub quarantine that adapter output stream pending investigation, or does it pass malformed events downstream

### 6. Orphan result handling and the uncorrelated event: lab middleware occasionally

- Orphan result handling and the uncorrelated event: lab middleware occasionally receives results for specimens with no matching order — check whether interop handles the equivalent: a GitHub webhook for a repository the adapter has no bead mapping for, a Notion page update with no local file counterpart, and whether these uncorrelated events are logged, dead-lettered, or silently dropped

## Severity Calibration

- **P0**: A Notion page updated via the Notion adapter contains a bidirectional link to a local file; the canonical event stores the Notion block ID but not the local file path; when the event is routed to the FS adapter, the FS adapter cannot find the target file and silently drops the write — the Notion update succeeds, the local file is not updated, and the two systems silently diverge
  - When: When the canonical Event type does not carry enough routing context for every downstream adapter to resolve the target entity, and missing context causes silent drops rather than explicit errors
- **P1**: The GitHub adapter is updated to handle the new GitHub webhook payload format (v3 schema); the update changes the canonical event field names for PR events; the beads adapter, which consumes those events, is not updated simultaneously and silently ignores the renamed fields, causing GitHub PR to beads sync to stop working until the beads adapter is also updated
  - When: When canonical event schema changes are not versioned and adapters do not declare which schema version they consume, allowing silent incompatibilities between adapters updated at different times
- **P2**: The Notion adapter emits events for every block-level change in a Notion page during a bulk edit session, producing hundreds of events for a single user action; the beads adapter processes each event as an independent update, creating hundreds of beads history entries for one logical change; the event log is noisy and the downstream state is correct but unsearchable
  - When: When the adapter does not implement event debouncing or logical change aggregation, emitting one canonical event per external API event rather than per logical user action

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Does each adapter translate faithfully between the external system native protocol and the hub canonical event schema, the way laboratory middleware translates between instrument-native result formats and HL7 messages — with round-trip fidelity, schema version tracking, and field-level mapping audits? If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
