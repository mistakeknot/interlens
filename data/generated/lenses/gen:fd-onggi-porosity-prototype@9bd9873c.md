## Review Approach

### 1. What is the renderer's porosity?

- What is the renderer's porosity? — the essential functional constraint: onggi's identity is defined by a single functional constraint: the clay must breathe. Everything else (shape, size, decoration) is secondary. What is the ASCII colony sim renderer's porosity — the single functional property without which it is not itself? Candidates: (a) the rendering must produce a legible grid at terminal speed on WASM, (b) the visual output must be parseable as a colony sim map by a player familiar with the genre, (c) the renderer must support the full range of entity types without per-entity special-casing. Does the decision identify this essential constraint and evaluate every option against it FIRST, before evaluating secondary properties like visual richness or code reuse efficiency?

### 2. Material

- Material-level prototyping vs. paper-level design: you cannot determine an onggi clay body's porosity by analyzing the clay's composition on paper. You must fire a test piece and see if it breathes. Analogously: you cannot determine whether Bevy-in-WASM renders an ASCII colony sim acceptably by analyzing Bevy's architecture in a document. You must build a test piece — a minimal prototype that renders a representative scene — and see if it 'breathes' (performs acceptably, preserves aesthetic identity, fits in WASM binary size constraints). Does the decision include material-level prototyping (actually building and testing a minimal renderer with each candidate approach) before committing to an architecture? A paper comparison of Bevy vs. custom vs. lightweight tools is clay composition analysis — necessary but insufficient.

### 3. The prototype teaches

- The prototype teaches, production applies: in onggi, the test firing teaches whether the clay works. The production firing applies that knowledge to make vessels. These are different activities with different success criteria. A prototype onggi that cracks but proves the porosity is a SUCCESSFUL prototype. A production onggi that cracks is a failed vessel. Does the renderer decision plan distinguish between prototype success (we learned whether the approach works) and production success (the renderer ships and performs)? A Bevy prototype that takes a week and reveals fatal WASM size problems is a successful prototype. The same investment viewed as production work is a failure. The framing determines whether discovery is valued or punished.

### 4. Functional constraint as identity

- Functional constraint as identity, not aesthetic choice: onggi's rough surface, visible clay body, and absence of interior glaze are not aesthetic choices — they are functional necessities for porosity. A 'beautiful' onggi with interior glaze that blocks porosity is a failed vessel, not a successful aesthetic upgrade. The ASCII aesthetic has analogous functionally-necessary features: the grid structure enables spatial reasoning, the character-per-cell constraint enables rapid scanning, the limited color palette prevents visual overload. If the renderer 'upgrade' to rich multi-pixel tiles removes these functionally necessary constraints to achieve visual sophistication, it produces a beautiful vessel that cannot ferment — a renderer that looks impressive but fails at its primary function (supporting colony sim gameplay). Does the decision distinguish between aesthetic constraints that are functionally necessary (grid structure for spatial reasoning) and aesthetic constraints that are merely inherited (single character per cell because that's what terminals do)?

### 5. The kiln determines the clay

- The kiln determines the clay, not the other way around: onggi potters select their clay body based on the kiln they have — different kilns produce different peak temperatures and atmospheres, which determine which clay bodies achieve correct porosity. The analogous question: which 'kiln' does the renderer fire in? If the kiln is WASM-in-browser, the 'clay body' (renderer approach) must be selected for that kiln's constraints (binary size limits, no native GPU without WebGPU, JavaScript interop overhead, single-threaded by default). Selecting a clay body (Bevy+MetalFX) that achieves correct porosity in a different kiln (native macOS) and expecting it to work in the WASM kiln is a category error. Does the decision evaluate renderer approaches against the TARGET deployment kiln rather than against the sibling project's native kiln?

### 6. Living quality

- Living quality and metabolic participation: an onggi participates metabolically in fermentation — it is not an inert container but a living element of the system. The renderer is analogous: it should not be an inert display layer but should participate in the game's systems — procedural art generation that responds to game state, visual feedback that supports gameplay decisions, aesthetic properties that interact with the elf beauty system. Does the decision evaluate renderer approaches for their capacity to participate in game systems (living quality) rather than merely display them (inert containment)?
