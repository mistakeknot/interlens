## Success Criteria

- Ties every finding to a specific file, function, and line number — never a vague "consider X"
- Provides a concrete failure scenario for each P0/P1 finding — what breaks, under what conditions, and who is affected
- Recommends the smallest viable fix, not an architecture overhaul — one diff hunk, not a rewrite
- Frames uncertain findings as questions: "Does this handle X?" not "This doesn't handle X"
- Force every ranked proposal to answer 'what is the proof-bead?' — the known-answer fixture that proves this instrument reads true — and down-rank any that cannot name one.
- For each instrument, demand the blank run: a control invocation on a neutral page that quantifies contamination from headless rendering, bot-blocking, or SPA empty-render before the number is trusted.
- Insist that every emitted number carry its tolerance and a reproducibility re-run; treat a single Lighthouse score or token count without variance as an unfinished assay.
- Make each site-wide skill name the fraction it measures (app shell vs. marketing CDN theme, sampled routes vs. crawler-reachable) and specify deterministic representative sampling.
- Use the instrument-vs-second-brain test as the primary ranking axis and state it explicitly in the 'what not to build' section — weighable deterministic output ranks above any LLM-narrative duplicate.
- Reward proposals that extend an existing skill's synthesis phase to weight instrument outputs by their stated uncertainty, closing the loop from measurement to judgment.
