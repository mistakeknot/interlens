## Task Context

Palantir-style ontology format and architecture for a Rust ECS game (Elf Revel). The ontology maps typed objects with relationships across both a development meta-layer (555 game features, dependency graphs, audits) and an in-game simulation layer (ECS components, flora species, elf relationships, composition properties). Key tension: formal enough to query, lightweight enough for a solo Rust game project. Format candidates: RON, TOML, SQLite, markdown+frontmatter, Rust type system, RDF-lite, JSON-LD. The project was forked from agent-fortress and many architectural patterns are inherited. The project uses AI agents extensively for brainstorming and planning, creating multiple document sources that may describe the same entities differently.

## Review Approach

### 1. Colophon

- Colophon-as-provenance — tracking ontology entry origins: every Syriac manuscript has a colophon recording its creation context and source chain. The ontology's 555 features, ECS components, and entity definitions similarly need provenance: was this definition derived from the agent-fortress parent project (the exemplar)? Was it authored fresh for Elf Revel? Was it auto-generated from a brainstorm document? When did it last change? Who (human or AI agent) changed it? Without colophon-equivalent metadata, the ontology becomes an orphan text — claims without verifiable origin. Does the format naturally support per-entry provenance? SQLite can add created_at, source, modified_by columns. Markdown frontmatter can include provenance fields. RON has no natural metadata layer. Rust types carry no provenance at all. Which format makes colophons natural rather than bolted-on?

### 2. The stemmatic problem

- The stemmatic problem — resolving contradictions between sources: when a Syriac text exists in three manuscripts that disagree, stemmatic analysis traces the copying tree to determine which reading is earliest. The Elf Revel ontology may have contradictions between sources: the brainstorm document says flora species have 5 growth stages, the sprint plan says 3, the Rust code implements 4. These are variant readings of the same 'text.' Does the format support identifying and resolving such contradictions? A single-source-of-truth format (Rust types, SQLite) eliminates contradictions by fiat — there is only one manuscript. A multi-source format (markdown documents scattered across docs/) creates a transmission problem. If multiple sources exist, is there a stemmatic method for determining which is authoritative?

### 3. The palimpsest

- The palimpsest — layers of overwritten ontology: a palimpsest preserves earlier text beneath later overwriting. The Elf Revel ontology is being built on agent-fortress's architecture — the original 'text' (agent-fortress patterns) has been 'overwritten' with Elf Revel's adaptations. But the original patterns are still recoverable (the parent project exists at ../agent-fortress). Does the format preserve palimpsest-style layering — making it clear which ontology entries are inherited patterns, which are adaptations, and which are original? This is critical for understanding why an architectural decision was made. A flora species definition that descends from an agent-fortress mob definition has different design constraints than one invented from scratch.

### 4. Faithful copying vs

- Faithful copying vs. deliberate revision — inherited vs. modified definitions: Syriac scribes distinguished between faithful transcription and deliberate revision (correction, harmonization, interpolation). The ontology must similarly distinguish between definitions inherited unchanged from the parent project or brainstorm documents (faithful copies) and definitions modified to fit the current architecture (deliberate revisions). Does the format mark the difference? Without this distinction, a developer cannot tell whether a definition's current form is intentional (deliberate revision) or accidental (faithfully copied from an outdated source). Git history partially serves this role, but only if the ontology entries existed as distinct files from the beginning.

### 5. Recensions

- Recensions and branching — when the ontology forks: Syriac texts often exist in multiple recensions — the same work revised into distinct editions by different communities. The Elf Revel ontology may branch: a sprint plan creates one version of a feature's specification, implementation creates another, and post-implementation documentation creates a third. These are recensions of the same ontological entity. Does the format acknowledge that multiple recensions may coexist and provide a mechanism for reconciliation? Or does it assume a single canonical version exists at all times? Single-source formats (Rust types) enforce one recension. Multi-document formats (markdown) allow uncontrolled proliferation of recensions. Which approach matches the solo developer's actual workflow?

## Severity Calibration

- **P0**: The ontology has no provenance mechanism, and a definition inherited from the agent-fortress parent project is treated as an original Elf Revel decision — when the inherited definition turns out to be wrong for the new context, there is no record that it was inherited rather than deliberately designed, causing the developer to defend a decision they never actually made
  - When: The format has no per-entry provenance fields, the ontology is populated by bulk import from brainstorm documents or parent project, and at least 30% of entries are inherited rather than original
- **P1**: Multiple contradictory definitions of the same entity exist across brainstorm documents, sprint plans, and implementation code, with no stemmatic method for determining which is authoritative — the developer discovers the contradiction only when runtime behavior differs from their documentation-based expectation
  - When: The ontology format permits multiple sources to define the same entity (markdown docs in different directories, plus Rust code, plus RON data files) without a declared authority hierarchy or validation that detects contradictions
- **P2**: Ontology entries that were faithfully inherited from brainstorm documents are indistinguishable from entries that were deliberately designed for the current sprint, making it impossible to prioritize which entries need expert review vs. which have already been vetted
  - When: The format does not distinguish between entry sources (brainstorm-derived, plan-derived, implementation-derived, human-authored) and all entries appear equivalently authoritative regardless of their origin

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
