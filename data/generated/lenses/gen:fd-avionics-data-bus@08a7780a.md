## Task Context

Tuivision's annotated format delivers rich terminal state to LLM consumers that must act correctly on that state. The safety-critical parallel is the avionics requirement that display consumers correctly parse messages under degraded conditions — the same discipline applies to ensuring LLMs don't silently misparse annotated terminal state or act on transient frames.

## Review Approach

### 1. Mandatory vs. optional field discipline

- Mandatory vs. optional field discipline — ARINC 429 message words have a fixed set of mandatory fields (label, SDI, data, SSM, parity) and a defined set of optional equipment-specific extensions. The mandatory/optional split is explicitly certified. Assess whether the annotated format has an explicit mandatory/optional split: which attributes (text content, cursor position, inverse flag) are always present and which are optional (color, role, bold) — and whether compact mode correctly suppresses only optional fields.

### 2. Consumer failure mode classification

- Consumer failure mode classification — avionics systems classify consumer parse failures into: detectable with recovery (checksum mismatch -> request retransmit), detectable without recovery (unknown message type -> display X), and silent misparse (undetected wrong value -> wrong display). Assess whether the annotated format is designed so that an LLM that misparses [r fg=red] fails detectably (refuses to act, asks for clarification) rather than silently miscategorizing the terminal state.

### 3. Refresh rate vs. fidelity tradeoff and the compact default

- Refresh rate vs. fidelity tradeoff and the compact default — avionics displays choose refresh rate based on the parameter's criticality: altitude updates at 10Hz, cabin temperature at 0.1Hz. The format governs how much information fits in each transmission slot. Assess whether the compact default is calibrated against how often agents call get_screen (burst during active navigation vs. polling during wait states) and whether the format supports indicating 'I am in a wait state, send minimal data'.

### 4. Schema versioning and forward-compatibility certification

- Schema versioning and forward-compatibility certification — avionics systems require that new message formats are backward-compatible with all certified display software, and a format change requires re-certification. Assess whether the annotated format has a versioning mechanism (format header, schema version field) that allows future tuivision versions to add fields without breaking LLM consumers that were trained or prompted on the current schema.

### 5. BIT (Built-In Test) and self-validation

- BIT (Built-In Test) and self-validation — avionics messages include status bits that indicate whether the source data is valid, stale, or in test mode. Assess whether the annotated format has an equivalent: a way for the terminal capture to signal 'this screen is mid-render' or 'this is a loading state' rather than a stable UI state — reducing false positive actions from LLMs acting on transient terminal states.

## Severity Calibration

- **P1**: The compact default suppresses color information for cells where the LLM's correct action depends on color semantics (e.g., a status line where red=error, yellow=warning, green=ok) — the LLM reads the text content correctly but misses that a red error is present because compact mode omitted the fg attribute for 'unchanged from default' cells
  - When: When compact mode suppresses color attributes using a 'no change from default' optimization without defining what the default color is, causing the LLM to assume no color annotation means default-fg when the actual default differs between terminal themes
- **P1**: An LLM receives annotated output from a terminal mid-render (splash screen, loading bar, partial draw) and correctly parses the format but acts on the transient state — no mechanism in the format signals 'this is an unstable frame'
  - When: When the annotated format has no validity/stability signal and the brainstorm's wait_for_screen_change is a separate MCP call that agents must remember to use, rather than a stability indicator embedded in get_screen output
- **P2**: The role= attribute extension is added in a future version — LLMs prompted on the current schema see [r fg=red role=error] and interpret 'role=error' as an unknown attribute, possibly treating the entire marker as malformed rather than gracefully ignoring the unknown attribute
  - When: When LLM prompts that teach the [r]...[/] format describe the grammar as 'fg= or bg= attributes only', causing models to treat unknown attributes as parse errors rather than extensions to ignore

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
