## Task Context

Choosing a rendering stack for a native Rust colony sim. Options span: reusing a proven sibling project renderer vs. building fresh vs. lighter frameworks vs. hybrid prototype→production. Core tension: proven reuse vs. 2D-first design without 3D baggage.

## Review Approach

### 1. Qualification cost of COTS component: aerospace make

- Qualification cost of COTS component: aerospace make-buy analysis counts the cost of qualifying a COTS component for the new system — for the sibling renderer, what is the cost to qualify it for the colony sim's requirements (performance envelopes, 2D assumptions, native platform behavior)?

### 2. Integration risk delta: integrating a third

- Integration risk delta: integrating a third-party subsystem introduces interface risk, schedule risk, and defect attribution complexity — does the sibling renderer's codebase have the modularity to integrate cleanly, or will it require invasive modification that destroys the benefit of reuse?

### 3. Non

- Non-recurring engineering (NRE) honest accounting: make-buy analysis distinguishes recurring unit cost from NRE — what is the NRE to adapt the sibling renderer vs. the NRE to build fresh? NRE is often underestimated for COTS adaptation.

### 4. Component obsolescence risk: COTS avionics components are...

- Component obsolescence risk: COTS avionics components are deprecated; the sibling project may evolve independently — does reusing the sibling renderer create a long-term maintenance coupling where both projects must stay in sync?

### 5. Specification compliance before selection: aerospace OEMs...

- Specification compliance before selection: aerospace OEMs require a component to meet the system specification before purchase order — is there a formal specification for the colony sim's rendering requirements against which each option is evaluated, or is the decision being made before the spec exists?

### 6. Risk

- Risk-reduction prototyping as qualification: aerospace uses engineering development units (EDUs) to qualify components before production commitment — does the hybrid prototype→production path function as a proper EDU phase with go/no-go criteria, or is it an open-ended exploration without commitment criteria?

## Severity Calibration

- **P1**: Reuse decision made without a rendering requirements specification — qualification cannot be assessed because the target performance envelope is undefined
  - When: No documented FPS target, tile count budget, platform minimum spec, or 2D rendering feature list before evaluating options
- **P0**: Sibling renderer integrated without interface isolation — a defect or evolution in the sibling project propagates directly into the colony sim's rendering path
  - When: No explicit API boundary defined between the colony sim's ECS and the reused renderer; direct internal API usage
- **P2**: NRE for COTS adaptation exceeds the NRE estimate for fresh build after 3 months of integration work
  - When: Make-buy analysis used optimistic integration estimates without a comparable fresh-build NRE estimate

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Is the rendering stack reuse decision being evaluated with make-buy discipline — explicit qualification cost for the off-the-shelf component, explicit integration risk for bringing it into the new system, and explicit fallback if qualification fails? Or is reuse being chosen because it feels cheaper without that analysis? - P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
