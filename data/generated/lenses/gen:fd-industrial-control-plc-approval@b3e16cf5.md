## Task Context

Hassease implements a per-tool Signal approval flow: read/grep/glob/ls auto-approve, edits to test files auto-approve, edits to src files require Signal approval ('y'/'n'/'show'/'diff'/'preview'), Bash always requires approval. The approval interaction is the primary human-in-loop mechanism for a daemon that otherwise runs headlessly.

## Review Approach

### 1. Approval scope binding and anti-reuse enforcement: in industrial permit-to-work

- Approval scope binding and anti-reuse enforcement: in industrial permit-to-work systems, a permit authorizes a specific work order on a specific equipment item — it cannot be reused for adjacent equipment or extended work scope without reauthorization — verify that Hassease's approval state is scoped to the exact tool call that was proposed (specific file, specific line range, specific bash command), and that a 'y' response to one edit proposal cannot be interpreted as blanket approval for subsequent edits in the same agent turn, even if those edits were described in the same Signal message

### 2. Ambiguous response handling and safe default: DCS operator interfaces are

- Ambiguous response handling and safe default: DCS operator interfaces are designed so that ambiguous or missing responses fail safe — a timeout or partial acknowledgment causes the automation to hold, not proceed — check whether Hassease's approval parser treats unrecognized responses (emoji reactions, partial words, responses in other languages, Signal read receipts without text) as approval, denial, or hold, and whether the safe default is to hold and re-prompt rather than to proceed or skip

### 3. Competing operator actions and approval race conditions: in multi-operator DCS

- Competing operator actions and approval race conditions: in multi-operator DCS environments, two operators can simultaneously issue conflicting commands — verify that Hassease's approval flow handles the case where the human sends a follow-up Signal message while an approval is pending (e.g., 'actually cancel everything' arriving after 'y' was sent but before the edit executed), and whether the approval flow has a defined window during which a retraction can be processed before execution commits

### 4. Auto-approve boundary configuration and test-file classification: ICS

- Auto-approve boundary configuration and test-file classification: ICS auto-approve rules must have a precisely defined safe operating range — a valve at 15% open might be auto-approvable while 85% requires permit — assess whether Hassease's test-file auto-approve rule has a precise definition of what constitutes a 'test file' (by path pattern, by naming convention, by file type), and whether a file that is both a test fixture and an integration entry point falls inside or outside the auto-approve boundary

### 5. Approval audit trail completeness and non-repudiation: permit-to-work systems

- Approval audit trail completeness and non-repudiation: permit-to-work systems maintain a complete audit trail (permit number, authorizing operator, timestamp, equipment ID, work description, close-out time) that satisfies regulatory non-repudiation requirements — check whether Hassease's JSONL evidence trail records the full approval interaction (proposed action, Signal message content, operator response, response timestamp, execution outcome) with sufficient detail to reconstruct the human-in-loop chain for any given tool execution

### 6. Timeout fallback and unresponsive-operator protocol: DCS systems define

- Timeout fallback and unresponsive-operator protocol: DCS systems define explicit escalation paths when the operator does not acknowledge within a timeout period — pause automation, alert supervisor, log the timeout — assess whether Hassease defines a response timeout for Signal approval requests, what happens when the timeout fires (does the task hang indefinitely, does it deny by default, does it escalate to a different Signal contact), and whether the timeout duration is configurable per tool type

## Severity Calibration

- **P1**: The agent proposes to edit src/auth/token.go and the human responds 'y'. The agent then proposes a second edit to src/auth/refresh.go in the same turn. The approval parser, finding 'y' already received for this turn's approval context, treats the first 'y' as covering all edits in the turn and executes the second edit without sending a new Signal approval request. The second edit introduces a regression — but the audit trail records it as approved because the approval context was reused.
  - When: When the approval context is scoped to the agent turn rather than to the individual tool call, allowing a single operator response to authorize multiple distinct tool executions within the same turn
- **P1**: The human sends 'yes please' as the approval response. The Signal message parser uses exact string matching against ['y', 'approve', 'go'] and does not match 'yes please'. The parser's unrecognized-response branch logs a warning and treats the response as denial — but it immediately re-prompts with 'Unrecognized response, please reply y or n'. The human, reading the re-prompt in Signal, believes the edit is pending and types 'y'. Between the denial and the re-prompt, the agent has already moved to the next step and is proposing a different edit — the 'y' is now parsed as approval for the new proposal, not the original one.
  - When: When unrecognized responses trigger immediate re-prompting while the agent continues processing, creating a timing window where a delayed operator response is attributed to the next pending approval rather than the original one
- **P2**: A Bash command requires approval. The human sends 'show' to preview. The agent outputs the bash command text to Signal. The human then goes offline. Twenty minutes later, the human returns and sends 'y' — but a different Bash command has been queued in the interim by a new Signal instruction. The approval parser matches 'y' to the most recently pending approval rather than the one the human previewed, executing a Bash command the human never saw.
  - When: When approval state tracks only the most recently pending approval per conversation thread, rather than associating operator responses with the specific approval request that was sent, so offline periods allow queued approvals to accumulate and misattribute responses

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
