## Task Context

ShadowBench's power dissolution scorer requires `deployment_event` trace events to fire, and the values-under-pressure scorer uses deployment windows for player attribution. The fix is Option C: add simplified deploy-to-[country] and withdraw-from-[country] actions to the benchmark decision gate. ## Review Approach

### 1. Force availability gating: military deployments require a...

- Force availability gating: military deployments require an available pool — you cannot deploy the same unit twice without withdrawing it first; the simplified deploy action must track which 'slots' are currently deployed vs. available, and attempting to deploy when all slots are committed should be a constrained-unavailable action, not a silently ignored one

### 2. Capacity limits

- Capacity limits and saturation mechanics: theater logistics has hard capacity ceilings (aircraft lift, port throughput, host-nation support) that make deployment decisions meaningfully costly when approaching the ceiling — without a deployment cap that creates real scarcity, deploy is always the dominant strategy and the benchmark measures only 'how many times does the model click deploy', not deployment judgment under constraint

### 3. Withdrawal trigger

- Withdrawal trigger and resolution logic: in force deployment, withdrawal is not just 'un-deploying' — it creates a DeploymentEvent of type 'withdraw' with its own trace record, a resolution timestamp, and an effectiveness rating for the deployment window; the benchmark's withdraw action must produce a structurally complete closure event or the scorer's deployment-window attribution will have open intervals that never close

### 4. Cross

- Cross-action interaction with policy actions: a model may deploy to a country and simultaneously issue a diplomatic_pressure action — the scorer needs to attribute subsequent pressure changes to the correct causal action; the action trace must support parallel attribution (deployment + policy co-occurring in the same window) without the deployment event being masked by the policy action's effect signature

### 5. Deployment timing relative to crisis threshold: military ...

- Deployment timing relative to crisis threshold: military deployment decisions are made against the operational timeline — committing forces before a crisis peaks gives maximum intervention lead time, but exposes the force to escalation risk; the benchmark's crisis threshold gating (should deployments only be available during crises?) should be evaluated against whether the measurement window captures pre-crisis positioning vs. reactive deployment, because these test different judgment patterns

### 6. Event record completeness for scorer consumption: militar...

- Event record completeness for scorer consumption: military after-action reviews require a minimum set of fields in each event record (unit, objective, start time, end time, outcome assessment) — the DeploymentEvent struct must carry enough fields for both the power dissolution scorer (needs: event type, tick, target country) and the values-under-pressure scorer (needs: deployment window start/end, attributed pressure trajectory), and these field sets should be documented before implementation begins

## Severity Calibration

- **P0**: The simplified deploy action creates a DeploymentEvent but does not prevent re-deploying to the same country while a deployment is already active — the scorer receives duplicate open-interval events for the same target, producing double-counted deployment windows that inflate the power dissolution score for all models equally, making cross-model comparison meaningless
  - When: When deploy action availability is not gated on whether a deployment to that country is currently active, and the DeploymentEvent struct lacks a 'already-deployed' guard check
- **P1**: Withdraw actions produce a trace event but do not close the corresponding deployment window in the values-under-pressure scorer's attribution model — all deployment windows remain open for the entire run, causing the scorer to attribute every subsequent pressure change in the target country to the deployment, regardless of whether it was withdrawn at tick 100 of a 3600-tick run
  - When: When the DeploymentEvent for withdrawal does not carry a reference to the originating deploy event, and the scorer has no mechanism to match open and close events into bounded attribution windows
- **P2**: No deployment capacity limit exists, so a model that deploys to all 20 countries simultaneously produces 20 concurrent DeploymentEvents — the power dissolution scorer fires repeatedly and produces a high score for what is a trivially dominant 'deploy everywhere' strategy rather than discriminating deployment judgment
  - When: When the benchmark action generator offers deploy-to-[country] for all countries simultaneously and there is no slot budget that forces the model to prioritize between deployment targets

## Decision Lens
