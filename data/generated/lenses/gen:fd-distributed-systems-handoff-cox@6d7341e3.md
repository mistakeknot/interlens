## Severity Calibration

- **P0**: An executor edits one repository revision while the validator reruns against another, both report PASS, and the orchestrator lands a commit that never satisfied the frozen plan.
  - When: Plan, report, and validation evidence lack a shared immutable revision identity or landing rechecks it incorrectly.
- **P1**: A retry after a partial commit can duplicate edits, overwrite a sibling item, or consume the second strike without determining what state the first attempt left behind.
  - When: The pilot protocol has no idempotency key, preflight state check, or recovery rule for partial effects.
- **P2**: Reports omit the plan hash or executed commit SHA, forcing the orchestrator to reopen artifacts and infer which attempt produced the evidence.
  - When: The result is recoverable but increases context and makes stale evidence easier to accept.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

A handoff is safe only when the receiver can identify the exact state and contract it was derived from, reject stale preconditions before mutation, and retry without duplicating or obscuring observable effects. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.
