## Severity Calibration

- **P0**: The manifest is 'rewritten atomically' via write-then-rename, but the design doesn't specify an fsync/flush before rename on the containing directory; on iOS, a rename without a directory fsync can be reordered by the storage layer relative to a crash, so a kill immediately after a lifecycle event can leave the manifest referencing artifacts that were never fully flushed to disk, silently corrupting the session's provenance record.
  - When: atomic write description omits fsync of the file and/or directory entry before or as part of the rename
- **P0**: The reclaim engine writes the node-side deletion receipt to the manifest before (or without transactionally coupling to) actually deleting the local raw quarantine copy; a crash between receipt-write and local delete leaves the manifest claiming the raw was reclaimed while the raw file still occupies quarantine storage, and a naive 'trust the manifest' storage-accounting pass would then never re-attempt cleanup — a slow storage leak that looks like the reclaim system is working.
  - When: no explicit ordering guarantee (or idempotent re-check) between manifest state update and actual file deletion for the reclaim path
- **P1**: Storage-ceiling thresholds are checked via a polled available-capacity call on a timer, but frame-selective mode is entered specifically because the app is writing fast enough to threaten the ceiling — if the polling interval is coarser than the write burst rate, the app can blow through the hard ceiling into truly-zero free space before the pause transition fires, at which point AVAssetWriter/file writes start failing with unhandled errors rather than the app proactively pausing.
  - When: no specification of polling cadence relative to worst-case write rate, or no safety margin buffer beyond the nominal hard-ceiling threshold
- **P1**: NSFileProtection .completeUnlessOpen is applied session-wide, but if AVAssetWriter needs to finalize one file and open a new one (e.g., on a FrameGate mode transition or file-size rotation) while the device is locked mid-session, the newly created file is subject to normal .completeUnlessOpen rules and may fail to open until unlock — silently stalling capture with no indicator change, since the UI-level indicator logic doesn't model file-system-level open failures.
  - When: the design assumes a single long-lived writer handle for the whole session without addressing mode-transition-driven file rotation while locked
- **P2**: Dead-letter detection ('sessions whose routed stages never confirm... land in a dead-letter state') has no specified timeout or trigger condition — without a concrete definition of 'never confirm' (duration, retry count, explicit permanent-unavailability signal), sessions may linger in an ambiguous limbo indefinitely with the sessions-list UI unable to distinguish 'still pending, working as intended' from 'should be flagged dead-letter.'
  - When: no timeout/threshold or explicit state-transition trigger is defined for entering dead-letter state

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
