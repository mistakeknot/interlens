## Task Context

Tuivision's brainstorm proposes changing the get_screen default from 'full' (12K tokens) to 'compact', introducing color quantization, and adding an annotated format. Each of these is a data format evolution decision with downstream consumer implications that market data feed engineering has formalized into precise breaking-change and migration disciplines.

## Review Approach

### 1. Breaking change classification and migration discipline

- Breaking change classification and migration discipline — market data vendors classify default changes as breaking regardless of backward compatibility because any subscriber relying on implicit defaults is broken. Assess whether the brainstorm's 'mitigation: full remains available' is sufficient, or whether the default change requires a deprecation period, explicit version header in output, and migration guide for existing integrations.

### 2. Lossy quantization acceptability criteria

- Lossy quantization acceptability criteria — data feeds routinely reduce precision (price to 4dp, volume to nearest 100) but always define the conditions under which lossy reduction is safe: when the decision the subscriber makes doesn't depend on the lost precision. Check whether the brainstorm defines the LLM decision types for which 16-color quantization is safe vs. unsafe (e.g., detecting a selected row is safe; detecting a custom-branded UI color is not).

### 3. Delta encoding and stateful format risks

- Delta encoding and stateful format risks — FAST and MDP 3.0 use delta encoding (send change from last value, not full value) which creates a stateful format where a dropped message corrupts all subsequent values. Assess whether the annotated format is stateless (each output fully self-describing) or whether any planned extensions (diff mode, dictionary compression) introduce statefulness that could corrupt LLM context if a capture is missed.

### 4. Default stream selection and subscriber segmentation

- Default stream selection and subscriber segmentation — exchanges offer multiple feed tiers (consolidated, direct, full-depth) with different defaults for different subscriber classes. Assess whether tuivision should segment callers by use case (agent vs. human-readable vs. debugging) with different defaults per caller class, rather than a single global default change.

### 5. Format version signaling

- Format version signaling — production data feeds include a message type or version field so subscribers can detect format changes and route accordingly. Assess whether the annotated format output includes a format identifier (e.g., a header line or a wrapper field) that lets consumers detect which format they received, enabling gradual migration without breaking existing parsers.

## Severity Calibration

- **P1**: The default format change from 'full' to 'compact' ships without a format version identifier in the output — an existing integration that parses get_screen output receives compact output, fails to find expected fields, and silently misinterprets the terminal state rather than erroring
  - When: When the compact and full formats are structurally different enough that a parser written for full will not produce an obvious error on compact input, instead producing subtly wrong data
- **P2**: 16-color quantization is applied uniformly without a caller-specified 'I need exact colors' escape hatch — an agent debugging a color-picker TUI or a theme editor receives quantized colors and reports incorrect state
  - When: When the annotated format has no per-call opt-out for color quantization, forcing callers who need exact colors to use the full or SVG format and losing all other annotated-format benefits
- **P2**: The planned diff mode (deferred child .6) will introduce stateful output — but the annotated format is being designed now without statefulness constraints, making diff mode a potentially breaking format revision rather than a clean additive extension
  - When: When the stateless/stateful boundary is not an explicit design constraint in the annotated format spec, leaving the door open for future extensions that create hidden state dependencies

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
