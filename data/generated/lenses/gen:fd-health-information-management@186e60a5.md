## Task Context

Brainstorm for Gmail purchase import pipeline: Auraken parses order confirmation emails, calls interjawn MCP to upsert SKUs and wardrobe entries in jawncloud, and builds purchase-pattern context in Auraken's preference models. MVP covers Amazon + App Store + Steam + Kindle. Pipeline is consent-gated (Gmail OAuth gmail.readonly), idempotent, and private-by-default.

## Review Approach

### 1. Consent granularity vs. all-or-nothing OAuth: the pipeline requests

- Consent granularity vs. all-or-nothing OAuth: the pipeline requests gmail.readonly (full inbox access) to extract purchase emails — assess whether the consent UX communicates what specific email types will be accessed, whether the user can opt specific categories out (e.g., 'import Amazon but not App Store'), and whether the narrow-scope claim in the brainstorm is accurate given that gmail.readonly grants access to the entire mailbox, not just order confirmation emails

### 2. Right-to-correct: if a parsed email produces an incorrect SKU (wrong product

- Right-to-correct: if a parsed email produces an incorrect SKU (wrong product name due to a parser bug), what is the user's path to correct it — assess whether the system surfaces the source email alongside the imported item so the user can judge whether the import was accurate, and whether the correction propagates back to the preference model or leaves stale signals in place

### 3. Right-to-delete at item granularity: the brainstorm states 'private by default'

- Right-to-delete at item granularity: the brainstorm states 'private by default' but does not address deletion — assess whether a user can delete a specific imported purchase from both jawncloud and the Auraken context DB without requiring a full history wipe, and whether deletion from jawncloud cascades correctly to the preference model or leaves orphaned signals

### 4. Longitudinal record completeness and the re-import problem: on re-import

- Longitudinal record completeness and the re-import problem: on re-import, upsert_sku is idempotent — but if a parser bug was fixed between runs, corrected records will overwrite the previous bad import silently — assess whether the pipeline logs which version of the parser produced each record, enabling the user to see that their Kindle imports were re-parsed after a fix

### 5. Post-import summary depth: the brainstorm specifies showing 'N purchases across

- Post-import summary depth: the brainstorm specifies showing 'N purchases across M categories' — assess whether this summary gives the user enough information to make an informed decision about what was imported, or whether it aggregates to the point where a systematic parse error (e.g., all App Store prices imported as $0.00) would not be visible in the summary

### 6. Consent revocation path: if the user revokes Gmail OAuth access

- Consent revocation path: if the user revokes Gmail OAuth access, what happens to already-imported data — assess whether the pipeline architecture distinguishes between 'consent to access Gmail' (revocable) and 'consent to store what was already imported' (separate decision), and whether revocation documentation is clear that imported data persists after OAuth revocation

## Severity Calibration

- **P1**: A parser bug imports App Store subscription renewals as one-time purchases — the user's preference model accumulates 24 'purchases' of the same app over two years, significantly distorting their spending rhythm and category distribution signals — there is no mechanism to identify and bulk-correct the systematic error without wiping all App Store imports
  - When: When the post-import summary does not surface per-parser statistics (App Store: 24 imports, all from noreply@email.apple.com, all same app name) that would make the systematic error visible
- **P1**: The user revokes Gmail OAuth access expecting that their purchase data is deleted — but imported SKUs and wardrobe entries persist in jawncloud and Auraken's preference DB because the pipeline treats import as a separate consent from ongoing Gmail access — the user experiences this as a violation of their expectation, not a documented behavior
  - When: When the consent UX at OAuth time does not explicitly explain that imported data persists after OAuth revocation and requires separate deletion
- **P2**: A user wants to delete a specific purchase (a gift they don't want in their preference model) but the only deletion path is 'clear all purchase history' — the item-granular deletion path does not exist because jawncloud deletion and Auraken context DB deletion are not linked
  - When: When the delete-item flow only removes the jawncloud wardrobe entry but leaves the purchase-pattern signal in Auraken's preference model, or when no item-level deletion path exists at all

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
