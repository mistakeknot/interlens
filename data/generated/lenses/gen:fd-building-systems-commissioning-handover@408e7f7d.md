## Task Context

Choosing a rendering stack for a native Rust colony sim. Options span: reusing a proven sibling project renderer vs. building fresh vs. lighter frameworks vs. hybrid prototype→production. Core tension: proven reuse vs. 2D-first design without 3D baggage.

## Review Approach

### 1. Load profile match: the sibling project's rendering stack...

- Load profile match: the sibling project's rendering stack was sized and tuned for its specific load — tile counts, animation cadence, overlay layers, update frequency — does the colony sim's 2D-first load profile fall within, at, or beyond those design parameters?

### 2. Interface contract fidelity: commissioned systems have de...

- Interface contract fidelity: commissioned systems have defined input/output contracts (voltage ranges, pressure setpoints, sensor locations) — what are the exact API contracts the sibling renderer exposes, and does the colony sim's ECS tick pipeline honor them without shimming?

### 3. Commissioning documentation quality: a system is only as ...

- Commissioning documentation quality: a system is only as transferable as its documentation — is the sibling renderer's architecture documented well enough to know what assumptions are baked in vs. what is configurable?

### 4. Failure mode inheritance: commissioning engineers audit f...

- Failure mode inheritance: commissioning engineers audit failure modes before handover — does reusing the sibling stack mean inheriting its known failure modes (e.g., 3D depth buffer assumptions surfacing in 2D edge cases)?

### 5. Retrofit cost vs

- Retrofit cost vs. new-build cost: MEP engineers know that retrofitting a system to a building it wasn't designed for often costs more than new construction — what is the honest retrofit cost estimate if the 2D-first requirements diverge from the 3D-heritage design?

### 6. Phased commissioning as risk mitigation: large systems ar...

- Phased commissioning as risk mitigation: large systems are commissioned in phases, not all at once — does the hybrid prototype→production path map to a phased commissioning model where each phase has clear acceptance criteria before proceeding?

## Severity Calibration

- **P1**: The sibling renderer's camera/projection model is load-bearing in ways not visible at the API surface — 2D mode is a special case of 3D, not a first-class path
  - When: No commissioning audit of the sibling stack's internal assumptions about coordinate space, Z-ordering, and depth buffer usage before adoption decision
- **P0**: Interface shim layer accumulates over 6 months until it is larger than the renderer itself — the 'reuse' decision created more work than fresh build
  - When: No pre-adoption load profile comparison between sibling project requirements and colony sim requirements
- **P2**: The sibling renderer's performance tuning parameters are hardcoded for its tile size and entity count — tuning for the colony sim requires forking rather than configuring
  - When: Commissioning documentation absent; assumptions discovered by trial and error

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Does the proposed rendering stack reuse transfer represent a genuine fit between host requirements and system design parameters, or is it a cargo-cult transplant that will require extensive rework once the new building's actual load profile is understood? What are the interface contracts that must hold for the transplant to succeed? ## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
