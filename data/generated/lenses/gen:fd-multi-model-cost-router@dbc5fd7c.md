## Severity Calibration

- **P1**: The router classifies refactors as 'multi-file edit' rather than 'refactor' when the instruction uses non-canonical vocabulary — routes to Qwen 3.6 for a cross-module refactor that produces subtly broken imports, requiring Claude Sonnet rework at 3x the original cost.
  - When: Task classification is keyword-based with no semantic understanding of instruction intent; no retry-cost tracking to detect systematic misclassification.
- **P1**: GLM API goes down during an active session; the router returns an error rather than falling back to Qwen — the session stalls with no automatic recovery and the builder receives no Signal notification.
  - When: No provider health tracking, no fallback chain, no builder notification on unrecoverable routing failure.
- **P2**: Cost accounting is per-session totals only — the operator cannot see which task types are driving cost overruns and cannot tune routing thresholds based on empirical data.
  - When: No per-task cost logging, no cost-per-model-per-task-type breakdown, no feedback path to routing policy.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

The router is a cost-quality tradeoff engine, not a capability gating system. Every routing decision has a cost of misclassification: too cheap wastes the builder's time on rework; too expensive wastes money on tasks that didn't need it. Evaluates the router against the principle that routing signal quality must improve over time — a static decision tree is a liability, not a policy. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
