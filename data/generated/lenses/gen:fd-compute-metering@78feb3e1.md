## Task Context

Garden Salon 'bring your own compute' model where contributors supply API keys and the platform records token usage per contributor per direction. Attribution is the foundational primitive from which governance, economics, and revenue sharing may later be derived.

## Review Approach

### 1. Attribution unit correctness

- Attribution unit correctness — input and output tokens are counted separately by providers but have different costs and different semantic weight. The design conflates them into 'token count per contributor.' This may produce misleading attribution.

### 2. Self-attribution gaming

- Self-attribution gaming — if participants control when agents run under their key, they can inflate their own token counts. What prevents a participant from spinning large no-op completions to gain governance weight?

### 3. Provider-side verification gap

- Provider-side verification gap — the garden records what happened, but relies on self-reported or API-side data. Is there a reconciliation path against provider billing records?

### 4. Attribution for abandoned directions

- Attribution for abandoned directions — the open question is acknowledged but unanswered. Tokens spent on abandoned work should still be recorded; if they are silently dropped, the accounting ledger is inconsistent.

### 5. Multi-provider attribution

- Multi-provider attribution — the design assumes one API key per contributor, but a participant may use multiple providers (OpenAI + Anthropic + local). How are heterogeneous token counts normalized or aggregated?

### 6. Real-time vs batch accounting

- Real-time vs batch accounting — live attribution display requires near-real-time counts, but billing data from providers may lag. The design does not address this staleness window.

## Severity Calibration

- **P0**: Attribution used as governance weight with gameable inputs
  - When: If token count directly determines voting weight in a Cooperative model, and participants can self-inflate counts with low-cost completions, the governance system is trivially attackable. This is a data integrity issue that corrupts governance.

- **P1**: Input/output token conflation
  - When: Output tokens cost 3-5x more than input tokens for most frontier models. Treating them as equivalent understates the compute contribution of generation-heavy participants and overstates the contribution of prompt-heavy ones, producing systematically unfair attribution.

- **P2**: Attribution gap on abandoned directions
  - When: The open question is flagged but the design leans toward recording tokens regardless. If the storage schema does not enforce this, abandoned direction attribution will silently disappear at the database layer when directions are deleted.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
