## Task Context

Garden Salon is a pnpm + Turborepo monorepo with Next.js 16 frontend, salon-core (CRDT + attribution), and meadowsyn (visualization). Deployed to Vercel. Clerk auth. Neon Postgres (pending provisioning). The review target is architectural fitness of the monorepo, deployment model, and infrastructure choices.

## Review Approach

### 1. Monorepo architecture
- Is the package split (web, salon-core, meadowsyn) correct? Should there be more packages (e.g., salon-db, salon-proxy)?
- salon-core has both CRDT code and DB/attribution code — are these the same concern?
- Does the Turborepo task graph correctly express build dependencies?
- Are workspace dependencies correctly declared?

### 2. Deployment model
- The WebSocket relay needs persistent connections. Vercel Functions are request/response. What's the plan?
- The platform proxy at `/api/ai/[...path]` forwards to AI providers — is Vercel Functions the right home for this? Latency, timeout, streaming?
- Is there a plan for the relay server (packages/salon-core/src/server/)? It can't run on Vercel.

### 3. Database and infrastructure
- Neon Postgres is TBD. The attribution schema exists in code but there's no DB provisioned.
- Drizzle migrations: `db:generate` and `db:migrate` scripts exist. What's the migration deployment strategy?
- The append-only trigger SQL — when does this get applied? Is it part of the migration pipeline?

### 4. Auth and security
- Clerk is installed in apps/web. Is it correctly integrated with the proxy?
- The proxy receives API keys in the request body. Are these logged anywhere? Vercel function logs?
- CORS configuration for the API routes?

### 5. Build pipeline gaps
- No CI configuration visible (GitHub Actions mentioned in roadmap but not implemented)
- No Playwright or e2e test infrastructure
- No environment variable management beyond `vercel env pull`

## Severity Calibration

- **P1:** salon-core is becoming a god package mixing unrelated concerns
