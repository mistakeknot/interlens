## Task Context

The brainstorm proposes a hybrid push-webhook-plus-periodic-poll detection strategy where GitHub push events provide sub-10-second latency and 5-minute tree-SHA polling provides correctness guarantees. The webhook handler is part of the existing GitHub adapter infrastructure shared with Issues/PR sync from earlier phases.

## Review Approach

### 1. The design specifies webhook signature verification using the HMAC-SHA256

- Verify the design specifies webhook signature verification using the HMAC-SHA256 signature in the X-Hub-Signature-256 header before processing any push event payload — absent verification means any HTTP POST to the webhook endpoint can trigger file writes, a direct code-execution risk given that the adapter writes to the local filesystem

### 2. Whether the design addresses GitHub's webhook disablement policy: GitHub

- Check whether the design addresses GitHub's webhook disablement policy: GitHub automatically disables a webhook endpoint after it returns non-2xx responses for a sustained period — the sync system must return 200 quickly (before any processing) and handle errors asynchronously to avoid disabling its own webhook

### 3. The brainstorm accounts for push event ordering inversion: GitHub delivers push

- Confirm the brainstorm accounts for push event ordering inversion: GitHub delivers push events in delivery order, but network conditions can cause an older push event to arrive after a newer one — the adapter must use the push event's after SHA (the resulting commit SHA) to detect stale events, not just process them in arrival order

### 4. Assess whether the push payload parsing is robust to repo variations: push

- Assess whether the push payload parsing is robust to repo variations: push events include a commits array where each commit has added, removed, and modified file arrays — force-pushes produce a single commit entry with all changed files marked forced, while normal pushes produce individual commits; the parser must handle both

### 5. The gap-filling strategy between webhook and periodic poll: if the poll runs

- Validate the gap-filling strategy between webhook and periodic poll: if the poll runs every 5 minutes and a webhook is missed, changes can sit unsynced for up to 5 minutes — the design should specify whether this latency is acceptable and what the recovery path is if the poll itself fails (e.g., GitHub API unavailable)

### 6. Whether the design handles webhook payload size limits: GitHub caps push event

- Check whether the design handles webhook payload size limits: GitHub caps push event payloads at 25MB, and repos with large binary files or many changed files in a single push may trigger truncation, causing the push event to omit the file list — the adapter must detect truncation and fall back to a full tree comparison for that push

## Severity Calibration

- **P0**: An attacker sends a crafted HTTP POST to the interop webhook endpoint mimicking a push event payload that specifies docs/CLAUDE.md as modified with attacker-controlled content — without HMAC signature verification, the crafted event can be used to trigger arbitrary file fetches and overwrites on the local filesystem
  - When: When the webhook handler processes push event payloads without first verifying the X-Hub-Signature-256 header against the configured webhook secret
- **P1**: A CI pipeline that runs on every push causes the interop webhook endpoint to receive 50 push events in 2 minutes, each triggering a sync attempt — if the endpoint takes more than 10 seconds to respond due to blocking on GitHub Contents API reads, GitHub marks responses as slow and eventually disables the webhook endpoint, eliminating all real-time sync
  - When: When the webhook handler blocks on downstream processing (API calls, file writes) before returning 200 instead of enqueuing the event and returning immediately
- **P2**: A force-push to the default branch rewrites 30 commits — the push event's commits array contains a single synthesized entry that GitHub marks with forced: true, and the added/removed/modified arrays reflect only the diff from the force-push ancestor, not the full set of changed files relative to the previous default branch state
  - When: When the push event handler does not check the forced flag and fall back to a full tree comparison for force-push events, relying instead on the commit file arrays which are incomplete in this case

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

A webhook is an at-most-once delivery mechanism with no ordering guarantee and an automatic disablement policy — any sync design that relies on webhooks for correctness rather than using them only as a latency optimization will fail silently when GitHub disables the endpoint after sustained failures. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
