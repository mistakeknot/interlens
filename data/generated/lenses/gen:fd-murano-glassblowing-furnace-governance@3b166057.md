## Task Context

interop is a long-running Go daemon on zklw with goroutine-isolated adapters sharing an event bus (Go channels), connection pools, and an identity mapping table. It must run continuously alongside Docker Compose services, handling webhook traffic from GitHub and Notion, fsnotify events from local files, and beads CLI event watching. The Murano furnace lens examines whether the shared daemon infrastructure is governed for continuous long-term operation, whether adapter isolation truly contains failures, whether resource contention is managed with backpressure, and whether restart/recovery preserves operational state.

- Furnace as shared daemon lifecycle: the furnace runs continuously for months but requires regular maintenance (removing clinker from the fire grate, patching the furnace wall, adjusting the draft) — assess whether interop's daemon has a maintenance model (log rotation, connection pool refresh, memory leak monitoring, Dolt server health checks for beads) or whether it assumes the Go binary will run indefinitely without degradation, and whether there are health check endpoints that detect slow degradation before it becomes a crash

### 2. Glory hole scheduling as adapter concurrency: each artisan needs access to the

- Glory hole scheduling as adapter concurrency: each artisan needs access to the glory hole (reheating chamber) at specific times in their piece's lifecycle, and two artisans trying to use the same glory hole simultaneously ruin both pieces — assess whether interop's adapter goroutine pools contend for shared resources (API rate limits, database connections, file locks on local FS) in a way that can cause both adapters to fail rather than one waiting for the other, and whether the event bus provides backpressure when an adapter falls behind rather than queuing unboundedly

### 3. Dropped-piece containment as panic recovery: a piece dropped near the furnace

- Dropped-piece containment as panic recovery: a piece dropped near the furnace can shatter, sending shards into other artisans' work areas and potentially into the melt pot — assess whether an adapter panic in interop is truly contained within its goroutine pool or whether it can corrupt shared state (a half-written event on the bus channel, a locked mutex that is never released, a leaked goroutine that continues writing to a closed channel), and whether the panic recovery mechanism verifies shared-state consistency after recovery rather than just restarting the goroutine

### 4. Campaign season as daemon longevity: the furnace campaign lasts eight months

- Campaign season as daemon longevity: the furnace campaign lasts eight months, and a failure in month six wastes the entire season's momentum — assess whether interop is designed for months-long continuous operation (no memory leaks from event accumulation, no goroutine leaks from improperly closed adapters, no file descriptor exhaustion from webhook connection handling), and whether there are integration tests that simulate long-running operation with realistic event volumes

### 5. Shift handoff as daemon restart: when the furnace transitions between shifts

- Shift handoff as daemon restart: when the furnace transitions between shifts, in-progress pieces must be safely parked in annealers, new artisans must know the state of each piece, and the furnace temperature must be maintained through the transition — assess whether interop's daemon restart (for deployment, config changes, or crash recovery) preserves in-flight event state, whether adapters can resume from their last acknowledged event rather than re-processing from the beginning, and whether the restart protocol is documented and tested

## Severity Calibration

- **P0**: The event bus channel has no backpressure mechanism — when the Notion adapter falls behind (Notion API rate-limited), events accumulate in the channel buffer unboundedly, consuming memory until the daemon OOMs and crashes, taking down all four adapters simultaneously for a failure that originated in one adapter's external dependency
  - When: When event bus channels are unbuffered or have a fixed buffer without a backpressure signal, and a slow consumer causes memory growth proportional to event production rate multiplied by consumer lag duration
- **P1**: An adapter panic leaves a mutex locked or a channel in a half-written state — the panic recovery restarts the goroutine pool but the shared state is inconsistent, causing the restarted adapter or other adapters to deadlock or process corrupted events, requiring a full daemon restart to recover
  - When: When panic recovery in goroutine pools uses recover() to catch panics but does not include shared-state cleanup (mutex release, channel drain, partial-write rollback) before restarting the goroutine
- **P2**: The daemon runs for weeks without issues but gradually accumulates goroutines from adapters that encountered errors and were 'restarted' without properly stopping the old goroutine pool — each restart leaks the previous pool's goroutines, slowly consuming memory and file descriptors until the daemon degrades
  - When: When adapter restart creates a new goroutine pool without confirming that all goroutines in the old pool have exited, and there is no monitoring for goroutine count growth over time

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

Every long-running shared-resource system evaluated as a furnace governance problem: is the shared resource (event bus, daemon process, network connections) protected by continuous monitoring and scheduled maintenance, or is it treated as fire-and-forget infrastructure that will 'just run'? Are individual worker failures (adapter panics) truly isolated from the shared environment, or can they contaminate it? Is there a clear protocol for graceful degradation when the shared resource degrades, and is there a maintenance window strategy, or does the system assume continuous availability? The furnace master knows that 'it has been running fine for months' is the most dangerous sentence in glassblowing — it means maintenance has been deferred, not that maintenance is unnecessary. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
