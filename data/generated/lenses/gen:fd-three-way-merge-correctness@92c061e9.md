- Check whether the merge algorithm handles the case where the local and GitHub versions are identical to the ancestor — this is the most common case (one side changed, the other is at the ancestor) and must produce a clean merge without invoking the user-facing conflict path

- Assess the design's handling of concurrent edits to non-overlapping regions of the same file: a true three-way merge should auto-resolve non-overlapping line-range changes without surfacing a conflict, but a naive diff-based approach may produce false conflicts when both sides add content at the same line offset (e.g., both append a new section at the end of a file)

- Confirm the AncestorStore update protocol: when is the ancestor updated after a successful sync? If the ancestor is updated before the write is confirmed on both sides, a subsequent failure leaves an incorrect ancestor that will cause future merges to produce wrong results

## Severity Calibration

- **P0**: The AncestorStore records the ancestor as the version interop last wrote, but the user edits the file locally while interop's write to GitHub is in-flight and not yet confirmed — the next sync uses the pre-write ancestor, classifies both the in-flight write and the local edit as diverging from a stale base, and produces a merge that silently drops one side's content
  - When: When the ancestor is recorded at write-initiation time rather than at write-confirmation time (i.e., after both the Contents API PUT returns 200 and the local file update is complete)
- **P1**: Both the user locally and a collaborator on GitHub append a new section to the same markdown file at the same end-of-file location — the three-way merge sees both sides adding content at the same line offset, reports a conflict, and dead-letters the event rather than producing a merge that includes both appended sections in document order
  - When: When the merge algorithm uses a strict line-based diff that treats same-position insertions as conflicts rather than a smarter algorithm that can sequence independent insertions
- **P2**: A file enters a conflict state and is dead-lettered to the SyncJournal — subsequent local edits to the same file continue generating sync events, but the adapter skips the file because it is in conflict state — three days later, the user has made 15 additional local edits that are not on GitHub, and the SyncJournal has accumulated 15 unresolved entries with no user notification
  - When: When the conflict state for a file does not trigger a user-visible notification and does not block the user from continuing to edit the file locally while the conflict persists

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Decision Lens

A three-way merge is only as correct as its ancestor — if the AncestorStore returns a stale or wrong ancestor version, the merge produces a result that neither side intended, and the system reports success while silently corrupting the file. If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
