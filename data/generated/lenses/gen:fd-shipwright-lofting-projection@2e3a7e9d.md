## Task Context

A paradigm question for Elf Revel (Rust colony sim, WASM): can ASCII characters serve as geometric primitives in an isometric/top-down spatial scene? The game currently renders as a flat TUI at 120x40 chars with simple single-character glyphs and basic colors. The user wants to explore paradigms where characters ARE the geometry — textured surfaces, scaled sprites, SVG fills, character-as-polygon. The core tension: gaining spatial richness (depth, perspective, procedural art) while preserving the ASCII identity. This is not about incremental rendering improvements but about a fundamental shift in how the character grid is conceived — from text display to spatial medium.

## Review Approach

### 1. Three

- Three-view mutual constraint and the single-view trap: lofting encodes 3D form through three views that MUTUALLY CONSTRAIN each other — no single view is complete. Current TUI rendering uses a single top-down view that tries to encode all spatial information (terrain type, elevation, entities, weather) in one character per tile. The lofting paradigm suggests that a SECOND VIEW (sidebar elevation profile, cross-section detail, or toggled perspective) would not just add information but would fundamentally change how the player construes the primary view. Does the design explore how adding even one constrained alternate view (a persistent elevation strip, a hover-triggered cross-section) transforms a flat grid into a spatially-specified scene? Two mutually-constraining views convey more spatial information than one view with twice the resolution.

### 2. Batten fairness

- Batten fairness and interpolation between key points: shipwrights draw curves by pinning a flexible batten at key offsets and letting the wood's natural spring create fair intermediate curves. The ASCII equivalent is defining terrain contours, elevation changes, or spatial boundaries at KEY TILES and using color/brightness interpolation to create visually fair gradients between them. Does the design treat spatial properties as FIELDS with key-point definitions and interpolated values, rather than as per-tile independent assignments? A terrain elevation defined at 10 key tiles with smooth brightness interpolation between them creates a more spatially coherent surface than 120 tiles each independently assigned a brightness.

### 3. Full

- Full-scale fidelity and the dangers of scaling: lofting is done at full scale because scaling down introduces errors that compound into unfair curves. The analogy: designing ASCII spatial rendering in a zoomed-in or magnified preview mode and then scaling to actual terminal display may introduce visual artifacts that only appear at the TRUE DISPLAY SCALE (actual font size, actual terminal dimensions). Does the design process work at the actual target resolution (120x40 at real terminal font size) rather than in magnified mockups? The lofting tradition warns that spatial rendering MUST be evaluated at its intended scale.

### 4. Offsets table as data format

- Offsets table as data format — separating specification from rendering: the lofting process begins with an OFFSETS TABLE — a numeric table of key measurements at each station. This data format completely specifies the hull before any line is drawn. The table is the canonical truth; the drawn lines are a rendering of it. Does the ASCII spatial paradigm separate the SPATIAL SPECIFICATION (a data structure defining terrain elevation, entity positions, spatial relationships) from the RENDERING (the specific characters, colors, and effects that visualize it)? This separation enables the same spatial data to be rendered in multiple paradigms (flat ASCII, pseudo-isometric, half-block detail) without redefining the spatial truth.

### 5. Station spacing

- Station spacing and non-uniform detail allocation: lofting defines cross-sections (stations) at regular intervals along the hull, but critical shape-change regions (bow, stern, rudder post) get CLOSER station spacing for higher fidelity. The 120x40 grid has uniform cell spacing, but the spatial data BEHIND it need not be uniform. Does the paradigm allow non-uniform spatial detail — more data points where terrain changes rapidly (cliff edges, river banks, building boundaries) and fewer where it is uniform (open meadow, deep forest interior)? The rendering can interpolate sparse-data regions while rendering dense-data regions with full cell-by-cell fidelity.

### 6. Fairing across views

- Fairing across views and visual consistency checking: lofting's fairing process involves drawing a curve in one view, cross-checking measurements against another view, and adjusting until all three views agree. The rendering paradigm equivalent is ensuring that visual encoding of spatial properties is INTERNALLY CONSISTENT across different rendering channels. If brightness encodes elevation, color encodes terrain type, and character encodes entity — do these three channels agree at every cell? A cell with 'high brightness' (high elevation), 'blue color' (water), and 'mountain character' (^) is visually unfair — the three channels contradict. Does the design include a fairing step that cross-checks visual encoding consistency?

## Severity Calibration

- **P1**: The paradigm commits to a single top-down view carrying all spatial information and never explores how a second constrained view (elevation profile, cross-section) would transform spatial perception — missing the lofting insight that mutual view constraint conveys more depth than single-view resolution increase
  - When: All isometric/spatial rendering concepts operate within the single main viewport, with no design exploration of persistent or togglable secondary views that constrain the player's spatial interpretation of the primary view
- **P2**: Spatial properties (elevation, terrain type, entity presence) are encoded in independent visual channels (brightness, color, character) with no consistency checking — the three channels can contradict, creating visually 'unfair' cells that break spatial coherence
  - When: Each encoding channel (brightness for depth, color for type, character for entity) is designed independently with no fairing process ensuring that the channels agree on the spatial story at every cell
- **P2**: Spatial rendering is designed and evaluated in magnified mockups or zoomed-in test views rather than at actual terminal display scale, introducing visual artifacts that only appear at the true merge distance
  - When: Rendering design process uses enlarged screenshots, magnified character views, or non-standard font sizes rather than evaluating at the actual 120x40 display at standard terminal font size

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
