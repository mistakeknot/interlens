## Task Context

Ockham uses fmt.Errorf with %w for error wrapping. check.go uses a degraded-continue pattern throughout. The new BYPASS trigger will be added to anomaly.Evaluator.Evaluate() or a new method called from evaluateSignals(). The halt sentinel write is a safety-critical operation that must not silently degrade.

## Review Approach

### 1. PersistSignal() and persistPleasure() in evaluator.go silently discard errors

- persistSignal() and persistPleasure() in evaluator.go silently discard errors from SetSignalState (they return without checking the error). For F7, if persistSignal is called mid-BYPASS-evaluation and fails, the BYPASS trigger may fire again on the next check run. Assess whether these silent discards are acceptable or must be surfaced.

### 2. BYPASS trigger error handling: the trigger will call os.WriteFile (or

- BYPASS trigger error handling: the trigger will call os.WriteFile (or os.OpenFile) for factory-paused.json and a file write for halt-record.json. If factory-paused.json write succeeds but halt-record.json write fails, the error must not be silently swallowed — this is a partial sentinel write that leaves the double-sentinel in an inconsistent state.

### 3. Check.go degraded-continue pattern: runCheck() logs all step errors to stderr

- check.go degraded-continue pattern: runCheck() logs all step errors to stderr and returns nil. This means ockham check always exits 0 even if signal evaluation failed, halt reconstruction failed, and reconfirmation check failed. For cron-scheduled check runs, this makes it impossible to detect check failures via exit code monitoring.

### 4. Resume command error wrapping: the new ockham resume command must wrap all

- resume command error wrapping: the new ockham resume command must wrap all errors with context ('resume: clear interspect record: ...', 'resume: reset ratchet_state: ...') so that a failed resume produces a diagnostic message that identifies which step failed.

### 5. DB recovery error handling in NewDB: recover() returns (true

- DB recovery error handling in NewDB: recover() returns (true, nil) on success but (true, err) on partial recovery. The caller in NewDB checks if recovered and returns recErr — but WasRecovered() is also set. Verify that a partial recovery (recovered=true, err!=nil) surfaces clearly to the user rather than proceeding with a potentially partially-initialized DB.

## Severity Calibration

- **P1**: BYPASS trigger writes factory-paused.json, then halt-record.json write fails, error is swallowed
  - When: halt-record.json write returns permission error (e.g. ~/.clavain/interspect/ directory does not exist). Error is logged to stderr but BYPASS trigger returns nil. The factory is halted (file exists) but reconstructHalt() will never be able to validate from the secondary sentinel. Double-sentinel guarantee is broken silently.
- **P1**: ockham check exits 0 when BYPASS trigger fails to write sentinel
  - When: Disk is full. os.WriteFile for factory-paused.json returns ENOSPC. evaluateSignals() logs to stderr and returns nil. runCheck() returns nil. Cron monitoring sees exit 0. Factory runs unsupervised.
- **P2**: persistSignal errors are swallowed during BYPASS evaluation
  - When: Signal state for a theme fails to persist. On next check run, loadPriorSignal returns StatusCleared (not found). Drift re-evaluates from scratch. If the drift condition still holds, the BYPASS trigger fires again — writing factory-paused.json a second time (O_EXCL returns IsExist) and emitting a second halt notification. Redundant halt events pollute the audit trail.

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.

## Success Criteria

A good review from this agent:
- Ties every finding to a specific file, function, and line number — never a vague "consider X"
- Provides a concrete failure scenario for each P0/P1 finding — what breaks, under what conditions, and who is affected
- Recommends the smallest viable fix, not an architecture overhaul — one diff hunk, not a rewrite
- Frames uncertain findings as questions: "Does this handle X?" not "This doesn't handle X"
- Grep for all places where errors from file writes are not returned to the caller — in F7 code, any file write to factory-paused.json or halt-record.json must propagate errors.
- The degraded-continue pattern is appropriate for snapshotAuthority() (external data source). It is NOT appropriate for BYPASS trigger writes (safety-critical path).
- Review the error wrapping chain from BYPASS trigger up through evaluateSignals() up through runCheck() — each level must either wrap and return or make an explicit, documented decision to degrade.

## Decision Lens

Every error is either: (a) fatal — caller cannot proceed safely, (b) degraded — caller can proceed but must log and track, or (c) ignorable — genuinely expected and safe to discard. The classification must be explicit, not implicit. Errors from safety-critical writes are always (a). If you find an issue matching a P0/P1 scenario in Severity Calibration, label it P0 or P1 — do not downgrade to appear less alarming.

## Prioritization

- P0: Issues that block other work, cause data loss or corruption — drop everything
- P1: Issues required to exit the current quality gate
- P2: Issues that degrade quality or create maintenance burden
- P3: Improvements and polish — suggest but don't block on these
- For each P0/P1 finding, describe the concrete failure scenario: what breaks, under what conditions, and who is affected
- Always tie findings to specific files, functions, and line numbers
- Frame uncertain findings as questions, not assertions
