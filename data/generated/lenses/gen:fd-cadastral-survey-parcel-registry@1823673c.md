## Review Approach

### 1. Layer separation on shared substrate: a cadastral registr...

- Layer separation on shared substrate: a cadastral registry describes the same physical ground through at least four independent layers (physical, legal, economic, historical) that update at different rates — topography changes over decades, ownership changes in hours, valuation changes annually, history only appends. The Elf Revel ontology similarly describes the same entities through a development meta-layer (features, dependencies, audits) and a simulation layer (ECS components, relationships, properties) with radically different update cadences. Does the chosen format enforce layer separation, or will meta-layer edits (marking a feature 'done') intermingle with simulation-layer definitions (ECS component schemas)? RON and TOML flatten everything into one document. SQLite naturally separates via tables. Markdown+frontmatter separates via the frontmatter/body boundary. Which format's natural grain matches this dual-layer reality?

### 2. The Torrens principle

- The Torrens principle — registry as authority: the Torrens system's insight was that the registry itself should be the source of truth, not a secondary index over scattered deed documents. If the ontology is an authoritative registry, every entity and relationship in the game should derive from it. If it is a secondary index, it will drift from the Rust source code it describes. RON and TOML files checked into the repo become authoritative if the build system reads them. SQLite becomes authoritative if queried at runtime. Markdown+frontmatter is almost never authoritative — it is documentation, a secondary description. Does the chosen format support being the Torrens-style authority, or does it inevitably become a narrative deed that drifts from the actual property?

### 3. Parcel identifiers

- Parcel identifiers and entity addressing: cadastral systems replaced narrative descriptions ('John's field by the river') with formal parcel identifiers (Lot 12, Block 3, Township 4N, Range 2E) that are globally unique, hierarchically structured, and machine-queryable. The ontology needs stable identifiers for 555 features, hundreds of ECS components, flora species, elf relationships, and composition properties. Does the format enforce stable, hierarchical identifiers or permit narrative descriptions that break under rename? RON uses struct names (tied to Rust types — stable but rigid). TOML uses dotted keys (flexible but no schema enforcement). SQLite uses primary keys (stable, queryable, but require migration on schema change). Which addressing scheme supports both the development meta-layer's feature identifiers and the simulation layer's entity identifiers?

### 4. Easements

- Easements and cross-cutting relationships: in cadastral law, an easement is a right that crosses parcel boundaries — a utility easement may affect dozens of parcels, and querying 'all parcels affected by this easement' is a fundamental operation. The ontology's dependency graphs and relationship types are structural easements — a single dependency may cross-cut dozens of features, and querying 'all features blocked by X' must be efficient. Does the format support cross-cutting relationship queries natively, or does every cross-reference require full-document scanning? SQLite handles this with JOIN. RON and TOML require custom tooling. Markdown+frontmatter requires grep. The format's native support for easement-style queries determines whether the dependency graph is queryable or merely describable.

### 5. Subdivision

- Subdivision and schema evolution: cadastral registries handle subdivision (one parcel becomes three) and consolidation (three parcels become one) as first-class operations with provenance chains. The ontology will evolve as features are decomposed, merged, or restructured. Does the format handle schema evolution gracefully? Can a feature that was one entity become three sub-features without losing its provenance chain? SQLite handles this through migration scripts. RON/TOML files handle this through version control diffs. Markdown handles this poorly — renaming a document breaks all inbound links. Which format's evolution model matches the expected rate of ontology mutation?

### 6. The rectangular survey problem

- The rectangular survey problem — global queryability vs. local accuracy: the US rectangular survey system imposed a uniform grid on varied terrain, trading local accuracy for the ability to identify any parcel from its coordinates alone. The ontology faces the same tradeoff: a uniform schema (every entity has the same fields) enables global queries but may poorly describe entities that are structurally different (a flora species vs. an elf relationship vs. a build dependency). RDF-lite and JSON-LD favor uniform triples. RON and Rust types favor locally accurate schemas. Does the format allow per-entity-type accuracy while preserving cross-type queryability?

## Severity Calibration

- **P0**: The ontology is implemented as a secondary index (markdown documentation) rather than an authoritative registry, and within weeks it drifts from the Rust source code it describes — the 555 feature count becomes wrong, dependency links point to renamed items, audit states are stale
  - When: Markdown+frontmatter is chosen as the primary format without a build-time validation step that enforces consistency between the ontology documents and the actual codebase artifacts they describe
- **P1**: Cross-cutting dependency queries ('what features are blocked by the ECS flora component?') require scanning all 555 feature documents because the format has no native support for relationship indexing — making the dependency graph describable but not queryable
  - When: RON, TOML, or markdown is chosen without an accompanying index or query layer, and the ontology has more than 50 cross-cutting dependency relationships
- **P2**: The development meta-layer and simulation layer are stored in the same format with the same schema, causing meta-operations (marking features done, updating audit timestamps) to create noisy diffs in files that also contain stable simulation definitions (component schemas, species properties)
  - When: A single-file-per-entity approach is used where feature metadata and simulation schema coexist in the same document, and both layers are checked into version control

When in doubt: describe the failure scenario. If it wakes someone at 3 AM, it is P0/P1. If it degrades quality over weeks, it is P2.
